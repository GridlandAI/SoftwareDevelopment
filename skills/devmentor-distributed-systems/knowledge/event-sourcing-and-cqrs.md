# Event Sourcing and CQRS

**Domain:** 07 - Distributed Systems, Scalability, and Resilience
**Primary sources:** Real-World Event Sourcing: Distribute, Evolve, and Scale (Hoffman, 2025)

## Overview
Event sourcing inverts the usual relationship between state and change. In a conventional ("stateful," "imperative," or "CRUD") application, state simply *is*: the only source of truth is whatever happens to be in storage at any given moment, and every update overwrites history. In an event-sourced application, state is *derived*: the application's state is determined by replaying a sequence of immutable events that occurred in the past. Events are not merely *a* source of truth, they are the *one and only* source of truth. Martin Fowler's definition captures it: every change to application state is captured in an event object, and those event objects are stored in the sequence they were applied for the same lifetime as the application state itself. The core mechanic is a pure function, written `f(state, event) = state'`, the same immutable-data tenet found in functional programming. A bank account is the canonical example: the ledger of deposit and withdrawal events is the truth, and the balance is just a derivation.

Kevin Hoffman frames event sourcing pragmatically and prescriptively. There are degrees of conformity: "event-driven," "event-based," and "reactive" all mean business logic is triggered by events somewhere, but the source of truth is usually a hybrid of events and persistent state. Only *formal* event sourcing demands adherence to a specific set of rules, which Hoffman distills into ten "Laws of Event Sourcing," each one learned from a production system "engulfed in flame." The payoff for the discipline is substantial: trivial testing (everything is a pure function), painless replay for disaster recovery and upgrades, a complete audit trail, temporal queries, and dramatically simplified scaling. The cost is a steeper conceptual model and apparent boilerplate, which only looks like overkill on "hello world" problems and becomes mandatory at real-world scale.

## Core concepts

- **Event** - an immutable, past-tense record of something that actually happened. It cannot be modified and always refers to a real occurrence. Do not model the absence of a thing or a thing that did not occur; if an error did not result in some immutable thing happening, it should not be an event.
- **Command** - a request (an imperative) to do something; ephemeral and not stored. Commands are validated and either rejected or turned into events. "Commands are ephemeral and don't truly exist. They're simply one possible stimulus that produces an event." Only events are persisted and replayed.
- **Aggregate** - a single, uniquely identifiable entity that has state, validates commands, and emits events. It exists only when paired with its unique key (for example `BankAccount` with `account_number`). Required characteristics: validates incoming commands and returns one or more events; applies events to state to produce new state; both application of events and of commands is *pure* and *referentially transparent* (no side effects, same input always yields same output). Aggregate state is internal and never shared for external consumption. `f(state, command) = e1 ... en`.
- **Rehydration / replay** - rebuilding an aggregate's (or projection's) current state by applying its event stream from the beginning (or from a snapshot). Because the functions are pure, two replays of the same log against fresh state must produce identical results; if they do not, the model is "effectful" and hides a side effect that must be removed before going live.
- **Snapshot** - a persisted copy of aggregate state produced by applying the event function to a stream, optimized for fast read/write by key in O(1) time (key-value or document stores are ideal). Snapshots let you avoid replaying an entire stream on every load and bound how much of the live event log you must keep online.
- **Projection / projector** - a projection is a read model (a materialized view) optimized to answer specific consumer queries in fixed O(1) time; a projector is the code that consumes events and produces that read model. Projections are *disposable*: they can be destroyed and regenerated from the event log because nothing inside the system's perimeter (no aggregate or process manager) relies on them.
- **Process manager (saga)** - manages a stateful, long-running process, where "long-running" refers to the plurality of events needed to complete it, not elapsed time. Behaviorally the inverse of an aggregate: it *consumes events and emits commands*. It has internal state used to validate events and populate commands. A process always needs an inciting (start) event and at least one terminating (end) event; advancing (middle) events are common but optional.
- **Injector and notifier (gateways)** - the perimeter components that handle input and output. Because aggregates, process managers, and projectors may not perform side effects, all interaction with the outside world (the "work") happens through gateways: injectors bring external events in, notifiers push events out to external consumers.
- **CloudEvents** - a standard JSON envelope (specversion, id, type, source, datacontenttype, time, data) for describing events in a vendor-neutral, interoperable way; used throughout the book for inter-system events and as the carrier for crypto-shredded PII.
- **Event store** - the durable home of the write model (the event log), the only true source of truth; everything else can be regenerated from it. Distinct from snapshot and projection stores.

## Frameworks & models

- **The three data types, stored separately** - an event-sourced system has three kinds of persistent data with different access patterns, and you should choose storage for each independently (and may use a simple store in development and robust, highly available stores in production):
  1. *Aggregate state (snapshots)* - read/write by single key, atomically, in O(1); key-value or document/NoSQL stores fit.
  2. *Projections (read models / materialized views)* - shapes vary widely (rows, attributes); relational, key-value, or graph stores; often several projections per entity, each tailored to one query.
  3. *Event log (write model)* - queried in time sequence with little filtering, from an index or timestamp; time-series databases are popular for the live log, with replicas shipped to offline stores for analytics, data warehousing, and ML training.
- **CQRS pairing** - Command Query Responsibility Segregation falls out naturally: the write model is the immutable event log plus aggregate state; the read model is the set of projections. Separating the model that supports logic from the model that supports queries is essential because using one structure for both is impractical or impossible and forces expensive joins on every read. The key is to anticipate consumers and pregenerate the data each query needs so reads run in fixed time.
- **The replay equation as a litmus test** - because aggregates are `f(state, command) = events` and projectors/aggregate-rehydration are `f(state, event) = state'`, testing reduces to testing pure functions: supply scenario state and input, assert output. If a model cannot be tested this way, or if two replays diverge, the model is broken.
- **Capacity planning formula** - rough monthly storage = (size of largest event) x (events per hour) x 720 (30 days x 24 hours). Recompute monthly against measured usage. A runaway growth rate signals an overly chatty or cyclic event model. Keep it in perspective: "If you can fit your event log on an SD card, you don't have a capacity problem." Do not over-prepare for capacity you will not need.
- **Schema evolution model** - events are immutable, but applications always change. The resolution: a change to an event schema produces a *new event type* (for example `AccountCreated`, then `AccountCreated2`, then `AccountCreated3`), never an in-place modification. Old event types are never deleted; they simply stop occurring. Reuse processing code across versions, but never obscure the distinction between versions.
- **Ordering strategies at scale** - prefer to design the model so order does not matter (commutative events). When order matters, delegate to an event store or broker that provides ordering (NATS, RabbitMQ, Cassandra, EventStoreDB, Kafka) rather than writing your own distributed-ordering algorithm. Use *causation* IDs (this event caused that one) to establish logical sequence even when events arrive out of order, and *correlation* IDs to relate events when order is irrelevant; keep these in the model only if they belong to the domain rather than the infrastructure.

## Patterns

- **Event Sourcing** - Intent: persist state as an append-only log of immutable past-tense events and derive all state by replaying them. When to use: domains needing audit/history, temporal queries, replay-based recovery and upgrades, or simplified scaling; core domains with real complexity. Trade-offs: complete history, trivial testing, and disposable read models, at the cost of a harder conceptual model, apparent boilerplate, and the discipline of the laws (especially purity and immutability).
- **CQRS (Command Query Responsibility Segregation)** - Intent: separate the write model (event log plus aggregates) from one or more read models (projections), each independently shaped and scaled. When to use: whenever read and write shapes diverge or reads must be fast and pregenerated; effectively mandatory with event sourcing. Trade-offs: O(1) tailored reads and independent evolution, at the cost of eventual consistency between write and read sides and the work of maintaining projectors.
- **Projection / read-model regeneration** - Intent: build query-optimized views by applying projectors to the event stream, and regenerate them by replay when they change or are lost. When to use: every consumer-facing query. Trade-offs: fast, disposable, adaptable views, but projections lag (eventual consistency) and must never feed business logic.
- **Snapshotting** - Intent: persist periodic aggregate-state checkpoints so rehydration replays only events since the last snapshot. When to use: long streams where full replay on load is too slow, or to shrink the online event log. Trade-offs: faster loads and smaller live storage, at the cost of managing checkpoints (keep the last several) and regeneration logic.
- **Process Manager (Saga)** - Intent: coordinate a multi-event business flow by consuming events and emitting commands, holding flow state from an inciting event to a terminating event. When to use: a flow with a discrete beginning/middle/end, that acts in response to events, whose state is meaningful beyond start/complete, and that may repeat per entity. Trade-offs: explicit, recoverable coordination, but one flow per manager and no reading from projections.
- **Explicit event versioning (new type per change)** - Intent: model every schema change as a brand-new event type rather than mutating an existing one. When to use: any time an event's fields must change. Trade-offs: preserves the log as a reliable source of truth and keeps historical context, at the cost of maintaining version-specific logic; avoids the "backward-compatibility trap."
- **Crypto-shredding (right to be forgotten)** - Intent: support GDPR erasure (articles 17 and 19) without deleting events, by encrypting PII on each event with a per-subject key and then destroying ("shredding") that key to make the data permanently unreadable. When to use: any event stream containing personally identifiable information. Trade-offs: honors immutability and erasure simultaneously, at the cost of key management and the fact that already-decrypted copies elsewhere must also be handled.
- **Wait-for-my-writes (read-your-writes at the edge)** - Intent: let a client read its own write in a replicated, edge-distributed system by tracking the projection's last sequence number (LSN / version / high watermark) at write time and waiting until that revision arrives. When to use: when read-your-writes consistency matters and you cannot simply tolerate staleness. Trade-offs: simple and effective, but naively waiting for any version bump reads "anyone's writes," so it needs care; CRDTs or merge strategies are the heavier alternative.
- **Idempotent / duplicate-tolerant processing** - Intent: handle at-least-once delivery safely by deduplicating on unique event IDs or a broker "duplicate window," or by making handlers naturally idempotent. When to use: any broker that does not guarantee exactly-once (most). Trade-offs: protects state integrity under retries, at the cost of tracking processed IDs; at-most-once delivery trades duplicates for possible loss (acceptable for high-frequency IoT/gaming streams that self-correct).

## Principles & best practices

The ten Laws of Event Sourcing (Hoffman, 2025), each "unbreakable":

1. **All Events Are Immutable and Past Tense** - an event records something that actually happened; never model absences or non-occurrences.
2. **Applying a Failure Event Must Always Return the Previous State** - applying a bad, unexpected, or explicitly modeled failure event must return the existing state unchanged; failure events record that something failed in the past, they are not command rejections.
3. **All Data Required for a Projection Must Be on the Events** - the event is the only source of truth; all keys, metadata, and payload must come from the event and nowhere else. Supplying contradicting parameters can corrupt an entire stream. (Projectors may keep internal state also derived from the log, as long as they stay referentially transparent.)
4. **Work Is a Side Effect** - aggregates, process managers, and projectors must never read external data or do "work" (mutating the outside world); side effects happen only through gateways. (Projectors may create external read data but still do no work.)
5. **All Projections Must Stem from Events** - every piece of projected data must derive from at least one event; never build projection data from information outside the stream, or you break replay.
6. **Never Manage More than One Flow per Process Manager** - each manager owns a single isolated process instance; lumping flows together lets one flow's failure cascade and corrupt another's state.
7. **Process Managers Must Not Read from Projections** - projections are owned by others, subject to schema change/removal, and (being eventually consistent) unreliable; reading them breaks consistency and replay predictability.
8. **Event Schemas Are Immutable** - any schema change produces a new, distinct event type; never mutate an existing schema.
9. **Different Projectors Cannot Share Projections** - projectors share nothing; a projector may read and write only its own projection.
10. **Never Test Internal State** - internal aggregate/process-manager state can change shape and purpose; tests supply input and assert output, never the shape of internal state.

Additional best practices: keep aggregate and command application pure and referentially transparent; never use wall-clock time for logic (it breaks replay); treat the event log as permanent the moment you go to a persistent store (corrections are new events, never edits); choose storage per data type; recompute capacity monthly; design events to be commutative where possible; delegate ordering and exactly-once concerns to proven brokers; model flows with diagrams and Event Storming before coding.

## Anti-patterns & pitfalls

- **The backward-compatibility trap** - treating a new event version as backward compatible with old ones by adding optional/nullable fields and filling defaults. Defaults are external context not stored in the event; when the default-supplying code changes, historical state is silently corrupted, and you can no longer distinguish a field absent because it predated the schema, intentionally left blank, or blank because of a bug. Reject every evolution plan built on backward compatibility.
- **Sharing internal/aggregate state for queries** - exposing an aggregate's internal state for user-facing reads instead of building a projection; violates the read/write separation and the laws.
- **Reaching outside the event stream** - aggregates or projectors using a running clock, external lookups, or supplied parameters that contradict the event; makes the model effectful and replays non-deterministic.
- **Lumping multiple flows into one process manager** - invites cascading failure and cross-flow state corruption.
- **Process managers querying projections** - couples to another owner's eventually consistent, changeable data and breaks replay predictability.
- **Modeling failures as events that mutate state** - failure events must return prior state; using them as command rejections is wrong.
- **Treating event sourcing as event-driven** - adopting events as triggers while keeping a hybrid source of truth, then expecting the full benefits; only formal adherence to the laws delivers replay safety and testability.
- **Over-engineering consistency and capacity** - building your own CRDTs, consensus, or global-ordering algorithms, or over-provisioning storage, when proven tools or simple tolerance of staleness would do; "you're building an application, not a CRDT framework."
- **Assuming monolithic data locality at scale** - expecting to read your own writes from an edge-local replica; distributed and edge replication break that assumption and require explicit handling.

## Decision guidance

- Reach for event sourcing when history, audit, temporal queries, replayable recovery, or scaling are first-class needs, or in complex core domains; do not adopt it for trivial CRUD where the ceremony outweighs the benefit.
- Pair it with CQRS by default: keep the event log plus aggregates as the write model and build a separate projection per query shape; accept eventual consistency between the two sides.
- Decide the inside-the-perimeter shape (aggregates, process managers, projectors) strictly by the laws, and push every side effect to injector/notifier gateways.
- Choose storage per data type: key-value/document for snapshots, query-appropriate stores for projections, time-series or a dedicated event store (for example EventStoreDB) for the log.
- Evolve by adding new event types, never mutating schemas; keep version-specific logic and never conflate versions.
- For scale, prefer commutative event models so ordering does not matter; when it does, lean on a broker (NATS, Kafka, RabbitMQ, Cassandra, EventStoreDB) for ordering and exactly-once, and dedupe on event IDs for at-least-once delivery.
- Tolerate eventual consistency where the business allows it; use wait-for-my-writes (LSN tracking) only when read-your-writes is genuinely required, and CRDTs only as a last resort via existing products.
- Handle PII with crypto-shredding so erasure requests are honored without violating event immutability.
- Test the model as pure functions (input/output only); inability to do so is a signal the model violates a law.

## Recent developments (2024–2026)
- **CQRS and event sourcing are now mainstream defaults in high-concurrency systems.** 2025 commentary frames them as no longer fringe, driven by read/write asymmetry (read throughput commonly 10:1 or higher over writes), auditability, and consistency needs, which is the exact justification this file gives for separating write and read models. (SQLServerCentral, "Why CQRS & Event Sourcing Matter in High-Concurrency Systems", 2025, https://www.sqlservercentral.com/articles/why-cqrs-and-event-sourcing-are-gaining-ground-in-high-concurrency-web-systems)
- **"Lightweight, framework-free" adoption is rising.** More teams build minimal CQRS/event-sourcing implementations (often functional core / imperative shell, handlers returning events) rather than adopting full frameworks, to gain the architectural benefits without lock-in. (ricofritzsche.me, "Beyond Aggregates: Lean, Functional Event Sourcing", 2025, https://ricofritzsche.me/functional-event-sourcing/)
- **Selective-use guidance hardened.** The consistent 2025-2026 caution is not to apply event sourcing/CQRS to simple CRUD, low-volume, or no-audit domains where the operational cost (versioning, eventual consistency, projector upkeep) buys nothing, matching this file's "do not adopt for trivial CRUD" stance. (microservices.io event sourcing pattern, updated; matterai.so, "Event Sourcing vs CQRS", 2025, https://www.matterai.so/guides/event-sourcing-vs-cqrs-choosing-the-right-pattern-for-your-domain)
- **Event-store landscape: EventStoreDB vs. Kafka-as-substrate vs. Axon/Polecat.** Purpose-built stores (EventStoreDB) coexist with Kafka used as the log/projection substrate in high-throughput deployments; tooling and versioning practice ("new event type per change") are an active 2026 topic. (dasroot.net, "Event Sourcing and CQRS with Databases", 2026, https://dasroot.net/posts/2026/04/event-sourcing-cqrs-databases-eventstoredb-axon-polecat/; johal.in, "Event Sourcing with Event Stores and Versioning in 2026", https://www.johal.in/event-sourcing-with-event-stores-and-versioning-in-2026/)
- **The laws and mechanics are stable.** Immutability/past-tense events, purity, explicit versioning (new type per change), projections-as-disposable, process managers, crypto-shredding for GDPR, and wait-for-my-writes remain the accepted discipline; this period reinforces rather than revises them.
