# MCP and Agent Protocols

**Domain:** 10 - AI, GenAI, and Agentic Systems
**Primary sources:** The MCP Standard (Srinivasan Sekar, 2026); AI Agents with MCP (Kyle Stratis, 2025); Build a Multi-Agent System (from Scratch) With MCP and A2A (Val Andrei Fajardo, 2025); AI-agent Communication Network (ACN) White Paper (China Mobile Think Tank, 2025)

## Overview

Before standardization, every organization building agentic AI invented its own way to expose tools, data, and prompts to an LLM, and every model needed its own connectors. Stratis names this the **MxN problem**: to support M models and N tools you write M times N connectors that largely repeat each other, multiplying bug surface. The Model Context Protocol (MCP), introduced by Anthropic and inspired by the Language Server Protocol (LSP), provides a common interface for tools, resources, and prompts and turns the M times N problem into M plus N: write N MCP servers once and any MCP-capable host can use them.

MCP solves the *vertical* integration problem (an agent talking to its tools and data). A second protocol family solves the *horizontal* problem (agents talking to each other): Google's Agent2Agent (A2A) standardizes agent-to-agent interaction so agents built on different frameworks can collaborate, and operator-led efforts like China Mobile's AI-agent Communication Network (ACN) propose network-level standards for trusted, ubiquitous agent communication. The future architecture combines them: an orchestrator uses A2A to delegate a sub-task to a specialized agent, and that agent uses MCP to reach its own tools (databases, search, code execution). These protocols matter in the SDLC because they replace bespoke, brittle integrations with a federated, interoperable ecosystem, and because they introduce a new class of agentic security risks that the SDLC must now account for.

## Core concepts

**The three MCP architectural roles (Sekar).** Every MCP interaction involves a Host, a Client, and a Server, a deliberate separation of concerns.

- **Host - the conductor / director.** The program the user interacts with directly (Claude Desktop, Cursor, VS Code, a custom enterprise app). The Host owns the user experience and conversation history, maintains session state (it acts as the AI's memory so context is never lost), decides which servers to connect to and when (often via a config file such as `mcp.json`), and is the **ultimate governance gatekeeper**: it controls which resources the AI can access and enforces the **human-in-the-loop approval gate** for powerful or irreversible tool actions (deleting files, sending email, altering databases).
- **Client - the translator / diplomat.** A component *inside* the Host; the Host creates one Client per Server. The Client manages the connection lifecycle (handshake, transport selection, graceful teardown, error recovery), serializes/deserializes between native objects and JSON-RPC messages, and performs **dynamic capability discovery** (on connect it asks the Server for a machine-readable menu of all Tools, Resources, and Prompts with descriptions and argument schemas). A key constraint (Stratis): a single Client talks to a single Server; to use multiple Servers you launch multiple Clients.
- **Server - the specialist.** An external program wrapping a specific capability (a database, a library, a third-party API). It advertises its skills (high-quality plain-language tool descriptions written *for the LLM*, not for humans), listens for and executes requests (decode, execute, encode), and ranges from a 20-line local stdio script to a containerized microservice on Kubernetes to a public SaaS-backed offering.

**The three MCP primitives and their locus of control (Sekar).** The protocol's core design principle is *separation of control*: who or what is in charge of each primitive.
- **Tools - the verbs - Model Control.** Executable actions with side effects (computation, external-system interaction). The AI/LLM decides when to invoke them. Defined with `registerTool` (name, config, async handler); best practice is to define schemas with Zod for type safety and automatic JSON-schema generation.
- **Resources - the nouns - Application Control.** Read-only context the Host can safely give the AI (files, records). The application controls access, often via URI templates, to ensure security. `ResourceLink` allows reference-by-link for large collections.
- **Prompts - the grammar - User Control.** Template conversations the user invokes to shape the AI's behavior and give it a persona for a task.

**Client-provided capabilities (Stratis).** The relationship is bidirectional. A Client can offer capabilities back to a Server:
- **Sampling**: the Server can request a chat completion from the LLM the Client is connected to, enabling nested tool choice or server-side reasoning. Because this gives an external server access to the model you pay for, both Anthropic and the author strongly recommend a human-in-the-loop approval step before any sampling request reaches the LLM.
- **Roots**: tell Servers which areas of the Host's filesystem they may access. Servers *should* respect these boundaries but are not required to.
A Client must advertise whatever capabilities it provides during the initialization handshake.

**Transport layer (Sekar).** MCP is transport-agnostic but standardizes two:
- **stdio**: line-delimited JSON-RPC over a process's stdin/stdout/stderr. For same-machine communication, typically a local Server launched as a child process of the Host (IDE). Fast, no network stack, ideal for desktop integration, development, and testing.
- **Streamable HTTP**: the modern, recommended transport for remote/network communication. Establishes a persistent session over a single `/mcp` endpoint: `POST /mcp` carries client requests, `GET /mcp` is the server-to-client notification channel (historically Server-Sent Events, now deprecated in favor of Streamable HTTP), and `DELETE /mcp` ends a session gracefully. An `mcp-session-id` HTTP header, issued by the server after initialization and echoed on every subsequent request, lets one stateful server manage many concurrent clients. Broken connections can be resumed with a `Last-Event-ID` header so the server replays missed messages on the same stream.

**Message format (Sekar).** All messages, over any transport, use **JSON-RPC 2.0**. A request carries `jsonrpc` ("2.0"), `method` (e.g., `tools/call`), `params`, and a client-generated `id` the server must echo so responses match requests. Methods include `tools/call`, `resources/read`, and discovery (`mcp/discover`). Results return a `content` array; errors use JSON-RPC error codes.

**Agent communication networks (ACN White Paper).** The ACN proposes operator-provided networks for AI-agent communication, built on five capability levels from bottom to top: **access**, **networking**, **session**, **enablement**, and **collaboration**. Levels 1-3 deliver autonomous, controllable interconnection; levels 4-5 deliver collective intelligence and network enablement. AI agents differ from conventional devices by three traits: **autonomy** (they can request access and form connections without human input), **digital identity** (each agent holds a unique identity bound to the user/tenant it serves, enabling authentication, authorization, supervision, and tracing), and **capability sharing** (agents share sensing/decision/operational capabilities through capability openness and orchestration to achieve collective intelligence).

## Frameworks & models

**MCP as MxN-to-M+N solver.** The architectural payoff: a single MCP server works with many different hosts/clients, and each new client increases the value of every server and vice versa (a two-sided network effect).

**The MCP discovery and interaction trace (Sekar).** A complete flow: user query in the Host, the Client sends a discovery request and receives the Server's capability menu, the Host presents possible actions to the LLM, the LLM proposes a `tools/call`, the Host's governance layer requests human approval if the action is impactful, the Client serializes and sends the call, the Server decodes/executes/encodes, and the result returns through the Client to the Host for synthesis.

**MCP server ecosystem categories (Sekar).** Knowledge and memory (Zep Graphiti knowledge-graph memory, RAG-as-a-service like Ragie and Vectara), developer tools and code execution (Jupyter, E2B sandboxes, GitHub/GitLab, AWS/Cloudflare/Vercel), database and data-platform access (MindsDB unified access, Qdrant/Weaviate/Neon/Supabase), web access and automation (Playwright/Puppeteer browser control, Bright Data/Firecrawl scraping), and workplace/productivity connectors.

**Registries and the federated model (Sekar).** The official MCP Registry acts as a secure, open "app store" for AI capabilities, giving clients a programmatic way to find and add servers. Enterprises run private internal registries (a curated catalogue of company-approved servers) behind their firewall. This federated model balances a central public standard with private, secure deployment.

**ACN networking model (ACN White Paper).** The ACN is user-centric: each agent serves a specific user or tenant. Within the network reside **user-centric subnets**, each subdivided into **Logical Communication Domains (LCDs)**. Agents within a domain have full mesh connectivity and share that domain's network resources; agents in different domains are isolated by default to prevent disturbance and data leakage. An agent can join multiple domains or bridge between them. LCDs support self-service lifecycle management (a user may manage tens to thousands, reconfigured minute-by-minute without operator renegotiation), and an LCD can span subnets to let different users' agents collaborate under authorization policy. LLM-enabled agents can decompose a task, find partner agents, and initiate a dynamic LCD autonomously, which is released on task completion. Abnormal agents can be isolated or forced offline.

**ACN sessions and enablement (ACN White Paper).** Sessions support direct end-to-end establishment via routable digital identity (point-to-point or point-to-multipoint with QoS, buffering, and replication). A standardized agent communication protocol is needed for interoperability between heterogeneous agents, plus **modality conversion** (the network converts between, say, an RGB-camera agent's semantic map and a Lidar agent's, leveraging in-network multimodal AI). Intrinsic intelligence empowerment lets the network enhance inference and sensing for lightweight agents (wearables, UAVs) via device-network synergy. **Task orchestration and collaboration** lets the ACN identify intent, decompose and dispatch tasks across high/medium/low-level agents using its global view, or act as an agent itself, useful when no single agent can plan globally.

## Patterns

**Host-Client-Server separation of concerns** - Intent: split an AI integration into a governing Host, a translating Client, and a specialist Server. When to use: any MCP integration; it is the protocol's foundation. Trade-offs: yields modular, secure, scalable, reusable capabilities; adds the conceptual overhead of three roles and per-server client instances. *(Sekar)*

**Locus-of-control primitive split (Tools / Resources / Prompts)** - Intent: classify each capability by who controls it (model, application, user) to enforce clean security boundaries. When to use: designing any MCP server. Trade-offs: prevents the AI from accessing sensitive data inappropriately and keeps interactions safe; requires discipline to keep side-effecting actions in Tools and read-only context in Resources. *(Sekar)*

**Human-in-the-loop approval gate** - Intent: have the Host pause and request explicit user approval before any powerful or irreversible tool call. When to use: tools that delete, send, pay, deploy, or modify state; also before granting a Server sampling access to the model. Trade-offs: makes agentic systems safe enough for real-world use; adds friction and latency to each gated action. *(Sekar; Stratis)*

**Dynamic capability discovery** - Intent: let a Client query a Server's tools/resources/prompts at runtime rather than hardcoding them. When to use: adaptable systems where agents should pick up new tools on the fly. Trade-offs: enables flexible, evolving toolchains; the LLM depends on high-quality descriptions to choose correctly, so poor descriptions degrade the whole system. *(Sekar)*

**Streamable HTTP session with session-id** - Intent: maintain a stateful, resumable client-server session over HTTP using an `mcp-session-id` header. When to use: remote/cloud-hosted servers serving many concurrent clients. Trade-offs: supports long-lived bidirectional AI conversations and reconnection; more complex than stateless REST and requires session-state management. *(Sekar)*

**Client-provided sampling (server-initiated LLM calls)** - Intent: let a Server request completions from the Client's LLM to enable nested agentic behavior on the server side. When to use: servers that need reasoning or sub-tool selection. Trade-offs: powerful composability; exposes the model the client pays for, so it requires a human-in-the-loop guard. *(Stratis)*

**MCP + A2A layering** - Intent: use A2A for agent-to-agent delegation and MCP for each agent's tool access. When to use: multi-agent systems combining orchestration with specialized tool use. Trade-offs: clean separation of horizontal (agent-agent) and vertical (agent-tool) concerns; requires both protocol stacks and their security models. *(Sekar; Fajardo)*

**Federated capability registry** - Intent: pair a central public registry with private enterprise registries of vetted servers. When to use: organizations adopting MCP at scale who need both public reach and internal control. Trade-offs: balances openness with security and governance; requires maintaining the internal catalogue and vetting process. *(Sekar)*

**Digital-identity-bound agent (ACN)** - Intent: bind each agent a unique network identity derived from its owning user/tenant for authentication, authorization, supervision, and tracing. When to use: networks of autonomous agents needing accountability and access control. Trade-offs: enables trusted, traceable autonomous communication and quick isolation of misbehaving agents; requires a network-wide identity and authorization infrastructure. *(ACN White Paper)*

**Task-level Logical Communication Domain (ACN)** - Intent: dynamically form an isolated, mesh-connected domain of agents for a specific task and release it on completion. When to use: ad-hoc multi-agent collaboration, possibly across users, with strict isolation needs. Trade-offs: gives efficient, secure, on-demand collaboration with default cross-domain isolation; depends on operator-level networking and authorization policy. *(ACN White Paper)*

## Principles & best practices

- **Write tool descriptions for the LLM.** Description quality directly determines whether the model selects and uses a tool correctly; treat them as part of the interface, not documentation.
- **Keep the Host as the locus of control and security.** All governance (resource gating, approval gates) should converge there.
- **Use type-safe schemas (Zod / JSON Schema)** for tools so arguments are validated before execution.
- **Choose transport by locality.** stdio for same-machine child-process servers; Streamable HTTP for anything over a network.
- **Sanitize untrusted tool/resource content** and enforce strict access controls and input cleaning, especially for filesystem access and external APIs.
- **Maintain a trusted-server allowlist.** A sophisticated Host keeps a vetted list; tools from untrusted/new servers should be surfaced for review or subjected to more aggressive sanitization before reaching the LLM.
- **Avoid technology lock-in via open standards.** Using MCP for tools and OpenTelemetry for observability keeps platforms portable (O'Mahony, cross-referenced).

## Anti-patterns & pitfalls

- **The lethal trifecta (Sekar).** When an agent has, simultaneously, (1) exposure to untrusted content (an injection vector), (2) access to sensitive data (the target), and (3) an exfiltration capability (the escape route), a breach becomes a matter of *when*, not *if*. Real 2025 incidents (AgentSmith in LangSmith's Prompt Hub stealing API keys; EchoLeak in Microsoft 365 Copilot) followed this pattern.
- **Toxic flow / hijacked agent (Sekar).** Indirect prompt injection plants a "data landmine" (e.g., a malicious GitHub issue) that the agent ingests during a legitimate task; the agent then chains individually legitimate tool calls into a catastrophic data breach (the May 2025 GitHub MCP exploit read a private repo and posted secrets to a public PR). Mitigations: maintain a clear boundary between trusted instructions and untrusted data (instructional fencing, sanitization), and run runtime guardrails / Toxic Flow Analysis that block suspicious tool-call sequences (e.g., a `readFile` on a sensitive path immediately followed by an external send).
- **Tool poisoning (Sekar).** Attackers hide malicious instructions inside a tool's own description, tricking the LLM into harmful behavior. Sanitize tool descriptions before presenting them to the model.
- **Granting sampling without a guard (Stratis).** Letting a server call the client's LLM unchecked exposes cost and abuse risk; always gate with human approval.
- **Assuming servers honor roots boundaries.** Servers *should* respect filesystem roots but are not required to; do not rely on this for security.

## Decision guidance

- **MCP vs A2A.** Use MCP for the vertical channel (an agent reaching tools, data, and prompts). Use A2A for the horizontal channel (agents delegating to and collaborating with each other). Most real systems layer both.
- **Local vs remote server.** Start with stdio for development and tightly integrated desktop tooling; move to Streamable HTTP for shared, network-hosted, multi-client servers.
- **Build a server vs build an agent (cross-ref O'Mahony).** If a capability does one thing well and should be shared across the organization, expose it as an MCP server (a tool) rather than wrapping it in its own agent.
- **Where to enforce security.** Concentrate governance in the Host (approval gates, resource gating, trusted-server allowlist), add server-side hardening (input sanitization, least privilege, sandboxing), and layer LLM-centric defenses (instructional fencing, description sanitization, runtime Toxic Flow Analysis). Treat the new agentic security stack (MCP-scan, runtime guardrails) as the WAF-equivalent for AI applications.
- **Security model for the protocol's future (Sekar).** Expect a hardened OAuth 2.1 model with clearer grant-type guidance (e.g., `client_credentials` for agent-to-agent communication), richer capability schemas, and more granular error handling as MCP moves toward a formal 1.0.

## Recent developments (2024-2026)

- **MCP moved to neutral, multi-vendor governance.** In December 2025 Anthropic donated MCP to the Agentic AI Foundation (AAIF), a directed fund under the Linux Foundation co-founded with Block and OpenAI, with founding backing from AWS, Google, Microsoft and others. MCP is now community-governed infrastructure rather than a single vendor's project (modelcontextprotocol.io / Linux Foundation, 2025).
- **MCP spec matured through 2025 to the 2025-11-25 revision.** Key milestones: the 2025-03-26 transport overhaul (Streamable HTTP replacing the old HTTP+SSE transport) and an OAuth 2.1-based authorization framework; the 2025-06-18 release added structured tool output, user *elicitation* (servers can request structured input mid-call), and security hardening; the 2025-11-25 "first anniversary" release added asynchronous/long-running operations, improved statelessness, and stronger server identity (modelcontextprotocol.io blog, 2025).
- **Official MCP Registry launched.** Announced September 2025, the community registry grew to roughly 2,000 server entries, giving clients a programmatic "app store" to discover servers; enterprises mirror it with curated private registries (Pento / modelcontextprotocol.io, 2025).
- **A2A moved to the Linux Foundation and saw real adoption.** Google's Agent2Agent protocol (released April 2025) was contributed to the Linux Foundation as the Agent2Agent Project in June 2025. By its first year it surpassed 150 supporting organizations (AWS, Cisco, IBM, Microsoft, Salesforce, SAP, ServiceNow), 22,000+ GitHub stars, and five production SDKs (Python, JS, Java, Go, .NET); it runs over HTTP/JSON-RPC 2.0 with Agent Card discovery (Linux Foundation press, 2025).
- **MCP + A2A convergence is now the default interop stack.** Major agent frameworks and enterprise platforms (Microsoft Agent Framework, Google ADK, AWS Bedrock AgentCore, Salesforce Agentforce) ship MCP for tool access and A2A for agent-to-agent calls, validating this file's "MCP vertical, A2A horizontal" layering thesis (Visual Studio Magazine / vendor docs, 2025-2026).
- **The agentic threat landscape this file describes became mainstream.** Simon Willison's "lethal trifecta" (private data + untrusted content + external communication) was named in June 2025 and is now standard security vocabulary; indirect prompt injection moved from theory to confirmed exploit, including the GitHub MCP private-repo exfiltration pattern and a malicious npm package impersonating an email-integration MCP server that copied outbound mail to an attacker (HiddenLayer / Simon Willison / Oso, 2025-2026). Client-side MCP guardrails remain uneven across hosts.
- **Government standardization is forming.** NIST's Center for AI Standards and Innovation launched an AI Agent Standards Initiative (February 2026) covering identity/authorization, security, and monitoring, with an AI Agent Interoperability Profile planned for Q4 2026, echoing this file's call for digital-identity-bound agents and trusted-server allowlists (Pillsbury / NIST, 2026).
