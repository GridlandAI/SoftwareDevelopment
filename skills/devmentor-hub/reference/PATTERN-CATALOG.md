# Pattern Catalog

Consolidated index of patterns captured across the knowledge base. Each entry: **Name** - intent; when to use; trade-offs; source domain/file. Built incrementally during synthesis.

## Domain 04 - Software Architecture Fundamentals

### Governance & characteristics

- **Architecture fitness function** - Intent: provide an objective integrity assessment of one or more architecture characteristics so they can be governed automatically as the system evolves. When to use: a characteristic is important but not urgent (modularity, layering rules, page-load budgets, cycle avoidance) and likely to erode. Trade-offs: up-front effort and developer buy-in; weak assertions give false confidence; must not be ivory-tower. *(architecture-characteristics-and-quality-attributes.md; trade-off-analysis-the-hard-parts.md)*

### Component & modularity

- **Modular monolith** - Intent: single deployable unit partitioned around domains with one database. When to use: strong default for new systems; stepping-stone to microservices. Trade-offs: keeps deployment simple while aligning code to the business; needs boundary governance to avoid hidden coupling. *(components-modularity-coupling-cohesion.md; architecture-styles-overview-and-selection.md)*
- **Component identification (iterative)** - Intent: discover right-sized building blocks. When to use: start of every new system. Cycle: identify → assign requirements → analyze roles/responsibilities → analyze characteristics → restructure. Trade-offs: first draft is never right; value is in iterating with developers. *(components-modularity-coupling-cohesion.md)*
- **Actor/Actions discovery** - Intent: map roles and their actions to components. When to use: general-purpose default; monolith or distributed. Trade-offs: simple and broadly applicable; less message-oriented than event storming. *(components-modularity-coupling-cohesion.md)*
- **Event storming** - Intent: build components around events/messages. When to use: DDD/microservices. Trade-offs: aligns with messaging architectures; assumes event-driven communication. *(components-modularity-coupling-cohesion.md)*
- **Workflow approach** - Intent: build components around workflows without requiring messaging. When to use: non-DDD, non-message systems. Trade-offs: generic; less prescriptive. *(components-modularity-coupling-cohesion.md)*

### Decomposition & trade-off (Hard Parts)

- **Tactical forking** - Intent: restructure a big ball of mud by cloning the monolith and deleting unwanted code. When to use: unstructured codebases, need to move fast. Trade-offs: fast start, deletion easier than extraction; leaves latent code, does not improve internal quality. *(trade-off-analysis-the-hard-parts.md)*
- **Component-based decomposition** - Intent: incrementally extract well-defined components into services via six refactoring patterns. When to use: codebases with namespace/directory structure. Trade-offs: more analysis but controlled and lower-risk; pairs with service-based architecture as a stepping-stone. *(trade-off-analysis-the-hard-parts.md)*
- **Saga (transactional)** - Intent: maintain consistency across services without distributed ACID by chaining local transactions with compensations. When to use: a workflow spans services owning their own data. Trade-offs: eight variants trade coupling/complexity against scale and eventual-consistency handling; orchestrated variants simplify coordination but hurt performance/consistency latency. *(trade-off-analysis-the-hard-parts.md)*
- **Consumer-driven contracts** - Intent: let consumers specify and verify what they need from a producer's contract as a fitness function. When to use: loose contracts in microservices where decoupling matters but drift is a risk. Trade-offs: restores safety to loose contracts at the cost of maintaining contract tests. *(trade-off-analysis-the-hard-parts.md)*

### Style selection

- **Style selection (method)** - Intent: choose the least-worst architecture style. When to use: start of design and major restructuring. Method: prioritized characteristics → quantum count → data placement → communication style. Trade-offs: every style is a fixed bargain; the method narrows the field and surfaces trade-offs to record in ADRs. *(architecture-styles-overview-and-selection.md)*

### Architecture styles (selection profiles; deep detail in domain 05)

- **Layered (n-tier) monolith** - simplicity, familiarity, low cost; weak deployability/testability/scalability. For small, simple, budget-constrained apps and as a starting point.
- **Pipeline (pipes and filters)** - simple, extensible; monolithic limits. For data transformation/ETL.
- **Microkernel (plug-in)** - customizability, extensibility; monolithic core limits scale. For product-based and pluggable domains.
- **Service-based** - good agility/deployability/testability/fault tolerance at lower complexity; coarse-grained, shared DB. Stepping-stone to microservices.
- **Event-driven** - high performance/scalability/elasticity/responsiveness; hard to test/debug, complex consistency. For reactive, asynchronous workloads.
- **Microservices** - best-in-class agility/scalability/deployability/differing characteristics per service; high complexity, distributed data, needs mature DevOps.
- **Space-based** - extreme scalability/elasticity via in-memory data grids; complex and costly. For very high variable concurrency.

*(All style entries: architecture-styles-overview-and-selection.md)*

## Domain 05 - Architecture Patterns and Styles

### API design & REST

- **Hypermedia (HATEOAS) responses** - Intent: embed links/forms in responses so clients discover next valid actions at runtime instead of hardcoding them. When to use: APIs that must evolve without breaking clients, discoverable pagination/state transitions, and AI/LLM consumers. Trade-offs: harder to design (every representation must advertise related resources and respect access control) and harder to consume; pays off in decoupling and longevity. *(api-design-and-rest-patterns.md)*
- **Semantic profile / published vocabulary** - Intent: describe an API's problem space and terms in a machine-readable profile (ALPS, JSON-LD, schema.org) separate from the wire format. When to use: cross-organization interoperability, machine clients. Trade-offs: extra artifact; enables runtime profile negotiation and closes the semantic gap. *(api-design-and-rest-patterns.md)*
- **Idempotent action / client-supplied identifier** - Intent: make writes safely repeatable via a client-generated key or idempotent modeling. When to use: unreliable networks, create operations, retry logic. Trade-offs: server must dedupe/store keys; improves reliability and throughput. *(api-design-and-rest-patterns.md)*
- **Standardized error reporting (Problem Details, RFC 9457)** - Intent: a consistent machine-readable error body (type, title, status, detail, instance) via application/problem+json. When to use: every API. Trade-offs: minor extra structure; big gains in consumer experience and tooling; extendable with custom fields. *(api-design-and-rest-patterns.md)*
- **Evolution-only (additive change) with Postel's law** - Intent: evolve a single version by only adding optional things and never removing/altering existing ones; clients ignore unknown fields. When to use: stability and a single shared version are priorities. Trade-offs: strict discipline; breaking changes force a new resource variant (new URI). *(api-design-and-rest-patterns.md)*
- **Hybrid versioning model** - Intent: evolve non-breaking changes in place, introduce a new version only for breaking changes (Stripe model). When to use: most public APIs balancing innovation and stability. Trade-offs: must run deprecation/sunset machinery well. *(api-design-and-rest-patterns.md)*
- **Deprecation and sunsetting** - Intent: a transparent end-of-life lifecycle signaled at runtime (Sunset header RFC 8594, Deprecation header, Link to migration guide) and in docs. When to use: any breaking change or retirement. Trade-offs: ongoing communication/monitoring; prevents calcification and decay. *(api-design-and-rest-patterns.md)*
- **API facade** - Intent: present a simple, self-consistent interface over a complex/legacy subsystem (design ideal API, implement with stubs, then mediate). When to use: modernization, partner-facing APIs over messy internals. Trade-offs: extra layer; decouples consumers from internal complexity. *(api-design-and-rest-patterns.md)*
- **Partial response / field selection** - Intent: let clients request only needed fields (?fields=...). When to use: bandwidth-constrained or diverse clients. Trade-offs: server parsing complexity; reduces over-fetching without full GraphQL. *(api-design-and-rest-patterns.md)*
- **Pagination (offset vs cursor)** - Intent: navigate large collections predictably; offset/limit for stable data, cursor/keyset for real-time/large data. When to use: any collection resource. Trade-offs: offset drifts when data changes mid-browse; cursor is robust but more complex. Provide self/next/prev links and collection metadata. *(api-design-and-rest-patterns.md)*

### SOA & service design

- **Enterprise Service Bus (ESB)** - Intent: mediation/broker for service communication, transformation, and integration over a distributed bus. When to use: many applications expose reusable services and protocol transformation is needed. Trade-offs: infrastructure cost, can be over-bought; avoids point-to-point sprawl and the hub-and-spoke single point of failure. *(soa-and-service-design.md)*
- **API Gateway** - Intent: single entry point routing client requests to one or more services. When to use: front door for service/microservice estates. Trade-offs: potential bottleneck; centralizes cross-cutting concerns; favored by MSA over heavy ESBs. *(soa-and-service-design.md)*
- **Service Gateway / Service Proxy** - Intent: gateway abstracts a provider's functionality behind a clean interface; proxy is the consumer-side interface to a remote service. When to use: hide implementation complexity (gateway) or invoke external services (proxy). Trade-offs: indirection; strong decoupling. *(soa-and-service-design.md)*
- **Orchestration (central coordinator, BPEL)** - Intent: execute services in a pre-defined sequence with a central engine controlling the workflow. When to use: complex multi-service business processes. Trade-offs: central coordinator can be a single point of failure and costly for trivial flows. *(soa-and-service-design.md)*
- **Choreography (distributed coordination)** - Intent: execute services in sequence without a central coordinator; each service decides when to invoke the next. When to use: simple, distributed, low-cost process execution. Trade-offs: decision logic spread across services; harder global view. *(soa-and-service-design.md)*
- **Compensating action** - Intent: cancel the effects of selected actions within an orchestration. When to use: long-running processes needing rollback without distributed ACID. Trade-offs: must design compensations carefully. *(soa-and-service-design.md)*
- **Service governance (validation + management patterns)** - Intent: design-time validation against enterprise policy (registry/repository) and run-time monitoring/policy enforcement for SLAs. When to use: enterprise service estates crossing org boundaries. Trade-offs: governance overhead; necessary to prevent drift and meet QoS. *(soa-and-service-design.md)*

### Micro frontends

- **Shell / container application** - Intent: a stable, predictable platform that composes micro frontends and owns cross-cutting concerns (routing, state, auth, shared deps, resilience). When to use: any non-trivial micro frontend system, especially per-feature slicing. Trade-offs: can accumulate too many responsibilities and become a coupling point; keep its public contract small. *(micro-frontends.md)*
- **Per-feature slicing (domain-aligned)** - Intent: one micro frontend per bounded context. When to use: DDD/microservice-aligned orgs seeking autonomy and cohesion. Trade-offs: multiple micro frontends per page raise integration, shared-state, and performance challenges. *(micro-frontends.md)*
- **Per-page slicing** - Intent: one micro frontend per route, one active at a time. When to use: migrating a legacy monolith, isolated features, no DDD/microservices. Trade-offs: misaligns ownership with domains; duplicates shared structures. *(micro-frontends.md)*
- **Module Federation as public contract** - Intent: run-time sharing/exposing of components and dependencies across independent builds. When to use: client-side run-time integration where shared deps and bundle size matter. Trade-offs: historically Webpack-coupled (eased by MF 2.0); needs shared team agreement. *(micro-frontends.md)*
- **Web Components as public contract** - Intent: standardized custom-element interface per micro frontend with Shadow DOM CSS isolation. When to use: cross-framework interoperability with partial isolation. Trade-offs: shared JS global context risks app-wide crashes. *(micro-frontends.md)*
- **iFrame isolation** - Intent: maximal sandboxing of an embedded micro frontend. When to use: security-sensitive or untrusted third-party content (payment, auth). Trade-offs: performance, communication (postMessage-only), SEO/accessibility, styling, and UX costs. *(micro-frontends.md)*
- **Shared messaging service (pub/sub anti-corruption layer)** - Intent: a singleton subscribe/publish broker abstracting environment details (namespaces, security, non-browser targets) over native events. When to use: event-based communication beyond a single window or needing grouping/security. Trade-offs: a shared dependency to distribute. *(micro-frontends.md)*
- **Selective state exposure (public type)** - Intent: expose only the minimal fields a micro frontend's bounded context owns, projected from internal models. When to use: any shared state, since exposed state becomes a contract. Trade-offs: extra mapping; protects maintainability. *(micro-frontends.md)*
- **Shared dependencies (Module Federation / CDN / import maps)** - Intent: a common set of library versions to cut conflicts and bundle size. When to use: only when real performance/consistency problems appear (YAGNI). Trade-offs: less independence, resilience, autonomy; Module Federation's declarative sharing with fallback is most robust. *(micro-frontends.md)*
- **Atomic Design (design system hierarchy)** - Intent: build a consistent UI from atoms -> molecules -> organisms -> templates -> pages, governed by tokens and standards. When to use: unifying UX across autonomous micro frontend teams. Trade-offs: requires centralized design-system ownership and documentation. *(micro-frontends.md)*

## Domain 05 - Architecture Patterns and Styles

### Event-driven architecture

- **Event Notification** - Intent: signal that something happened with a minimal event, letting consumers fetch detail on demand. When to use: low-coupling notifications where consumers rarely need full state. Trade-offs: small payloads and loose coupling vs. chatty callbacks and weak end-to-end traceability. *(event-driven-architecture.md)*
- **Event-Carried State Transfer** - Intent: put enough data in the event for consumers to maintain local read copies. When to use: consumers need producer data but you want to remove runtime dependency and improve availability. Trade-offs: better autonomy/availability vs. data duplication and replication lag. *(event-driven-architecture.md)*
- **Event Sourcing** - Intent: persist state as an append-only sequence of events; rebuild state by replay. When to use: audit, temporal queries, replay/debugging, very high write throughput. Trade-offs: powerful history and throughput vs. need for projections and event-schema versioning. *(event-driven-architecture.md)*
- **CQRS (Command Query Responsibility Segregation)** - Intent: split read and write models so each scales and evolves independently, synchronized via an event bus. When to use: high read-to-write ratios, multiple distinct views, or differing read/write consistency needs. Trade-offs: independent scaling and clearer intent vs. eventual consistency between models and added moving parts. *(event-driven-architecture.md)*
- **Saga (orchestrated and choreographed)** - Intent: maintain consistency across services without 2PC via chained local transactions plus compensations. When to use: a workflow spans services owning their own data and 2PC is undesirable. Trade-offs: scalability and no long-held locks vs. compensation complexity, idempotency requirements, and eventual-consistency windows. Transactions are at-most-once, compensations at-least-once; both idempotent, compensations commutative. *(event-driven-architecture.md)*
- **Process Manager / Saga Execution Coordinator (SEC)** - Intent: a mediator that drives a multi-step flow and records progress in a replayable distributed log so any instance can resume after a crash. When to use: orchestrated sagas needing recoverability. Trade-offs: clear control and recovery vs. a coordination hotspot that must be highly available. *(event-driven-architecture.md)*
- **Idempotent Receiver** - Intent: make repeated processing of the same message safe. When to use: at-least-once delivery, retries, sagas, interleaved logs. Trade-offs: safe duplicates vs. tracking processed IDs / designing naturally idempotent operations. *(event-driven-architecture.md; enterprise-integration-patterns.md)*

### Enterprise integration (Hohpe & Woolf catalog)

- **Integration styles (File Transfer, Shared Database, RPC, Messaging)** - Intent: four ways to integrate applications. When to use: Messaging for loosely coupled fresh fine-grained exchange across heterogeneous systems; File Transfer for bulk/batch; Shared Database for always-consistent shared state with few apps; RPC for synchronous, strongly typed calls to trusted, co-evolving services. Trade-offs: messaging gives best loose coupling at the cost of a more complex, harder-to-debug model. *(enterprise-integration-patterns.md)*
- **Message Channel / Point-to-Point / Publish-Subscribe** - Intent: addressable conduits decoupling sender from receiver; one receiver vs. broadcast to all subscribers. Trade-offs: temporal/location decoupling vs. channel management overhead. *(enterprise-integration-patterns.md)*
- **Content-Based Router** - Intent: route a message to a destination chosen from its content. When to use: a logical function spread across physical systems. Trade-offs: centralizes routing knowledge; router must know destinations (mitigate with Dynamic Router). *(enterprise-integration-patterns.md)*
- **Splitter / Aggregator / Resequencer / Scatter-Gather** - Intent: decompose composite messages, recombine related ones, restore order, and fan-out/gather replies. When to use: batch items, parallel sub-processing, out-of-order streams. Trade-offs: powerful composition vs. correlation/state management and completeness conditions. *(enterprise-integration-patterns.md)*
- **Routing Slip** - Intent: attach an ordered list of steps to a message so it visits each in turn. When to use: per-message step sequence known at send time but varying per message. Trade-offs: flexible vs. logic embedded in the slip rather than centrally visible. *(enterprise-integration-patterns.md)*
- **Message Translator / Canonical Data Model / Normalizer / Content Enricher / Claim Check** - Intent: reconcile differing formats: transform, define a format-independent canonical model (N not N² mappings), unify equivalent formats, add missing data, or replace large payloads with a reference. Trade-offs: linear translation and smaller messages vs. maintaining the canonical model and enrichment lookups. *(enterprise-integration-patterns.md)*
- **Messaging Gateway / Messaging Mapper / Service Activator** - Intent: encapsulate messaging access behind app-friendly interfaces and expose services over messaging and non-messaging. Trade-offs: clean domain/infra separation vs. extra layers. *(enterprise-integration-patterns.md)*
- **Guaranteed Delivery / Dead Letter Channel / Invalid Message Channel** - Intent: persist messages to survive failures, and divert undeliverable or nonsensical messages rather than lose them. When to use: any reliable messaging flow. Trade-offs: durability and triage vs. throughput cost and operational monitoring. *(enterprise-integration-patterns.md; messaging-and-async-communication.md)*
- **Control Bus / Wire Tap / Message History / Message Store / Smart Proxy / Detour / Test Message** - Intent: operate and observe a loosely coupled messaging system. When to use: production messaging needing administration, tracing, and debugging. Trade-offs: visibility/operability vs. added infrastructure. *(enterprise-integration-patterns.md)*

### Messaging and async communication (AMQP / RabbitMQ)

- **Competing Consumers (Work Queue / Task Queue)** - Intent: distribute messages from one queue across many consumers so one processes each (round-robin by default). When to use: scale out throughput / parallelize independent tasks. Trade-offs: easy horizontal scaling vs. no per-consumer ordering and need for idempotent handlers. *(messaging-and-async-communication.md)*
- **Publish/Subscribe (broker)** - Intent: deliver a copy of each message to every interested consumer via fanout/topic exchanges and per-consumer queues. When to use: events with multiple independent reactors. Trade-offs: clean decoupling vs. duplication and more queues. *(messaging-and-async-communication.md)*
- **Request/Reply over a broker** - Intent: get a response asynchronously using a callback queue and correlation. When to use: need a reply but want broker decoupling/resilience. Trade-offs: resilience and buffering vs. added latency and client-side wait logic. *(messaging-and-async-communication.md)*
- **Exchange types (Direct / Fanout / Topic / Headers / Default)** - Intent: control how exchanges route to queues. When to use: direct for exact filtering, fanout for broadcast, topic for wildcard categorization, headers for multi-attribute matching. Trade-offs: topic is most flexible but slowest; fanout/direct are faster and signal intent. *(messaging-and-async-communication.md)*
- **Dead Letter Exchange** - Intent: capture undeliverable, rejected, expired, or overflow messages for triage or replay. When to use: any production queue. Trade-offs: prevents loss vs. monitoring/draining burden and loop risk. *(messaging-and-async-communication.md)*
- **Retry with backoff and jitter** - Intent: tolerate transient failures without hammering the target; randomize intervals to avoid retry storms. When to use: direct calls or redelivery to flaky dependencies. Trade-offs: smooths transient faults vs. latency and the need for a final give-up path. *(messaging-and-async-communication.md)*
- **Circuit Breaker** - Intent: stop calling a failing dependency, fail fast, and probe for recovery. When to use: high-throughput callers of failure-prone services. Trade-offs: protects callers and callee vs. tuning thresholds and open-circuit fallbacks. *(messaging-and-async-communication.md)*
- **Priority Queue / Consumer Priority** - Intent: deliver important messages or route to preferred consumers first. When to use: mixed-urgency workloads. Trade-offs: responsiveness for hot items vs. extra resources and no effect when queues rarely back up. *(messaging-and-async-communication.md)*
- **Quorum Queue** - Intent: replicated, consensus-backed queues for HA durability. When to use: mission-critical durable queues in a cluster. Trade-offs: stronger availability/durability vs. replication cost and latency. *(messaging-and-async-communication.md)*

### Microservices patterns (Newman; Richardson; Mitra & Nadareishvili; Fowler; Khan et al.)

*Some collaboration patterns (Saga, CQRS, Event Sourcing) also appear under "Event-driven architecture" above; entries here add the microservices-specific framing. Source files: microservices-patterns-catalog.md; microservices-architecture-fundamentals.md; microservices-production-readiness.md.*

- **Strangler Fig** - Intent: incrementally migrate a monolith to services instead of a big-bang rewrite. When to use: every monolith→microservices migration. Trade-offs: continuous value/feedback vs. effort against legacy code. *(microservices-architecture-fundamentals.md)*
- **Modular monolith** - Intent: one deployable with well-bounded modules. When to use: default for new/small systems; stepping-stone to microservices. Trade-offs: simple deploy/fast feedback vs. DB resists later decomposition. *(microservices-architecture-fundamentals.md)*
- **Universal Sizing Formula** - Intent: start with few coarse services and split toward decreasing coordination. When to use: sizing services greenfield or in migration. Trade-offs: avoids over-decomposition; splitting later beats merging. *(microservices-architecture-fundamentals.md)*
- **Database per service** - Intent: each service owns and hides its data behind its API. When to use: default. Trade-offs: independent deployability + polyglot persistence vs. cross-service query/consistency complexity. Physical clusters may be shared; logical tables may not. *(microservices-patterns-catalog.md)*
- **Data delegate** - Intent: make one service the authoritative owner that others call instead of sharing a table. When to use: data currently shared via a table. Trade-offs: restores ownership vs. an added hop/runtime coupling. *(microservices-patterns-catalog.md)*
- **Data lake (read-only replication)** - Intent: stream copies of system-of-record data into a query sink for analytics/audit/reporting. Trade-offs: solves reporting without sharing operational data; never a system of record. *(microservices-patterns-catalog.md)*
- **Transactional outbox** - Intent: atomically persist state + an outbox message in one local transaction; a relay/CDC publishes it. When to use: reliable saga/event publishing. Trade-offs: no lost/ghost messages without distributed tx vs. needing a relay + idempotent consumers. *(microservices-patterns-catalog.md)*
- **API composition** - Intent: distributed query by calling owning services and joining in memory. When to use: simple cross-service reads. Trade-offs: easy vs. inefficient, couples the composer, poor for large joins. *(microservices-patterns-catalog.md)*
- **Command-side replica** - Intent: keep a local read-only replica of another service's data for hot-path commands. Trade-offs: removes write-path runtime coupling vs. staleness. *(microservices-patterns-catalog.md)*
- **API gateway** - Intent: single external entry point routing to services and handling edge cross-cutting (auth, TLS, rate limit, aggregation). Trade-offs: simpler clients vs. bottleneck/over-centralization risk. *(microservices-patterns-catalog.md)*
- **Backends for Frontends (BFF)** - Intent: a dedicated gateway per client type tailored to its needs. When to use: divergent client requirements. Trade-offs: optimized per-client experience vs. more gateways to own. *(microservices-patterns-catalog.md)*
- **Service discovery (client-side / server-side / registry)** - Intent: locate live service instances dynamically. Trade-offs: enables scaling vs. registry must be HA. *(microservices-patterns-catalog.md)*
- **Access token (JWT)** - Intent: gateway authenticates and propagates signed identity/roles to each service. Trade-offs: stateless/scalable vs. key + revocation management. *(microservices-patterns-catalog.md)*
- **Microservice chassis + service template** - Intent: framework + copyable template for cross-cutting concerns. Trade-offs: removes boilerplate/enforces consistency vs. chassis-version coupling. *(microservices-patterns-catalog.md)*
- **Service mesh** - Intent: sidecar layer for traffic/mTLS/policy/observability, decoupled from service code. When to use: many services needing consistent reliability/security/observability. Trade-offs: consistency at scale vs. ops complexity + latency. *(microservices-patterns-catalog.md)*
- **Timeout (with circuit breaker + bounded retry)** - Intent: bound waits on synchronous calls so callers fail fast and free resources. When to use: every sync call. Trade-offs: responsiveness vs. oversized timeouts being an anti-pattern; never retry long sync chains (retry storm). *(microservices-patterns-catalog.md)*
- **Consumer-driven contract tests** - Intent: verify a service meets each client's expectations without testing services together. When to use: to preserve independent deployability. Trade-offs: replaces slow/brittle e2e tests vs. contract maintenance cost. *(microservices-patterns-catalog.md)*
- **Canary deployment** - Intent: roll out to a 2–5% production pool before full release. When to use: every production rollout. Trade-offs: limited blast radius vs. needing monitoring to judge the canary. *(microservices-production-readiness.md)*
- **Defensive caching** - Intent: cache dependency data so a dependency outage doesn't break your SLA. Trade-offs: protects availability vs. staleness/invalidation complexity. *(microservices-production-readiness.md)*
- **Chaos testing** - Intent: inject scheduled and random failures in production to prove resiliency. When to use: mature ecosystems pursuing fault tolerance. Trade-offs: strongest resiliency evidence vs. needing blast-radius control. *(microservices-production-readiness.md)*
- **Production-readiness audit → roadmap → automation → culture** - Intent: operationalize Fowler's eight standards (stability, reliability, scalability, fault tolerance, catastrophe preparedness, performance, monitoring, documentation) so availability scales with the service count. Trade-offs: earns production trust vs. standardization effort and buy-in. *(microservices-production-readiness.md)*

### Implementation realization & stack mapping (.NET / Spring / JVM)

*These add stack-specific realization of the conceptual patterns above. Source files: microservices-implementation-patterns.md; microservices-dotnet-and-jvm-stacks.md.*

- **Design-pattern → enabler mapping** - Intent: realize each cross-cutting concern at the right layer (library / sidecar / platform / mesh) using a concrete enabler rather than reinventing it. When to use: deciding where discovery, config, resilience, tracing, and health live. Trade-offs: reuse and consistency vs. coupling to a specific enabler; prefer the platform/mesh you already operate. *(microservices-implementation-patterns.md)*
- **Resilience library bundle (Resilience4j / Polly)** - Intent: one library implementing circuit breaker, retry-with-jitter, timeout/time-limiter, bulkhead, rate limiter, and fallback, wired into the HTTP client. When to use: every synchronous call. Trade-offs: in-process control and observability (Actuator/Micrometer; IHttpClientFactory) vs. per-language duplication; combine timeout + jittered retry + circuit breaker to avoid retry storms and self-inflicted DoS. *(microservices-implementation-patterns.md)*
- **Edge server realization (Spring Cloud Gateway / Ocelot / YARP / managed APIM)** - Intent: implement the API gateway in-stack. When to use: Gateway (reactive JVM edge), YARP (C# reverse-proxy middleware), Ocelot (in-stack gateway with auth/rate-limit/aggregation/Polly), APIM (managed, thin). Trade-offs: control vs. monolith-aggregator risk; split per client/business boundary. *(microservices-implementation-patterns.md)*
- **Centralized configuration server (Spring Cloud Config + Bus)** - Intent: per-environment config in one place with live refresh pushed over a message bus; or Kubernetes ConfigMaps/Secrets. Trade-offs: single source + hot reload vs. critical infrastructure to operate. *(microservices-implementation-patterns.md)*
- **Sidecar runtime (Dapr) and dev-time orchestration (.NET Aspire)** - Intent: Dapr exposes uniform HTTP/gRPC APIs for invoke/pub-sub/state/secrets/telemetry across languages; Aspire's AppHost + ServiceDefaults gives a uniform dev chassis and dashboard. Trade-offs: language neutrality / consistency vs. extra container per service and possible overlap with a mesh. *(microservices-implementation-patterns.md)*
- **Distributed tracing realization (Sleuth+Zipkin / OpenTelemetry+Jaeger)** - Intent: propagate correlation ID / W3C trace context across services and export spans (async) to a backend. Trade-offs: end-to-end visibility vs. instrumentation; export asynchronously to avoid coupling services to the tracing backend. *(microservices-implementation-patterns.md)*
- **Reference application as living architecture (eShopOnContainers / Larsson landscape)** - Intent: prove an architecture with a complete runnable system. Trade-offs: concrete end-to-end template vs. dev-only simplifications that must change for production (e.g., DBs in containers). *(microservices-dotnet-and-jvm-stacks.md)*
- **Rich domain model with command handlers (DDD/CQRS internals)** - Intent: keep business logic inside aggregates; handlers load→behave→persist; queries use separate read models. When to use: services with real domain complexity. Trade-offs: testable, change-tolerant domains vs. ceremony; anemic handlers are a smell. *(microservices-dotnet-and-jvm-stacks.md)*
- **Microservice testing pyramid (unit → integration → contract → resilience → E2E)** - Intent: many fast unit tests (in-memory domain via repositories), fewer in-process integration tests (WebApplicationFactory / Testcontainers), consumer-driven contract tests at seams, fault-injection resilience tests, few landscape/E2E tests. Trade-offs: fast confident feedback vs. discipline to keep slow tests few. *(microservices-dotnet-and-jvm-stacks.md)*
- **Containerized promotion pipeline (Compose/Aspire → Kubernetes/Helm)** - Intent: build one image, run the test pyramid in isolated environments, promote the same artifact into Kubernetes via Helm (add mesh only when justified). Trade-offs: independent, repeatable deploys vs. orchestration complexity; managed DBs and externalized secrets in production. *(microservices-dotnet-and-jvm-stacks.md)*

## Domain 06 - Software Design Patterns and DDD

### Strategic DDD - context mapping (team-collaboration patterns)

- **Partnership** - Intent: integrate two bounded contexts by ad hoc, two-way coordination. When to use: teams with strong, frequent communication and dependent goals, ideally co-located. Trade-offs: needs continuous integration and high commitment; poor fit for distributed teams. *(domain-driven-design-strategic.md)*
- **Shared kernel** - Intent: a small co-owned model (ideally only integration contracts) shared by multiple contexts and kept consistent across all. When to use: cost of duplication exceeds cost of coordination (volatile core), partnership infeasible, legacy modernization, or same-team contexts. Trade-offs: couples context lifecycles, violates single-owner principle; keep minimal with integration tests. *(domain-driven-design-strategic.md)*
- **Conformist** - Intent: downstream adopts the upstream model as-is. When to use: power favors upstream and its model is good enough or a standard. Trade-offs: loses modeling autonomy; never for a downstream core subdomain. *(domain-driven-design-strategic.md)*
- **Anticorruption layer (ACL)** - Intent: downstream translates the upstream model into its own behind a protective layer. When to use: downstream is core, upstream model is messy/legacy, or upstream churns. Trade-offs: translation cost in exchange for protecting the consumer's language. *(domain-driven-design-strategic.md)*
- **Open-host service / published language (OHS)** - Intent: upstream exposes a stable, versionable integration contract decoupled from its internal model. When to use: power favors consumers, many downstream consumers. Trade-offs: supplier pays the translation cost; enables multi-version migration. *(domain-driven-design-strategic.md)*
- **Separate ways** - Intent: do not integrate; duplicate functionality per context. When to use: collaboration too costly, subdomain generic and trivially local, or models diverge sharply. Trade-offs: duplication over coordination; never for core subdomains. *(domain-driven-design-strategic.md)*
- **Context map** - Intent: visualize all bounded contexts and their integration relationships. When to use: from project start, maintained as a shared (ideally code-managed) artifact. Trade-offs: reveals high-level design and organizational dysfunction; drifts if not maintained. *(domain-driven-design-strategic.md)*

### Tactical DDD - domain-model building blocks

- **Value object** - Intent: model a concept by its values, immutably, with behavior. When to use: properties of entities, statuses, money, anything identifiable by value. Trade-offs: extra small types/equality code for expressiveness, safety, and centralized logic; cures primitive obsession. *(domain-driven-design-tactical.md)*
- **Entity** - Intent: model a concept with a distinct, stable identity and mutable state. When to use: instances must be distinguished beyond their values. Trade-offs: requires identity management; in DDD used only within an aggregate. *(domain-driven-design-tactical.md)*
- **Aggregate (+ aggregate root)** - Intent: a transactional consistency boundary clustering entities/value objects, mutated only through its root. When to use: complex invariants must always hold across a small object cluster. Trade-offs: one-instance-per-transaction discipline and cross-aggregate eventual consistency; design small. *(domain-driven-design-tactical.md)*
- **Domain event (DDD)** - Intent: an immutable past-tense record of something significant, published for subscribers. When to use: integrating aggregates, eventual consistency, cross-context communication, event sourcing. Trade-offs: needs reliable publishing (Outbox) and idempotent, out-of-order-tolerant subscribers. *(domain-driven-design-tactical.md)*
- **Domain service** - Intent: stateless host for logic spanning multiple aggregates or belonging to none. When to use: a calculation reads data from several aggregates or has no natural object home. Trade-offs: easy to overuse; must not break one-aggregate-per-transaction (coordinates reads). *(domain-driven-design-tactical.md)*
- **Factory** - Intent: encapsulate complex, invariant-respecting construction of aggregates/value objects. When to use: non-trivial assembly. Trade-offs: indirection; keeps entities free of construction concerns. *(domain-driven-design-tactical.md)*
- **Repository** - Intent: collection-like, persistence-ignorant access to whole aggregates. When to use: any persisted aggregate. Trade-offs: one per aggregate type; natural home for optimistic concurrency. *(domain-driven-design-tactical.md)*
- **Application service** - Intent: thin transactional orchestration at the system boundary, no business logic. When to use: every entry point into a domain-model context. Trade-offs: must stay thin; logic leaking here is a smell. *(domain-driven-design-tactical.md)*
- **Domain model (business-logic pattern)** - Intent: encode complex logic as behavior-rich objects speaking the ubiquitous language. When to use: core subdomains with complex rules/invariants. Trade-offs: more design effort; overkill for CRUD/supporting subdomains. *(domain-driven-design-tactical.md)*
- **Event-sourced domain model** - Intent: persist aggregate state as a stream of domain events. When to use: complex core logic needing audit, time-travel, or analytics; money. Trade-offs: requires CQRS to query, event versioning, consistency mindset. *(domain-driven-design-tactical.md)*
- **Layered architecture (within a context)** - Intent: separate presentation/business/data-access by top-down dependency (optional service layer). When to use: transaction-script/active-record contexts. Trade-offs: simple; ill-suited to a persistence-ignorant domain model. *(domain-driven-design-tactical.md)*
- **Ports and adapters (hexagonal/onion/clean)** - Intent: invert dependencies so business logic depends on nothing; infrastructure implements ports. When to use: domain-model and event-sourced contexts. Trade-offs: more interfaces/wiring for testability and persistence ignorance. *(domain-driven-design-tactical.md)*
- **CQRS (DDD framing)** - Intent: segregate a strongly consistent write model from rebuildable read projections (polyglot persistence). When to use: multiple persistent representations, or event sourcing (required). Trade-offs: projection lag/eventual consistency and projection maintenance. *(domain-driven-design-tactical.md)*
- **Outbox** - Intent: reliably publish domain events by committing them with the aggregate, then relaying to the bus and marking published. When to use: any reliable event publishing. Trade-offs: at-least-once delivery (idempotent subscribers); needs a relay. *(domain-driven-design-tactical.md)*
- **Saga (DDD)** - Intent: coordinate a process spanning aggregates/contexts via events and commands with compensations. When to use: a long-running (in transactions) process crosses aggregate boundaries. Trade-offs: distributed complexity; stateful sagas as event-sourced aggregates. *(domain-driven-design-tactical.md)*
- **Process manager (DDD)** - Intent: a stateful coordinator driving a branching business process (more decision logic than a saga). When to use: workflows needing explicit state and routing. Trade-offs: more machinery than simple event-reaction. *(domain-driven-design-tactical.md)*
- **Model translation (ACL/OHS implementation)** - Intent: translate between a context's model and an external one, stateless (proxy/API gateway) or stateful (aggregating/unifying sources). When to use: implementing ACLs/OHS. Trade-offs: stateless is cheap/on-the-fly; stateful needs storage but handles batching/multi-source. *(domain-driven-design-tactical.md)*

### Clean Architecture - SOLID principles (Martin)

- **Single Responsibility Principle (SRP)** - Intent: give each module one reason to change by making it responsible to a single actor. When to use: any class/function serving multiple stakeholders. Trade-offs: more, smaller types (optionally a Facade) for safety against cross-actor breakage; becomes CCP at the component level. *(clean-architecture-and-dependency-rule.md)*
- **Open-Closed Principle (OCP)** - Intent: make artifacts open for extension, closed for modification, so new behavior needs little or no change to existing code. When to use: anywhere requirements are expected to grow. Trade-offs: up-front abstraction/indirection in exchange for cheap extension; realized via SRP + DIP and a protected dependency hierarchy. *(clean-architecture-and-dependency-rule.md)*
- **Liskov Substitution Principle (LSP)** - Intent: keep subtypes substitutable for their base type so clients need no special cases. When to use: any interface with multiple implementations (classes, REST contracts). Trade-offs: constrains inheritance/contract design; a single violation pollutes the system with conditional mechanisms. *(clean-architecture-and-dependency-rule.md)*
- **Interface Segregation Principle (ISP)** - Intent: stop clients depending on members they do not use by splitting fat interfaces. When to use: broad interfaces causing needless recompilation/redeployment or unwanted transitive baggage. Trade-offs: more interfaces for lower coupling; generalizes to CRP at the component level. *(clean-architecture-and-dependency-rule.md)*
- **Dependency Inversion Principle (DIP)** - Intent: depend only on abstractions, hiding volatile concretions behind stable interfaces. When to use: across every architectural boundary. Trade-offs: requires Abstract Factories and a concrete `main`-like component to gather residual concrete dependencies; control flows one way, source-code dependencies the other. *(clean-architecture-and-dependency-rule.md)*

### Clean Architecture - component cohesion & coupling principles (Martin)

- **REP (Reuse/Release Equivalence Principle)** - Intent: make the granule of reuse the granule of release (cohesive, versioned, documented components). When to use: deciding component contents for reuse. Trade-offs: inclusive (larger components); pulls against CRP. *(clean-architecture-and-dependency-rule.md)*
- **CCP (Common Closure Principle)** - Intent: group classes that change together for the same reasons; separate those that change differently (SRP for components). When to use: optimizing for maintainability/develop-ability. Trade-offs: inclusive (larger components); favored early in a project. *(clean-architecture-and-dependency-rule.md)*
- **CRP (Common Reuse Principle)** - Intent: do not force consumers to depend on classes they do not use; keep only co-reused classes together (ISP for components). When to use: optimizing for reuse. Trade-offs: exclusive (smaller components); pulls against REP/CCP. *(clean-architecture-and-dependency-rule.md)*
- **ADP (Acyclic Dependencies Principle)** - Intent: keep the component dependency graph a DAG (no cycles). When to use: any multi-component/multi-team build. Trade-offs: avoids morning-after syndrome and forced co-release; break cycles via DIP or a new shared component; the graph grows and jitters, not designed top-down. *(clean-architecture-and-dependency-rule.md)*
- **SDP (Stable Dependencies Principle)** - Intent: depend in the direction of stability (I metric decreases along dependencies; I = Fan-out/(Fan-in+Fan-out)). When to use: arranging component dependencies. Trade-offs: easy-to-change components must not be depended on by hard-to-change ones; measurable. *(clean-architecture-and-dependency-rule.md)*
- **SAP (Stable Abstractions Principle)** - Intent: make a component as abstract as it is stable (A = Na/Nc), keeping stable components extensible. When to use: with SDP (together = DIP for components). Trade-offs: avoid the Zone of Pain (stable+concrete, e.g., volatile DB schema) and Zone of Uselessness (abstract+unused); aim for the Main Sequence, D = |A+I−1|. *(clean-architecture-and-dependency-rule.md)*

### Clean Architecture - structural patterns (Martin; Fenwick; Wallace)

- **Clean Architecture (concentric layers + Dependency Rule)** - Intent: isolate Entities/Use Cases from Interface Adapters and Frameworks so details are pluggable and policy is testable in isolation; source-code dependencies point only inward. When to use: systems outliving their frameworks/data stores or needing high testability. Trade-offs: more interfaces, indirection, and DTO mapping for independence and deferred decisions. *(clean-architecture-and-dependency-rule.md)*
- **Ports and Adapters / Hexagonal (Cockburn)** - Intent: surround the core with ports implemented by driving/driven adapters so the core depends on nothing external. When to use: swappable UIs/data stores/services and headless core testing. Trade-offs: more wiring for clearer boundary contracts; kin to Onion/DCI/BCE. *(clean-architecture-and-dependency-rule.md)*
- **Onion Architecture** - Intent: concentric rings, domain at center, infrastructure at edge, dependencies inward. When to use: domain-centric apps. Trade-offs: equivalent to Clean/Hexagonal; mainly a vocabulary difference. *(clean-architecture-and-dependency-rule.md)*
- **Screaming Architecture** - Intent: organize top-level structure around use cases/business domain, not the framework, so the architecture announces what the system does. When to use: every app; aids onboarding and deferring framework choices. Trade-offs: requires resisting framework-first scaffolding. *(clean-architecture-and-dependency-rule.md)*
- **Humble Object** - Intent: split a unit into a hard-to-test humble part (e.g., View) and an easy-to-test part (e.g., Presenter) so a testability boundary coincides with an architectural boundary. When to use: GUIs, DB gateways, ORMs/data mappers, service listeners. Trade-offs: extra indirection for a large testability gain. *(clean-architecture-and-dependency-rule.md)*
- **Partial boundary** - Intent: do the boundary design work but keep both sides in one component (or use a facade/one-way boundary), deferring full separation. When to use: a boundary may be needed later but full separation is not yet worth it. Trade-offs: keeps the option open cheaply; risk the latent boundary erodes. *(clean-architecture-and-dependency-rule.md)*
- **Abstract Factory (DIP enforcement)** - Intent: let high-level policy create volatile concrete instances without a source-code dependency on them. When to use: enforcing DIP across a boundary. Trade-offs: indirection; concentrates the unavoidable concrete dependency. *(clean-architecture-and-dependency-rule.md)*

### Balancing Coupling (Khononov)

- **Integration strength selection** - Intent: choose the weakest viable integration interface (contract > model > functional > intrusive) to minimize shared knowledge and cascading change. When to use: every integration decision. Trade-offs: weaker contracts cost translation/mapping; sequential/transactional requirements mandate strong coupling. *(balancing-coupling.md)*
- **Rebalancing by adjusting a sibling dimension** - Intent: restore the strength/distance/volatility balance after a strategic change by moving a different dimension than the one that shifted. When to use: any time a dimension changes (new functionality, subdomain/org/environment shift). Trade-offs: may convert local complexity to global or vice versa; some growth needs deeper restructuring. *(balancing-coupling.md)*
- **Distance reduction to absorb strong, volatile coupling** - Intent: colocate strongly coupled, highly volatile components (merge/move) so high strength is offset by minimal distance (high cohesion). When to use: a core subdomain needs transactional/symmetric consistency with another component. Trade-offs: risks local complexity if unrelated logic is dragged along. *(balancing-coupling.md)*
- **Tolerating complexity under low volatility** - Intent: accept globally/locally complex coupling when the upstream is stable (frozen legacy, trivial duplicated logic). When to use: legacy integration; simple non-evolving shared logic. Trade-offs: cheap now, but must be revisited if a business-strategy shift raises volatility (generic/supporting -> core). *(balancing-coupling.md)*

### Domain modeling foundations (Bjørner)

- **Triptych development (D to R to S)** - Intent: derive requirements and software from a validated domain description, keeping traceability. When to use: high-assurance, long-lived, regulated/safety domains. Trade-offs: heavy up-front formal modeling; domain description is validated, not verified. *(domain-modeling-foundations.md)*
- **Endurant/perdurant analysis** - Intent: classify everything in scope as enduring things vs unfolding processes, then describe each. When to use: start of any rigorous domain study. Trade-offs: unambiguous but heavier than informal DDD discovery. *(domain-modeling-foundations.md)*
- **Internal-qualities description (identity + mereology + attributes)** - Intent: describe each part by identity, part-whole relations, and attributes. When to use: when topology/relationships matter (networks, supply chains). Trade-offs: precise but verbose. *(domain-modeling-foundations.md)*
- **Facet-driven analysis** - Intent: use the seven facets (intrinsics, support technologies, rules and regulations, scripts, license languages, management and organization, human behaviour) as a coverage checklist. When to use: any analysis at risk of missing non-obvious constraints. Trade-offs: comprehensive; can expand scope. *(domain-modeling-foundations.md)*
- **Requirements derivation (projection/instantiation/determination/extension/fitting)** - Intent: mechanically transform a domain description into domain and interface requirements with stakeholders. When to use: when requirements must be traceable to a domain model. Trade-offs: needs an existing formal domain description; rigorous but front-loaded. *(domain-modeling-foundations.md)*

### Enterprise application patterns (Fowler PoEAA)

*Source file: enterprise-application-patterns.md (Fowler 2002).*

- **Transaction Script** - Intent: one procedure per business action. When to use: simple/procedural domain logic, small apps; pairs with Row/Table Data Gateway. Trade-offs: easiest model and transaction boundaries; duplicates code as logic grows. *(enterprise-application-patterns.md)*
- **Domain Model** - Intent: a web of behavior-rich objects organized around domain nouns. When to use: complex, evolving rules/invariants. Trade-offs: scales with complexity and enables OO techniques; high learning cost, needs a Data Mapper layer. *(enterprise-application-patterns.md)*
- **Table Module** - Intent: one class per table operating on a Record Set. When to use: Record-Set-centric platforms, moderate complexity. Trade-offs: more structure than Transaction Script and great tooling fit; no per-instance OO techniques. *(enterprise-application-patterns.md)*
- **Service Layer** - Intent: a use-case-oriented API over the domain hosting transaction/security policy. When to use: a Domain Model/Table Module needing a clear application boundary. Trade-offs: clean API and cross-cutting home; keep thin or logic leaks in. *(enterprise-application-patterns.md)*
- **Table Data Gateway** - Intent: one object per table holding all its SQL, returning Record Sets. When to use: with Table Module or stored-procedure access. Trade-offs: SQL isolation; not OO per row. *(enterprise-application-patterns.md)*
- **Row Data Gateway** - Intent: one object per row mirroring a DB row, no domain logic. When to use: with Transaction Script. Trade-offs: clean separation; awkward finders, can block test substitution. *(enterprise-application-patterns.md)*
- **Active Record** - Intent: a domain object wrapping a row with its own CRUD plus simple logic. When to use: simple logic mapping one-to-one to tables. Trade-offs: minimal indirection, very productive; breaks down as model diverges from schema. *(enterprise-application-patterns.md)*
- **Data Mapper** - Intent: a separate layer moving data between objects and DB, both kept ignorant. When to use: a rich Domain Model. Trade-offs: full isolation and independent evolution; most complex (usually buy an ORM). *(enterprise-application-patterns.md)*
- **Unit of Work** - Intent: track reads/changes and coordinate one ordered atomic commit. When to use: nontrivial DB interaction with a Domain Model. Trade-offs: removes scattered saves, solves commit ordering/concurrency; central mechanism to build/buy. *(enterprise-application-patterns.md)*
- **Identity Map** - Intent: one in-memory object per loaded row. When to use: any session that may load a row twice. Trade-offs: prevents inconsistent duplicates and doubles as cache; purpose is correctness, not speed. *(enterprise-application-patterns.md)*
- **Lazy Load** - Intent: a placeholder fetching an object/collection only on first access. When to use: large object graphs. Trade-offs: bounds initial reads; risks N+1 and navigation surprises. *(enterprise-application-patterns.md)*
- **Identity Field** - Intent: store the DB key in the object to map references to rows. When to use: any persisted entity. Trade-offs: tedious but foundational for reference mapping. *(enterprise-application-patterns.md)*
- **Foreign Key Mapping** - Intent: map an inter-object reference/collection to a foreign key. When to use: one-to-one and one-to-many associations. Trade-offs: standard; collection handling needs add/remove detection. *(enterprise-application-patterns.md)*
- **Association Table Mapping** - Intent: map many-to-many via a dedicated link table. When to use: collections on both ends. Trade-offs: only relational option for many-to-many; an extra table. *(enterprise-application-patterns.md)*
- **Dependent Mapping** - Intent: one class persists another used only within its scope. When to use: strictly owned child objects. Trade-offs: simpler mapping; only valid for owned objects. *(enterprise-application-patterns.md)*
- **Embedded Value** - Intent: map a small value object's fields into the owner's table. When to use: money, date ranges. Trade-offs: no extra table/Identity Map; cannot be queried independently. *(enterprise-application-patterns.md)*
- **Serialized LOB** - Intent: save an object cluster as one large column. When to use: isolated hierarchic structures. Trade-offs: cuts round-trips; opaque to SQL queries. *(enterprise-application-patterns.md)*
- **Single/Class/Concrete Table Inheritance** - Intent: three strategies to map a class hierarchy to tables. When to use: Single (few type-specific fields), Class (normalized/DBA clarity), Concrete (query by concrete type). Trade-offs: simplicity/no-joins vs. normalization vs. ripple-on-change; respectively wide nullable tables, multi-join loads, hard abstract queries. *(enterprise-application-patterns.md)*
- **Metadata Mapping** - Intent: hold mapping as data and generate mapping behavior (basis of modern ORMs). When to use: many similar mappings. Trade-offs: removes repetitive code; harder to debug generated behavior. *(enterprise-application-patterns.md)*
- **Query Object** - Intent: an object representing a query in domain terms, translated to SQL. When to use: complex/composable, DB-independent queries. Trade-offs: ubiquitous-language queries; nontrivial to build. *(enterprise-application-patterns.md)*
- **Repository (PoEAA)** - Intent: collection-like interface mediating domain and data mapping, queried with criteria. When to use: a Domain Model wanting persistence ignorance. Trade-offs: clean domain-facing access; another layer over the mapper. *(enterprise-application-patterns.md)*
- **Model View Controller** - Intent: separate model, view, and input controller so presentation/domain vary independently. When to use: nearly all interactive presentation. Trade-offs: testability and multiple presentations; more parts and an overloaded "controller" term. *(enterprise-application-patterns.md)*
- **Page Controller / Front Controller** - Intent: one controller per page/action vs. a single handler interpreting all requests. When to use: page-oriented sites vs. centralized cross-cutting handling. Trade-offs: simple/intuitive but can duplicate, vs. centralized policy but more complex. *(enterprise-application-patterns.md)*
- **Template View / Transform View / Two Step View** - Intent: render via markers in HTML, via a transform (XSLT), or via a logical-screen-then-render two-stage pipeline. When to use: designer-friendly markup; XML data; or site-wide consistent look/multi-device. Trade-offs: logic-in-page risk; awkward transform language; needs a stable shared logical screen. *(enterprise-application-patterns.md)*
- **Application Controller** - Intent: a layer deciding screen flow/navigation. When to use: the machine controls screen order (wizards). Trade-offs: reusable flow; obstructive when the user controls navigation. *(enterprise-application-patterns.md)*
- **Remote Facade** - Intent: a coarse-grained facade over fine-grained objects, existing only to provide a remote interface. When to use: crossing a process/network boundary. Trade-offs: minimizes remote calls and keeps cost explicit; delegation only. *(enterprise-application-patterns.md)*
- **Data Transfer Object (DTO)** - Intent: a serializable object carrying a batch of data across the wire in one round-trip. When to use: aggregated data over a remote interface. Trade-offs: collapses many reads into one transfer; references only DTOs/primitives, adds mapping. *(enterprise-application-patterns.md)*
- **Optimistic Offline Lock** - Intent: detect conflicts at commit via a version marker. When to use: rare/cheap-to-redo conflicts; liveness matters. Trade-offs: best concurrency and easiest; failure discovered late. *(enterprise-application-patterns.md)*
- **Pessimistic Offline Lock** - Intent: prevent conflicts by acquiring locks before editing. When to use: likely/painful conflicts. Trade-offs: early failure and protected work; less concurrency, deadlock risk. *(enterprise-application-patterns.md)*
- **Coarse-Grained Lock / Implicit Lock** - Intent: lock a group of related objects with one lock; acquire locks automatically in framework code. When to use: aggregates that change together; enforcing lock discipline. Trade-offs: far less bookkeeping; needs domain knowledge / hides behavior. *(enterprise-application-patterns.md)*
- **Client / Server / Database Session State** - Intent: store session state on the client, in server memory, or in the database. When to use: maximize scalability; convenience; durability + app-server statelessness. Trade-offs: size/security limits; memory and failover cost; extra DB load. *(enterprise-application-patterns.md)*
- **Gateway / Money / Special Case / Layer Supertype / Registry / Separated Interface / Service Stub (base patterns)** - Intent: encapsulate external access; model amount+currency safely; replace null/edge checks (Null Object); share layer behavior; provide a known lookup; split interface from implementation; stub a service for tests. Trade-offs: small reusable building blocks; watch for god-class Layer Supertypes and Registry as global state. *(enterprise-application-patterns.md)*

### GoF design patterns (Sarcar; Wilson; Gang of Four)

*Source file: gof-design-patterns.md.*

- **Factory Method** - Intent: define an interface for creating an object but let subclasses decide which class to instantiate. When to use: a class cannot anticipate the concrete type, or wants subclasses to specify it. Trade-offs: removes `new` coupling, supports open/closed; adds a parallel hierarchy. *(gof-design-patterns.md)*
- **Abstract Factory** - Intent: create families of related objects without specifying concrete classes. When to use: products come in compatible families and the system must be creation-independent. Trade-offs: enforces family consistency; adding a product type changes every factory. *(gof-design-patterns.md)*
- **Builder** - Intent: separate construction of a complex object from its representation so the same process makes different representations. When to use: multi-part, multi-step (often fluent) construction. Trade-offs: readable step-by-step build; more classes (Builder/ConcreteBuilder/Director/Product). *(gof-design-patterns.md)*
- **Prototype** - Intent: create new objects by cloning a prototypical instance. When to use: costly creation or runtime-chosen class with a good template. Trade-offs: cheap creation and runtime flexibility; deep-vs-shallow copy hazards. *(gof-design-patterns.md)*
- **Singleton** - Intent: ensure one instance with a global access point. When to use: a single coordinator (cache, config, pool) with costly construction. Trade-offs: controlled single instance; global state that hurts testing/concurrency. *(gof-design-patterns.md)*
- **Dependency Injection (IoC)** - Intent: supply a class's dependencies from outside to satisfy the Dependency Inversion Principle. When to use: decoupling from concrete collaborators, enabling testing/config. Trade-offs: loose coupling and testability; needs wiring/containers and indirection. *(gof-design-patterns.md)*
- **Adapter** - Intent: convert one interface into another clients expect. When to use: reuse a class with a mismatched interface. Trade-offs: reuse without changing the adaptee; one more wrapper. *(gof-design-patterns.md)*
- **Decorator** - Intent: attach responsibilities dynamically by wrapping in a compatible object. When to use: add behaviors (logging, timing) without subclass explosion. Trade-offs: flexible runtime composition; many small wrappers, harder identity/debugging. *(gof-design-patterns.md)*
- **Facade** - Intent: a simple unified interface over a complex subsystem. When to use: hide complexity, decouple clients from internals. Trade-offs: easier use and looser coupling; can become a god-object. *(gof-design-patterns.md)*
- **Proxy** - Intent: a surrogate controlling access (lazy, remote, protection, caching). When to use: defer creation, mediate remote access, add access control. Trade-offs: transparent indirection and control; extra layer/latency. *(gof-design-patterns.md)*
- **Composite** - Intent: compose objects into trees and treat individual and composite uniformly. When to use: part-whole hierarchies. Trade-offs: uniform client code; can over-generalize leaf vs. composite. *(gof-design-patterns.md)*
- **Bridge** - Intent: decouple an abstraction from its implementation so both vary independently. When to use: avoid combinatorial class explosion across two dimensions. Trade-offs: independent extension; more indirection. *(gof-design-patterns.md)*
- **Flyweight** - Intent: share fine-grained objects via intrinsic/extrinsic state separation. When to use: huge numbers of similar objects. Trade-offs: large memory savings; managing shared/extrinsic state is complex. *(gof-design-patterns.md)*
- **Strategy** - Intent: define interchangeable algorithms selected at runtime. When to use: multiple variants of a behavior. Trade-offs: swap algorithms, avoid conditionals; clients must know the strategies. *(gof-design-patterns.md)*
- **Observer** - Intent: a one-to-many dependency notifying dependents of state changes. When to use: events, model-view updates. Trade-offs: loose coupling; update order/cascades hard to follow. *(gof-design-patterns.md)*
- **Command** - Intent: encapsulate a request as an object, enabling queue/log/undo. When to use: parameterize actions, undo/redo, decouple invoker from receiver. Trade-offs: first-class operations and undo; many small classes. *(gof-design-patterns.md)*
- **State** - Intent: let an object change behavior when its internal state changes. When to use: state-machine behavior. Trade-offs: removes large conditionals; one class per state. *(gof-design-patterns.md)*
- **Template Method** - Intent: a parent defines an algorithm skeleton calling abstract steps subclasses implement. When to use: invariant flow with varying steps. Trade-offs: structural reuse; relies on inheritance and parent-owned flow. *(gof-design-patterns.md)*
- **Iterator** - Intent: hide structure differences so everything is processed with uniform loops. When to use: traverse collections without exposing representation. Trade-offs: uniform traversal; an extra abstraction per structure. *(gof-design-patterns.md)*
- **Mediator** - Intent: encapsulate how a set of objects interact via a mediator. When to use: tangled many-to-many interactions. Trade-offs: less direct coupling; mediator can grow complex. *(gof-design-patterns.md)*
- **Chain of Responsibility** - Intent: each handler processes a request or passes it on. When to use: multiple possible handlers chosen at runtime (e.g., pattern matcher). Trade-offs: decoupled, extensible; no guarantee of handling (pair with Null Object). *(gof-design-patterns.md)*
- **Visitor** - Intent: take the operation to each element, separating traversal from per-node operation. When to use: many operations over a stable tree (validator, linter). Trade-offs: add operations without touching nodes; adding node types touches every visitor. *(gof-design-patterns.md)*
- **Memento** - Intent: capture/externalize internal state for later restore without breaking encapsulation. When to use: undo/checkpoints. Trade-offs: clean state capture; memory cost. *(gof-design-patterns.md)*
- **Null Object** - Intent: a placeholder with the expected methods that do nothing, used instead of null. When to use: eliminate repeated null checks; terminate handler chains. Trade-offs: removes special cases; can hide genuinely missing values. *(gof-design-patterns.md)*

### Empirical design, refactoring, and craft (Beck; Mancuso; Tornhill)

*Source file: empirical-design-refactoring-and-craft.md.*

- **Tidying (small reversible structure change)** - Intent: a tiny, safe, structure-only change that makes the next behavior change easier. When to use: first/after/later relative to a behavior change. Trade-offs: cheap, reversible, compounding; risks a "tidying binge" if unbounded. *(empirical-design-refactoring-and-craft.md)*
- **Separate Tidying** - Intent: keep structure changes in their own small pull requests. When to use: any code-review team. Trade-offs: reviewable and low-risk, faster reviews; risks "pointless PR" pushback. *(empirical-design-refactoring-and-craft.md)*
- **First/After/Later/Never decision** - Intent: choose when to tidy relative to a behavior change using economics (cash flow vs. options). When to use: every messy change. Trade-offs: aligns design effort with value; judgment, not a formula. *(empirical-design-refactoring-and-craft.md)*
- **Reversibility framing** - Intent: invest caution in proportion to how hard a decision is to undo, and make risky decisions reversible first. When to use: any consequential design/deploy decision. Trade-offs: avoids costly irreversible mistakes and wasted ceremony; requires honest reversibility assessment. *(empirical-design-refactoring-and-craft.md)*
- **Hotspot analysis** - Intent: rank modules by complexity x change frequency to target refactoring. When to use: prioritizing technical debt in a large codebase. Trade-offs: lightweight, defect-correlated; probabilistic, confirm with inspection. *(empirical-design-refactoring-and-craft.md)*
- **Complexity-trend analysis** - Intent: track a module's complexity over time (Lehman's law) to see improvement vs. decay. When to use: monitoring a hotspot under repair. Trade-offs: cheap direction signal; a proxy metric. *(empirical-design-refactoring-and-craft.md)*
- **Change (temporal) coupling analysis** - Intent: find files that change together in version control to reveal implicit dependencies. When to use: architectural review, finding DRY violations/entanglement. Trade-offs: surfaces dependencies static analysis cannot; needs interpretation. *(empirical-design-refactoring-and-craft.md)*
- **Organizational / knowledge-map analysis** - Intent: mine authorship to find coordination bottlenecks, truck-factor risk, and Conway's-Law misalignment. When to use: scaling teams, planning ownership, de-risking key people. Trade-offs: makes invisible social risk visible; depends on clean commit data and respectful use. *(empirical-design-refactoring-and-craft.md)*

## Domain 07 - Distributed Systems, Scalability, and Resilience

### Stability patterns (Nygard, Release It!)

*Source file: resilience-and-stability-patterns.md. Each counters one or more stability antipatterns (Integration Points, Chain Reactions, Cascading Failures, Users, Blocked Threads, Attacks of Self-Denial, Scaling Effects, Unbalanced Capacities, Slow Responses, SLA Inversion, Unbounded Result Sets).*

- **Use Timeouts** - Intent: bound every wait on an integration point or resource pool so a slow/hung dependency cannot become a Blocked Thread. When to use: every networked call, resource checkout, and blocking primitive. Trade-offs: averts Cascading Failures and frees resources; immediate retries usually re-hit the fault, so queue and retry later. *(resilience-and-stability-patterns.md)*
- **Circuit Breaker** - Intent: after a failure threshold, stop calling a sick dependency and fail fast, then probe for recovery. When to use: any high-throughput caller of a failure-prone remote service. Trade-offs: protects caller and callee; needs threshold tuning, fallbacks, and operations-visible state. Use with Timeouts (the timeout is the failure signal). *(resilience-and-stability-patterns.md)*
- **Bulkheads** - Intent: partition capacity (thread pools, CPUs, servers) so a failure in one compartment cannot sink the whole. When to use: when one workload/consumer must not exhaust shared capacity. Trade-offs: containment costs reserve capacity per partition; choose a useful granularity. *(resilience-and-stability-patterns.md)*
- **Steady State** - Intent: run a full deployment cycle without recurring human intervention; pair every data accumulation with cleanup. When to use: any long-running system (logs, caches, sessions, history). Trade-offs: eliminates fiddling-induced outages; requires app-logic purging, capped caches, and log rotation. *(resilience-and-stability-patterns.md)*
- **Fail Fast** - Intent: return an error immediately when the SLA cannot be met; verify resources and integration points before expensive work. When to use: middle-tier services and transactions with cheap-to-check preconditions. Trade-offs: turns slow failures into kind quick ones; adds precondition/reservation logic. *(resilience-and-stability-patterns.md)*
- **Handshaking** - Intent: let a server signal a client it is too busy, creating cooperative demand throttling. When to use: when you control both ends or can add health checks for protocols lacking it. Trade-offs: regulates load to serviceable levels; needs both-end support. *(resilience-and-stability-patterns.md)*
- **Test Harness** - Intent: a malicious test double emulating out-of-spec failures (slow/no/garbage responses, drops) real systems cannot reliably produce. When to use: verifying caller failure-mode behavior in isolation. Trade-offs: reveals handling other tests miss; supplements, does not replace, functional tests. *(resilience-and-stability-patterns.md)*
- **Decoupling Middleware** - Intent: integrate via asynchronous, fully decoupling middleware so participants never block on one another. When to use: when total decoupling is worth a large, nearly irreversible architecture commitment decided early. Trade-offs: reduces Integration Points, Cascading Failures, Slow Responses, and Blocked Threads and boosts adaptability; ripples through the whole system. *(resilience-and-stability-patterns.md)*

### Reactive architecture (Boner)

*Source file: reactive-architecture.md.*

- **Bulkheading (failure isolation)** - Intent: divide the system into isolated compartments so failure cannot cascade and sink the whole. When to use: any service boundary needing failure containment. Trade-offs: requires genuine isolation (incomplete bulkheads spill over) achievable only by dropping synchronous coupling. *(reactive-architecture.md)*
- **Service supervision / supervisor hierarchies** - Intent: manage failure orthogonally to the workflow via a hierarchy where parents heal subordinates. When to use: actor-style systems (Erlang, Akka) needing self-healing. Trade-offs: separates failure handling from logic; needs a supervision-capable runtime. *(reactive-architecture.md)*
- **Asynchronous message-passing (share-nothing default)** - Intent: communicate between services asynchronously and non-blocking to decouple in time and space. When to use: all inter-service communication. Trade-offs: makes network failure first-class and frees scarce threads; harder reasoning/tooling; synchronous REST is a poor inter-service default. *(reactive-architecture.md)*
- **Location transparency via virtual addressing** - Intent: address a service through a stable, virtual address hiding location/replication so it can scale, relocate, and fail over without client changes. When to use: any elastic, mobile service. Trade-offs: needs discovery infrastructure; enables load-balancing, active-passive replication, and relocation. *(reactive-architecture.md)*
- **Service discovery (Inversion of Control)** - Intent: services report their location to the platform instead of hardcoding addresses. When to use: any dynamic/elastic system. Trade-offs: keeps services decoupled and mobile; the discovery service must be available. *(reactive-architecture.md)*
- **API Gateway (reactive)** - Intent: single entry point routing/translating/composing requests for external clients that assume synchronous communication. When to use: bridging clients to an internal asynchronous system. Trade-offs: simplifies clients; centralized solutions are hard to scale, so prefer decentralized/platform-provided. *(reactive-architecture.md)*
- **Publish-Subscribe backbone (modern ESB)** - Intent: logically decouple senders/receivers and route by rules via a scalable broker or AP-style store. When to use: once point-to-point grows into chatter beyond a handful of services. Trade-offs: tames coupling; reintroduces a streaming/queue backbone to operate. *(reactive-architecture.md)*
- **Back-pressured streaming (Reactive Streams)** - Intent: bridge systems with asynchronous back-pressured streams so a fast producer cannot overload a slow consumer. When to use: integration and continuous/unbounded streams. Trade-offs: improves reliability and performance; requires Reactive Streams-compatible components both ends. *(reactive-architecture.md)*

### Event sourcing and CQRS (Hoffman)

*Source file: event-sourcing-and-cqrs.md. Governed by the ten Laws of Event Sourcing.*

- **Event Sourcing** - Intent: persist state as an append-only log of immutable past-tense events; derive state by replay. When to use: audit/history, temporal queries, replay recovery/upgrades, simplified scaling, complex core domains. Trade-offs: full history, trivial pure-function testing, disposable read models; harder model, apparent boilerplate, law discipline. *(event-sourcing-and-cqrs.md)*
- **CQRS** - Intent: separate the write model (event log plus aggregates) from query-optimized read models (projections). When to use: divergent read/write shapes; effectively mandatory with event sourcing. Trade-offs: O(1) tailored reads and independent evolution; eventual consistency and projector maintenance. *(event-sourcing-and-cqrs.md)*
- **Projection / read-model regeneration** - Intent: build query-optimized views via projectors and regenerate by replay. When to use: every consumer-facing query. Trade-offs: fast, disposable, adaptable; projections lag and must never feed business logic. *(event-sourcing-and-cqrs.md)*
- **Snapshotting** - Intent: persist periodic aggregate-state checkpoints so rehydration replays only events since the snapshot. When to use: long streams or to shrink the online log. Trade-offs: faster loads and smaller live storage; manage checkpoints and regeneration. *(event-sourcing-and-cqrs.md)*
- **Process Manager (Saga)** - Intent: coordinate a multi-event flow by consuming events and emitting commands, holding state from inciting to terminating event. When to use: flows with discrete begin/middle/end, meaningful state, possibly repeated per entity. Trade-offs: explicit recoverable coordination; one flow per manager, no reading projections. *(event-sourcing-and-cqrs.md)*
- **Explicit event versioning (new type per change)** - Intent: model each schema change as a new event type, never mutating an existing one. When to use: any time event fields must change. Trade-offs: keeps the log a reliable source of truth and preserves history; maintain version-specific logic; avoids the backward-compatibility trap. *(event-sourcing-and-cqrs.md)*
- **Crypto-shredding (right to be forgotten)** - Intent: support GDPR erasure without deleting events by encrypting PII per-subject and destroying the key. When to use: streams containing PII. Trade-offs: honors immutability and erasure together; needs key management and handling of decrypted copies. *(event-sourcing-and-cqrs.md)*
- **Wait-for-my-writes (read-your-writes at the edge)** - Intent: read your own write in a replicated/edge system by tracking the projection's last sequence number and waiting for it. When to use: read-your-writes consistency is required and staleness intolerable. Trade-offs: simple/effective; naive version-waiting reads anyone's writes, so needs care; CRDTs are the heavier alternative. *(event-sourcing-and-cqrs.md)*
- **Idempotent / duplicate-tolerant processing** - Intent: handle at-least-once delivery via unique event IDs, broker duplicate windows, or naturally idempotent handlers. When to use: any broker without exactly-once. Trade-offs: protects state under retries; tracks processed IDs; at-most-once trades duplicates for possible loss. *(event-sourcing-and-cqrs.md)*

## Domain 07 - Distributed Systems, Scalability, Resilience

### Data-intensive systems (DDIA)

*Source file: data-intensive-systems.md.*

- **Single-leader replication** - Intent: route all writes through one leader that streams a replication log to read-only followers. When to use: read-heavy workloads needing simple consistency and conflict-free writes. Trade-offs: simple and consistent, but the leader is a write bottleneck and failover hazard; replication lag causes stale reads. *(data-intensive-systems.md)*
- **Multi-leader replication** - Intent: accept writes at several leaders that replicate to each other. When to use: multi-datacenter, offline clients, collaborative editing. Trade-offs: better write availability/locality; inevitable write conflicts need resolution (LWW, version vectors, CRDTs). *(data-intensive-systems.md)*
- **Leaderless replication (Dynamo-style)** - Intent: read/write many replicas directly using quorums. When to use: maximum availability, tunable consistency (Cassandra, Riak). Trade-offs: failure-tolerant but best-effort consistency; needs read repair and anti-entropy. *(data-intensive-systems.md)*
- **Quorum reads/writes (w + r > n)** - Intent: guarantee read/write overlap so reads see the latest write. When to use: leaderless systems tuning consistency vs availability. Trade-offs: tunable, but sloppy quorums and concurrent writes still allow staleness/conflicts. *(data-intensive-systems.md)*
- **Read-your-writes / monotonic-reads / consistent-prefix-reads** - Intent: targeted consistency guarantees that paper over replication lag where users notice. When to use: asynchronously replicated read replicas. Trade-offs: cheaper than linearizability; each needs specific routing/tracking. *(data-intensive-systems.md)*
- **Hash / range partitioning (sharding)** - Intent: split a dataset across nodes by key to scale storage and throughput. When to use: data/load exceeds one node. Trade-offs: range scans vs hot spots (range) or even spread but no range queries (hash); secondary indexes partition by document or term. *(data-intensive-systems.md)*
- **Consistent hashing / rebalancing** - Intent: move minimal data when nodes join/leave. When to use: elastic clusters. Trade-offs: fixed-partition vs dynamic schemes trade simplicity for flexibility; avoid auto-rebalance during failures. *(data-intensive-systems.md)*
- **Two-phase commit (2PC)** - Intent: atomic commit across nodes via a coordinator's prepare/commit. When to use: distributed transactions needing cross-system atomicity. Trade-offs: atomic but blocks on coordinator failure; slow and fragile. *(data-intensive-systems.md)*
- **Total order broadcast (atomic broadcast)** - Intent: deliver the same messages to all nodes in the same order. When to use: linearizable storage, replicated state machines, consensus. Trade-offs: equivalent to consensus; strong ordering at the cost of coordination and partition-time availability. *(data-intensive-systems.md)*
- **LSM-tree storage engine** - Intent: append writes to a sorted memtable, flush immutable SSTables, compact in background. When to use: write-heavy ingestion, log/time-series. Trade-offs: very high write throughput and good compression; read/compaction overhead and write amplification. *(data-intensive-systems.md)*
- **B-tree storage engine** - Intent: keyed access via balanced fixed-size pages updated in place with a WAL. When to use: read-latency-sensitive, transaction-heavy, range queries. Trade-offs: predictable reads and strong transactional fit; writes at least twice and slower random writes. *(data-intensive-systems.md)*
- **Column-oriented storage** - Intent: store values column-by-column so analytic queries read only needed columns. When to use: OLAP/data-warehouse workloads. Trade-offs: strong compression and vectorized scans; harder writes, kept separate from OLTP via ETL/CDC. *(data-intensive-systems.md)*
- **Schema-driven binary encoding (Avro/Protobuf/Thrift)** - Intent: compact, evolvable serialization preserving backward and forward compatibility. When to use: persisted data and service messages across rolling upgrades. Trade-offs: interoperable and evolvable; requires schema discipline (add only optional fields, never reuse tags). *(data-intensive-systems.md)*

### Distributed & real-time computing foundations (Buttazzo; PDCAT)

*Source file: distributed-and-realtime-computing-foundations.md.*

- **Rate Monotonic priority assignment** - Intent: give shorter-period periodic tasks higher fixed priority (optimal fixed-priority scheduling). When to use: periodic hard real-time tasks on a static-priority RTOS. Trade-offs: simple and analyzable; wastes up to ~31% CPU at the worst-case utilization bound (ln 2). *(distributed-and-realtime-computing-foundations.md)*
- **EDF dynamic scheduling** - Intent: always run the job with the nearest absolute deadline. When to use: maximizing utilization (U ≤ 1) and mixed periodic/aperiodic load. Trade-offs: full utilization and optimality vs higher run-time overhead and ungraceful overload (domino misses). *(distributed-and-realtime-computing-foundations.md)*
- **Response Time Analysis (RTA)** - Intent: prove schedulability exactly by computing each task's worst-case response time. When to use: fixed-priority systems, especially when deadlines differ from periods. Trade-offs: exact and general; iterative per-task computation. *(distributed-and-realtime-computing-foundations.md)*
- **Aperiodic/sporadic server (bandwidth reservation)** - Intent: bound interference of irregular jobs with a replenishing execution budget. When to use: mixing event-driven aperiodic work with guaranteed periodic tasks. Trade-offs: responsive aperiodic service while preserving hard guarantees; server-management complexity. *(distributed-and-realtime-computing-foundations.md)*
- **Priority Ceiling / Stack Resource Policy** - Intent: bound priority-inversion blocking to one critical section and prevent deadlock/chained blocking. When to use: real-time tasks sharing mutually-exclusive resources. Trade-offs: strong guarantees vs ceiling bookkeeping; PIP is simpler but weaker. *(distributed-and-realtime-computing-foundations.md)*
- **Non-blocking collective communication (overlap)** - Intent: overlap a collective such as Allreduce with computation, doubling as a liveness/health check. When to use: bulk-synchronous and dynamic HPC simulations. Trade-offs: hides communication latency and detects stragglers; more complex progress management. *(distributed-and-realtime-computing-foundations.md)*
- **List-based workflow scheduling** - Intent: order ready DAG tasks by priority and greedily map onto heterogeneous resources to minimize makespan. When to use: workflow scheduling on clusters/grids. Trade-offs: fast scalable heuristics; learned (RL) policies can beat them at the cost of training and explainability. *(distributed-and-realtime-computing-foundations.md)*
- **Atomic broadcast coordination (Zab-style)** - Intent: deliver ordered, fault-tolerant updates so all replicas agree, underpinning a coordination service. When to use: leader-based coordination, configuration, locking. Trade-offs: strong consistency and fault tolerance vs leader-election cost and partition-time availability; warrants formal verification. *(distributed-and-realtime-computing-foundations.md)*

## Domain 07 - Distributed Systems, Scalability, and Resilience

### AKF Scale Cube and scaling techniques (Abbott & Fisher)

*Source file: scalability-principles.md.*

- **X-Axis Cloning (Horizontal Duplication)** - Intent: scale transaction volume by running N identical, stateless instances (apps) or read replicas (data) behind a load balancer with no routing bias. When to use: transaction growth is the primary driver and the codebase/dataset is not the constraint; the default first move. Trade-offs: cheapest and simplest, easy capacity planning; does not scale data size or code complexity, limited by replication fan-out. *(scalability-principles.md)*
- **Y-Axis Functional/Service Split** - Intent: scale code and data complexity by separating the monolith into services along verb (action) or noun (resource) boundaries. When to use: the application is growing in features/size, response times suffer from competing functions, or you want fault isolation and team autonomy. Trade-offs: scales complexity and creates fault isolation; requires code/data rework and more operational configs. *(scalability-principles.md)*
- **Z-Axis Sharding (Lookup-Oriented Split)** - Intent: scale customer/data growth by partitioning users or data into pods via a lookup service or deterministic hash/modulus. When to use: customer base and per-customer data are the constraint; you need geographic dispersion or per-segment rollouts. Trade-offs: near-infinite data scale, best cache locality, fault isolation; most costly, needs routing logic, does not reduce code complexity. *(scalability-principles.md)*
- **Swim Lane (Fault Isolation Zone)** - Intent: isolate a unit of functionality so a failure or capacity exhaustion in one lane cannot cascade to others. When to use: protect revenue-generating flows, isolate the biggest incident sources, or segment along natural (customer) barriers. Trade-offs: dramatically improves availability and pinpoints failures; not free, apply only where return justifies it. Rules: nothing shared, nothing crosses the boundary, transactions run along (not across) lanes. *(scalability-principles.md)*
- **Stateless Service** - Intent: remove per-request affinity so any clone can serve any request. When to use: any service intended to scale horizontally. Trade-offs: makes X-axis cloning trivial and improves failover; requires pushing state to a shared store or the client. *(scalability-principles.md)*
- **Read-Replica Leader/Follower Replication** - Intent: scale read throughput by writing to one leader and serving reads from N followers. When to use: read-heavy workloads tolerating small replication delay. Trade-offs: simple, native to most databases; reads can be stale, replication caps follower count, writes do not scale this way. *(scalability-principles.md)*
- **Cache-Aside / Distributed Cache Tier** - Intent: serve hot data from a fast in-memory tier (e.g., Redis) to cut latency and offload the database. When to use: read-heavy data with high reuse and tolerable staleness. Trade-offs: large latency/load reductions; introduces invalidation complexity and a consistency window. *(scalability-principles.md; system-design-method.md)*
- **Asynchronous Messaging / Queueing** - Intent: decouple producers from consumers via a queue or bus so callers do not block on slow downstream work. When to use: work that need not complete synchronously (notifications, fan-out, ETL) and bursty load. Trade-offs: improves scalability, availability, burst absorption; adds eventual consistency, ordering/duplicate concerns, operational components. *(scalability-principles.md; system-design-method.md)*
- **N+1 Capacity / Headroom Planning** - Intent: size components with the formula Headroom = (Ideal Usage % x Max Capacity) - Current Usage - planned growth, planning to 50–75% of max, never 100%. When to use: every capacity and procurement decision. Trade-offs: absorbs estimation error and avoids unpredictable near-ceiling behavior (thrashing); leaves deliberate slack. *(scalability-principles.md)*

### System-design method and building blocks (Tan; Sinha & Chopra)

*Source file: system-design-method.md.*

- **Requirements-first design loop** - Intent: reach a defensible architecture by clarifying scope and numbers before drawing components (clarify -> API -> data model -> failure/ops -> complexity). When to use: any new service, major rearchitecture, or design interview. Trade-offs: prevents wasted detail and missed requirements; feels slow when the prompt seems obvious. *(system-design-method.md)*
- **Back-of-the-envelope estimation** - Intent: convert user counts into QPS, storage (per item x volume x retention), and bandwidth to size the system and locate bottlenecks. When to use: immediately after requirements, before choosing technologies. Trade-offs: cheap and decisive about distribution/sharding/caching; only as good as its stated assumptions. *(system-design-method.md)*
- **Timeline fan-out (push vs. pull)** - Intent: deliver feed items by writing into each follower's timeline on post (push) or assembling at read time (pull). When to use: push for modest follower counts (fast reads); pull or hybrid for celebrities (avoid write amplification). Trade-offs: push = fast reads, heavy writes; pull = cheap writes, slow reads; hybrid balances both. *(system-design-method.md)*
- **API gateway** - Intent: single entry point handling routing, authentication, rate limiting, and request/response transformation. When to use: any microservices system with external clients. Trade-offs: centralizes cross-cutting concerns; can become a bottleneck or SPOF if not scaled and isolated. *(system-design-method.md)*
- **Rate limiting (token bucket / leaky bucket / window counters)** - Intent: cap a client's request rate to protect downstream services. When to use: public APIs and shared services. Trade-offs: token bucket allows bursts to a cap; leaky bucket smooths to constant rate; fixed-window is simple but allows edge bursts; sliding-window log is accurate but memory-heavy; sliding-window counter approximates cheaply. Counts in an in-memory store (Redis); deploy as sidecar or shared service. *(system-design-method.md)*
- **Denormalization for read performance** - Intent: duplicate data into a single table/document so common reads avoid JOINs. When to use: read-heavy access patterns with known queries. Trade-offs: fast reads; write amplification and consistency upkeep. *(system-design-method.md)*
- **Consistent hashing (with virtual nodes)** - Intent: map keys and nodes onto a ring so adding/removing a node remaps only a fraction of keys. When to use: sharded databases, distributed caches, CDNs. Trade-offs: minimal rebalancing and even-ish distribution (virtual nodes smooth hot spots); adds ring-management complexity. *(system-design-method.md)*
- **Quorum consistency tuning (R + W vs. N)** - Intent: tune read/write replica counts so R+W>N yields strong consistency, otherwise eventual. When to use: any replicated datastore balancing correctness against latency/availability. Trade-offs: precise control over the consistency/latency/availability trade; requires understanding the workload's correctness needs. *(system-design-method.md; scalability-principles.md)*

### Data mesh (Menon; Gopalan et al.)

*Source files: data-mesh.md; data-lakes-and-lakehouse.md.*

- **Domain-oriented decentralized data ownership** - Intent: assign full lifecycle ownership of analytical data to the business domain that produces it. When to use: large organizations where a central data team is a bottleneck and data has lost business context. Trade-offs: better quality, context, agility, accountability vs. needing skilled people in every domain, new roles/budgets, and per-domain governance. *(data-mesh.md)*

- **Self-serve data platform** - Intent: a platform letting domains create/operate data products without central specialists (platform thinking + DataOps). When to use: to remove central bottlenecks and scale data work across teams. Trade-offs: speed and autonomy vs. up-front platform investment, training, and shared-responsibility security. *(data-mesh.md)*
- **Federated computational governance** - Intent: decentralized governance with minimum global standards plus domain-specific policies, ideally automated. When to use: any data mesh, to keep interoperability/compliance while preserving autonomy. Trade-offs: balances control and freedom vs. governance machinery and cross-domain coordination bodies (DMO, governance council, domain leadership). *(data-mesh.md)*
- **Fully Governed mesh (hub-and-spoke)** - Intent: a central hub enforces consistent governance across spoke domains exposing data via standardized APIs. - **Fully Federated mesh (peer-to-peer)** - Intent: autonomous domains share directly with no central hub, mapping to a common ontology and a shared contract model. When to use: highly specialized domains needing maximum autonomy. Trade-offs: agility and no central bottleneck vs. domains self-enforcing governance and integrity. *(data-mesh.md)*
- **Hybrid mesh (shared-domain connector)** - Intent: connect governed and federated domain networks via a shared domain acting as hub for one and peer for the other. - **Domain placement scoring** - Intent: place a domain on the governance-flexibility spectrum by scoring its independence across functional context, people/skills, regulations, operations, and technical capabilities (weighted sum; ≥3 federated, <3 governed). When to use: deciding each domain's topology. Trade-offs: an explicit, defensible choice vs. requiring honest assessment and weighting. *(data-mesh.md)*

### Data lakes and lakehouse (Gopalan et al.; Lad)

*Source file: data-lakes-and-lakehouse.md.*

- **Medallion zones (Raw/Bronze, Enriched/Silver, Curated/Gold, + Sandbox)** - Intent: organize a data lake by processing stage and value density to control access, retention, and quality. When to use: any data lake. Trade-offs: clear lifecycle and governance hooks vs. discipline needed to avoid a data swamp. *(data-lakes-and-lakehouse.md)*
- **ELT (extract, load, transform)** - Intent: load raw data into cheap storage first and transform later, preserving the original signal. When to use: data lakes and lakehouses. Trade-offs: future-proofing/flexibility vs. raw zone needing management to avoid sprawl. *(data-lakes-and-lakehouse.md)*
- **Lakehouse (open table format + compute engine)** - Intent: run BI/SQL and data science on one lake with ACID guarantees via Delta Lake / Apache Iceberg / Apache Hudi over columnar Parquet. When to use: to eliminate the warehouse copy and unify teams. Trade-offs: low cost and no silos vs. careful format/engine selection and a less out-of-the-box path than a warehouse. *(data-lakes-and-lakehouse.md)*
- **Modern data warehouse (lake + warehouse)** - Intent: cheap lake storage and ML alongside a warehouse for familiar BI/SQL. When to use: modernizing while preserving SQL/BI investments. Trade-offs: familiar tooling vs. two infrastructures, data copies, and an engineer-dependent critical path. *(data-lakes-and-lakehouse.md)*
- **Disaggregated compute and storage** - Intent: store data once and query it in place with many stateless engines. When to use: cloud analytics at scale. Trade-offs: independent scaling and low cost vs. the architect must choose the right format/engine per query pattern. *(data-lakes-and-lakehouse.md)*

### Big data architecture (Azarmi; Lad)

*Source file: big-data-architecture.md.*

- **Lambda architecture** - Intent: combine a batch layer (accurate, comprehensive precomputed views) with a speed layer (low-latency views of recent data), merged in a serving layer, balancing latency, throughput, and fault tolerance. When to use: workloads needing both accurate historical aggregates and real-time views (recommendations, fraud/security, log analytics). Trade-offs: completeness plus low latency vs. dual codebases that must stay consistent, residual latency, and double-processing cost. *(big-data-architecture.md)*
- **Kappa architecture** - Intent: treat all data as an immutable, replayable stream processed by one engine, serving both real-time and historical analytics from a single codebase. When to use: streaming-first systems, IoT, continuous pipelines, on-demand analytics where a separate batch stack is unjustified. Trade-offs: simplicity, one source of truth, easy reprocessing via replay vs. everything must fit a streaming model and single engine. *(big-data-architecture.md)*
- **SLA-driven architecture split (batch / stream / serving)** - Intent: divide processing by latency requirement and prioritize/isolate resources accordingly (e.g., YARN Capacity Scheduler queues). When to use: multitenant data platforms with mixed-urgency workloads. Trade-offs: predictable resource sharing and SLA adherence vs. operational complexity of queues and isolation. *(big-data-architecture.md)*
- **Shipping → buffering → processing ingestion pipeline** - Intent: decouple producers from processors via a durable distributed message broker (Kafka) so no data is lost and bursts are absorbed. When to use: any streaming ingestion at scale. Trade-offs: resilience and elasticity vs. an extra broker tier to operate and monitor. *(big-data-architecture.md)*
- **Stream-first (streaming as the default)** - Intent: stream data first and only batch-store it if needed, rather than standing up a full Hadoop batch stack by default. When to use: most modern use cases where one processing API serves both needs. Trade-offs: less hardware/software complexity vs. continuous operations and sizing to absorb data bursts. *(big-data-architecture.md)*

### Classic data architecture foundations (Tupper; Inmon)

*Source file: data-architecture-foundations.md.*

- **Subject-area orientation** - Intent: organize the warehouse/atomic layer around major enterprise subjects (customer, product, claim) rather than by application or process. When to use: any integrated, nonvolatile decision-support store. Trade-offs: coherent reusable structure insulated from process change vs. up-front enterprise data analysis. *(data-architecture-foundations.md)*
- **Star schema (dimensional model)** - Intent: a central fact table of numeric measures surrounded by denormalized dimension tables so analytical queries need few joins. When to use: the consumer-facing detail layer / data marts where end users query directly. Trade-offs: simple, fast reads (~80% single-table browses) vs. heavy denormalization, duplication, aggregation loss, and instability when query needs shift; define the grain first. *(data-architecture-foundations.md)*
- **Normalized EDW with dimensional marts (Inmon-style hub-and-spoke)** - Intent: keep the foundational warehouse in 3NF for integrity/flexibility and derive dimensional star schemas into marts. When to use: large enterprises wanting both modular extensibility and query usability. Trade-offs: structured and change-resilient vs. more layers/ETL than building marts directly from business processes. *(data-architecture-foundations.md)*
- **Denormalization for performance** - Intent: deliberately reintroduce redundancy to cut joins and speed retrieval. When to use: known read-heavy access where join cost dominates. Trade-offs: faster reads, fewer objects vs. update/insert anomalies and consistency burden; justify and document for later renormalization. *(data-architecture-foundations.md)*
- **Generic domain-constraint / reference table** - Intent: house many limited-set validation values (codes, ranges, translations) without propagating foreign keys into the constraint tables. When to use: validation/lookup data shared by many entities. Trade-offs: avoids an enormous foreign-key web; keeps constraint tables independent reference data. *(data-architecture-foundations.md)*
- **Time as a database dimension** - Intent: model history explicitly (birth, state changes, termination) and archive per the structure at archival time. When to use: any system tracking recorded activity or answering historical queries. Trade-offs: enables trend analysis and audit vs. hard archival/retrieval when archived structure diverges from current. *(data-architecture-foundations.md)*
- **System of record + downstream reconciliation** - Intent: every detailed datum has one authoritative home; all copies reconcile back to it. When to use: any environment with distributed or replicated operational data. Trade-offs: eliminates conflicting values and gives a single reconciliation basis vs. disciplined ownership and a clear boundary. *(data-architecture-foundations.md)*
- **Primitive/derived separation (operational vs. DSS)** - Intent: physically separate single-entity primitive data (run the business) from multi-entity derived data (manage the business) across system-of-record, atomic, departmental, and individual layers. When to use: any analytics estate sitting alongside transactional systems. Trade-offs: right infrastructure per workload and no OLTP contention vs. ETL flow and defining scope of integration. *(data-architecture-foundations.md)*

### Modern data architecture at scale and for AI (Strengholt; Choudhury et al.)

*Source file: modern-data-architecture.md.*

- **CQRS / read replica as data product** - Intent: serve intensive reads from a separate read-optimized copy synced from the write store via events. When to use: any application whose data is read intensively by others; basis of data-product architectures. Trade-offs: independent scaling/technology and protects transactional systems vs. a sync layer, latency, and complexity. *(modern-data-architecture.md)*
- **Data product as a logical entity** - Intent: describe consumable data as a technology-agnostic logical entity referencing read-optimized physical assets, keeping metadata separate from data. When to use: distributing data across domains at scale where the same semantic data has multiple physical shapes. Trade-offs: clean ownership, lineage, security, flexibility vs. needing a metamodel and discipline. *(modern-data-architecture.md)*
- **Data fabric (metadata-driven automation / metalake)** - Intent: use a metalake (catalog + knowledge graph + ML) to automate discovery, lineage, quality, classification, and delivery across a distributed estate. When to use: complement to a data mesh, supplying the intelligence the mesh lacks. Trade-offs: self-service and observability at scale vs. heavy metadata-management investment and cultural change. *(modern-data-architecture.md)*
- **Data contract** - Intent: a versioned, machine-checkable agreement guaranteeing interface compatibility, SLAs, and usage/privacy terms between provider and consumer. When to use: any widely consumed data product in a distributed architecture. Trade-offs: detects breaking changes, decouples teams, adds transparency vs. schema-validation tooling and handshake workflows. *(modern-data-architecture.md)*
- **Lakehouse with open table format** - Intent: ACID transactions, schema enforcement, and time travel on cheap object storage (Delta Lake / Iceberg), unifying lake flexibility with warehouse reliability. When to use: AI/analytics estates needing both raw and curated data with reproducibility. Trade-offs: one unified platform with reproducible historical queries vs. table-format/engine lock-in and optimization overhead. *(modern-data-architecture.md)*
- **Feature store** - Intent: centralize and serve ML features for offline training and online inference. When to use: multiple models reusing features and needing training/inference consistency. Trade-offs: reuse, consistency, integrated versioning/lineage vs. another platform to operate and keep in sync. *(modern-data-architecture.md)*
- **Partitioning + indexing for AI workloads** - Intent: split datasets (horizontal/sharding, vertical, time-based) and index (B-tree, bitmap, inverted, spatial) for parallelism and fast retrieval. When to use: large-scale training, cross-validation, scalable inference, time-series AI. Trade-offs: faster queries and parallelism vs. index maintenance overhead and data-skew/hotspot risk. *(modern-data-architecture.md)*
- **Federated learning / privacy-preserving compute** - Intent: train across distributed sources without centralizing raw data (plus differential privacy, homomorphic encryption, SMPC). When to use: edge devices, cross-organization collaboration, regulated/sensitive data. Trade-offs: privacy and compliance with collaboration vs. cryptographic/coordination complexity and potential accuracy/latency cost. *(modern-data-architecture.md)*
- **MLOps lifecycle pipeline** - Intent: apply DevOps to ML - version code/data/models, CI/CD, automated testing of data and models, drift monitoring with feedback, and governance. When to use: any ML system moving from prototype to reliable production. Trade-offs: reproducibility, reliability, compliance vs. tooling and process investment (MLflow/Kubeflow/TFX/SageMaker). *(modern-data-architecture.md)*

### Data engineering design patterns (Konieczny)

*Source file: data-engineering-patterns.md. Roughly seventy recipes across ten categories (ingestion, error management, idempotency, data value, data flow, security, storage, quality, observability), each Problem/Solution/Consequences/Examples. Patterns often form evolution chains (Full -> Incremental -> CDC; Static -> Dynamic Joiner; Merger -> Stateful Merger; Single -> Concurrent Runner).*

- **Full Loader** - Intent: reload an entire small, slowly evolving source each run when there is no change-tracking attribute. When to use: reference/dimension data with no last-updated column and small row counts. Trade-offs: simplest extract-load; cost/runtime grow with volume (mitigate with autoscaling) and static clusters fail on sudden growth. *(data-engineering-patterns.md)*
- **Incremental Loader** - Intent: ingest only records added since the last run via a high-watermark. When to use: continuously growing immutable append-only sources. Trade-offs: bounded and efficient; needs a reliable watermark and careful boundary handling. *(data-engineering-patterns.md)*
- **Change Data Capture (CDC)** - Intent: stream every insert/update/delete from an OLTP table to a broker within seconds. When to use: low-latency replication where batch ingestion is too slow. Trade-offs: near-real-time and complete; requires CDC infrastructure and downstream update/delete handling. *(data-engineering-patterns.md)*
- **Passthrough Replicator / Transformation Replicator** - Intent: copy a dataset across environments unchanged, or while transforming it (for example masking PII). When to use: promoting reference data, or making real-shaped production data safely testable in lower environments. Trade-offs: trivial for homogeneous stores; the transforming variant adds a maintained step but enables compliant realistic testing. *(data-engineering-patterns.md)*
- **Compactor** - Intent: merge many small streaming-output files into fewer large ones. When to use: object-store datasets suffering small-files metadata overhead. Trade-offs: restores read performance; adds a periodic job and reader coordination. *(data-engineering-patterns.md)*
- **Readiness Marker** - Intent: publish an explicit completeness signal before consumers read a dataset/partition. When to use: downstream ML/BI consumers hitting partial reads. Trade-offs: eliminates partial reads; an extra publish step and a convention all consumers honor. *(data-engineering-patterns.md)*
- **External Trigger** - Intent: run ingestion only on an external new-data signal instead of a fixed schedule. When to use: irregular upstreams where scheduled reloads waste compute. Trade-offs: removes wasted runs; couples to a reliable external trigger. *(data-engineering-patterns.md)*
- **Dead-Letter** - Intent: route unprocessable records to a side store instead of failing the job. When to use: streaming/batch where bad records would crash the pipeline. Trade-offs: keeps the pipeline running and preserves records for triage; needs a dead-letter store and a triage process. *(data-engineering-patterns.md)*
- **Windowed Deduplicator** - Intent: drop duplicates within a bounded time window to approximate exactly-once. When to use: streaming sources with producer retries feeding business data. Trade-offs: simple and bounded; duplicates beyond the window slip through. *(data-engineering-patterns.md)*
- **Late Data Detector** - Intent: identify events arriving after their event-time window so a per-use-case strategy applies. When to use: any event-time pipeline with offline-buffering clients. Trade-offs: makes lateness explicit and actionable; needs event-time tracking and an allowed-lateness policy. *(data-engineering-patterns.md)*
- **Static / Dynamic Late Data Integrator** - Intent: re-integrate late data within a fixed window, or arbitrarily late without blindly replaying a fixed range. When to use: bounded correction horizon vs. full-correctness requirements. Trade-offs: bounded reprocessing cost (and silently dropped older records) vs. full correctness at the cost of tracking affected partitions. *(data-engineering-patterns.md)*
- **Filter Interceptor** - Intent: instrument the volume/reason of filtered-out records so a spike (data vs code regression) is visible. When to use: distributed jobs where silent over-filtering corrupts results. Trade-offs: filter-step observability for small metric overhead. *(data-engineering-patterns.md)*
- **Checkpointer** - Intent: persist streaming progress/intermediate results so a fatal failure resumes rather than restarting. When to use: long-running stateful streaming. Trade-offs: fast recovery; checkpoint storage and restart-compatibility care. *(data-engineering-patterns.md)*
- **Fast Metadata Cleaner** - Intent: achieve idempotency by dropping/recreating partitions via cheap metadata ops instead of row-level DELETE. When to use: large partitioned tables where DELETE-then-INSERT has become the bottleneck. Trade-offs: very fast re-runs; needs a metadata-aware table format and partition-aligned writes. *(data-engineering-patterns.md)*
- **Data Overwrite** - Intent: guarantee idempotency by overwriting an entire event-time partition each run. When to use: object-store partition-by-event-time datasets without a metadata layer. Trade-offs: simple and format-agnostic; rewrites whole partitions for small changes. *(data-engineering-patterns.md)*
- **Merger / Stateful Merger** - Intent: upsert CDC changes into a target so it mirrors the source, optionally versioned for rollback before a backfill. When to use: replicating a changing source into a Delta-Lake-style table; safe backfills. Trade-offs: consistent target (merge cost grows with size); the stateful variant adds point-in-time restore at the cost of retained versions. *(data-engineering-patterns.md)*
- **Keyed Idempotency** - Intent: deduplicate by writing to a key-value store keyed on deterministic identity so retries overwrite. When to use: streaming aggregations (for example per-user sessions). Trade-offs: clean keyed idempotency; needs a keyed-upsert store. *(data-engineering-patterns.md)*
- **Transactional Writer** - Intent: wrap writes in a transaction so partial/failed tasks leave no partial data. When to use: spot/preemptible runtimes where node loss is routine. Trade-offs: atomic all-or-nothing writes; transactional overhead and a supporting store. *(data-engineering-patterns.md)*
- **Proxy (immutable dataset)** - Intent: keep every produced version immutably but expose only the latest via a stable pointer. When to use: legal/audit retention with consumers seeing only current data. Trade-offs: full history with a simple consumer contract; storage growth and pointer management. *(data-engineering-patterns.md)*
- **Static / Dynamic Joiner** - Intent: enrich events against a static reference, or a continuously CDC-fed changing reference. When to use: stable context vs. high-churn context. Trade-offs: simple batch enrichment (stale when reference changes) vs. fresh enrichment at the cost of streaming join state. *(data-engineering-patterns.md)*
- **Wrapper / Metadata Decorator** - Intent: normalize heterogeneous input schemas into one structure, or attach technical context (job version, time) to each record. When to use: multi-provider inputs; frequently released jobs needing traceability. Trade-offs: one clean contract / cheap lineage, at the cost of evolving the wrapper and slightly larger records. *(data-engineering-patterns.md)*
- **Distributed / Local Aggregator** - Intent: compute large aggregates across a cluster with a shuffle, or within partition boundaries to avoid the shuffle when partitioning is stable. When to use: big dashboard rollups vs. static partitioning. Trade-offs: horizontal scale (expensive shuffle) vs. shuffle removal valid only when grouping aligns with partitioning. *(data-engineering-patterns.md)*
- **Incremental / Stateful Sessionizer** - Intent: build user sessions in batch from time-partitioned events, or in streaming with managed state for low latency. When to use: hourly-latency-acceptable vs. sub-hour session needs. Trade-offs: simple batch (latency bounded by partition) vs. seconds-level latency at the cost of streaming state. *(data-engineering-patterns.md)*
- **Bin Pack Orderer / FIFO Orderer** - Intent: batch and order records into size-optimized payloads, or forward a filtered subset in strict order with no buffering. When to use: cost-optimized delivery to an external API vs. lowest-latency ordered delivery. Trade-offs: efficient packing (added buffering) vs. strict order and minimal latency (no batching). *(data-engineering-patterns.md)*
- **Local / Isolated Sequencer** - Intent: split a monolithic job into resumable steps in one pipeline, or into independent team-owned pipelines chained by a published dataset. When to use: fragile long jobs vs. clear ownership boundaries. Trade-offs: partial restarts / clean ownership, at the cost of restructuring or an inter-team dataset contract. *(data-engineering-patterns.md)*
- **Aligned / Unaligned Fan-In** - Intent: aggregate fine-grained partitions into a coarser view, tolerating missing partitions in the unaligned variant. When to use: rollups where all inputs are present vs. partial-but-timely delivery preferred. Trade-offs: efficient rollup vs. availability over completeness with a gap-backfill mechanism. *(data-engineering-patterns.md)*
- **Parallel Split / Exclusive Choice** - Intent: run old and new implementations in parallel to validate a migration, then route by condition (for example run-date) to one version. When to use: rewriting a risky legacy pipeline, then cutting over while old dates backfill with old logic. Trade-offs: safe migration via comparison/branching, at the cost of doubled compute during overlap and branching logic. *(data-engineering-patterns.md)*
- **Single / Concurrent Runner** - Intent: orchestrate a pipeline sequentially, or run independent instances concurrently. When to use: ordered dependencies vs. independent loads where sequential execution backlogs. Trade-offs: simple correctness vs. higher throughput valid only when runs are truly independent. *(data-engineering-patterns.md)*
- **Vertical Partitioner (security) / In-Place Overwriter** - Intent: split immutable PII into a separately governed store, or comply with deletion on legacy time-partitioned storage by overwriting affected partitions. When to use: storage overhead and removal needs; legacy systems bound by privacy law. Trade-offs: cleaner deletion/less duplication (joins to reassemble) vs. erasure without a metadata layer (whole-partition rewrites). *(data-engineering-patterns.md)*
- **Fine-Grained Accessor (tables / resources)** - Intent: enforce row/column-level access beyond table grants, and least-privilege so a job touches only its datasets. When to use: users authorized for a table but not specific rows/columns; audits finding overly broad permissions. Trade-offs: precise least-privilege access at the cost of policy maintenance. *(data-engineering-patterns.md)*
- **Encryptor / Anonymizer / Pseudo-Anonymizer** - Intent: encrypt at rest/in transit, remove PII columns, or replace PII with stable usable surrogates. When to use: protection against interception/theft; third-party sharing with varying analytical needs. Trade-offs: confidentiality/privacy vs. key management, lost queryability (anonymize), or residual re-identification risk (pseudonymize). *(data-engineering-patterns.md)*
- **Secrets Pointer / Secretless Connector** - Intent: reference credentials from a secret manager, or authenticate via identity/role with no long-lived keys. When to use: any external credential; small teams avoiding key management. Trade-offs: prevents leaks; depends on a secret manager or platform identity federation. *(data-engineering-patterns.md)*
- **Horizontal Partitioner / Vertical Partitioner (storage)** - Intent: partition (often by time) for query pruning, or store immutable attributes once. When to use: time-filter queries gone slow; records with mutable/immutable attribute groups. Trade-offs: large read speedups (skew/partition-count risk) vs. less duplication (joins to reassemble). *(data-engineering-patterns.md)*
- **Bucket / Sorter** - Intent: hash a high-cardinality predicate column into fixed buckets, or physically sort within files by predicate columns. When to use: an attribute used in most queries but too high-cardinality to partition; known range-query patterns. Trade-offs: pruning/co-location without partition explosion (fixed bucket count) vs. lower read latency (sort cost on write). *(data-engineering-patterns.md)*
- **Metadata Enhancer / Dataset Materializer / Manifest** - Intent: add column statistics/zone maps for data skipping, precompute a materialized table for a slow view, or keep a file manifest so engines skip listing. When to use: subset queries within large partitions; repeated multi-partition view queries; object-store listing dominating runtime. Trade-offs: faster/cheaper reads at the cost of metadata maintenance, staleness/refresh, or manifest sync. *(data-engineering-patterns.md)*
- **Normalizer / Denormalizer** - Intent: split repeated attributes into related tables, or flatten relational models into wide tables to remove analytical joins. When to use: duplication inflating storage/updates vs. join-dominated analytical latency. Trade-offs: less duplication/cheaper updates (more joins) vs. fast analytical reads (storage growth, update anomalies). *(data-engineering-patterns.md)*
- **Audit-Write-Audit-Publish (WAP)** - Intent: compute to a staging location, audit, and publish only if it passes. When to use: business-critical aggregates where publishing wrong numbers is costly. Trade-offs: prevents bad data from being seen; adds a staging step and publish gate. *(data-engineering-patterns.md)*
- **Constraints Enforcer** - Intent: declare constraints (not-null, ranges, referential) so the load fails fast on violation without bespoke validation. When to use: jobs getting random nulls/invalid required fields. Trade-offs: declarative centralized validation; failing the load must be operationalized. *(data-engineering-patterns.md)*
- **Schema Compatibility Enforcer / Schema Migrator** - Intent: validate incoming schema against an expected/compatible schema and reject breaking changes, or evolve a sprawling schema into a cleaner domain-aligned one. When to use: upstreams altering depended-on fields; messages grown to dozens of dispersed fields. Trade-offs: protection against silent breakage (needs a registry/contract) vs. a clearer model at the cost of migration and dual-read/dual-write. *(data-engineering-patterns.md)*
- **Offline / Online Observer** - Intent: periodically profile dataset properties to catch drift the predefined rules miss, or check properties at runtime to catch regressions before publication. When to use: monitoring evolving upstreams without blocking vs. needing real-time detection. Trade-offs: broad visibility (detected after the fact) vs. non-propagation at the cost of inline computation. *(data-engineering-patterns.md)*
- **Flow Interruption Detector / Skew Detector** - Intent: detect "green but empty" runs and partial/half-empty datasets. When to use: streaming sync feeding many downstreams; jobs processing incomplete input without failing. Trade-offs: catches silent gaps/completeness regressions; needs expected-output and volume baselines. *(data-engineering-patterns.md)*
- **Lag Detector / SLA Misses Detector** - Intent: monitor consumer throughput vs. arrival rate, and alert when a job will miss or has missed its completion SLA. When to use: volume spikes risking slow delivery; critical deadline-bound downstreams. Trade-offs: proactive scaling/early warning; needs throughput/backlog instrumentation and SLA definitions. *(data-engineering-patterns.md)*
- **Dataset Tracker / Fine-Grained Tracker** - Intent: track table-level lineage, and column-level lineage answering which inputs feed which output columns. When to use: cross-team schema-change failures; wide denormalized tables with recurring provenance questions. Trade-offs: dependency visibility / precise impact analysis at the cost of lineage capture and storage. *(data-engineering-patterns.md)*

### Software engineering for data and stateful-system architecture (Nelson; Quaye)

*Source file: software-engineering-for-data.md.*

- **Notebook-to-script-to-package promotion** - Intent: graduate exploratory notebook code into reproducible scripts and installable packages as it proves reusable. When to use: code that will run again, be shared, or enter production. Trade-offs: up-front extract/structure/package effort repaid by reproducibility, testability, and reuse; skip for genuine one-offs. *(software-engineering-for-data.md)*
- **Arrange-Act-Assert unit testing** - Intent: pin behavior with small deterministic tests structured as setup, execution, and assertion. When to use: reused/modified code, pre-deployment, after a surprising error, before refactoring. Trade-offs: confidence and safe change vs. writing/maintaining tests; not worth it in pure exploration. *(software-engineering-for-data.md)*
- **Automated quality gate (pre-commit plus CI)** - Intent: run linting, formatting, type checks, and tests automatically before commit and in CI so standards hold across a team. When to use: any shared or production codebase. Trade-offs: initial setup complexity, then near-zero ongoing effort and far fewer team mistakes. *(software-engineering-for-data.md)*
- **Reproducible deployment via containers and environments** - Intent: deploy through staging then production using pinned virtual environments and Docker images. When to use: production deployment of data/ML code. Trade-offs: container/tooling learning curve for guaranteed environment parity. *(software-engineering-for-data.md)*
- **Event-Database Architecture (database-centric event sourcing for stateful systems)** - Intent: hold all state in a central database and drive behavior through Primary/Secondary Events whose definitions are Records, recording every event in an append-only history. When to use: stateful event-driven systems (games, simulations) needing designer-authorable behavior, multiplayer late-join sync, deterministic replay, and reproducible bug diagnosis. Trade-offs: full replay/reset, audit history, and design/code decoupling vs. routing all behavior through the database/event layer and maintaining Records and history. *(software-engineering-for-data.md)*
- **Events History / replay-and-reset correctness test** - Intent: append every Primary and Secondary Event chronologically and require resetting and replaying the world from any point without error as the conformance test. When to use: systems where determinism, recovery, and reproducibility are first-class. Trade-offs: enables sync, replay, and debugging; the history must never be reset except on world reset, and history length/content must be designed up front. *(software-engineering-for-data.md)*
- **Priority-weighted probabilistic event resolution** - Intent: resolve overlapping mutually-exclusive responses to the same event by selecting one with probability proportional to its priority. When to use: multiple features attach competing reactions to one trigger and all should be retained but only one fires at a time. Trade-offs: keeps conflicting features without deletion and tunes likelihood via priority; nondeterministic selection (mitigated for replay by recording the chosen event in the history). *(software-engineering-for-data.md)*

### Data observability and quality (Pinto and El Khammal)

*Source file: data-observability-and-quality.md. Framework, not a classic pattern set; entries below capture its reusable recipes.*

- **SLA / SLO / SLI for data** - Intent: encode quality as a vertical producer-consumer contract (SLA), engineer transversal dataset objectives (SLO) that satisfy all SLAs, and measure them with indicators (SLI). When to use: any producer-consumer data relationship needing trust. Trade-offs: aligns stakeholders and replaces ad hoc double-checking; requires negotiating contracts and instrumenting indicators. *(data-observability-and-quality.md)*
- **Contextual + synchronous + continuous-validation observability** - Intent: emit metrics from inside the running pipeline, scoped to the relevant columns/project, aligned with execution, and validated throughout the lifecycle. When to use: any pipeline where black-box monitoring detects issues too late. Trade-offs: near-zero detection latency and no error cascade vs. inline computation and instrumentation effort. *(data-observability-and-quality.md)*
- **Five observability pillars (schema, lineage, volume, distribution/metrics, freshness)** - Intent: instrument the observable surface from which SLIs and anomaly rules are built, including field-level lineage bound to each lineage run. When to use: making pipelines interpretable and enabling impact/root-cause analysis. Trade-offs: rich diagnosis and impact analysis vs. computing and storing metadata per run. *(data-observability-and-quality.md)*
- **Tiered anomaly detection (deterministic -> multi-indicator -> time-series)** - Intent: detect anomalies with single-metric rules, then combined-metric rules, then trend-plus-seasonality models (Holt-Winters, exponential smoothing, (S)ARIMA). When to use: graduating from immediate cheap checks to learned baselines as run history accumulates. Trade-offs: increasing power vs. needing more data points and modeling. *(data-observability-and-quality.md)*
- **Five-step data incident management** - Intent: detect, evaluate impact, find root cause, troubleshoot, and prevent recurrence, each supported by logs/metrics/traces. When to use: any data incident. Trade-offs: disciplined, lineage-driven resolution that drives down MTTD/MTTR vs. requiring observability infrastructure and impact-analysis rigor. *(data-observability-and-quality.md)*
- **Lineage-driven impact and root cause analysis** - Intent: use downstream lineage to enumerate affected stakeholders and upstream lineage to walk "why" to the source issue rather than treating symptoms. When to use: prioritizing and diagnosing incidents in multi-team pipelines. Trade-offs: fast, accurate scoping and source-fixing vs. depending on captured lineage and honest criticality assessment. *(data-observability-and-quality.md)*

### Cloud solutions architecture: Well-Architected pillars and design principles (Shrivastava, Srivastav & Kumar; Srivastav & Shrivastava)

*Source file: cloud-solutions-architecture.md. The six Well-Architected pillars and the cross-cutting cloud design principles. Pillars are quality-attribute lenses, each carrying its own design principles.*

- **Operational excellence (pillar)** - Intent: run and monitor systems to deliver business value and continuously improve, measured on agility, reliability, and performance. Design principles: organize teams around business outcomes; implement observability for actionable insights; safely automate where possible; make frequent, small, reversible changes; refine procedures frequently; anticipate failure; learn from all operational events; use managed services. *(cloud-solutions-architecture.md)*
- **Security (pillar)** - Intent: protect data, systems, and assets across all layers. Design principles: implement a strong identity foundation; maintain traceability; apply security at all levels (defense in depth); automate security best practices; protect data in transit and at rest; keep people away from data; prepare for security events. *(cloud-solutions-architecture.md)*
- **Reliability (pillar)** - Intent: recover from disruption, dynamically acquire resources, and mitigate misconfiguration and transient failures, minimizing single points of failure. Design principles: automatically recover from failure; test recovery procedures; scale horizontally to increase aggregate availability; stop guessing capacity; manage changes through automation. *(cloud-solutions-architecture.md)*
- **Performance efficiency (pillar)** - Intent: use computing resources efficiently and sustain efficiency as demand and technology change. Design principles: democratize advanced technologies; go global in minutes; use serverless architectures; experiment more often; consider mechanical sympathy. *(cloud-solutions-architecture.md)*
- **Cost optimization (pillar)** - Intent: avoid unnecessary cost and match spend to value, paying only for what is used. Design principles: implement cloud financial management; adopt a consumption model; measure overall efficiency; stop spending on undifferentiated heavy lifting; analyze and attribute expenditure. *(cloud-solutions-architecture.md)*
- **Sustainability (pillar)** - Intent: minimize the environmental impact of cloud workloads. Design principles: understand your impact; establish sustainability goals; maximize utilization; anticipate and adopt more efficient hardware/software; use managed services; reduce the downstream impact of workloads. *(cloud-solutions-architecture.md)*
- **Design for failure** - Intent: assume every component can fail and build redundancy and self-healing so "nothing will fail." When to use: any system with availability requirements. Trade-offs: resilience and uptime vs. the cost of redundancy; match the level to the application's actual criticality. *(cloud-solutions-architecture.md)*
- **Loose coupling** - Intent: have components interact through well-defined interfaces (load balancer for synchronous, queue for asynchronous) so failures and scaling do not cascade. When to use: any multi-component system. Trade-offs: independent scaling and fault isolation vs. added latency, infrastructure, and eventual consistency on async paths. *(cloud-solutions-architecture.md)*
- **Elasticity** - Intent: grow and shrink capacity automatically to match demand rather than provisioning statically. When to use: variable workloads on pay-as-you-go infrastructure. Trade-offs: cost efficiency and responsiveness vs. autoscaling configuration and brief latency during scale events. *(cloud-solutions-architecture.md)*
- **Immutable infrastructure ("cattle, not pets")** - Intent: replace servers from a golden image rather than patching them in place, requiring stateless design and infrastructure as code. When to use: cloud environments needing consistency and fast recovery. Trade-offs: reproducibility and drift elimination vs. image-build pipeline and stateless redesign. *(cloud-solutions-architecture.md)*
- **The 7 Rs migration model** - Intent: decide per application how to move to the cloud: retire, retain, relocate, rehost, replatform, repurchase, refactor. When to use: portfolio-level cloud migration planning. Trade-offs: rehost/relocate are fast and cheap with low optimization; refactor maximizes cloud-native value at high time and cost; choose by business driver (cost/speed vs. agility/innovation). *(cloud-solutions-architecture.md)*

### Cloud-native architecture & the twelve-factor app (Raj et al.; FreeWheel; Deshmukh et al.)

*Source file: cloud-native-architecture.md.*

- **Twelve-Factor App** - Intent: a blueprint of 12 principles for portable, cloud-friendly apps: (1) codebase, (2) dependencies, (3) config, (4) backing services, (5) build/release/run, (6) processes (stateless), (7) port binding, (8) concurrency (scale out via process model), (9) disposability, (10) dev/prod parity, (11) logs as event streams, (12) admin processes as one-offs. When to use: any application optimized for modern cloud deployment and horizontal scaling. Trade-offs: discipline and statelessness in exchange for easy deploy/scale/evolve. *(cloud-native-architecture.md)*
- **Beyond twelve factors (API-first, telemetry, auth)** - Intent: three modern additions: front every service with a well-designed API behind a gateway; design in telemetry collection; use cloud IAM/RBAC for authn/authz. When to use: production CNAs on third-party clouds with limited native visibility. Trade-offs: stronger integration/observability/security for added design effort. *(cloud-native-architecture.md)*
- **Cattle-not-pets / immutable infrastructure** - Intent: treat compute as disposable instances built from immutable images and replaced (not repaired) on failure or update. When to use: containerized cloud-native estates. Trade-offs: predictable rollouts/rollbacks and self-healing vs. requiring full automation and externalized state. *(cloud-native-architecture.md)*
- **Service mesh (sidecar)** - Intent: move network functions (resilient routing, retries, timeouts, circuit breaking, mTLS, telemetry) out of business logic into a sidecar proxy configured by a control plane. When to use: many containerized services needing consistent, transparent east-west reliability/security/observability that Kubernetes lacks natively. Trade-offs: uniform zero-code resilience vs. operational complexity and per-hop latency (Istio, Linkerd). *(cloud-native-architecture.md)*
- **API gateway (north-south edge)** - Intent: single entry point routing client requests to services and centralizing edge cross-cutting (auth, TLS, rate limiting, aggregation). When to use: front door for a service estate. Trade-offs: simpler clients/central policy vs. bottleneck/over-centralization risk. *(cloud-native-architecture.md)*
- **Infrastructure as Code / as Data (IaC/IaD)** - Intent: provision and manage infrastructure declaratively (JSON/YAML manifests) through APIs rather than manually. When to use: any environment needing repeatability, parity, and auditability. Trade-offs: version-controlled, drift-resistant infra vs. up-front tooling. *(cloud-native-architecture.md)*
- **GitOps (declarative reconciliation)** - Intent: make Git the single source of truth for app and infra state, with controllers reconciling the live cluster to the repo. When to use: Kubernetes estates wanting auditable, revertible delivery. Trade-offs: strong traceability/rollback vs. everything expressed declaratively. *(cloud-native-architecture.md)*
- **Chaos engineering** - Intent: inject simulated failures to verify resilience and self-healing before real incidents. When to use: mature cloud-native systems pursuing proven fault tolerance. Trade-offs: strongest resilience evidence vs. needing blast-radius control. *(cloud-native-architecture.md)*

### Serverless & FaaS patterns (Gilbert et al.; FreeWheel; Deshmukh et al.)

*Source file: serverless-architecture.md.*

- **Serverless-first / disposable architecture** - Intent: default to a managed serverless option per service to learn fast and cheaply, switching to self-managed only when metrics justify it (defer commitment, create knowledge). When to use: new features, spiky workloads, autonomous teams. Trade-offs: low up-front investment and self-service vs. potential cost at sustained high throughput. *(serverless-architecture.md)*
- **Autonomous service** - Intent: a self-contained service owning its own functions and data store so it survives others' failures. When to use: default unit of an event-first serverless system. Trade-offs: independent deployability/fault isolation vs. data duplication and eventual consistency. *(serverless-architecture.md)*
- **Backend for Frontend (BFF) + variations** - Intent: a service tailored to one actor/frontend, optimized via CQRS; variations: CRUD, List-of-values, Task, Search, Action, Dashboard/Reporting/Archive across the data life cycle. When to use: divergent client experiences. Trade-offs: per-actor optimization and read performance vs. more services and duplicated views. *(serverless-architecture.md)*
- **External Service Gateway (ESG) / anti-corruption layer** - Intent: macro-level ports-and-adapters boundary bridging domain events to/from external systems (third-party, legacy, sister subsystems, cross-cloud) and translating their models. When to use: integrating any system you do not control. Trade-offs: isolation and LSP substitution vs. an adapter per external system. *(serverless-architecture.md)*
- **Control Service (mediator/orchestrator)** - Intent: consolidate intricate control-flow and policy logic in a service between boundary services (orchestration, sagas, CEP, ML control). When to use: processes too complex for choreography. Trade-offs: traceable control vs. a potential coordination hotspot. *(serverless-architecture.md)*
- **Event hub / event-first topology** - Intent: connect autonomous services and subsystems through a central event hub in a fractal topology, evolving the system by adding consumers. When to use: building ever-evolving event-driven systems. Trade-offs: loose coupling and flexibility vs. async reasoning and eventual consistency. *(serverless-architecture.md)*
- **Bulkhead (inbound/outbound/account)** - Intent: use serverless resources (event hub outbound, per-service store inbound, separate cloud accounts per subsystem) to contain blast radius and buffer changes. When to use: every architectural boundary. Trade-offs: strong fault/security isolation vs. duplicated cross-cutting capabilities. *(serverless-architecture.md)*
- **System-wide event sourcing (stream-first / database-first via CDC)** - Intent: persist state as an append-only event stream that is the record of truth and supports replay; stream-first for generated data, database-first (CDC) for normalized entry. When to use: audit, replay/repair, seeding services, high write throughput. Trade-offs: powerful history/decoupling vs. projections and schema versioning. *(serverless-architecture.md)*
- **System-wide CQRS** - Intent: separate write model from rebuildable, lean read projections synchronized via the event hub. When to use: high read-to-write ratios, many views, polyglot storage. Trade-offs: independent scaling/performance vs. eventual consistency and projection maintenance. *(serverless-architecture.md)*
- **Strangler (event-first migration)** - Intent: modernize legacy non-invasively by wrapping it in an ESG that bi-directionally syncs events, building new features around it until it can be switched off with no cutover. When to use: every legacy modernization that must keep running. Trade-offs: continuous value and controlled risk vs. running old and new in parallel. *(serverless-architecture.md)*
- **Deterministic identifiers for idempotence** - Intent: client-generate the identifier (V4 UUID for entities, V1 for time-sortable events, or content-derived key) and use idempotent PUT so retries/replays affect one record. When to use: any at-least-once path. Trade-offs: safe retries vs. the client needing to remember the id. *(serverless-architecture.md)*
- **TTL for lean data** - Intent: set a per-record TTL so the database auto-expires data past its useful life, keeping tables lean. When to use: data with bounded useful life. Trade-offs: lower cost/easier evolution vs. not removing data so aggressively it breaks idempotence/order tolerance. *(serverless-architecture.md)*
- **Cache-control + CDN** - Intent: set cache-control headers and serve via a CDN so browsers/edge reuse responses. When to use: high-traffic read resources. Trade-offs: large cost/latency reduction on cache hits vs. staleness within max-age. *(serverless-architecture.md)*
- **Cold-start minimization** - Intent: reduce FaaS init latency via lightweight runtimes (JavaScript), small tree-shaken bundles, avoiding heavyweight DI/ORM, and raising memory for faster download. When to use: latency-sensitive FaaS. Trade-offs: faster cold starts vs. constraints on runtime/framework choices. *(serverless-architecture.md)*
- **Function memory/cost tuning (worth-based/FinOps)** - Intent: trade memory (which also raises CPU/network) against execution time toward lowest total gigabyte-second cost; tune only the expensive functions from production metrics. When to use: optimizing serverless spend. Trade-offs: cost/performance gains vs. tuning effort until it costs more than it saves. *(serverless-architecture.md)*
- **Choreography vs. orchestration (control flow)** - Intent: start with choreography (no coordinator, react to events) for data sync/simple flows; evolve to control-service orchestration for intricate processes. When to use: per-flow complexity. Trade-offs: decoupling/easy extension vs. hard-to-trace logic at scale (mitigated by control services). *(serverless-architecture.md)*

### Site Reliability Engineering practices (Huete Beloki)

*Source file: site-reliability-engineering.md.*

- **Error-budget gating** - Intent: use the remaining error budget (`1 − SLO`) as the objective control on change velocity - ship freely while budget remains, freeze risky changes when it is exhausted. When to use: any team balancing feature delivery against a reliability SLO. Trade-offs: aligns dev and ops incentives objectively vs. requiring trustworthy monitoring and an agreed SLO. *(site-reliability-engineering.md)*
- **Multi-window burn-rate alerting** - Intent: alert on how fast the error budget is burning, evaluated over both a long window (e.g., 1 hour) and a short window (e.g., 5 minutes), to catch fast burns early while suppressing noise. When to use: SLO-based alerting in production. Trade-offs: timely, low-noise alerts vs. more configuration than simple threshold alerts. *(site-reliability-engineering.md)*
- **Toil reduction through automation** - Intent: detect recurring incidents with alert rules and auto-remediate with runbooks (restart, scale, reconfigure), notifying a human only to confirm. When to use: manual, repetitive, automatable, reactive issues. Trade-offs: frees engineering time and improves morale/retention vs. up-front automation investment (Azure Monitor alerts + Azure Automation runbooks). *(site-reliability-engineering.md)*
- **Sustainable on-call rotation** - Intent: cover critical services without harming engineers via follow-the-sun shifts, primary/secondary escalation, "everyone takes the pager" (developers included), flexible schedules set weeks ahead, and a cap on ops load. When to use: any team owning production services. Trade-offs: reliable coverage and shared ownership vs. scheduling effort (Google caps ops at 50% of SRE time). *(site-reliability-engineering.md)*
- **Defined incident roles (ICS)** - Intent: bring order to incidents with an incident commander, first/second responders, scribe, communications lead, and technical leads/SMEs, following the Incident Command System (clear chain of command, roles, documentation, fast resolution). When to use: any non-trivial incident. Trade-offs: clarity and parallelism vs. requiring trained, rehearsed roles. *(site-reliability-engineering.md)*
- **Blameless postmortem** - Intent: treat every incident as a learning opportunity; build a documented timeline and focus on the system, never the person, assuming good intentions given what was known. When to use: after every significant incident. Trade-offs: surfaces systemic causes and builds psychological safety vs. requiring a genuine cultural shift from a generative (Westrum) culture. *(site-reliability-engineering.md)*
- **Chaos engineering / reliability testing** - Intent: inject failures and load (Azure Chaos Studio, Azure Load Testing) to validate resilience under real conditions before incidents occur, shifting effort from reactive to proactive. When to use: mature systems pursuing proven fault tolerance. Trade-offs: strongest resilience evidence vs. needing controlled blast radius. *(site-reliability-engineering.md)*
- **Dickerson's hierarchy of reliability** - Intent: prioritize SRE work bottom-up - Monitoring → Incident Response → Blameless Postmortems → Test/Release → Capacity Planning → Development → UX - since each layer depends on the ones below. When to use: deciding where to invest reliability effort. Trade-offs: disciplined sequencing vs. resisting the urge to jump to advanced work before fundamentals are solid. *(site-reliability-engineering.md)*

## Domain 09 - Cloud Infrastructure and Platform

### Containers & Docker (Raj et al.; Schenker)

*Source file: containers-and-docker.md.*

- **Multi-stage build** - Intent: produce a tiny, secure final image by separating build stages (with SDKs/compilers) from a minimal runtime stage that copies only the artifacts (`COPY --from`). When to use: any compiled or build-heavy app for production. Trade-offs: dramatically smaller images, smaller attack surface, faster pulls/startup vs. a slightly more involved Dockerfile. *(containers-and-docker.md)*
- **Layer-cache ordering (immutable-layer leverage)** - Intent: order Dockerfile instructions least-to-most volatile so expensive steps (dependency install) stay cached. When to use: frequently rebuilt images. Trade-offs: fast builds vs. discipline in ordering and splitting dependency manifests from source. *(containers-and-docker.md)*
- **Minimal-image hygiene** - Intent: keep images small via `.dockerignore`, no unnecessary packages, and multi-stage builds. When to use: every production image. Trade-offs: smaller attack surface and footprint vs. occasional effort to slim the base. *(containers-and-docker.md)*
- **Non-root container** - Intent: drop root inside the container (`USER` / `--user`) so a compromise cannot trivially gain host-root. When to use: all production containers. Trade-offs: much smaller breakout blast radius vs. adjusting file permissions. *(containers-and-docker.md)*
- **Immutable infrastructure** - Intent: never patch a running container/server in place; build a new immutable image and replace instances each update. When to use: containerized estates. Trade-offs: repeatability, easy rollback, tamper resistance vs. requiring full automation and externalized state. *(containers-and-docker.md)*
- **Container-as-a-service image** - Intent: package a long-running service with `ENTRYPOINT` launching the daemon in the foreground and `EXPOSE` documenting its port. When to use: shipping any server. Trade-offs: standardized deployment vs. the main process must run in foreground (PID 1). *(containers-and-docker.md)*
- **Registry-driven CI/CD trigger** - Intent: use registry webhook notifications on image push to trigger staging deploys or notify downstream. When to use: container delivery pipelines. Trade-offs: clean event-driven delivery vs. coupling to registry events. *(containers-and-docker.md)*
- **Named volume / data-volume container** - Intent: persist stateful data in Docker-managed named volumes (or a dedicated data-volume container) rather than the ephemeral writable layer. When to use: any stateful service. Trade-offs: durable, portable, shareable storage vs. needing backup/restore and storage monitoring. *(containers-and-docker.md)*

### Kubernetes & orchestration (Kubernetes Enterprise Guide)

*Source file: kubernetes-and-orchestration.md.*

- **Declarative reconciliation (control loop)** - Intent: express desired state and let a controller continuously converge actual state toward it. When to use: everything in Kubernetes; basis of self-healing. Trade-offs: resilient/automatable vs. eventually-consistent, async reasoning. *(kubernetes-and-orchestration.md)*
- **Deployment over bare Pod** - Intent: manage stateless workloads via Deployment (→ ReplicaSet → Pods) for rolling upgrades, rollbacks, self-healing, and scaling. When to use: any stateless app by default. Trade-offs: lifecycle features vs. one more abstraction; bare pods lose them all. *(kubernetes-and-orchestration.md)*
- **StatefulSet for stable identity and storage** - Intent: run stateful apps needing stable names, ordered lifecycle, and per-pod persistent volumes (VolumeClaimTemplate). When to use: databases, clustered stores. Trade-offs: stable identity/storage vs. slower ordered operations and more storage management. *(kubernetes-and-orchestration.md)*
- **DaemonSet for per-node agents** - Intent: guarantee one pod per node (and on new nodes) for node-level concerns (logging, monitoring, networking). When to use: cluster-wide agents. Trade-offs: automatic coverage vs. resource use on every node. *(kubernetes-and-orchestration.md)*
- **Service + label selector (stable endpoint)** - Intent: front a changing set of pods with a durable IP/name, auto-maintaining endpoints by label match. When to use: any reachable workload. Trade-offs: decouples callers from ephemeral pod IPs vs. needing consistent labels. *(kubernetes-and-orchestration.md)*
- **Ingress (Layer 7 edge routing)** - Intent: route external HTTP/HTTPS to services by host/path/header via an Ingress controller. When to use: exposing web apps/APIs. Trade-offs: central TLS/routing vs. needing a controller and being limited to HTTP/S (use L4 LoadBalancer otherwise). *(kubernetes-and-orchestration.md)*
- **Multi-level autoscaling (HPA / VPA / Cluster Autoscaler)** - Intent: scale pods out/in (HPA), right-size pod resources (VPA), and grow/shrink nodes (Cluster Autoscaler). When to use: variable load. Trade-offs: automated elasticity/cost control vs. tuning thresholds and avoiding HPA/VPA conflicts on the same metric. *(kubernetes-and-orchestration.md)*
- **Operator pattern (CRD + custom controller)** - Intent: encode operational knowledge as software by defining a CRD and a controller that reconciles instances. When to use: automating complex stateful systems or provisioning. Trade-offs: powerful declarative ops automation vs. building/maintaining a controller and cluster-wide CRD versioning constraints. *(kubernetes-and-orchestration.md)*
- **GitOps (Git as source of truth)** - Intent: store cluster/app config in Git and reconcile the live cluster to the repo. When to use: auditable, revertible delivery. Trade-offs: traceability/rollback vs. the firm rule that secrets must never live in Git. *(kubernetes-and-orchestration.md)*
- **Virtual cluster multi-tenancy (vCluster)** - Intent: give each tenant a nested virtual control plane in an unprivileged host namespace, with workloads still bound by host quotas/policies and shared Ingress. When to use: enterprise multi-tenancy needing tenant cluster-admin, isolated CRD versions, shared infra. Trade-offs: tenant autonomy + host security vs. operating vClusters and a sync engine. *(kubernetes-and-orchestration.md)*

### Kubernetes & container security (Lapaz)

*Source file: kubernetes-and-container-security.md.*

- **Threat modeling (proactive risk identification)** - Intent: analyze the system at design time (assets, controls, actors, attack surface, threats, mitigations) using STRIDE/PASTA/VAST and MITRE ATT&CK. When to use: every new app and cluster design. Trade-offs: early cheap risk discovery vs. needing to understand component interactions and bound scope. *(kubernetes-and-container-security.md)*
- **Principle of least privilege** - Intent: grant every subject and workload the minimum permissions, capabilities, and network/host access needed. When to use: RBAC, capabilities, network policies, host access everywhere. Trade-offs: limits compromise blast radius vs. careful role/scope design. *(kubernetes-and-container-security.md)*
- **RBAC over ABAC/AlwaysAllow** - Intent: use role-based access control (Roles/ClusterRoles + bindings) as the authorization mode for scalable least-privilege access. When to use: all production clusters. Trade-offs: easy, auditable updates vs. deliberate role design; prefer namespaced Roles. *(kubernetes-and-container-security.md)*
- **Admission-control policy enforcement** - Intent: intercept API requests to validate (reject) and mutate (inject defaults) before objects are created, via built-in controllers and validating/mutating webhooks (OPA/Gatekeeper, CEL). When to use: org-wide policy (no privileged pods, required labels, image provenance). Trade-offs: cluster-wide enforcement vs. moving parts and ordering. *(kubernetes-and-container-security.md)*
- **Pod Security Standards + SecurityContext hardening** - Intent: constrain pods to Baseline/Restricted and harden via non-root, dropped capabilities, no privilege escalation, read-only root FS, seccomp/AppArmor. When to use: all workloads. Trade-offs: smaller escape/escalation surface vs. breaking workloads that assume root. *(kubernetes-and-container-security.md)*
- **NetworkPolicy least-privilege segmentation** - Intent: default-deny and allow only required pod-to-pod and egress traffic to limit lateral movement. When to use: every production and especially multi-tenant cluster. Trade-offs: contains breaches vs. mapping flows and needing a CNI that enforces them. *(kubernetes-and-container-security.md)*
- **External secrets management** - Intent: keep sensitive data out of plaintext etcd and out of Git by externalizing to Vault and injecting at runtime, with encryption-at-rest baseline. When to use: compliance, GitOps. Trade-offs: stronger confidentiality/audit vs. integration and operational dependency. *(kubernetes-and-container-security.md)*
- **Shift-left image security (scan + SBOM + sign)** - Intent: scan images (Trivy/Grype/Clair), generate an SBOM (Syft), and sign/validate images, integrated into CI/CD. When to use: every image build pipeline. Trade-offs: early detection and fast CVE response vs. pipeline complexity and signing-key management. *(kubernetes-and-container-security.md)*
- **Runtime detection and response** - Intent: detect anomalous behavior at runtime (Falco on syscalls/audit events; Tetragon via eBPF) and alert/block, feeding central logging. When to use: production clusters needing escape/anomaly detection. Trade-offs: real-time visibility/enforcement vs. rule tuning and agent overhead. *(kubernetes-and-container-security.md)*
- **Defense in depth + high availability** - Intent: layer multiple controls so a single breach is contained, and keep control plane and workloads highly available (odd-numbered etcd/control-plane, replicas, load balancing). When to use: all serious clusters. Trade-offs: resilience and containment vs. cost and operational complexity. *(kubernetes-and-container-security.md)*

## Domain 10 - AI, GenAI, and Agentic Systems

### Agent architecture & multi-agent (Bin Xu; Fajardo; Stratis; O'Mahony)

*Source files: multi-agent-systems.md, agent-platforms.md.*

- **Planner-executor separation** - Intent: separate plan generation from execution so each runs under different permissions and validation. When to use: tasks with high-impact or irreversible steps needing human approval. Trade-offs: better controllability and smaller failure blast radius vs. coordination overhead and latency. *(multi-agent-systems.md)*
- **Role-specialized multi-agent team (planner / executor / reviewer)** - Intent: decompose a task across role-specialized agents for cross-checking and specialization. When to use: complex tasks decomposable into sub-tasks where focused agents beat a generalist. Trade-offs: specialization and evidence-based cross-checking vs. coordination cost and inconsistency risk; needs distinct tool access and explicit handoff artifacts. *(multi-agent-systems.md)*
- **Bounded-capability roles with permission budgets** - Intent: give each agent role an explicit tool-permission budget so collaboration scales without expanding any one agent's blast radius. When to use: production multi-agent graphs with side-effecting tools. Trade-offs: limits damage from a compromised/erring agent vs. per-role permission design. *(multi-agent-systems.md)*
- **Trace-first data flywheel** - Intent: log full trajectories (prompts, tool calls, outputs, outcomes) and mine failures for targeted improvements. When to use: production agents that must improve continuously. Trade-offs: continuous refinement and first-class eval suites vs. logging/storage and privacy considerations. *(multi-agent-systems.md)*
- **Adaptive fast-path / verified-path execution** - Intent: route routine cases through a fast path and high-risk actions through verified paths with budgets and permission gates. When to use: tool-rich deployments mixing low- and high-impact actions. Trade-offs: balances latency vs. safety; adds orchestrator branching complexity. *(multi-agent-systems.md)*
- **Evidence-based disagreement resolution** - Intent: resolve multi-agent disagreement via tool-output citations, trace-anchored critiques, and structured voting rather than free-form debate. When to use: multi-agent debate/review prone to correlated errors. Trade-offs: reduces correlated failures vs. needing a calibrated aggregation mechanism. *(multi-agent-systems.md)*
- **Graph-based agent (bounded autonomy state machine)** - Intent: limit agent autonomy to state transitions within a predefined graph for reliable, resilient execution. When to use: structured tasks (deep research) where raw autonomy under/over-runs. Trade-offs: reliability and predictability vs. less flexibility than a raw agent. *(agent-platforms.md, multi-agent-systems.md)*

### MCP and A2A protocols (Sekar; Stratis; Fajardo; ACN white paper)

*Source file: mcp-and-agent-protocols.md.*

- **Host-Client-Server separation of concerns** - Intent: split an AI integration into a governing Host, a translating Client, and a specialist Server. When to use: any MCP integration. Trade-offs: modular, secure, scalable, reusable capabilities vs. three-role overhead and per-server client instances. *(mcp-and-agent-protocols.md)*
- **Locus-of-control primitive split (Tools / Resources / Prompts)** - Intent: classify each capability by who controls it (model / application / user) to enforce security boundaries. When to use: designing any MCP server. Trade-offs: keeps the AI from inappropriate data access vs. discipline to keep side effects in Tools and read-only context in Resources. *(mcp-and-agent-protocols.md)*
- **Human-in-the-loop approval gate** - Intent: have the Host request explicit user approval before powerful/irreversible tool calls (and before granting a server sampling access). When to use: tools that delete, send, pay, deploy, or modify state. Trade-offs: makes agentic systems safe for real use vs. added friction and latency. *(mcp-and-agent-protocols.md)*
- **Dynamic capability discovery** - Intent: let a Client query a Server's tools/resources/prompts at runtime instead of hardcoding them. When to use: adaptable systems picking up new tools on the fly. Trade-offs: flexible evolving toolchains vs. dependence on high-quality tool descriptions. *(mcp-and-agent-protocols.md)*
- **Streamable HTTP session with session-id** - Intent: maintain a stateful, resumable client-server session over HTTP via an mcp-session-id header. When to use: remote/cloud servers serving many concurrent clients. Trade-offs: long-lived bidirectional sessions and reconnection vs. more complexity than stateless REST. *(mcp-and-agent-protocols.md)*
- **Client-provided sampling (server-initiated LLM calls)** - Intent: let a Server request completions from the Client's LLM for nested agentic behavior. When to use: servers needing reasoning or sub-tool selection. Trade-offs: powerful composability vs. exposing the model the client pays for, requiring a HITL guard. *(mcp-and-agent-protocols.md)*
- **MCP + A2A layering** - Intent: use A2A for agent-to-agent delegation and MCP for each agent's tool access. When to use: multi-agent systems combining orchestration with specialized tool use. Trade-offs: clean horizontal/vertical separation vs. running both protocol stacks and security models. *(mcp-and-agent-protocols.md)*
- **Federated capability registry** - Intent: pair a central public registry with private enterprise registries of vetted servers. When to use: organizations adopting MCP at scale. Trade-offs: openness plus internal control vs. maintaining the internal catalogue and vetting. *(mcp-and-agent-protocols.md)*
- **Digital-identity-bound agent (ACN)** - Intent: bind each agent a unique network identity derived from its owning user/tenant for auth, supervision, and tracing. When to use: networks of autonomous agents needing accountability. Trade-offs: trusted, traceable communication and quick isolation vs. network-wide identity/authorization infrastructure. *(mcp-and-agent-protocols.md)*
- **Task-level Logical Communication Domain (ACN)** - Intent: dynamically form an isolated, mesh-connected domain of agents for a task and release it on completion. When to use: ad-hoc multi-agent collaboration, possibly cross-user, with strict isolation. Trade-offs: efficient on-demand collaboration with default isolation vs. dependence on operator-level networking and policy. *(mcp-and-agent-protocols.md)*

### Anti-patterns to avoid (O'Mahony; Sekar)

*Source files: agent-platforms.md, mcp-and-agent-protocols.md.*

- **The God agent (avoid)** - A single agent meant to solve an entire complex domain chooses correct actions poorly; prefer smaller specialized subsystems. *(agent-platforms.md)*
- **AI for AI's sake (avoid)** - Using prompts where deterministic code (an `if` statement) suffices; if deterministic software solves it, use that. *(agent-platforms.md)*
- **Separate special runtime for AI apps (avoid)** - AI apps behave like services calling an LLM; build on the existing IDP instead of a duplicate runtime. *(agent-platforms.md)*
- **The lethal trifecta (avoid)** - Untrusted-content exposure + sensitive-data access + exfiltration capability together make a breach inevitable; break at least one leg. *(mcp-and-agent-protocols.md)*
- **Toxic flow / tool poisoning (avoid)** - Indirect prompt injection or malicious tool descriptions chain legitimate calls into a breach; use instructional fencing, description sanitization, and runtime Toxic Flow Analysis. *(mcp-and-agent-protocols.md)*

### Agentic design patterns - agent behavior (Gulli 2025; Tiwary 2025; Jewell & Li 2025)

*Source file: agentic-design-patterns.md.*

- **Prompt Chaining (Pipeline)** - Intent: decompose a complex task into a sequence of sub-tasks where each output feeds the next. When to use: task too complex for one prompt, multiple stages, tool interaction between steps, multi-step reasoning with state. Trade-offs: modularity and per-step accuracy vs. added latency and dependence on structured intermediate output. *(agentic-design-patterns.md)*
- **Routing** - Intent: analyze a request and dynamically direct control to the best tool/function/sub-agent (via LLM, rules, or embeddings). When to use: triage/classify input across distinct workflows. Trade-offs: adaptive flow vs. misclassification risk and an added decision point to evaluate. *(agentic-design-patterns.md)*
- **Parallelization** - Intent: run independent sub-tasks concurrently then aggregate. When to use: independent lookups/computations/service calls with no inter-dependency. Trade-offs: large latency wins vs. concurrency complexity, higher cost, and a sequential synthesis step. *(agentic-design-patterns.md)*
- **Reflection (Producer-Critic / Self-Correction)** - Intent: an agent evaluates output against criteria and iteratively refines; a separate critic avoids self-review bias. When to use: quality/accuracy matters over speed (code, drafting, fact-checking). Trade-offs: better quality vs. extra calls/latency; needs a stopping condition. *(agentic-design-patterns.md)*
- **Tool Use (Function Calling)** - Intent: describe external functions so the LLM emits structured calls an orchestrator executes. When to use: agent must act on real-time/private data, compute, code, or trigger actions. Trade-offs: enables action vs. attack/failure surface, schema needs, wrong-tool/hallucinated-argument risk. *(agentic-design-patterns.md)*
- **Planning** - Intent: generate an ordered plan of sub-goals before executing. When to use: requests needing interdependent steps in logical order. Trade-offs: strategic execution vs. wrong/over-engineered plans and need for re-planning. *(agentic-design-patterns.md)*
- **Multi-Agent Collaboration** - Intent: decompose a problem across specialized cooperating agents (sequential/parallel/hierarchical). When to use: too complex for one agent; benefits from diverse expertise or parallelism. Trade-offs: specialization synergy vs. coordination overhead and harder debugging. *(agentic-design-patterns.md)*
- **Memory Management** - Intent: dual short-term (context window) + long-term (vector store) memory. When to use: agents needing conversational context, multi-step progress, personalization, or learning. Trade-offs: coherence/personalization vs. infrastructure and irrelevant-retrieval risk. *(agentic-design-patterns.md)*
- **Learning and Adaptation** - Intent: refine knowledge/behavior from new data via RL, self-modification, or evolutionary search. When to use: dynamic/evolving environments needing continuous improvement. Trade-offs: autonomy vs. complexity, drift, and need for eval guardrails. *(agentic-design-patterns.md)*
- **Model Context Protocol (MCP)** - Intent: universal client-server interface to discover and invoke external tools/data/prompts. When to use: scalable, evolving, multi-tool enterprise systems needing dynamic discovery. Trade-offs: reusable interoperable ecosystem vs. protocol/server overhead; overkill for fixed toolsets. *(agentic-design-patterns.md; agentic-architecture-patterns.md)*
- **Goal Setting and Monitoring** - Intent: explicit measurable objectives plus progress monitoring and a corrective feedback loop. When to use: autonomous multi-step tasks needing reliable goal achievement. Trade-offs: proactive self-assessment vs. metric-design effort and monitoring infrastructure. *(agentic-design-patterns.md)*
- **Exception Handling and Recovery** - Intent: detect and recover from tool/API/data failures via retries, fallbacks, rollback, self-correction, or escalation. When to use: any real-world deployment. Trade-offs: robustness vs. added code paths and naive-retry cost amplification. *(agentic-design-patterns.md)*
- **Human-in-the-Loop (HITL)** - Intent: integrate human oversight, intervention, feedback, and escalation. When to use: high-stakes/ethical domains where full autonomy is unwise. Trade-offs: accuracy and accountability vs. poor scalability, operator-expertise dependence, privacy concerns. *(agentic-design-patterns.md)*
- **Knowledge Retrieval (RAG)** - Intent: semantic-search external knowledge and augment the prompt before generating, grounded with citations. When to use: answers needing currency, facts, verifiability, or private corpora. Trade-offs: less hallucination vs. retrieval-pipeline complexity and "doubly stochastic" noise. *(agentic-design-patterns.md)*
- **Inter-Agent Communication (A2A)** - Intent: open HTTP protocol for agents to discover (Agent Card), delegate structured tasks, and share info across frameworks. When to use: cross-framework/cross-org agent collaboration. Trade-offs: modular scalable ecosystem vs. protocol/discovery/network overhead. *(agentic-design-patterns.md; agentic-architecture-patterns.md)*
- **Resource-Aware Optimization** - Intent: a router classifies request complexity and dispatches to a cheap or powerful model, balancing quality vs. cost. When to use: strict budgets, latency-sensitive or edge apps. Trade-offs: cost efficiency vs. routing machinery and weak-model-on-hard-task risk. *(agentic-design-patterns.md)*
- **Reasoning Techniques (CoT, ToT, Self-Correction, ReAct)** - Intent: make problem-solving explicit and structured, interleaving reasoning and tool actions. When to use: problems too complex for a single-pass answer. Trade-offs: robustness/transparency vs. token cost and verbose/erroneous reasoning. *(agentic-design-patterns.md)*
- **Guardrails / Safety** - Intent: multi-layered defense (input validation, output filtering, behavioral/tool constraints, HITL) against harmful or adversarial behavior. When to use: any user-, system-, or reputation-affecting output. Trade-offs: trust and compliance vs. latency and false-positive blocking. *(agentic-design-patterns.md)*
- **Evaluation and Monitoring** - Intent: assess accuracy, latency, token use, trajectory, and quality (LLM-as-judge) with feedback loops and drift detection. When to use: production, version comparison, regulated domains, drift-prone systems. Trade-offs: foundational reliability vs. costly eval sets and flawed heuristics. *(agentic-design-patterns.md)*
- **Prioritization** - Intent: rank competing tasks/goals by urgency, importance, dependencies, and cost. When to use: autonomous management of conflicting tasks under resource constraints. Trade-offs: purposeful resource-aware behavior vs. mis-weighted criteria neglecting important work. *(agentic-design-patterns.md)*
- **Exploration and Discovery** - Intent: actively seek new information and "unknown unknowns," often multi-agent emulating the scientific method. When to use: open-ended undefined solution spaces (research, market analysis, creative). Trade-offs: novel knowledge vs. expense, unpredictability, hard evaluation. *(agentic-design-patterns.md)*
- **Orchestrator-worker / Evaluator-optimizer (workflow framings)** - Intent: an orchestrator decomposes an unknown task to workers and combines results; a generator is paired with an independent evaluator until accepted. When to use: dynamic decomposition; runtime reflection. Trade-offs: reliability and quality vs. coordination/extra-call overhead. *(agentic-design-patterns.md)*

### Agentic architecture patterns - topologies, coordination, reliability, production (Arsanjani & Bustos 2026; Jewell & Li 2025)

*Source file: agentic-architecture-patterns.md.*

- **Agent Router (intent-based routing)** - Intent: decouple intent from executor via semantic intent extraction + graph-constrained routing over a capability graph. When to use: many specialized agents with ambiguous NL input. Trade-offs: scalability and whitelist safety vs. routing layer and extraction accuracy. *(agentic-architecture-patterns.md)*
- **Supervisor Architecture (centralized orchestration)** - Intent: a central orchestrator decomposes goals and sequences specialized workers top-down. When to use: structured, auditable, regulated processes; default for most enterprise multi-agent systems. Trade-offs: predictable/governable vs. bottleneck and single point of failure; keep it a pure coordinator and checkpoint state. *(agentic-architecture-patterns.md)*
- **Swarm Architecture (decentralized emergent)** - Intent: peer-to-peer agents self-select tasks from a shared board; workflow emerges from local interactions. When to use: dynamic/creative/high-resilience problems with no acceptable single point of failure. Trade-offs: resilience and horizontal scale vs. hard-to-debug/govern emergent behavior. *(agentic-architecture-patterns.md)*
- **Blackboard Knowledge Hub** - Intent: central typed/versioned repository where expert agents post hypotheses and a controller arbitrates convergence. When to use: ill-defined problems with many weak experts and unpredictable contribution order. Trade-offs: flexibility and auditable chain-of-thought vs. latency, controller bottleneck, need for a forgetting mechanism. *(agentic-architecture-patterns.md)*
- **Contract-Net Marketplace (mediator + bids)** - Intent: solicitor broadcasts a task; agents bid (cost/ETA/confidence); highest-utility bidder wins at runtime. When to use: large dynamic heterogeneous agent pool optimizing cost/speed. Trade-offs: adaptive selection and high utilization vs. auction latency and bid-gaming risk. *(agentic-architecture-patterns.md)*
- **Supervision Tree with Guarded Capabilities** - Intent: hierarchical supervisors monitor children with recovery strategies (one-for-one restart) plus per-subtree capability guarding. When to use: production agents making risky autonomous tool calls (code exec, scraping). Trade-offs: self-healing and blast-radius control and least-privilege vs. architectural complexity and gateway communication. *(agentic-architecture-patterns.md)*
- **Multi-Agent Planning** - Intent: decompose a high-level goal into a sub-task graph assigned to the best agents, as a shared artifact. When to use: complex goals no single agent can execute. Trade-offs: structured collective work vs. plan-quality dependence and re-planning needs. *(agentic-architecture-patterns.md)*
- **Knowledge Sharing (Shared Epistemic Memory)** - Intent: a global persistent store all agents read/write so one agent's discovery benefits the collective. When to use: systems avoiding fragmented understanding and redundant work. Trade-offs: collective intelligence vs. shared-state consistency and storage infrastructure. *(agentic-architecture-patterns.md)*
- **Consensus** - Intent: iterative belief-exchange protocol until agent states converge within tolerance. When to use: conflicting data/forecasts needing a validated joint conclusion (Level 6). Trade-offs: validated agreement vs. round latency and possible non-convergence. *(agentic-architecture-patterns.md)*
- **Agent Negotiation** - Intent: structured offer/counter-offer protocol for agents with competing goals to compromise. When to use: conflicting objectives with a win-win region (e.g., shared-resource scheduling). Trade-offs: autonomous compromise vs. negotiation cost and termination needs. *(agentic-architecture-patterns.md)*
- **Resource Allocation** - Intent: distribute finite resources via centralized allocator, auctions, or fair-division, using priority queues. When to use: contended finite resources across differing-priority agents (Level 5). Trade-offs: contention prevention vs. allocator bottleneck and priority-rule design. *(agentic-architecture-patterns.md)*
- **Conflict Resolution** - Intent: resolve agent conflicts via hierarchical, policy-based, negotiation, or game-theoretic approaches. When to use: any multi-agent deadlock/contradiction risk; choose by control vs. emergence and auditability. Trade-offs: predictable/auditable (hierarchical/policy) but rigid vs. adaptive/nuanced (negotiation/game-theory) but complex. *(agentic-architecture-patterns.md)*
- **Formation Control** - Intent: decentralized control where each agent positions by its neighbors' states, yielding emergent collective structure. When to use: physical swarms (drones/robots) self-organizing around obstacles. Trade-offs: fluid resilient self-organization vs. unpredictability; spatial/embodied only. *(agentic-architecture-patterns.md)*
- **Instruction Fidelity Auditing** - Intent: an auditor agent verifies a worker's output meets the original instruction before finalizing. When to use: delegated workflows where local optimization may miss global constraints. Trade-offs: prevents instruction drift vs. extra audit call. *(agentic-architecture-patterns.md)*
- **Fractal Chain-of-Thought (FCoT) Embedding** - Intent: recursive multi-level reasoning structure enabling dynamic self-correction. When to use: complex collaborative reasoning beyond flat CoT. Trade-offs: richer self-correcting reasoning vs. structural/token overhead. *(agentic-architecture-patterns.md)*
- **Persistent Instruction Anchoring** - Intent: embed critical instructions in semantic tags so they stay salient down a long agent chain. When to use: deep hierarchical chains prone to mid-context "lost-in-the-middle" drift. Trade-offs: keeps goals visible cheaply vs. tagging discipline. *(agentic-architecture-patterns.md)*
- **Parallel Execution Consensus (Agent Failover to Agent)** - Intent: run independent agents on the same critical task and compare/escalate on disagreement. When to use: high-stakes decisions where a single LLM is a single point of failure. Trade-offs: cross-checked reliability vs. redundant-execution cost. *(agentic-architecture-patterns.md)*
- **Robustness pattern family (Watchdog Timeout, Adaptive Retry with Prompt Mutation, Auto-Healing, Fallback Model, Incremental Checkpointing, Rate-Limited Invocation, Delayed Escalation, Majority Voting, Causal Dependency Graph, Trust Decay/Canary Testing, Agent Mesh Defense, Execution Envelope Isolation)** - Intent: layered fault tolerance from reactive recovery to self-governed security, each paired with a metric. When to use: progressively by robustness maturity level for production reliability. Trade-offs: resilience/auditability/security vs. latency, token cost, and architectural complexity. *(agentic-architecture-patterns.md)*
- **Human-agent interaction family (Agent Calls Human, Human Delegates to Agent, Human Calls Agent, Agent Delegates to Agent, Agent Calls Proxy Agent)** - Intent: composable interaction/escalation/delegation patterns plus a credentialed proxy for secure external calls. When to use: progressively by interaction maturity, from transactional bots to proactive partners. Trade-offs: usability and safety vs. orchestration overhead; measure via escalation/resolution metrics. *(agentic-architecture-patterns.md)*
- **Tool and Agent Registry** - Intent: dynamic "yellow pages" where agents/tools register capabilities and are discovered by name or semantic query at runtime. When to use: true multi-agent ecosystems (Level 5) needing loose coupling. Trade-offs: decoupling and evolvability vs. a registry service to operate. *(agentic-architecture-patterns.md)*
- **Agent Authentication and Authorization** - Intent: treat each agent as a first-class service identity; gateway validates tokens/scopes/expiration and enforces least-privilege rotated credentials. When to use: from day one of any production agent. Trade-offs: secure agent-to-agent communication vs. IAM integration effort. *(agentic-architecture-patterns.md)*
- **Real-Time Compliance Monitoring** - Intent: intercept agent actions against a central policy engine, enforcing action-, row-, and field-level constraints (e.g., PII/PHI) before execution. When to use: workflows touching sensitive data or financial transactions. Trade-offs: granular pre-execution compliance vs. interception latency and policy maintenance. *(agentic-architecture-patterns.md)*
- **Event-Driven Reactivity** - Intent: agents subscribe to a message bus; events trigger the Sense component and reasoning loop, decoupling components. When to use: scalable, resilient, asynchronous agentic systems. Trade-offs: decoupling and scale vs. event-driven debugging complexity. *(agentic-architecture-patterns.md)*
- **Hybrid (Planner + Scorer) Architecture** - Intent: structurally separate generation from evaluation to enforce reflection before acting (implements the R5 "Reflect" discipline). When to use: self-improving/learning production agents. Trade-offs: objective self-critique and a self-improvement flywheel vs. extra scorer infrastructure. *(agentic-architecture-patterns.md)*

### GenAI application & cloud patterns (Karuparti & Singh; Kavanagh; Mukherjee & Saladi; Meyer; Del Sole)

*Source files: genai-on-cloud-platforms.md, building-genai-applications.md.*

- **Retrieval-Augmented Generation (RAG)** - Intent: ground LLM answers in trusted, current external data without retraining. When to use: knowledge changes faster than training; answers must be verifiable; per-query relevance and cost matter. Trade-offs: adds ingestion/chunk/embed/index complexity and a vector store; retrieval quality gates answer quality. *(genai-on-cloud-platforms.md)*
- **Fine-tuning / PEFT** - Intent: change a model's behavior/format/tone/task competence by updating weights (PEFT trains a small subset). When to use: stable domain behavior, prompts too long/repetitive, consistent specialized output. Trade-offs: upfront data/compute, catastrophic forgetting risk; does not keep facts current (use RAG). *(genai-on-cloud-platforms.md)*
- **Hybrid + semantic re-rank retrieval** - Intent: combine keyword and vector search then re-rank by deep models. When to use: vector recall misses exact terms or precision is critical. Trade-offs: extra ranking latency/cost; tune chunk size (~512 tokens, ~10% overlap). *(genai-on-cloud-platforms.md)*
- **ANN index selection (HNSW vs FAISS/IVF)** - Intent: trade slight accuracy for large speed gains. HNSW for dynamic high-precision real-time text; FAISS/IVF+PQ for billions, static, GPU batch. Trade-offs: ANN misses exact neighbors; quantization saves storage at accuracy cost. *(genai-on-cloud-platforms.md)*
- **Vector library vs vector database** - Intent: avoid over-engineering the data layer. Library (FAISS) for small static in-memory; database for millions/billions of changing records needing CRUD/replication/persistence/ms latency. Trade-offs: libraries lack CRUD/replication/persistence. *(genai-on-cloud-platforms.md)*
- **Multi-account/PTU + APIM "spillover" scaling** - Intent: exceed per-resource model quota and meet SLAs. When to use: enterprise traffic beyond one AOAI account's TPM. Method: stack accounts/regions behind one API Management; PTU first, spill to TPM; Premium APIM for DR. Trade-offs: APIM cost/config. *(genai-on-cloud-platforms.md)*
- **Retries with exponential backoff (scaling special sauce)** - Intent: absorb transient and 429/5xx rate-limit errors at scale. When to use: any cloud LLM call, high concurrency. Method: APIM retry policy on 429 and >=500 with growing intervals and max count. Trade-offs: can mask sustained capacity shortfalls; pair with monitoring. *(genai-on-cloud-platforms.md)*
- **LLM-as-a-judge evaluation** - Intent: automate large-scale quality assessment. When to use: manual ground-truth comparison does not scale. Method: Prompt Flow metaprompts scoring groundedness/relevance/retrieval score + custom metrics; supplement with ROUGE/BLEU/F1. Trade-offs: judge model can err; use a metric mix. *(genai-on-cloud-platforms.md)*
- **Kernel-centric orchestration (Semantic Kernel)** - Intent: a lightweight registry of services + plugins through which every prompt/function call passes for centralized service selection, templating, events, logging, responsible-AI hooks. When to use: any non-trivial SK app. Trade-offs: a layer to learn; richer kernels slow planners. *(building-genai-applications.md)*
- **Semantic function (prompt-as-plugin)** - Intent: separate prompt (skprompt.txt) and config (config.json) from code for reuse, versioning, and planner discovery via description. When to use: any reusable prompt. Trade-offs: more structure; descriptions are load-bearing. *(building-genai-applications.md)*
- **Native function (code-as-plugin)** - Intent: expose deterministic code to the kernel/planner via decorators + descriptions so the model can act. When to use: model must do something, not just generate. Trade-offs: must guard side effects; descriptions drive selection. *(building-genai-applications.md)*
- **Function chaining** - Intent: hand-built pipeline where each function's output feeds the next, mixing semantic and native steps. When to use: known fixed workflow; deterministic control and testability. Trade-offs: rigid; must anticipate all paths. *(building-genai-applications.md)*
- **Planner-driven workflow** - Intent: let the model assemble atomic functions into a plan from a natural-language goal. When to use: open-ended requests; emergent capability; auto-improves with model upgrades. Trade-offs: latency, token cost, nondeterministic testing; handle hallucinated/oversized plans (resubmit-and-fix); cache frequent plans. *(building-genai-applications.md)*
- **Stateful assistant (threads)** - Intent: offload conversation state, tools, and retrieval to a managed Assistants API. When to use: multi-turn assistants needing persistent threads, code interpreter, or file search. Trade-offs: vendor-managed state/behavior; less low-level control. *(building-genai-applications.md)*
- **Semantic memory** - Intent: give a stateless app long-term recall via embedding similarity search (not key lookup). When to use: personalization, long conversations, beyond-context knowledge. Trade-offs: fixed-length embeddings (can exceed source size); needs a vector store; quality depends on embedding model. *(building-genai-applications.md)*
- **Multi-agent collaboration with a manager** - Intent: decompose complex goals across specialized agents under an orchestrator. When to use: tasks with distinct sub-skills (research/design/copy/QA). Trade-offs: complexity, cost, emergent behavior; human-in-the-loop for high-impact actions. *(building-genai-applications.md)*
- **Pre-built AI service via SDK** - Intent: consume turnkey vision/language/speech/document/safety over REST/SDK rather than building models. When to use: standard tasks (OCR, sentiment, transcription, invoice extraction, moderation). Trade-offs: less control than custom; authenticate with managed identity, not keys. *(building-genai-applications.md)*

### LLM design patterns - prompting & reasoning (Huang 2025; Lakshmanan & Hapke 2025)

*Source files: llm-design-patterns.md, generative-ai-design-patterns.md.*

- **Chain-of-Thought (CoT) prompting** - Intent: elicit multi-step reasoning by showing intermediate steps (zero/few-shot, auto, dynamic, adaptive). When to use: math, logic, sequential, domain-specific multi-step problems. Trade-offs: higher tokens/latency and error propagation; no help when the failure is a data gap or non-sequential logic. *(llm-design-patterns.md; generative-ai-design-patterns.md)*
- **Tree-of-Thoughts (ToT) prompting** - Intent: treat reasoning as a tree search with branching, evaluation, pruning, and backtracking. When to use: strategic/creative problems needing multiple paths where CoT's single path fails. Trade-offs: large overhead generating/scoring branches; escalate from CoT only when needed. *(llm-design-patterns.md; generative-ai-design-patterns.md)*
- **ReAct (Reasoning + Acting)** - Intent: interleave reasoning with tool actions and observations so the model gathers info and acts. When to use: multi-hop QA, fact verification, tool use, environment interaction. Trade-offs: more calls/orchestration; reliability depends on agent prompt; loop/invalid-action risk. *(llm-design-patterns.md)*
- **ReWOO (Reasoning WithOut Observation)** - Intent: plan the full tool-call sequence up front, separating planning from execution. When to use: control-flow-heavy retrieval, autonomous agents, cost-sensitive multi-step work. Trade-offs: less adaptive than ReAct; planning errors propagate to the whole execution. *(llm-design-patterns.md)*
- **Prompt Optimization (indirection)** - Intent: add a level of indirection (e.g., DSPy) so prompts auto-update when models/dependencies change. When to use: brittle apps breaking on model-version changes. Trade-offs: more robust than manual prompt management, which still needs manual re-experimentation. *(generative-ai-design-patterns.md)*

### LLM design patterns - RAG & knowledge integration (Huang 2025; Lakshmanan & Hapke 2025; Rothman 2025)

*Source files: llm-design-patterns.md, generative-ai-design-patterns.md, llms-in-enterprise-and-context-engineering.md.*

- **Basic RAG** - Intent: ground responses in retrieved trusted documents injected into context. When to use: enterprise/confidential knowledge, post-cutoff facts, citable answers. Trade-offs: adds retrieval infra/latency; quality bounded by retrieval; irrelevant retrieval misleads. *(llm-design-patterns.md; generative-ai-design-patterns.md)*
- **Semantic Indexing** - Intent: embed chunks into a vector store and retrieve by cosine similarity (incl. multimodal). When to use: keyword indexing fails on complex/cross-domain docs. Trade-offs: chunking and embedding-model choices; domain models can help. *(generative-ai-design-patterns.md)*
- **Index-Aware Retrieval (hypothetical answers, query expansion, hybrid search, GraphRAG)** - Intent: bridge the question-document mismatch on top of semantic indexing. When to use: questions absent from KB, jargon mismatch, fine details, multi-chunk answers. Trade-offs: expansions risk hallucinated/obsolete matches and intent drift. *(generative-ai-design-patterns.md)*
- **Node Postprocessing (reranking)** - Intent: combine retrievers and rerank/filter chunks between retrieval and generation. When to use: similarity is not relevance; need disambiguation/freshness/personalization. Trade-offs: rerankers add latency/cost (mitigate with a small model like BGE). *(generative-ai-design-patterns.md)*
- **Graph-based RAG** - Intent: retrieve over a knowledge graph to reason over entity relationships. When to use: KG QA, explainable recommendations, biomedical/social reasoning. Trade-offs: traversal/embedding cost at scale; large subgraphs blow the context window; mitigate via subgraph sampling, ANN, graph DBs. *(llm-design-patterns.md)*
- **Advanced/iterative RAG** - Intent: multi-step, dynamic-query, adaptive retrieval beyond single-shot. When to use: complex synthesis, knowledge-intensive dialog, ambiguous queries. Trade-offs: each iteration adds inference+retrieval cost; needs stopping criteria/parallelization. *(llm-design-patterns.md)*
- **Deep Search** - Intent: iterative retrieve-think-generate loop using tools until good-enough or budget exhausted. When to use: multi-hop, verification-heavy, deep-reasoning queries. Trade-offs: slow/costly; parallelize subqueries, cut iterations short. *(generative-ai-design-patterns.md)*
- **Trustworthy Generation** - Intent: out-of-domain detection, citations, human-in-the-loop, validation, UI design (incl. self-RAG). When to use: production RAG where wrong answers erode trust. Trade-offs: self-RAG adds complexity/failure points; domain-specific threshold tuning. *(generative-ai-design-patterns.md)*
- **High-fidelity RAG with citations** - Intent: attach source metadata to every retrieved fact for citation-backed, verifiable reasoning. When to use: enterprise trust, traceability, regulated answers. Trade-offs: richer metadata/indexing pipeline. *(llms-in-enterprise-and-context-engineering.md)*
- **Dual RAG (factual + procedural separation)** - Intent: separate KnowledgeStore (facts) from ContextLibrary (procedural/style blueprints), retrieved by distinct agents. When to use: both grounded facts and consistent style/process matter. Trade-offs: two namespaces and more retrieval orchestration. *(llms-in-enterprise-and-context-engineering.md)*

### GenAI output control & tuning/efficiency (Lakshmanan & Hapke 2025; Huang 2025; Singh 2025; Menshawy & Fahmy 2025)

*Source files: generative-ai-design-patterns.md, llm-design-patterns.md, llms-in-enterprise-and-context-engineering.md.*

- **Logits Masking** - Intent: enforce style/format by intercepting sampling and zeroing disallowed tokens. When to use: rules where continuations can be censored leaving valid options. Trade-offs: needs backtracking when censoring removes all options. *(generative-ai-design-patterns.md)*
- **Grammar (constrained decoding)** - Intent: constrain output to a metasyntax (BNF or Pydantic schema) so it is always valid (JSON/SQL). When to use: downstream consumers need parseable structure. Trade-offs: more reliable than asking for JSON but requires defining the grammar. *(generative-ai-design-patterns.md)*
- **Style Transfer** - Intent: use input-output example pairs to mimic a target tone/style. When to use: content exists in wrong style, conformance not strict. Trade-offs: implicit enforcement only; fine-tuning raises success rate. *(generative-ai-design-patterns.md)*
- **Reverse Neutralization** - Intent: generate via a neutral form then fine-tune neutral->personal style. When to use: want personal style with no example in the target topic. Trade-offs: depends on a repeatable, unbiased neutral form. *(generative-ai-design-patterns.md)*
- **Content Optimization (preference-tuned style)** - Intent: optimize style toward a measurable outcome via preference tuning. When to use: outcome-driven content. Trade-offs: needs an evaluator and preference data. *(generative-ai-design-patterns.md)*
- **Fine-tuning** - Intent: adapt model weights to a domain/task with curated examples. When to use: in-context learning insufficient, need consistent behavior, enough data. Trade-offs: data/compute cost, catastrophic forgetting; choose vs. RAG (knowledge) vs. prompting (instruction). *(llm-design-patterns.md)*
- **Adapter Tuning (PEFT/LoRA)** - Intent: parameter-efficient fine-tuning via small adapter layers, cheap to train and swap. When to use: specialize a base model without full fine-tuning. Trade-offs: variations include merged models and provider-hosted fine-tunes. *(generative-ai-design-patterns.md)*
- **Evol-Instruct** - Intent: post-train on a synthetically evolved instruction dataset for novel enterprise tasks. When to use: complex tasks with no consumer analog. Trade-offs: dataset size scales with complexity/inverse model size; risk of forgetting other tasks. *(generative-ai-design-patterns.md)*
- **Model pruning** - Intent: remove low-magnitude weights/neurons/layers to shrink the model. When to use: latency/memory-constrained deployment. Trade-offs: accuracy loss; pair with fine-tuning to recover and quantization for compounding savings. *(llm-design-patterns.md)*
- **Quantization** - Intent: lower numeric precision of weights/activations (dynamic/static/QAT/mixed). When to use: cut size/cost, enable edge deployment. Trade-offs: precision loss; QAT recovers accuracy at training-complexity cost; static needs calibration data. *(llm-design-patterns.md)*
- **Model compression (utility vs. complexity)** - Intent: prune + quantize to shrink footprint for constrained hardware. When to use: cost/edge constraints. Trade-offs: over-compression hurts accuracy; balance against business requirements. *(llms-in-enterprise-and-context-engineering.md)*
- **Prompt Caching** - Intent: reuse prior responses (semantic/response) or model state (prefix/context), client- or server-side. When to use: repetitive queries. Trade-offs: client-side cuts latency most but is per-client/self-operated; server-side suits distributed/managed providers. *(generative-ai-design-patterns.md)*
- **Layered Caching -> Fine-Tuning** - Intent: progressive prompt/embedding/response caching that feeds data into targeted fine-tuning over time. When to use: high-volume domains (support, personalization). Trade-offs: monitor added-service latency. *(generative-ai-design-patterns.md)*
- **Small Language Model routing** - Intent: route suitable subtasks to a smaller/distilled model. When to use: cost/latency-sensitive, high-volume, on-device. Trade-offs: reduced capability; route only appropriate tasks. *(generative-ai-design-patterns.md)*
- **Dynamic batching for inference** - Intent: group requests into batches to raise GPU utilization and cut latency. When to use: real-time variable-load serving. Trade-offs: needs queue/scheduling sophistication and batch-size tuning vs. SLA. *(llms-in-enterprise-and-context-engineering.md)*

### GenAI reliability, safety & evaluation (Lakshmanan & Hapke 2025; Huang 2025; Singh 2025)

*Source files: generative-ai-design-patterns.md, llm-design-patterns.md.*

- **Reflection (generate-critique-revise)** - Intent: invoke the model two or more times - generate, critique via an evaluator (LLM/tool/human), revise - until a quality bar is met. When to use: stateless API calls needing self-correction. Trade-offs: extra calls; one of Ng's four core agentic patterns. *(llm-design-patterns.md; generative-ai-design-patterns.md)*
- **LLM-as-Judge** - Intent: use an advanced model to evaluate outputs (prompting/ML/fine-tuned), scaling beyond human eval. When to use: open-ended outputs traditional metrics cannot score. Trade-offs: nondeterminism and biases; reduce via temperature 0, caching, fixed seeds. *(generative-ai-design-patterns.md)*
- **Dependency Injection (mocking)** - Intent: replace LLM calls and external tools with mocks during development/testing of other components. When to use: testing nondeterministic GenAI code. Trade-offs: hardcoded mocks get harder to maintain as inter-step interaction grows. *(generative-ai-design-patterns.md)*
- **Guardrails** - Intent: layers on inputs/outputs/context/tool-parameters enforcing security, privacy, content moderation, anti-hallucination, alignment (NeMo, Guardrails AI, LLM Guard). When to use: any production app, especially public-facing/tool-calling. Trade-offs: centralize to avoid scattered checks; adds latency. *(generative-ai-design-patterns.md)*
- **Self-Check** - Intent: have the model verify its own output against criteria before returning. When to use: catch errors pre-delivery. Trade-offs: extra call; not a substitute for external validation. *(generative-ai-design-patterns.md)*
- **Template Generation / Assembled Reformat** - Intent: constrain output to fixed templates, or assemble validated pieces then reformat. When to use: regulated/branded structured outputs. Trade-offs: less flexibility; more pipeline steps. *(generative-ai-design-patterns.md)*
- **Adversarial robustness (defense + training)** - Intent: defend against character/word/sentence-level attacks and universal triggers via adversarial training and robustness evaluation. When to use: models exposed to untrusted input. Trade-offs: can slightly reduce clean accuracy and adds cost; not foolproof. *(llm-design-patterns.md)*
- **Degradation Testing** - Intent: test system behavior as quality/latency degrade. When to use: guarding production SLAs. Trade-offs: extra test infrastructure. *(generative-ai-design-patterns.md)*
- **Blending rule-based + generative** - Intent: deterministic rules for high-risk/compliance plus LLM flexibility, validated against the ruleset. When to use: regulated domains (IVR, healthcare, finance, legal). Trade-offs: dual maintenance of rules and prompts. *(generative-ai-design-patterns.md)*
- **Red & blue team dual-model evaluation** - Intent: one model generates, another critiques/defends to stress-test robustness/trust. When to use: safety/robustness evaluation. Trade-offs: extra compute. *(generative-ai-design-patterns.md)*

### Enterprise LLMs & context engineering (Menshawy & Fahmy 2025; Rothman 2025; Singh 2025)

*Source files: llms-in-enterprise-and-context-engineering.md, generative-ai-design-patterns.md.*

- **Tool Calling** - Intent: let the model invoke external functions/APIs (Responses API, LangGraph, MCP) to act beyond text. When to use: calculations, bookings, DB writes, refunds. Trade-offs: reliability needs clear function names/enums/policies; increases adversarial-attack surface. *(generative-ai-design-patterns.md)*
- **Multiagent Collaboration / Multiplexing (panel of experts)** - Intent: divide cognitive labor across specialized agents, or have an orchestrator route subtasks to specialists and synthesize. When to use: multistep, multi-domain, parallelizable work. Trade-offs: orchestration overhead; can show emergent behavior and emergent failure. *(generative-ai-design-patterns.md)*
- **Connected LLMs (orchestrated multi-LLM)** - Intent: connect models/tools/agents via orchestration, routing, shared memory, and MCP/A2A. When to use: complex enterprise workflows spanning reasoning, summarization, tools. Trade-offs: cuts dev time but adds a coordination layer to operate and observe. *(llms-in-enterprise-and-context-engineering.md)*
- **Semantic blueprint (5 levels of context)** - Intent: replace improvised prompts with a precise, role-structured plan the model executes reliably (goal -> role -> blueprint). When to use: any task needing repeatable, directed output. Trade-offs: more design effort up front; output still stochastic but consistently better than undirected prompts. *(llms-in-enterprise-and-context-engineering.md)*
- **Plan-Execute-Reflect Context Engine** - Intent: Planner decomposes a goal, Executor runs it passing evolving MCP context, Tracer logs every step (glass-box). When to use: transparent, debuggable multi-agent reasoning. Trade-offs: added latency from multiple calls; needs an Agent Registry with clear capability descriptions. *(llms-in-enterprise-and-context-engineering.md)*
- **Summarizer agent (context reduction)** - Intent: proactively compress information passed between agents to stay within token limits and cut cost. When to use: long contexts, multi-step pipelines accumulating context. Trade-offs: summarization can drop nuance; a registered agent the Planner invokes when needed. *(llms-in-enterprise-and-context-engineering.md)*
- **Input sanitization (anti prompt-injection)** - Intent: scan retrieved/external text for malicious patterns and discard tainted data before synthesis. When to use: any RAG over external/user content (defends data-poisoning -> prompt-injection). Trade-offs: pattern scanning is a first line only. *(llms-in-enterprise-and-context-engineering.md)*
- **Two-stage moderation + policy-driven safeguards** - Intent: moderation gates on input/output plus policy enforcement and human-in-the-loop governance. When to use: enterprise deployment with legal/brand/safety constraints. Trade-offs: requires organizational policy, not just code; adds latency/governance overhead. *(llms-in-enterprise-and-context-engineering.md)*
- **Latency budgeting** - Intent: explicitly budget and measure prompt size/latency before API calls to keep within SLA. When to use: production with response-time guarantees. Trade-offs: instrumentation; may force trade-offs against richer context. *(llms-in-enterprise-and-context-engineering.md)*
- **Domain-portable Context Engine (modular reuse)** - Intent: re-task the same multi-agent architecture across domains by swapping the knowledge base and blueprints, not the core logic. When to use: standardizing one platform across use cases. Trade-offs: requires clean modular boundaries and dependency injection from the start. *(llms-in-enterprise-and-context-engineering.md)*
- **Evaluation & monitoring (embed business metrics)** - Intent: embed ROI and model metrics (accuracy, latency, resource use) with continuous hallucination/drift monitoring and audits. When to use: every production LLM. Trade-offs: instrumentation/review cost vs. early regression detection. *(llms-in-enterprise-and-context-engineering.md)*
- **Responsible-AI controls** - Intent: enforce fairness (demographic parity, equality of opportunity, equalized odds, counterfactual fairness), real-time explainability probes, model documentation, and bias monitoring. When to use: people-facing or regulated decisions. Trade-offs: fairness/explainability instrumentation adds cost and can trade against raw accuracy. *(llms-in-enterprise-and-context-engineering.md)*
- **Knowledge graphs + LLMs / Memory cognition layer** - Intent: combine structured factual graphs (grounding/traceability) and a persistent memory layer (history, task context, feedback) with LLM reasoning. When to use: enterprises needing trustworthy grounding and cross-session personalization. Trade-offs: graph construction/maintenance; storage and privacy. *(generative-ai-design-patterns.md)*

## Domain 16 - Emerging Technologies

### Digital twins (Prasanth et al. 2025; Gahlawat & Tanwar 2026)

*Source file: digital-twins.md.*

- **Bidirectional twin synchronization** - Intent: keep a virtual replica and its physical counterpart in continuous two-way correspondence so changes to either propagate to the other. When to use: assets monitored and actuated in near-real time (manufacturing lines, patient monitoring, smart-city infrastructure). Trade-offs: distinguishes a true twin from a static model (no automatic exchange) or a one-way digital shadow, but demands reliable low-latency connectivity, conflict resolution, and safe command actuation onto the physical asset. *(digital-twins.md)*
- **Blockchain-secured digital twin** - Intent: anchor twin data and state transitions on an immutable distributed ledger so provenance, integrity, and access are verifiable without a central trusted party. When to use: regulated or multi-stakeholder settings (healthcare records, supply chains, shared assets) where data trust and auditability are paramount. Trade-offs: tamper-evidence, decentralized identity, and smart-contract automation paid for with throughput limits, storage cost, latency, and consensus overhead; prefer permissioned chains for confidentiality/performance, public chains for open verifiability. *(digital-twins.md)*
- **Edge-collected probabilistic data feed** - Intent: deploy edge nodes to collect and pre-process sensor data near the source (governed by data regulations, standards, policies) before sending it to the twin. When to use: dense sensor arrays where centralized collection does not scale. Trade-offs: reduces bandwidth and central load and improves responsiveness, at the cost of distributed-computing complexity and edge management. *(digital-twins.md)*
- **Event-streamed digital thread** - Intent: use a publish-subscribe streaming platform (Kafka-style) as the connectivity and homogenization layer linking IoT interfaces, cloud services, and analytics into a scalable real-time twin. When to use: many heterogeneous producers/consumers needing decoupling and schema governance (JSON Schema, Protobuf, Avro). Trade-offs: high scalability and clean producer/consumer decoupling, but adds streaming infrastructure and schema-management discipline. *(digital-twins.md)*
- **Patient digital twin for in-silico treatment** - Intent: build a virtual replica of a patient to simulate treatment responses, optimize dosing, and predict side effects before real-world application. When to use: precision/personalized medicine in Healthcare 5.0. Trade-offs: enables proactive individualized care but depends on high-fidelity multi-source data, raises privacy/ethical concerns, and requires secure (often blockchain-backed) data governance. *(digital-twins.md)*

### Specialized computing & physical-system platforms (Chaudhuri et al. 2025; Ribeiro & Montenegro 2024)

*Source file: specialized-computing-and-domain-systems.md.*

- **CA-transform feature extraction (CAML)** - Intent: model a system as cellular automata, evolve the CA, and extract a Feature Vector for a downstream ML mapping instead of feeding raw input to a network. When to use: structured/sequential domains (protein chains, language text) where training data, compute budget, interpretability, or hardware cost are tight. Trade-offs: dramatically lower data and compute needs plus transparency and built-in input obfuscation (privacy), but demands iterative domain-specific CA rule design and only suits systems decomposable into simple interacting entities. *(specialized-computing-and-domain-systems.md)*
- **Lightweight interpretable model over big black box** - Intent: prefer a compact, explainable model (CA + ML) to a large opaque neural/LLM model when data, compute, transparency, or hardware cost bind. - **Distributed smart-sensing for structural health monitoring** - Intent: push sensing and pre-processing into smart sensors/edge nodes rather than streaming everything to a central processor. When to use: dense sensor arrays on large physical assets (bridges, track) where central collection does not scale. Trade-offs: scalable and responsive, but adds distributed-system complexity, sensor management, and data-fusion challenges. *(specialized-computing-and-domain-systems.md)*
- **Predictive maintenance via physical-system digital twin** - Intent: mirror a large physical asset with sensor-fed simulation models to forecast condition and schedule maintenance before failure. When to use: high-value, safety-critical, expensive-to-inspect infrastructure (railways, civil structures). Trade-offs: cuts lifecycle cost and unplanned downtime, but requires accurate physics models, reliable sensing, and integration across IoT, edge, cloud, and AI layers. *(specialized-computing-and-domain-systems.md)*

### Blockchain-AI convergence (Dhillon, Metcalf & Hooper 2025; Sharma, Vajjhala, Kothari & Potluri eds. 2025)

*Source file: blockchain-and-ai-convergence.md.*

- **Three-stack layering (traditional / blockchain / AI integration)** - Intent: build an AI-blockchain system by inheriting layers from a foundational stack and adding model-deployment, interfacing, AI-contract, oracle, off-chain, and privacy layers. When to use: greenfield design of any decentralized AI application. - **Containerized model behind a smart-contract wrapper** - Intent: package a trained model (Docker) and expose it to the chain only through a smart-contract-mediated interface so it inherits blockchain security and can be metered/billed. Trade-offs: secure, billable model access vs. wrapper latency; the model still runs off-chain. *(blockchain-and-ai-convergence.md)*

When to use: contracts depending on external feeds for decisions. Trade-offs: higher data integrity vs. added model complexity and a new failure surface. *(blockchain-and-ai-convergence.md)*
- **Off-chain compute with on-chain settlement** - Intent: run heavy training/inference off-chain (TensorFlow Serving) and report results/payment back through a contract. When to use: computation exceeds on-chain limits. Trade-offs: scalability and lower cost vs. weaker on-chain verifiability of the computation (mitigate with ZKPs or on-chain inference). *(blockchain-and-ai-convergence.md)*
- **Dual-model guardrails (Constitutional AI)** - Intent: a smaller supervisory/policy model corrected by a larger constitutional/preference model, with a gatekeeper screening outputs before they reach users. When to use: deploying foundational models in sensitive domains (healthcare, finance). Trade-offs: stronger, persistent alignment vs. extra inference cost and architectural complexity. *(blockchain-and-ai-convergence.md)*
- **DAO-based AI governance with a safety override** - Intent: govern model development via token-weighted votes among developers/maintainers/vendors, with a stake-to-trigger safety contract that supersedes all others. When to use: multi-party or open-source model development needing transparent, accountable decisions. Trade-offs: transparency, accountability, and rapid safety response vs. governance overhead and on-chain coordination cost. *(blockchain-and-ai-convergence.md)*
- **Consensus-validated federated learning** - Intent: train across independent nodes without sharing raw data, then reach consensus on whether each model update meets performance/safety thresholds, rewarding contributors with tokens. When to use: privacy-sensitive, multi-party model training. Trade-offs: privacy preservation and reduced bias vs. coordination cost and difficulty designing the validation/consensus mechanism. *(blockchain-and-ai-convergence.md)*
- **ZKP-enhanced private AI** - Intent: use zero-knowledge proofs to train on or validate against sensitive data without revealing it, and to obfuscate identities of compute providers/edge devices. When to use: consortiums with confidential data; edge inference with payment. Trade-offs: strong privacy and verifiable validity vs. ZKP generation cost and engineering complexity. *(blockchain-and-ai-convergence.md)*
- **XAI-over-blockchain analytics** - Intent: store authentic data on an immutable ledger, then apply interpretable models (SHAP/LIME) so stakeholders see both verified data and explained recommendations. When to use: multi-stakeholder decisions needing both trust and explainability (supply chain, finance). Trade-offs: transparency and accountability vs. running two systems and reconciling their data models. *(blockchain-and-ai-convergence.md)*

## Domain 11 - AI-Assisted Development

### Vibe coding workflow & practices (Kim & Yegge 2025; Osmani 2025; Huang et al. 2025; Waseem et al. 2025)

*Source files: vibe-coding-practices.md, ai-assisted-engineering-discipline.md.*

- **The vibe coding loop** - Intent: frame objective -> decompose -> start conversation -> review -> test/verify -> refine -> automate the workflow. When to use: day-to-day AI-assisted development. Trade-offs: every step becomes critical at AI speed; skipping review/verify yields expensive rework. *(vibe-coding-practices.md)*
- **Conversations, not commands or contracts** - Intent: treat vibe chat like texting a colleague, disposable and impromptu, not durable prompt engineering. When to use: in-the-moment problem solving you throw away after. Trade-offs: tolerate mistakes/typos; be sloppy on style but precise on goals. *(vibe-coding-practices.md)*
- **Frame vague, request precise** - Intent: be disfluent but explicit about the problem, what you know, and the help wanted; first prompt is longest. When to use: every task kickoff. Trade-offs: under-specification invites hallucinated gap-filling. *(vibe-coding-practices.md)*
- **Let errors speak for themselves** - Intent: paste raw errors/stack traces/screenshots instead of describing them; give the agent access to read them itself (terminal, console, Puppeteer). When to use: any failure. Trade-offs: requires tool access and closing the agent's feedback loop. *(vibe-coding-practices.md)*
- **Give the agent tools (MCP)** - Intent: maximize the agent's direct environment access so it executes and validates its own work. When to use: agentic coding, UI, API work. Trade-offs: security surface; degrade gracefully to chat when a tool is unavailable. *(vibe-coding-practices.md)*
- **Plan-first / spec-first development** - Intent: write a lightweight plan/mini-PRD/spec with constraints and acceptance criteria before generating. When to use: anything beyond throwaway prototypes. Trade-offs: up-front effort; bounds output and reduces surprises. *(vibe-coding-practices.md; ai-assisted-engineering-discipline.md)*
- **Plan in a file, execute in small chunks** - Intent: draft a long plan but have the agent do only a few steps at a time (observed ~2.1/prompt), verifying between chunks. When to use: larger features with agents. Trade-offs: more turns/supervision; keeps control and limits blast radius. *(vibe-coding-practices.md)*
- **Focused vs. comprehensive context** - Intent: minimal context for leaf-node tasks; dump-everything for system-wide work or small projects; summarization/RAG/agentic search for large codebases. When to use: every interaction's context decision. Trade-offs: "the more on its clipboard, the dumber it gets" (saturation) vs. missing context. *(vibe-coding-practices.md)*
- **Ruthless context curation** - Intent: start new chats, compact, checkpoint to keep the window lean and avoid context saturation. When to use: long sessions nearing limits. Trade-offs: losing useful history; mitigated by summarization docs and save-game checkpoints. *(vibe-coding-practices.md)*
- **Tracer-bullet testing** - Intent: validate the agent can handle a tightly scoped critical path end-to-end before the full build. When to use: risky/unfamiliar critical paths. Trade-offs: small up-front cost avoids dead ends. *(vibe-coding-practices.md)*
- **Parallel exploration / optionality (FAAFO)** - Intent: spin up multiple agents/branches to try approaches at once and pick the best. When to use: exploration reduces risk or finds better solutions. Trade-offs: coordination, merge integration, supervision load (handful of agents is the practical ceiling). *(vibe-coding-practices.md)*
- **Delegation framework (Grove factors)** - Intent: size delegation by task novelty, agent experience, skill, impact, and reporting frequency. When to use: deciding how much rope to give an agent. Trade-offs: intuitions shift each model release; over-delegation sets the agent up to fail. *(vibe-coding-practices.md)*
- **AI as first drafter / pair programmer / validator** - Intent: three team workflow modes - AI drafts then human refines; constant-conversation pairing; human writes then AI/scanners validate. When to use: integrating AI into team workflow. Trade-offs: coordinate up front to avoid duplicate work; isolate AI commits. *(vibe-coding-practices.md; ai-assisted-engineering-discipline.md)*
- **Share and reuse effective prompts** - Intent: maintain a team repository of proven prompts and agent task templates. When to use: recurring task types; team standardization. Trade-offs: maintenance; prompts drift as models change. *(vibe-coding-practices.md)*

### AI engineering discipline & verification (Huang et al. 2025; Waseem et al. 2025; Osmani 2025; Kim & Yegge 2025)

*Source files: ai-assisted-engineering-discipline.md, vibe-coding-practices.md.*

- **Plan-then-validate control loop** - Intent: human as designer and verifier - plan, let the agent implement in small chunks, validate every change. When to use: production work and quality-sensitive tasks. Trade-offs: more turns/supervision; this is what makes output trustworthy (experienced developers control, not vibe). *(ai-assisted-engineering-discipline.md)*
- **NFRs/ASRs as quality-attribute scenarios in prompts** - Intent: have the agent identify ASRs and express them as scenarios with measurable fit criteria, linked to tests and CI budgets, before generating. When to use: any system where security/performance/reliability/evolvability matter. Trade-offs: up-front rigor; prevents silent NFR omission. *(ai-assisted-engineering-discipline.md)*
- **DDD + Hexagonal scaffolding for LLMs** - Intent: impose clear boundaries and testable interfaces (Ports and Adapters, layered separation) so regeneration does not create patchwork. When to use: multi-module/microservice VC systems. Trade-offs: architectural setup; controls context window and drift, supports TDD/ATDD/BDD. *(ai-assisted-engineering-discipline.md)*
- **Continuous security scanning in the dev loop** - Intent: run SAST/DAST/SBOM and IDE-time scanners (ESLint security, Bandit, CodeQL, Semgrep, Snyk) automatically on AI code, blocking risky imports/open configs. When to use: always, with extra vigilance at AI speed. Trade-offs: pipeline cost and false positives; strong safety net. *(ai-assisted-engineering-discipline.md)*
- **Separate-AI / cross-model security and code review** - Intent: have the generating model audit its own output and/or a different model review it independently. When to use: extra layer before human review. Trade-offs: false positives/missed subtleties; never replaces human review and testing. *(ai-assisted-engineering-discipline.md)*
- **Three-layer test discipline** - Intent: AI-generated unit tests plus human-written edge cases; contract/interface tests across services; continuous performance/security gates in CI. When to use: any system past prototype. Trade-offs: test maintenance; defeats the "illusion of reliability" from happy-path/mock-only tests. *(ai-assisted-engineering-discipline.md)*
- **Property-based testing and fuzzing of AI code** - Intent: assert invariants (ordering, idempotence, element preservation) and generate many inputs rather than hand-writing cases. When to use: AI-written algorithmic/transformation code. Trade-offs: learning curve; surfaces edge cases humans miss. *(ai-assisted-engineering-discipline.md)*
- **Count your babies** - Intent: systematically verify every requested component/function/test was delivered and works; watch diffs for silent deletions. When to use: after every agent task. Trade-offs: discipline overhead; catches silent omissions. *(ai-assisted-engineering-discipline.md)*
- **Inspect for cardboard muffins** - Intent: go beyond "tests pass" - verify tests assert meaningful behavior and error handling actually handles errors, not faked/hardcoded completions. When to use: whenever the agent reports success. Trade-offs: deeper review; defeats reward-hijacking. *(ai-assisted-engineering-discipline.md)*
- **Demand explicit quality standards** - Intent: specify structure/patterns/quality and ask the agent to review and minimize its own work, because you get the quality you ask for. When to use: any non-throwaway code. Trade-offs: more prompting; counters bare-minimum "half-assing." *(ai-assisted-engineering-discipline.md)*
- **Leave it cleaner than you found it** - Intent: instruct the agent to clean up and remove debris (stray logging, unused vars, temp files/branches) after each task. When to use: every session. Trade-offs: explicit cleanup steps; prevents AI code becoming immediate technical debt. *(ai-assisted-engineering-discipline.md)*
- **Isolate and label AI changes in version control** - Intent: commit AI changes separately with clear (optionally AI-tagged) messages; commit frequently as a safety net. When to use: all AI-assisted work. Trade-offs: granular history; enables bisect, rollback, targeted review. *(ai-assisted-engineering-discipline.md)*
- **Hardening / cleanup sprints** - Intent: alternate generation-heavy sprints with dedicated refactor-and-document sprints. When to use: after bursts of AI generation. Trade-offs: feature time traded for paying down debt before it compounds. *(ai-assisted-engineering-discipline.md)*
- **Autonomous-agent plan-gate oversight** - Intent: treat the agent's planning phase as the primary quality gate, monitor at runtime, scope concurrent agents to avoid merge conflicts, and use agent-specific review checklists. When to use: background coding agents (Codex, Jules, Devin, Cursor agents). Trade-offs: new oversight skills; reviewing the plan prevents costly rework. *(ai-assisted-engineering-discipline.md)*

### AI-assisted development anti-patterns (Osmani 2025; Kim & Yegge 2025; Waseem et al. 2025)

*Source files: ai-assisted-engineering-discipline.md.*

- **Pure vibing on production code** - accept-all, never-read-the-diffs behavior produces house-of-cards code that collapses under real conditions; experienced developers avoid it. *(ai-assisted-engineering-discipline.md)*
- **The "two steps back" loop** - fixing one AI-suggested bug breaks something else; fixing that creates two more, especially painful without the mental models to diagnose. *(ai-assisted-engineering-discipline.md)*
- **The demo-quality trap** - polished happy-path demos that fall apart under real users (nonsense errors, crashing edge cases, missing accessibility/performance); MVPs that "look done" fail basic security scans. *(ai-assisted-engineering-discipline.md)*
- **Reward-hijacking failure modes** - baby-counting (silent omissions), cardboard muffins (faked completions), half-assing (bare-minimum quality), litterbug (working-but-messy debris). *(ai-assisted-engineering-discipline.md)*
- **Regeneration outpacing review** - a single "fix this" rewrites large parts of the codebase before anyone sees the prior version, eroding architecture and breaking contracts. *(ai-assisted-engineering-discipline.md)*
- **Illusion of test reliability** - auto-generated suites that pass while the feature is broken because they exercise model-created mocks rather than real logic. *(ai-assisted-engineering-discipline.md)*
- **Skill atrophy / lost technical ownership** - over-reliance on agents without maintaining fundamentals leaves teams unable to audit, guide, or intervene. *(ai-assisted-engineering-discipline.md)*
- **Naive delegation of architecture** - agent-chosen architectural decisions "bite back"; high-level design is the most contested agent use. *(ai-assisted-engineering-discipline.md)*
- **Package hallucination** - AI invents/misremembers library names; attackers publish malicious packages under common hallucinated names. Verify before installing. *(ai-assisted-engineering-discipline.md)*
- **Insecure-by-default generation** - hard-coded secrets, concatenated SQL, unescaped output (XSS), plain-text passwords, user-enumeration error messages, weak crypto, leaked stack traces (25-33%+ of generated code flagged with weaknesses). *(ai-assisted-engineering-discipline.md)*

## Domain 12 - Enterprise and Business Architecture

### EA fundamentals: domains, frameworks, and artifacts (McCabe 2024; Iyamu 2024; Gray/Sykes/Homan 2025)

*Source files: enterprise-architecture-fundamentals.md.*

- **EA domain decomposition (EBA/EIA/EAA/ETA)** - Intent: structure the enterprise into four interdependent architecture domains (business, information, application, technical), each with distinct deliverables, methods, and owners. When to use: organizing any enterprise-scope architecture program. Trade-offs: clear separation of concerns and ownership vs. coordination overhead and ripple effects across domains. *(enterprise-architecture-fundamentals.md)*
- **Layered architectural domain model with capability mapping** - Intent: group capabilities into layered architecture domains, tying a business-capability model to a technical-capability model so technology traces to business outcomes. When to use: deciding where to invest, converge, or deprecate. Trade-offs: enduring, technology-agnostic view vs. modeling being "more art than science" and needing maintenance. *(enterprise-architecture-fundamentals.md)*
- **Architecture decision record (ADR)** - Intent: document a recommendation with id, metadata, stakeholders (RACI), status, problem statement, alternatives with trade-offs, rationale, and implications (incl. debt/risk). When to use: every architecture decision, especially deviations from standards. Trade-offs: documented rationale and governance support vs. discipline to keep records current. *(enterprise-architecture-fundamentals.md)*
- **Capability target architecture** - Intent: document the shared destination state for a domain's capabilities with conceptual/logical/physical views, sequence diagrams, and invest/deprecate/converge decisions. When to use: solution-architect domain planning. Trade-offs: strategic alignment vs. effort to keep the target current. *(enterprise-architecture-fundamentals.md)*
- **Reference architecture and patterns-as-code** - Intent: codify proven solutions as blueprints, reference implementations, or reusable templates/modules/libraries. When to use: when a solution recurs and reuse would accelerate teams. Trade-offs: acceleration and consistency vs. up-front cost and the need to prove patterns through real implementation. *(enterprise-architecture-fundamentals.md)*
- **OKR-based EA strategy** - Intent: define the EA strategy with measurable objectives and key results (outcome- and effort-based), tying architecture to business value. When to use: establishing or justifying an EA practice. Trade-offs: makes EA value visible vs. requiring data sources, ownership, and frequency; measure outcomes not artifact counts. *(enterprise-architecture-fundamentals.md)*
- **Hybrid architecture organization** - Intent: centralize EA strategy/enablement/oversight for objectivity and consistency while federating application architects (and some solution architects) for scale and empowerment. When to use: most mid-to-large organizations. Trade-offs: balances objectivity and proximity-to-delivery vs. organizational complexity. *(enterprise-architecture-fundamentals.md)*
- **Architectural Strategic Process (ASP)** - Intent: iterative four-step current-state -> requirements -> governance -> desired-state cycle (with gap analysis) applied per domain. When to use: enforcing EA practice consistently across domains. Trade-offs: structured, repeatable transition vs. process overhead and template upkeep. *(enterprise-architecture-fundamentals.md)*

### EA practice: maturity, governance, and survival skills (Graves & Beard 2025; Gray/Sykes/Homan 2025; McCabe 2024)

*Source files: enterprise-architecture-practice.md.*

- **Maturity-model capability development (Foundations + 5 steps)** - Intent: build EA capability in dependency-respecting increments cross-mapped to CMMI levels, solidifying foundations before transformation. When to use: standing up or maturing an EA practice. Trade-offs: reliable, repeatable effectiveness vs. slower than jumping to transformation; effectiveness capped by the weakest lower step. *(enterprise-architecture-practice.md)*
- **Outcome-based capability assessment** - Intent: assess EA by defining business outcomes, identifying needed people/process/tools capabilities, and mapping gaps, instead of scoring a static maturity ladder. When to use: deciding where to invest in the EA function. Trade-offs: dynamic and context-fit vs. less comparable/benchmarkable than a fixed model. *(enterprise-architecture-practice.md)*
- **Just-enough-architecture, just-in-time** - Intent: produce architecture to order against near-term demand using Kanban + MoSCoW, accepting "good enough" depth and breadth. When to use: fast-moving organizations where completeness is impossible. Trade-offs: speed and relevance vs. incomplete artifacts and heavy reliance on facilitation; not suited to long-horizon target-setting. *(enterprise-architecture-practice.md)*
- **Balanced governance: governance board + advisory group** - Intent: pair an enforcing architecture governance board with a supporting advisory group so stakeholders seek early help and approval later. When to use: any organization formalizing oversight. Trade-offs: support-plus-enforcement balance vs. cost of two bodies; must avoid bottleneck/audit roles. *(enterprise-architecture-practice.md)*
- **Architecturally significant decision triage** - Intent: define criteria for which decisions warrant governance and provide quick triage so trivial decisions are delegated. When to use: protecting governance capacity and delivery speed. Trade-offs: faster flow and clear thresholds vs. risk of mis-triaging significant decisions. *(enterprise-architecture-practice.md)*
- **Federal governance (central standards + regional autonomy)** - Intent: a central group sets certain standards and grants defined autonomy to business-unit/regional architectures. When to use: large, multi-region or multi-BU organizations. Trade-offs: local fit and scale vs. inconsistency and integration cost. *(enterprise-architecture-practice.md)*
- **Trust-equation advisory model** - Intent: operate as a trusted advisor by maximizing credibility, reliability, and intimacy while minimizing self-orientation. When to use: when the architect advises rather than decides (the common case). Trade-offs: durable influence without authority vs. slow to build and easily destroyed by one lapse. *(enterprise-architecture-practice.md)*
- **First-90-days mandate playbook** - Intent: secure executive sponsorship, find early-use scenarios and quick wins, stand up lightweight governance, time-box deliverables (80/20), and communicate per-audience. When to use: starting an EA role or practice. Trade-offs: builds reputation and momentum vs. pressure to show value before foundations are deep. *(enterprise-architecture-practice.md)*

### EA anti-patterns (Gray/Sykes/Homan 2025; McCabe 2024; Graves & Beard 2025)

*Source files: enterprise-architecture-fundamentals.md, enterprise-architecture-practice.md.*

- **The ivory tower** - overly academic architecture disconnected from practical reality; decisions made without context that add no business value. *(enterprise-architecture-practice.md; enterprise-architecture-fundamentals.md)*
- **Boiling the ocean** - trying to solve every aspect of the EA at once; broad, slow, low-impact. *(enterprise-architecture-practice.md)*
- **Analysis paralysis** - each step of analysis demanding more, leading to anxiety-inducing conclusions and no decision. *(enterprise-architecture-practice.md)*
- **Heavy governance / the "NO department"** - every decision needs approval, creating bottlenecks; the worst case approves nothing not originated by the architect. *(enterprise-architecture-practice.md)*
- **Over-standardization ("EA as dictator")** - so much prescription that innovation is stifled and teams rebel against architecture as a bottleneck. *(enterprise-architecture-fundamentals.md)*
- **Starting in the middle / skipping foundations** - transformation programs without Step 1 or foundations fail. *(enterprise-architecture-practice.md)*
- **Measuring volume not impact** - counting standards/artifacts/documents, or gameable targets like "reduce exceptions" by not looking. *(enterprise-architecture-practice.md; enterprise-architecture-fundamentals.md)*
- **Architecture as policing/audit** - turning governance into an audit function destroys collaboration and the value of crafted guidance. *(enterprise-architecture-practice.md)*

### Architecture modernization patterns (Tune & Perrin 2024; Pacheco & Sgro 2024)

*Source file: architecture-modernization.md.*

- **Strangler Fig** - Intent: migrate gradually by routing requests through a front that initially delegates to the legacy and progressively to modernized subsystems until legacy can be retired. When to use: the default for incremental migration when a full rewrite is too risky. Trade-offs: removes big-bang risk vs. data-sync complexity, legacy decoupling/integration work, harder debugging, and possible interim UX degradation. *(architecture-modernization.md)*
- **Strangler Fig for a distributed monolith (Gateway vs Merge)** - Intent: apply the strangler at scale by wrapping coupled services behind an API gateway (then refactoring consumers onto clean contracts) or merging and re-splitting them cleanly. When to use: untangling hundreds/thousands of microservices (Uber DOMA). Trade-offs: gateway abstracts the mess but adds a routing layer; merge restores clean boundaries but needs code migration. *(architecture-modernization.md)*
- **Bubble context** - Intent: place a new subsystem with a fresh domain model in front of legacy, delegating via an ACL and adding logic over time until legacy is replaced (reusing the legacy DB). When to use: a clean model unconstrained by legacy at one subsystem's granularity. Trade-offs: no data-sync risk vs. ACL that can grow more complex than the domain itself. *(architecture-modernization.md)*
- **Autonomous bubble** - Intent: a bubble with its own data store integrating with legacy via async data synchronization (e.g. domain events). When to use: the new subsystem must operate without synchronous legacy calls. Trade-offs: full autonomy/evolvability vs. reintroduced eventual-consistency and sync complexity. *(architecture-modernization.md)*
- **Anticorruption layer (ACL)** - Intent: translate between a new model and a legacy model so the new design is not corrupted. When to use: any cross-model integration during migration. Trade-offs: protects model integrity vs. being a maintained component that can become a complexity hotspot. *(architecture-modernization.md)*
- **Lift and shift (rehost)** - Intent: move to new infrastructure (e.g. cloud) with minimal change for quick elasticity/operational gains. When to use: as a fast first step before per-subdomain modernization. Trade-offs: quick and low-risk vs. carrying legacy coupling forward unless followed by remodeling. *(architecture-modernization.md)*
- **Expose-then-extract (per subdomain)** - Intent: first expose legacy functionality via a clean API/event with minimal change, then extract and remodel behind it. When to use: decoupling a subdomain from a tightly coupled monolith. Trade-offs: early value and de-risked extraction vs. interim contracts that may need rework. *(architecture-modernization.md)*
- **Contract-first slicing of a monolith** - Intent: pick a subset/generic function, define a clean contract, expose it, migrate only the consumers that truly need it one at a time, then move the code to a standalone service or private module. When to use: draining a classical monolith into SOA or a modular monolith. Trade-offs: low-risk and steady vs. slow; avoid migrating fake consumers. *(architecture-modernization.md)*
- **Modernization Strategy Selector (per subdomain)** - Intent: choose a strategy per subdomain on platform and product/domain axes (maintain -> lift-and-shift -> replatform; expose -> polish -> remodel -> reinvent), placing named strategies by value/risk/effort. When to use: planning modernization across a heterogeneous estate. Trade-offs: right-sized investment per area vs. requiring per-subdomain assessment; positions are typical, not fixed. *(architecture-modernization.md)*
- **Independent value stream (IVS)** - Intent: organize modern architecture around domain-aligned, outcome-oriented, team-empowered, software-decoupled value streams owned by stream-aligned teams. When to use: the target building block for modernized systems and teams. Trade-offs: autonomy and fast flow vs. requiring real domain boundaries and the funding/operating-model change to support them. *(architecture-modernization.md)*
- **Architecture Modernization Enabling Team (AMET)** - Intent: a temporary facilitating team that kickstarts modernization, sustains momentum, facilitates better design and durable change, and communicates progress, with explicit expiry conditions. When to use: to overcome inertia and keep a program on track. Trade-offs: builds trust and momentum vs. risk of becoming a permanent crutch if expiry is ignored. *(architecture-modernization.md)*
- **Assessment-before-strategy** - Intent: read the code and inventory the estate per component before choosing a strategy, converting intelligence into a prioritized plan. When to use: the prerequisite to any credible modernization plan. Trade-offs: avoids guessing vs. up-front effort (and is not the same as a waterfall project). *(architecture-modernization.md)*
- **Build vs. buy tradeoff** - Intent: decide per subdomain whether to build or buy using cost, commoditization, EOL, maintainability, and differentiation criteria. When to use: every modernization scope decision. Trade-offs: avoids both NIH and hollowing out core functions vs. the hard-to-buy reality that integration is rarely off-the-shelf. *(architecture-modernization.md)*

### Agile-enterprise patterns (Moreira 2017)

*Source file: agile-enterprise.md.*

- **Outcomes over outputs** - Intent: steer the enterprise by customer outcomes (purchase/usage) instead of delivery outputs (releases). When to use: defining success measures at every level. Trade-offs: aligns the whole org to value vs. outcomes being harder to measure/attribute than countable outputs. *(agile-enterprise.md)*
- **Agile Galaxy mapping** - Intent: map where agile processes, roles, and culture actually live to expose non-agile pockets. When to use: assessing transformation readiness/progress. Trade-offs: reveals end-to-end gaps that team metrics hide vs. needing honest org-wide visibility. *(agile-enterprise.md)*
- **Engine of Customer Value** - Intent: institutionalize the thrusters (personas, idea capture, continuous feedback, delivery, outcome data, reflection) for continuous customer engagement. When to use: building a customer-value-driven operating model. Trade-offs: keeps the org customer-anchored vs. requiring real customer channels and data. *(agile-enterprise.md)*
- **Enterprise Idea Pipeline** - Intent: route customer ideas through visualize -> prioritize (cost of delay) -> shape (Lean Canvas/feedback/story mapping) -> connect to backlogs. When to use: replacing fixed-scope intake with discovery-driven intake. Trade-offs: builds validated, prioritized value vs. an added discovery/governance layer. *(agile-enterprise.md)*
- **Cost of Delay prioritization** - Intent: sequence pipeline items by the economic cost of delaying them. When to use: allocating constrained capacity across competing ideas. Trade-offs: economically rational ordering vs. needing value/urgency estimates. *(agile-enterprise.md)*
- **Lean Canvas idea capture** - Intent: validate an idea on one page before it consumes delivery capacity. When to use: early discovery of any new idea. Trade-offs: fast falsification of weak ideas vs. being a sketch, not real customer validation. *(agile-enterprise.md)*
- **Agile budgeting** - Intent: fund incrementally toward outcomes instead of fixed annual project budgets. When to use: removing the funding model as a barrier to agility. Trade-offs: money follows value and adapts to learning vs. conflict with traditional annual finance cycles. *(agile-enterprise.md)*
- **Reinvented HR (team-based rewards, self-management)** - Intent: realign people practices to reward team-based, customer-focused behavior and support agile roles. When to use: when individual-hero rewards undermine agile teams. Trade-offs: reinforces agile behaviors vs. being a deep, slow change to entrenched HR systems. *(agile-enterprise.md)*

### Applied EA / security / unit-oriented patterns (Carter 2024; Gouigoux & Tamzalit 2024; Stevens 2025; Milchman 2025)

*Source file: applied-enterprise-architecture.md.*

- **Holistic diagram as documentation index** - Intent: one abstraction-first diagram with uniform shapes gives a shared system view and drives which detailed artifacts are needed. When to use: cross-audience communication and documentation planning. Trade-offs: clarity vs. deliberate loss of detail (must be backed by deeper docs). *(applied-enterprise-architecture.md)*
- **Urbanization (zones / quarters / blocks)** - Intent: organize the business-capability map like a city to keep functions cohesive and org-aligned. When to use: structuring an information system's functional layer; diagnosing misalignment. Trade-offs: durable business-aligned structure vs. requiring a BCM most companies must first build. *(applied-enterprise-architecture.md)*
- **Externalization of business rules / processes / authorization** - Intent: keep processes, rules, and authorization out of application code so strategy changes do not force software changes. When to use: industrializing an IS for agility. Trade-offs: agility and reuse vs. extra infrastructure (rules engines, low-code, externalized identity). *(applied-enterprise-architecture.md)*
- **Write-only data referential (then add query)** - Intent: build MDM services with a clear write side, then add query, governing key data in a dedicated MDM zone. When to use: eliminating duplicated, divergent master data. Trade-offs: single source of truth vs. up-front service design and migration. *(applied-enterprise-architecture.md)*
- **Defense in depth (layered security)** - Intent: stack multiple controls so a single failure is backed by others. When to use: any enterprise security architecture. Trade-offs: resilience to single-control failure vs. cost and complexity of layers. *(applied-enterprise-architecture.md)*
- **Zero trust architecture** - Intent: assume no implicit trust; verify every access continuously with least privilege and segmentation. When to use: distributed/cloud enterprises with a dissolved perimeter. Trade-offs: reduced lateral-movement risk vs. implementation and segmentation complexity. *(applied-enterprise-architecture.md)*
- **Security by design / minimize attack surface** - Intent: build security in from inception and remove unnecessary services/protocols/apps. When to use: every system from the start. Trade-offs: cheaper and stronger than bolt-on vs. requiring security thinking at every SDLC stage. *(applied-enterprise-architecture.md)*
- **Distributed composition** - Intent: decentralize components to operate independently. When to use: maximizing resilience, scalability, flexibility. Trade-offs: redundancy and fault tolerance vs. coordination/sync overhead and divergent-standards risk. *(applied-enterprise-architecture.md)*
- **Partitioned composition** - Intent: divide the system into distinct, non-overlapping sections. When to use: simplifying management and isolating functions/failures. Trade-offs: clarity, specialization, contained failures vs. effort duplication and cross-partition silos. *(applied-enterprise-architecture.md)*
- **Interlocked composition** - Intent: tightly link components for shared resources and close coordination. When to use: when seamless cross-part flow is paramount. Trade-offs: high efficiency/integration vs. interdependency, hard troubleshooting, cascade risk. *(applied-enterprise-architecture.md)*
- **Fused composition** - Intent: merge components into a unified whole. When to use: where the strongest cohesion is required. Trade-offs: maximal integration vs. loss of independent evolvability. *(applied-enterprise-architecture.md)*
- **Integrative core + operational periphery (armada/fleet/flotilla)** - Intent: keep a thin central integrative core for strategy/governance while operational units stay agile and locally connected (optional double-nesting). When to use: globally distributed enterprises balancing coherence and responsiveness. Trade-offs: unified direction plus local autonomy vs. nesting complexity hidden behind a flat-network appearance. *(applied-enterprise-architecture.md)*

## Domain 13 - Quality, Testing, and Verification

### Testing strategy & example design (Adzic, Evans & Roden 2015; Saini 2025)

*Source files: testing-strategy-and-practices.md, test-design-patterns.md.*

- **Shared quality pyramid** - Intent: build a multi-layered, cross-functional definition of quality (works at all / works well / usable / useful / successful) so groups stop arguing past each other. When to use: once per milestone with senior reps of each discipline. Trade-offs: high-level by design; needs facilitation and quantification of vague terms. *(testing-strategy-and-practices.md)*
- **Explore capabilities, not features** - Intent: base exploratory sessions on user capabilities to escape feature tunnel vision and find unexpected risks. When to use: exploratory testing of completed stories. Trade-offs: wider net needs the capability frame for focus; features still drive deterministic checks. *(testing-strategy-and-practices.md)*
- **Focus on key examples** - Intent: illustrate a story with a few simple, well-chosen scenarios instead of an exhaustive dump. When to use: writing acceptance criteria / executable specs. Trade-offs: demands the right abstraction; resist the false completeness of long scenario lists. *(testing-strategy-and-practices.md)*
- **Contrast examples with counter-examples** - Intent: pair each positive example with a counter-example to sharpen a rule's boundary. When to use: defining acceptance criteria. Trade-offs: more examples; exposes hidden assumptions. *(testing-strategy-and-practices.md)*
- **Describe what, not how** - Intent: write checks in business-intent terms, not UI/implementation mechanics, so they survive refactoring. When to use: acceptance/spec checks. Trade-offs: needs domain vocabulary; tests become more abstract. *(testing-strategy-and-practices.md)*
- **Given-When-Then in strict sequence / One test, one topic / Write assertions first** - Intent: keep each check single-context, single-behavior, expectation-led for readability and localized failure. When to use: any scenario-based check. Trade-offs: forces smaller tests; multi-action workflows modeled separately. *(testing-strategy-and-practices.md)*
- **Decouple coverage from purpose** - Intent: use coverage to find untested code, never to define a test's value. When to use: reasoning about suite health. Trade-offs: needs judgment; prevents coverage theater. *(testing-strategy-and-practices.md)*
- **Split just-in-case tests from key examples / Optimise for reading** - Intent: separate must-pass illustrative examples from defensive edge tests and invest in readability. When to use: managing large long-lived suites. Trade-offs: extra structure and authoring effort; large maintenance payoff. *(testing-strategy-and-practices.md)*
- **Wait for events not time; set up before async tests; provide atomic external resources; wrap sync DB tests in transactions** - Intent: testability tactics that remove flakiness and ease cleanup. When to use: async, shared-environment, or DB integration tests. Trade-offs: provisioning/setup overhead; kills major flakiness sources. *(testing-strategy-and-practices.md, test-design-patterns.md)*

### Test design & automation patterns (Saini 2025)

*Source file: test-design-patterns.md.*

- **Arrange-Act-Assert (AAA)** - Intent: give each test a clear three-phase shape. When to use: nearly every automated test. Trade-offs: discourages multi-behavior tests; minimal overhead. *(test-design-patterns.md)*
- **Data-driven testing** - Intent: run one test body over a table of input/expected pairs. When to use: a rule with many equivalence cases. Trade-offs: centralizes maintenance; keep the table focused. *(test-design-patterns.md)*
- **Keyword-driven testing** - Intent: compose tests from reusable named actions. When to use: tests authored/read by non-programmers; large repetitive flows. Trade-offs: an abstraction layer to maintain. *(test-design-patterns.md)*
- **Page Object Model (POM)** - Intent: encapsulate a screen's locators/interactions so UI tests reference intent, not selectors. When to use: any non-trivial UI automation. Trade-offs: extra classes; isolates tests from UI churn. *(test-design-patterns.md)*
- **Service / API client object** - Intent: wrap an API behind a reusable client so API tests express calls semantically and share auth. When to use: API/contract testing. Trade-offs: indirection; centralizes endpoint/auth changes. *(test-design-patterns.md)*
- **Test data builder / factory** - Intent: build valid test objects with defaults plus per-test overrides. When to use: tests needing structured domain objects. Trade-offs: a builder to maintain; removes brittle setup. *(test-design-patterns.md)*
- **Fixture (setup/teardown)** - Intent: share controlled, isolated state across tests. When to use: tests needing common setup. Trade-offs: scope choice trades speed against isolation. *(test-design-patterns.md)*
- **Test doubles - Stub / Spy / Fake / Mock** - Intent: stand in for real dependencies; stub returns fixed data, spy records interactions, fake is a lightweight working impl, mock gives full behavior/interface control. When to use: isolate the unit; simulate failures. Trade-offs: use the lightest double that isolates; over-mocking yields tests that pass while the system is broken. *(test-design-patterns.md)*
- **Service virtualization** - Intent: simulate whole complex services with realistic latency/error behavior. When to use: real service unavailable, costly, or needs fault injection. Trade-offs: tooling/config overhead; far closer to production than a bare mock. *(test-design-patterns.md)*
- **Layer-distribution patterns - Foundation-First / Layer-Specific / Balanced / Simplicity-Driven / Risk-Based / Feedback-Focused** - Intent: sequence and allocate tests across application layers. When to use: planning and growing a layered automation suite. Trade-offs: each biases coverage differently; combine rather than apply one dogmatically. *(test-design-patterns.md)*

### Formal verification techniques (Almeida, Frade, Pinto & Melo de Sousa 2026)

*Source file: formal-methods-and-verification.md.*

- **Design by contract (pre/postconditions, invariants)** - Intent: specify each routine's obligations/guarantees for runtime checking or static proof. When to use: interfaces and safety-critical code (Eiffel, SPARK, JML, ACSL). Trade-offs: disciplined annotation; runtime overhead (removable); static proof needs deductive tooling. *(formal-methods-and-verification.md)*
- **Loop invariant annotation** - Intent: supply the property preserved across iterations so a verifier can prove loops. When to use: deductive verification of non-trivial loops. Trade-offs: finding the invariant is the main intellectual cost. *(formal-methods-and-verification.md)*
- **Verification-condition generation (VCGen + SMT/proof tools)** - Intent: reduce an annotated program to first-order proof obligations dischargeable by solvers/assistants. When to use: deductive pipelines (Why3, Dafny, Frama-C, SPARK). Trade-offs: undecidable in general; failed VCs may mean a missing invariant, not a bug. *(formal-methods-and-verification.md)*
- **Model checking (temporal-logic properties)** - Intent: exhaustively verify safety/liveness of a finite-state model, yielding counterexamples. When to use: protocols, concurrency, reactive/real-time control. Trade-offs: state-space explosion; needs tractable abstraction. *(formal-methods-and-verification.md)*
- **Bounded model checking (incl. of software)** - Intent: find bugs within a fixed execution depth via SAT/SMT (CBMC, ESBMC). When to use: bug-hunting where full proof is infeasible. Trade-offs: cannot prove absence of deeper bugs beyond the bound. *(formal-methods-and-verification.md)*
- **Abstraction** - Intent: shrink an intractable model to an analyzable one preserving soundness. When to use: model checking large systems. Trade-offs: over-approximation yields spurious counterexamples. *(formal-methods-and-verification.md)*
- **Separation-logic local reasoning** - Intent: reason about heap-manipulating/concurrent programs by isolating disjoint memory. When to use: pointer-heavy structures, concurrency (Viper, Infer, VeriFast). Trade-offs: more sophisticated logic/tooling. *(formal-methods-and-verification.md)*
- **Lightweight relational modeling (Alloy)** - Intent: catch design errors early via instance/counterexample generation. When to use: requirements/design exploration before code. Trade-offs: bounded analysis - no counterexample in scope is not a full proof. *(formal-methods-and-verification.md)*

## Domain 14 - Information Architecture and UX

### Frontend architecture & UX engineering (Uluca 2024; Joshi 2025)

*Source file: frontend-architecture-and-ux-engineering.md.*

- **Router-first architecture** - Intent: design navigation, routes, and lazy-load boundaries before business logic so teams agree on screens up front and the app scales by feature. When to use: line-of-business and enterprise SPAs (Uluca's default for Angular). Trade-offs: needs discipline and early roadmap/wireframe work; avoids costly late-stage layout/navigation rework and enables parallel team ownership. *(frontend-architecture-and-ux-engineering.md)*
- **Feature module / feature-folder structure** - Intent: group related components, services, hooks, and routes by business function (not file type) into independently loadable units. When to use: any app expected to grow. Trade-offs: more up-front organization and explicit imports (esp. Angular standalone components); delivers low coupling, high cohesion, lazy-loadable bundles. *(frontend-architecture-and-ux-engineering.md)*
- **Lazy loading / code splitting** - Intent: defer downloading non-critical code until a route/component is needed, minimizing initial bundle and time-to-interactive. When to use: any app where first paint matters (53% mobile abandon at >3 s). Trade-offs: slight transition delay (mitigable via preloading); essential for scale and costly to retrofit. *(frontend-architecture-and-ux-engineering.md)*
- **Smart / presentational (container / component) split** - Intent: separate data-fetching/stateful containers from pure presentational components that render from props. When to use: views mixing data and rendering concerns. Trade-offs: more components to wire; yields reuse, testability, clean data flow. *(frontend-architecture-and-ux-engineering.md)*
- **Stateless, data-driven component** - Intent: components hold references to data but store no bookkeeping/state in instance variables. When to use: router-first Angular apps; broadly to reduce state bugs. Trade-offs: needs a shared data anchor (readonly BehaviorSubject); greatly improves predictability/testability. *(frontend-architecture-and-ux-engineering.md)*
- **Subject-in-a-service / data anchor (BehaviorSubject)** - Intent: share data across components via a reference in a singleton service exposed as an observable, syncing views without a global store. When to use: most Angular apps (REST + user input). Trade-offs: lighter than NgRx but you manage subscriptions/memory; sufficient for most apps. *(frontend-architecture-and-ux-engineering.md)*
- **Context + reducer (scoped state)** - Intent: manage shared React state without libraries by pairing Context with useReducer, splitting state and dispatch contexts to limit re-renders. When to use: medium-complexity cross-component state. Trade-offs: raw Context re-renders if not split; no devtools/middleware. *(frontend-architecture-and-ux-engineering.md)*
- **Atomic state (Jotai / Recoil)** - Intent: define each piece of state as an independent atom components subscribe to individually, with derived atoms for computed state. When to use: apps needing fine-grained reactivity and minimal re-renders. Trade-offs: another mental model/dependency; excellent render performance. *(frontend-architecture-and-ux-engineering.md)*
- **Lightweight global store (Zustand)** - Intent: Redux-like global state with a tiny API, selector subscriptions, and middleware without provider wrappers. When to use: teams wanting Redux predictability without boilerplate. Trade-offs: less ecosystem/convention than Redux; flat learning curve. *(frontend-architecture-and-ux-engineering.md)*
- **Server-state cache (React Query / SWR)** - Intent: manage remote data separately from client state with automatic caching, background refresh, and stale handling. When to use: any app with meaningful API data. Trade-offs: a layer to learn; removes manual fetch/cache bugs and respects server state's distinct lifecycle. *(frontend-architecture-and-ux-engineering.md)*
- **Atomic Design hierarchy** - Intent: compose UIs from atoms -> molecules -> organisms -> templates -> pages to build a design system rather than disconnected screens. When to use: design-system-driven products; design/dev collaboration. Trade-offs: up-front taxonomy discipline; yields consistency, reuse, shared vocabulary. *(frontend-architecture-and-ux-engineering.md)*
- **Design-system component library** - Intent: a reusable, documented, versioned set of UI components (Storybook stories, typed props, a11y notes) as the single source of UI truth. When to use: multi-team/multi-product orgs. Trade-offs: maintenance and governance; "pick one and stick to it, but avoid vendor lock-in." *(frontend-architecture-and-ux-engineering.md)*
- **Service-boundary / API client object** - Intent: hide protocol details behind a stable service interface so consumers don't know whether data comes from REST, GraphQL, or cache. When to use: any non-trivial app integrating external systems. Trade-offs: an abstraction to maintain; lets backends evolve without breaking the UI and centralizes auth/error handling. *(frontend-architecture-and-ux-engineering.md)*
- **Flux / unidirectional store (NgRx, Redux)** - Intent: single source of truth mutated only via actions and read via selectors, isolating side effects in effects/middleware. When to use: 3+ input streams, offline-first PWAs, or complex shared state needing persist/restore. Trade-offs: significant boilerplate; not the default - prefer lighter patterns until complexity is real. *(frontend-architecture-and-ux-engineering.md)*
- **Error boundary / graceful failure** - Intent: contain rendering failures to a subtree and show a fallback instead of crashing the app. When to use: around risky or data-dependent UI regions. Trade-offs: extra wrapping components; materially better resilience and UX. *(frontend-architecture-and-ux-engineering.md)*

### AI UX patterns (Nudelman & Kempka 2025)

*Source file: ux-for-ai.md.*

- **Value matrix** - Intent: assign real-world cost/benefit to each confusion-matrix outcome so design targets impact, not accuracy. When to use: any AI decision with unequal error consequences. Trade-offs: needs honest cost estimates and cross-functional input; replaces a misleading accuracy number with actionable ROI. *(ux-for-ai.md)*
- **Restating** - Intent: have the AI echo back its interpretation of input before or instead of acting. When to use: ambiguous natural-language input, especially before consequential actions. Trade-offs: adds a step; essential when false positives are costly, skippable when cheap. *(ux-for-ai.md)*
- **Auto-complete (preponing)** - Intent: suggest valid concepts/vocabulary as the user types to prevent miscommunication before it happens. When to use: query/search over known data. Trade-offs: expensive to build well; sharply reduces missed queries. *(ux-for-ai.md)*
- **Talk-back** - Intent: have the AI explain errors, ask clarifying questions, and guide exploration. When to use: complex, exploratory, conversational tasks. Trade-offs: needs a chat interface and space; far richer than passive restating. *(ux-for-ai.md)*
- **Initial suggestions** - Intent: seed the interaction with context-tuned prompts to beat the blank page. When to use: entry points of generative/query tools. Trade-offs: generic suggestions add little; value comes from tuning to data and history. *(ux-for-ai.md)*
- **Next steps** - Intent: infer and surface the likely next question after a result, using deep analysis plus click-based reinforcement learning. When to use: chat/exploration flows. Trade-offs: requires continuous retraining; sustains exploration. *(ux-for-ai.md)*
- **Regen tweaks** - Intent: provide one-click controls to regenerate creative output with variation. When to use: creative-generation (hot-model) flows. Trade-offs: only fits creative flows, not consistency-seeking ones. *(ux-for-ai.md)*
- **Guardrails** - Intent: enforce content/policy limits on AI output. When to use: any user-facing generative system. Trade-offs: never bypass-proof; once data is in the model there is no reliable access control, so isolate truly private data in a locked-down model. *(ux-for-ai.md)*
- **Confirm-before-consequential-action (value-matrix gated)** - Intent: require explicit confirmation before AI executes an action whose false positive is costly. When to use: send/pay/delete/dose and other irreversible actions. Trade-offs: friction; gate on the value matrix so cheap actions stay frictionless. *(ux-for-ai.md)*
- **Supervisor + worker agents (agentic flow)** - Intent: a reasoning agent orchestrates specialized semi-autonomous workers while the human steers via accept/reject on suggested observations. When to use: investigation, troubleshooting, multi-step research/automation. Trade-offs: autonomy reduces control and can surface wrong hypotheses; keep the human reviewing evidence and conclusions. *(ux-for-ai.md)*
- **Human-in-the-loop control over autonomous AI** - Intent: ensure humans can understand, override, and stop AI action, especially in safety-critical systems. When to use: any consequential or autonomous AI (cf. the Lion Air MCAS UX failure). Trade-offs: may slow full automation; prevents catastrophic loss of human control. *(ux-for-ai.md)*
- **Bookending / disciplined brainstorming** - Intent: rapidly diverge on AI UI ideas by borrowing from other products/domains and stopping before polish. When to use: early ideation for AI features. Trade-offs: produces rough sketches needing refinement; reliably reaches novel directions. *(ux-for-ai.md)*
- **Copilot real-estate tiering** - Intent: size the copilot surface to task importance (side panel / large overlay / full page). When to use: embedding a copilot in a SaaS product. Trade-offs: full-page surfaces dominate the host UI; match to task weight. *(ux-for-ai.md)*

### IA disciplines, systems & structures (Rosenfeld & Morville 2002; Spencer 2010; Martin 2019; Covert 2014; Wodtke & Govella 2009)

*Source files: information-architecture.md and information-architecture-practice.md.*

- **Polar bear four-systems model** - Intent: decompose any IA into organization, labeling, navigation, and search systems so each is designed deliberately. When to use: framing or auditing any information environment. Trade-offs: the four overlap (organization vs. labeling blurs); pair with the browsing-aids/search-aids/content/invisible decomposition when boundaries get fuzzy. *(information-architecture.md)*
- **Exact organization scheme** - Intent: divide content into well-defined, mutually exclusive sections (alphabetical, chronological, geographic) for known-item lookup. When to use: users know the exact term/date/place they want. Trade-offs: easy to build and unambiguous, but useless for exploration ("alphabet is for research, not discovery"). *(information-architecture.md)*
- **Ambiguous organization scheme** - Intent: group content subjectively (topical, task-oriented, audience-specific, metaphor, hybrid) to support exploratory, associative discovery. When to use: users browse to learn rather than retrieve a known item. Trade-offs: requires educated guesses that must be revisited; harder to maintain; hybrids in one menu confuse. *(information-architecture.md)*
- **Hierarchy / taxonomy structure** - Intent: organize content into familiar parent-child categories as the browsing backbone. When to use: almost always, as the starting structure. Trade-offs: balance breadth vs. depth (avoid narrow-and-deep and broad-and-shallow extremes); rigid hierarchies force single placement - mitigate with polyhierarchy. *(information-architecture.md)*
- **Database / faceted structure** - Intent: model content as records with metadata fields to enable sorting, filtering, and faceted browse (bottom-up). When to use: large, homogeneous content sets (catalogs, listings). Trade-offs: needs disciplined metadata and content modeling up front. *(information-architecture.md)*
- **Hypertext structure** - Intent: connect content by associative links rather than a master hierarchy (e.g., a wiki). When to use: evolving content of unknown final shape. Trade-offs: depends entirely on authors linking; no automatic related-content surfacing; usually reorganized once content stabilizes. *(information-architecture.md)*
- **Faceted classification (Ranganathan)** - Intent: describe content along multiple independent dimensions instead of one taxonomy ("how can I describe this?"). When to use: content with orthogonal attributes users mix-and-match (e-commerce, media). Trade-offs: requires reliable data for every facet; more modeling effort. *(information-architecture.md)*
- **Controlled vocabulary / thesaurus (synonym management)** - Intent: map variant terms to preferred terms (synonym ring -> authority file -> classification scheme -> thesaurus) to defeat language ambiguity and improve recall. When to use: search-heavy, multi-author, or regulated domains. Trade-offs: synonym rings can lower precision; full thesauri are expensive to build and govern. *(information-architecture.md)*
- **Best bets / editorial search overrides** - Intent: manually associate high-value results with ambiguous high-traffic query terms. When to use: known queries that retrieve poor automatic results. Trade-offs: manual curation; can mislead users who assume results are algorithmic. *(information-architecture.md)*
- **Global / local / contextual navigation** - Intent: layer site-wide, area-specific, and inline associative navigation so users keep orientation and onward paths. When to use: any multi-section site. Trade-offs: inconsistency between layers causes disorientation; global nav must be heavily tested. *(information-architecture.md)*
- **LATCH organization framework (Wurman)** - Intent: structure anything via Location, Alphabet, Time, Category, or Hierarchy as a reassurance that organization is never arbitrary. When to use: brainstorming organizational approaches. Trade-offs: imperfect (mixes grouping and ordering methods; omits "shape"); a springboard, not a formula. *(information-architecture.md)*
- **Focused entry points** - Intent: keep one primary structure (usually a hierarchy) but add task/audience entry points for users the main scheme fails. When to use: large sites serving diverse needs. Trade-offs: entry points need not cover all content; better than forcing task/audience as the whole structure. *(information-architecture-practice.md)*
- **Card sorting (open / closed)** - Intent: discover (open) or validate (closed) how users group and name content, revealing mental models. When to use: building or testing an organization scheme. Trade-offs: time-consuming; needs synthesis; only as good as participant selection. *(information-architecture-practice.md)*
- **Tree testing / task-based IA assessment** - Intent: validate a draft hierarchy's groups and labels by asking users where they would look for tasks, before building nav or pages. When to use: as soon as a draft IA exists; fast and cheap. Trade-offs: tests structure in isolation (no visual design) - which is also its strength. *(information-architecture-practice.md)*
- **Content inventory & audit** - Intent: list (inventory) and assess (audit) all content before designing IA so structure and content fit. When to use: any content-heavy redesign or migration. Trade-offs: full inventory is valuable but expensive - use partial inventory or qualitative audit for huge sites. *(information-architecture-practice.md)*
- **Sitemap / blueprint** - Intent: document pages and their relationships via box-and-arrow diagram, outline, or spreadsheet (using Garrett's Visual Vocabulary). When to use: communicating structure, stakeholder buy-in, migration/wireframing. Trade-offs: choose fidelity by audience; one limited artifact; never launches perfect. *(information-architecture-practice.md)*
- **Wireframe (page schematic)** - Intent: low-fidelity outline of one page's elements, relationships, and importance to build shared vision and document handoff. When to use: page-level design after structure is set. Trade-offs: easy to over/under-specify; annotation is essential since rationale is forgotten fast. *(information-architecture-practice.md)*
- **Zoning & reusable modules** - Intent: divide a page into zones by user need, then group tightly related elements into reusable modules. When to use: page-level interface design. Trade-offs: up-front reuse thinking; pays back in consistency and engineering reuse. *(information-architecture-practice.md)*
- **Seven-step sensemaking process (Covert)** - Intent: tame any information mess via Identify -> State Intent -> Face Reality -> Choose a Direction -> Measure the Distance -> Play with Structure -> Prepare to Adjust. When to use: domain-independent structuring of confusing situations. Trade-offs: non-linear; requires honest stakeholder collaboration ("design with, not for"). *(information-architecture-practice.md)*
- **Controlled vocabulary / words-you-don't-say (Covert)** - Intent: reduce linguistic insecurity by documenting preferred terms, their histories/myths/alternatives, and explicitly the terms you will NOT use. When to use: aligning multi-stakeholder language; ontology decisions. Trade-offs: labor-intensive; the "don't say" list is often more powerful than the "do say" list. *(information-architecture-practice.md)*

## Domain 15 - Documentation and Delivery Practices

### Architecture documentation (Clements et al. 2010)

*Source file: documenting-software-architecture.md.*

- **View-based documentation** - Intent: document an architecture as a set of views, each one structure for one stakeholder set, since no single view captures the whole. When to use: any non-trivial system needing communication, analysis, or maintenance. Trade-offs: more artifacts to keep consistent; each view stays tractable and serves its readers. *(documenting-software-architecture.md)*
- **Standard view template** - Intent: document every view identically (primary presentation, element catalog, context diagram, variability guide, rationale). When to use: always, once you produce more than one view. Trade-offs: upfront template agreement; pays back in navigability and completeness. *(documenting-software-architecture.md)*
- **Three viewtypes (module / C&C / allocation)** - Intent: cover static code structure, runtime structure, and mapping to environment. When to use: as the menu from which you select needed views. Trade-offs: too many views waste effort, too few leave concerns unaddressed. *(documenting-software-architecture.md)*
- **View packet** - Intent: hand each stakeholder only the slice of a view they need, with navigation links to related packets. When to use: large views that would be one unreadable diagram. Trade-offs: fragmentation and link upkeep; avoids overwhelming readers. *(documenting-software-architecture.md)*
- **Context diagram** - Intent: bound a view's scope by showing what is inside vs outside and how they connect. When to use: every view. Trade-offs: minimal cost; prevents scope confusion. *(documenting-software-architecture.md)*
- **Variability guide** - Intent: document variation points so a product/config can be tailored without re-reading the design. When to use: product lines, configurable platforms, plug-in architectures. Trade-offs: extra section; indispensable when variation is real. *(documenting-software-architecture.md)*
- **Mapping between views** - Intent: record how elements correspond across views so readers see one whole. When to use: whenever two views share elements. Trade-offs: a table/rule to maintain; restores the unity view separation breaks. *(documenting-software-architecture.md)*
- **Architecture Decision Record (ADR)** - Intent: capture each significant decision with issue, alternatives, choice, and consequences as durable rationale. When to use: decisions that are costly, contested, unusual, or hard to reverse. Trade-offs: discipline to write as decisions are made; pays back as external memory and fewer re-litigated debates. *(documenting-software-architecture.md)*
- **Active design review** - Intent: drive an architecture review with questions reviewers must answer (exercising the document), not passively scan. When to use: serious architecture evaluations. Trade-offs: harder to author questions and find experts; surfaces far more defects. *(documenting-software-architecture.md)*

### Technical documentation (Corleissen et al. 2021; Wieteska 2025)

*Source file: technical-documentation.md.*

- **Audience persona** - Intent: distill research into a representative reader so every writing decision can be checked against a real goal. When to use: start of any docs effort. Trade-offs: needs real research to avoid fiction; prevents writing for an imagined reader. *(technical-documentation.md)*
- **Friction log** - Intent: walk a real task and record every confusion point to expose doc and product gaps. When to use: before/after writing and on every new feature. Trade-offs: time to do honestly; yields the most actionable gap list available. *(technical-documentation.md)*
- **Four content types (Divio/Diataxis)** - Intent: match document structure to reader intent - learn (tutorial), do (how-to), look up (reference), understand (conceptual). When to use: planning a docs set; diagnosing a do-everything doc. Trade-offs: requires splitting mixed docs; produces focused, maintainable content. *(technical-documentation.md)*
- **Escape hatch** - Intent: signal a misrouted reader they are in the wrong place and point them elsewhere. When to use: prerequisites/intros of procedural docs. Trade-offs: minimal; reduces wasted time. *(technical-documentation.md)*
- **Generated reference from annotated source** - Intent: keep API/config reference in sync by generating it from in-code annotations. When to use: any API surface that changes with the code. Trade-offs: tooling and annotation discipline; eliminates drift. *(technical-documentation.md)*
- **Docs-as-code** - Intent: author docs in Markdown, version with the code, review via PRs, publish via pipeline. When to use: any org already using Git/CI. Trade-offs: writers learn the toolchain; docs stay current and contributable. *(technical-documentation.md)*
- **Metric cluster** - Intent: judge doc quality from a correlated set of signals plus qualitative feedback, not one number. When to use: measuring doc effectiveness. Trade-offs: more to collect/reason about; avoids misleading single-metric conclusions. *(technical-documentation.md)*

### Version control and delivery (Mishra 2024; Wieteska 2025)

*Source file: version-control-and-delivery.md.*

- **Feature-branch workflow** - Intent: isolate each unit of work on its own branch and integrate via PR. When to use: most team development. Trade-offs: branch management overhead; enables independent review and parallel work. *(version-control-and-delivery.md)*
- **Short-lived branches / integrate often** - Intent: keep branches alive only briefly to avoid divergence. When to use: always, regardless of branching model. Trade-offs: frequent merging and strong CI needed; eliminates big-bang merge conflicts. *(version-control-and-delivery.md)*
- **Fork-and-pull-request** - Intent: contribute to a repo you do not own by forking, changing, and proposing via PR. When to use: open-source and cross-team contribution. Trade-offs: extra upstream-sync step; enables safe outside contribution. *(version-control-and-delivery.md)*
- **Small, focused pull request** - Intent: one PR addresses one concern for clean review and integration. When to use: every change. Trade-offs: more PRs to manage; faster reviews, easier tracing, fewer escaped bugs. *(version-control-and-delivery.md)*
- **Atomic commit** - Intent: one self-contained change per commit. When to use: always. Trade-offs: more frequent committing and selective staging; clean history, easy revert and bisect. *(version-control-and-delivery.md)*
- **Conventional commit message (subject/body/footer)** - Intent: structured, imperative-mood message recording the why and linking issues. When to use: every commit. Trade-offs: discipline to write well; durable, searchable history. *(version-control-and-delivery.md)*
- **Code review as collaboration** - Intent: critique the code, give context, reinforce standards, learn both ways. When to use: every PR. Trade-offs: reviewer time; higher quality and shared knowledge. *(version-control-and-delivery.md)*
- **CI on every pull request** - Intent: run automated build/tests on each PR so broken changes never merge. When to use: any repo with tests. Trade-offs: pipeline upkeep and runner cost; protects main. *(version-control-and-delivery.md)*
- **GitOps (Git as single source of truth)** - Intent: drive infrastructure and deployment from version-controlled desired state reconciled automatically. When to use: cloud-native/IaC environments needing auditability and fast rollback. Trade-offs: tooling and cultural shift; strong reliability, recovery, compliance. *(version-control-and-delivery.md)*
- **Infrastructure as Code** - Intent: define infrastructure as versioned code for consistency and repeatability. When to use: any non-trivial environment. Trade-offs: upfront codification; reproducible, reviewable infrastructure. *(version-control-and-delivery.md)*
- **Immutable infrastructure** - Intent: replace rather than mutate deployed infrastructure. When to use: with IaC/GitOps pipelines. Trade-offs: rebuild cost; eliminates configuration drift. *(version-control-and-delivery.md)*
