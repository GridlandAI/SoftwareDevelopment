# Formal Methods and Verification

**Domain:** 13 - Quality, Testing, and Verification
**Primary sources:** Rigorous Software Development - An Introduction to Program Verification, 2nd ed. (Almeida, Frade, Pinto & Melo de Sousa, 2026)

## Overview
Formal methods are a mathematical approach to software reliability: instead of sampling the input space the way testing does, they reason about the *complete* set of data and configurations a system can encounter. Where testing yields confidence proportional to coverage, verification - when it succeeds - yields a proof that a property holds for all executions. That power comes at a cost in expertise, effort, and tool maturity, which is why formal methods historically lived in safety-critical niches and only recently became practical for wider industrial use as tools matured.

This topic covers the landscape Almeida and colleagues lay out: what specification and verification mean, the families of formal methods (model-based and algebraic specification, model checking, deductive verification, theorem proving and proof assistants), design by contract, Hoare logic and verification-condition generation, the lightweight-versus-heavyweight distinction, and when formal methods pay off relative to testing.

## Core concepts

**Specification.** A model of a system describing its desired behavior - *what* is to be implemented, not *how*. It may be fully abstract (a description of behavior) or operational (behavior implied by the model). The central problem of formal methods splits into two parts: (1) *model validation* - does the specification capture the intended behavior? and (2) the *specification-implementation relation* - does an implementation actually behave as the specification says, established either by construction or by verification (a formal proof)?

**Verification vs. validation.** Verification asks "did we build the system right" (against the spec); validation asks "did we specify the right thing." Almeida's two sub-problems map onto exactly this pair.

**Invariants.** A property that must hold in all reachable states (state-based view) or for all admissible data (algebraic view) throughout a system's evolution. Invariants are the workhorse of correctness arguments. In deductive verification they reappear as *loop invariants*; in state machines they are the standard way to prove *safety* properties.

**Safety and liveness.** *Safety* properties say "nothing bad ever happens" (often: certain states are never reached - e.g., two threads never in a critical section together); they are typically proved via invariants. *Liveness* properties say "something good eventually happens" (progress toward a goal); defined over infinite executions and expressed in temporal logic. Not all safety properties are invariants - temporal ordering constraints need temporal logic.

**Transition systems and state machines.** The operational backbone of most formal models: a set of states plus transitions between them. Finite state machines, finite automata, Petri nets (for concurrency), timed automata (clocks), and hybrid automata (other physical quantities) are progressively richer members of this family used to model reactive, concurrent, distributed, and real-time systems.

**Why testing is not enough (the motivating contrast).** Testing feeds representative data and compares outputs, but the value space is usually immense or infinite, so exhaustive testing is impractical; coverage gives only relative confidence. Formal methods reason over the whole data space, which is precisely what lets them guarantee rather than sample (Almeida, Ch. 1).

## Frameworks & models

**Lightweight vs. heavyweight formal methods.** A central taxonomy by ease of use and automation. *Lightweight* methods need little deep expertise and are largely automatic (e.g., Alloy's bounded analysis, SMT-backed checkers, static analyzers); they trade some power and completeness for accessibility. *Heavyweight* methods (interactive proof assistants, full deductive verification of functional correctness) are more powerful and fine-grained but less automatic and demand specialist skill - reserved for areas where the cost is justified.

**Specification styles.**
- **Model-based / state-based specification** focuses on internal state and how operations modify it. Languages: B Method (abstract machines with machine invariants and internal consistency, tools Atelier B, ProB, Rodin/Event-B), Z and VDM (set-theoretic), abstract state machines (Gurevich's evolving algebras).
- **Algebraic / axiomatic specification** focuses on data and the relations among operations.
- **Declarative / relational specification** models systems as sets and relations: Alloy (signatures and relations, analyzed by the Alloy Analyzer via model-instance generation), well suited to early-stage modeling, rapid prototyping, and exploring designs.

**Model checking.** An automatic technique for verifying finite-state systems (especially concurrent ones). Safety and liveness properties are written in temporal logic; efficient symbolic algorithms traverse the entire state space; if a property fails, a *counterexample* is produced. *Explicit* model checking enumerates states (good for irregular software state spaces); *symbolic* model checking represents state sets compactly with structures like BDDs (good for large regular spaces like hardware). The fundamental limit is *state-space explosion* - the graph grows exponentially. Mitigations: *abstraction* (a simplified model that preserves soundness but may introduce spurious counterexamples) and *bounded model checking* (BMC), which explores executions up to a fixed depth using SAT/SMT solvers. Tools: SPIN (explicit), nuSMV/nuXmv (symbolic), UPPAAL (timed), PRISM (probabilistic), TLC (for TLA+). *Bounded Model Checking of Software* (BMCSW) applies this to source code: CBMC, ESBMC, 2LS, FuSeBMC - effective at finding bugs (assertion violations, memory errors, overflows) but cannot in general prove full correctness because of the bound.

**Theorem proving and proof assistants.**
- **Automated theorem provers / SMT solvers** (Z3, cvc5, Yices2, Alt-Ergo, MathSAT5) provide decision procedures for theories over integers, reals, arrays, bit-vectors, lists, etc. They can reason about infinite sets via techniques like induction. They are the proof engines behind most modern verifiers.
- **Proof assistants** (Rocq/Coq, Agda, Lean, Isabelle) use highly expressive, undecidable logics (higher-order/type theory). Proofs are built interactively via *tactics*; the resulting proof term is independently type-checked, which underpins proof-carrying code. Two design philosophies: define-your-own object logic (Isabelle) vs. one integrated foundational language (Rocq, Agda, Lean). Automated and interactive proving can be combined (as in the B Method's discharge of leftover lemmas).

**Deductive verification and design by contract.**
- **Design by contract** annotates routines with *preconditions* (must hold on entry) and *postconditions* (guaranteed on exit), pioneered by Eiffel with *runtime assertion checking*: the compiler injects checks; once validated, the program can be recompiled without them. Many languages now have a contracts layer: SPARK (a safe Ada subset for safety-critical systems, with both runtime and static checking), JML for Java, ACSL for C, Gospel for OCaml.
- **Deductive verification** goes further than runtime checking: it uses logic to prove that *all* possible executions conform to the contracts. It is *not* fully automated (verifying arbitrary contracts is undecidable), so users supply annotations - notably loop invariants. The standard architecture is a *Verification Conditions Generator (VCGen)* that turns an annotated program into first-order proof obligations (verification conditions), plus one or more proof tools (automated or interactive) that discharge them; the program is correct w.r.t. its spec iff all VCs are valid. Tools grounded in this tradition: Why3 (WhyML + many provers, also an intermediate verifier), Dafny (verification-aware language over Boogie + Z3), Viper (permission-based reasoning for concurrent/heap programs), Frama-C (C analysis with runtime and deductive plug-ins), KeY/Krakatoa/ESC-Java (Java).

**Hoare logic and separation logic.** *Hoare logic* is the semantic foundation of deductive verification: behavior is specified with *Hoare triples* {P} C {Q} - if precondition P holds and command C runs (and terminates), postcondition Q holds. A calculus of inference rules (including the assignment and consequence rules) lets one derive triples; verification conditions are synthesized from this calculus, with loop invariants supplied by the user. *Separation logic* extends Hoare logic to reason about mutable shared memory (pointers, dynamic data structures); its separating conjunction (`*`) asserts that two assertions hold for disjoint heap regions, enabling *local reasoning*. It powers Viper and analyzers like Infer, Smallfoot, and VeriFast, and integrates into higher-order frameworks (Iris) within proof assistants.

**Refinement, extraction, execution.** Three routes from spec to implementation: *refinement* progressively transforms a specification into code preserving correctness (B, Event-B); *extraction* derives executable code from constructive proofs in a proof assistant; *execution* runs an executable specification directly.

**Lifecycle integration.** The V life-cycle (common in critical-software industry) pairs each descending design stage with an ascending validation stage. The *Balzer life cycle* explicitly inserts formal methods - requirements analysis, formal model/specification, functional prototype, then implementation derived from model and prototype - and can be integrated "downward" into the V model. Industrial standards (e.g., CENELEC EN 50128 with SIL safety-integrity levels) can *require* formal methods at the highest assurance levels.

## Patterns / techniques (intent; when to use; trade-offs)

- **Design by contract (pre/postconditions, invariants)** - Intent: specify each routine's obligations and guarantees so they can be checked at runtime or proved statically. When to use: interfaces and modules where correctness matters; safety-critical code. Trade-offs: writing good contracts takes discipline; runtime checking adds overhead (removable after validation); static proof needs deductive tooling and annotations.
- **Loop invariant annotation** - Intent: supply the property preserved across loop iterations so a verifier can prove loops. When to use: deductive verification of any non-trivial loop. Trade-offs: finding the right invariant is the main intellectual cost of deductive verification.
- **Verification-condition generation** - Intent: mechanically reduce an annotated program to first-order proof obligations dischargeable by SMT solvers or proof assistants. When to use: deductive verification pipelines (Why3, Dafny, Frama-C, SPARK). Trade-offs: undecidable in general; failed VCs may reflect a missing invariant rather than a real bug.
- **Model checking with temporal-logic properties** - Intent: exhaustively verify safety/liveness of a finite-state (often concurrent) model and get a counterexample on failure. When to use: protocols, concurrency, reactive/real-time control. Trade-offs: state-space explosion; needs a tractable abstraction.
- **Bounded model checking (incl. of software)** - Intent: find bugs within a fixed execution depth using SAT/SMT. When to use: bug-hunting in C/C++/other code where full proof is infeasible. Trade-offs: cannot prove absence of deeper bugs beyond the bound.
- **Abstraction** - Intent: shrink an intractable model to an analyzable one that preserves soundness. When to use: model checking large systems. Trade-offs: over-approximation yields spurious counterexamples (refinement loop needed).
- **Separation-logic local reasoning** - Intent: reason about heap-manipulating and concurrent programs by isolating disjoint memory regions. When to use: pointer-heavy/dynamic data structures, concurrency. Trade-offs: more sophisticated logic and tooling.
- **Lightweight relational modeling (Alloy)** - Intent: catch design errors early by generating instances/counterexamples of a relational model. When to use: requirements/design exploration before code. Trade-offs: bounded analysis - absence of a counterexample within scope is not a full proof.

## Principles & best practices

- **Reason over the whole space, not samples,** when a property must truly always hold - that is the unique value formal methods add over testing (Almeida, Ch. 1).
- **Match weight to need.** Use lightweight, automatic methods broadly (static analyzers, SMT-backed checkers, Alloy); reserve heavyweight interactive proof for the highest-assurance components.
- **Specify before deriving.** A formal specification clarifies hidden ambiguities and can be animated/prototyped to validate intent before implementation effort.
- **Let invariants carry the argument.** Both state-machine safety proofs and loop-based deductive proofs hinge on finding the right invariant.
- **Use the implementation as the spec basis where possible.** Annotation-based verification (contracts in the source) is increasingly seen as the practical solution to the central problem, because the real code - not a separate model - is what gets verified.
- **Treat adoption as a methodological shift.** Almeida stresses formal-methods adoption is strategic, not just tool procurement: it changes how teams think, manage, and produce software, and must integrate with existing practice and budget.

## Anti-patterns & pitfalls

- **Confusing coverage with correctness.** 100% coverage means all parts were exercised by *some* test, not that the program is correct.
- **Expecting full automation from deductive verification.** It is undecidable in general; missing annotations (especially loop invariants) stall proofs and look like failures.
- **Ignoring state-space explosion.** Naive model checking of a large or infinite-state system will not terminate usefully without abstraction or bounding.
- **Reading a bounded result as a guarantee.** BMC and Alloy analysis only cover a finite depth/scope; no counterexample found ≠ proved correct.
- **Adopting heavyweight methods without expertise or justification.** Cost and skill requirements make them appropriate only where the assurance need (and often a standard) justifies them.

## Decision guidance

- **Testing vs. verification:** if a property must hold for *all* inputs (memory safety, a security/access invariant, a critical numeric computation, a concurrency safety property), prefer verification; for broad behavioral confidence under change, testing remains the pragmatic default (see testing-strategy-and-practices.md).
- **Which verification family:** finite-state/concurrent/protocol properties -> model checking (symbolic for regular spaces, explicit for irregular software state). Functional correctness of source code against contracts -> deductive verification (Why3/Dafny/Frama-C/SPARK). Deep mathematical properties or trusted-kernel guarantees -> proof assistants. Early design-error hunting -> lightweight relational modeling (Alloy) or BMC.
- **How much rigor:** let the assurance need and any governing standard (e.g., SIL level under EN 50128) set the bar; apply heavyweight proof only to the critical core and lighter methods around it.
- **Runtime vs. static contracts:** start with runtime assertion checking (cheap, catches violations in tested executions); escalate to static deductive verification where you need a guarantee over all executions.

## Recent developments (2024-2026)

- **LLM-guided theorem proving reaches competition-grade results.** Specialized systems generating formally verified Lean proofs (e.g. Aristotle, Seed-Prover) achieved gold-medal-level performance on the 2025 International Mathematical Olympiad problems with machine-checked solutions, not just English answers, marking a step change in automated/interactive proving. Reported benchmark gains include systems such as HILBERT reaching ~99.2% on miniF2F and ~70.0% on PutnamBench. (VentureBeat, 2025: https://venturebeat.com/ai/lean4-how-the-theorem-prover-works-and-why-its-the-new-competitive-edge-in)
- **LLMs supplying proof hints for auto-active verification.** The miniF2F-Dafny benchmark (Dafny 2026 / POPL 2026) translated the miniF2F reasoning benchmark to Dafny: Dafny's automation verifies 40.6% of the test set with empty proofs, and for the remainder LLMs were evaluated as proof-hint generators, the best reaching 55.7% pass@4. This shows the source's VCGen-plus-prover architecture increasingly augmented by LLMs that draft the annotations (notably loop invariants) users must otherwise supply. (arXiv, 2025: https://arxiv.org/pdf/2512.10187 ; POPL 2026: https://popl26.sigplan.org/details/dafny-2026-papers/16/)
- **Verified program synthesis benchmarks.** New benchmarks and frameworks evaluate end-to-end "vericoding" (formally verified program synthesis), including VeriBench and AlphaVerus, a self-improving framework that translates programs from Dafny to Verus and uses verifier feedback, extending the deductive-verification toolchain (Why3/Dafny/Frama-C/SPARK) with AI-in-the-loop generation. (VeriBench: https://openreview.net/pdf?id=rWkGFmnSNl ; vericoding benchmark, 2025: https://arxiv.org/pdf/2509.22908)
- **Formal verification as a guardrail for AI reasoning.** A 2025 framework (Safe) uses Lean4 to verify each step of an LLM's chain-of-thought by translating claims into Lean4 and checking the proof, an application of formal methods to constrain AI rather than the reverse, complementing this file's "reason over the whole space" rationale. (VentureBeat, 2025: https://venturebeat.com/ai/lean4-how-the-theorem-prover-works-and-why-its-the-new-competitive-edge-in)
- **Foundations stable; tooling more automated.** The lightweight/heavyweight taxonomy, model checking, deductive verification, Hoare and separation logic, design by contract, and the testing-vs-verification boundary in the source remain accurate; the 2024-2026 development is LLM assistance in writing specifications, invariants, and proofs, plus the new role of provers like Lean/Dafny as checkers of AI-generated reasoning and code. The undecidability limits and the need for human-supplied (or human-validated) annotations still hold.
