# Microservices Implementation Patterns (Cross-Stack Realization)

**Domain:** 05 - Architecture Patterns and Styles
**Primary sources:** .NET Microservices: Architecture for Containerized .NET Applications (de la Torre, Wagner & Rousos, 2022); Microservices Design Patterns in .NET, 2nd Edition (Williams, 2025); Microservices with Spring Boot and Spring Cloud, 2nd Edition (Larsson, 2021); Microservices Design Patterns with Java (Seroukhov, 2024)

## Overview

The microservice pattern *language* (decomposition, sagas, CQRS, API gateway, circuit breaker, and so on) is documented in `microservices-patterns-catalog.md` after Richardson and Newman. This file is deliberately different: it captures **how those concerns are actually realized** by the two dominant enterprise stacks (the JVM with Spring Boot / Spring Cloud, and .NET with ASP.NET Core), plus the language-agnostic framing the Java- and platform-oriented books add. The point of view is the practitioner who has already decided to build microservices and now must wire up service discovery, an edge server, externalized configuration, resilience, and observability without reinventing each one.

A useful organizing insight from Larsson is that every cross-cutting concern is a *design pattern* with a stated problem, solution, and solution requirements, and that each pattern can be implemented by more than one **software enabler**: an application framework (Spring Boot, ASP.NET Core), a framework-plus-services layer (Spring Cloud, Steeltoe, Dapr), a container orchestrator (Kubernetes), or a service mesh (Istio, Linkerd). The same logical pattern (say, service discovery) is implemented at the language/library level by Eureka, at the platform level by Kubernetes Services, and at the mesh level by Envoy sidecars. Choosing *where* a concern lives - in application code, in a sidecar, in the platform, or in the mesh - is the central implementation decision, and the answer shifts the operational burden between application teams and platform teams.

## Core concepts

- **The concern can live at four layers.** Library (in-process, e.g., Resilience4j or Polly), sidecar (out-of-process companion, e.g., Dapr or Envoy), platform (orchestrator primitives, e.g., Kubernetes Services / ConfigMaps / probes), and mesh (cross-cutting data plane). Most concerns can be satisfied at more than one layer; pushing a concern down the stack frees application code but adds infrastructure to operate (Larsson; Williams).
- **Production readiness is the real driver.** Spring Boot or ASP.NET Core alone gets you a service; the Spring Cloud / Dapr / mesh layer is what makes a *landscape* of services scalable, robust, configurable, secure, and resilient (Larsson). Failures must be treated as the normal state, not the exception.
- **Client-side vs server-side routing.** In client-side discovery the caller's library queries the registry and picks an instance (Eureka + Spring Cloud LoadBalancer). In server-side routing a reverse proxy / platform component does it on the caller's behalf (Kubernetes kube-proxy + Service, mesh ingress). The same pattern, two realizations (Larsson; Seroukhov).
- **Synchronous chains are the dominant failure amplifier.** Long chains of blocking HTTP calls re-create a "distributed monolith" - one slow dependency drains thread pools and cascades. Both stacks therefore push reactive/non-blocking I/O and async messaging, and wrap any remaining synchronous calls in resilience policies (de la Torre; Larsson; Williams).
- **W3C Trace Context and OpenTelemetry are converging the tracing story.** Dapper begat OpenTracing/OpenCensus, which merged into OpenTelemetry; modern stacks propagate `traceparent`/`tracestate` headers automatically and export OTLP to backends like Jaeger, Zipkin, or Prometheus (Larsson; Williams).

## Frameworks & models

- **The "design pattern → enabler" matrix (Larsson).** Larsson's mapping is the cleanest cross-stack reference. Service discovery → Eureka + Spring Cloud LoadBalancer / Kubernetes Service / Istio. Edge server → Spring Cloud Gateway / Kubernetes Ingress / Istio ingress gateway. Central configuration → Spring Cloud Config / Kubernetes ConfigMaps + Secrets. Circuit breaker → Resilience4j / mesh outlier detection. Distributed tracing → Sleuth + Zipkin / Jaeger. Control loop → Kubernetes controller managers. Centralized logging → EFK (Elasticsearch, Fluentd, Kibana). The lesson: a given concern is often satisfiable by the platform you already run, so do not add a library if Kubernetes or the mesh already covers it.
- **The microservice chassis / template (Seroukhov; Richardson).** A chassis is a set of templates and boilerplate bundling the recommended cross-cutting patterns so each new service starts production-ready: standard component structure, externalized configuration, sync + async communication, interface versioning, error propagation, observability (logging + metrics), automated tests, and packaging into a deployable unit (Docker image, servlet, or function). Seroukhov notes template engines (T4, StringTemplate) drift out of date quickly; an alternative is to nominate one or two "golden standard" services and clone-and-adapt them. .NET Aspire's `ServiceDefaults` library is a concrete modern chassis: a shared library exposing `AddServiceDefaults()` and `MapDefaultEndpoints()` that wires OTel, health checks, service discovery, and Polly resilience identically across every service (Williams).
- **Spring Cloud's evolution model.** Spring Cloud began (2015) as a wrapper around Netflix OSS - Eureka (discovery), Ribbon (client load balancer), Zuul (edge), Hystrix (circuit breaker) - plus a config server and Spring Security OAuth. As Netflix froze features, Spring replaced them: Hystrix → Resilience4j, Hystrix Dashboard/Turbine → Micrometer + monitoring, Ribbon → Spring Cloud LoadBalancer, Zuul → Spring Cloud Gateway. By the Ilford release (2020.0.0) the only remaining Netflix component is Eureka. The model to internalize: pick the *current* enabler, not the historically famous one (Larsson).
- **Dapr building blocks (Williams; Seroukhov).** Dapr is a portable sidecar exposing uniform HTTP/gRPC APIs for service invocation, pub/sub, state, secrets, bindings, and telemetry. Code calls `localhost` endpoints (`/v1.0/invoke/...`, `/v1.0/publish/...`, `/v1.0/state/...`); the sidecar handles discovery, retries with backoff, circuit breaking, mTLS, trace-context propagation, and integration with Redis/Kafka/Service Bus/Cosmos/Key Vault via YAML-defined **components**. Because the API is language-neutral, teams pick any stack without re-coding cross-cutting concerns.

## Patterns

### Service discovery and load balancing

- **DNS-based round-robin (rejected baseline)** - Intent: resolve a logical name to a list of instance IPs. When to use: almost never for volatile microservice instances. Trade-offs: DNS clients pin to one working IP rather than rotating per request, carry no health checks, and store only IPs (no ports/metadata); instances that crash linger in records. Larsson demonstrates this failing empirically. *(Larsson ch. 9; Seroukhov ch. 4)*
- **Discovery server (registry) with client-side discovery** - Intent: a registry tracks live instances and their full connection metadata; the client's library fetches the list and load-balances locally. When to use: when you want round-robin and failover without a separate proxy hop. Realization: Netflix Eureka with `DiscoveryClient`/`LoadBalancerClient` abstractions and Spring Cloud LoadBalancer; instances send heartbeats, clients cache the registry and pick instances round-robin. Spring also has `DiscoveryClient` implementations for Consul and ZooKeeper. Trade-offs: rich metadata and health-aware routing; ties clients to the registry; requires the registry itself to be highly available. *(Larsson ch. 8–9; Seroukhov ch. 4)*
- **Self-registration** - Intent: a service registers itself with the discovery server at startup (heartbeats keep it alive). When to use: when the same team owns services and consumers, so coupling to the registry is acceptable. Realization: Eureka client dependency + `eureka.client.serviceUrl` config. Trade-offs: no external tooling needed; couples the service to the infrastructure and needs explicit register/deregister steps. *(Seroukhov ch. 4)*
- **Server-side discovery / platform routing** - Intent: a platform component routes to instances so the caller needs no discovery library. Realization: Kubernetes `Service` + kube-proxy (a stable virtual IP/DNS name fronting the pods), or a mesh's data plane. Trade-offs: zero client coupling and language neutrality; the platform must own health and load balancing. Larsson explicitly contrasts this with Eureka and notes Kubernetes can replace Eureka entirely. *(Larsson ch. 16–17; Seroukhov)*
- **Available discovery enablers** - Eureka (Spring/AWS), etcd (Kubernetes' own store), Consul (HashiCorp), ZooKeeper (Apache), Nomad. None are standardized, so each ties clients to its API. *(Seroukhov ch. 4)*

### Edge server / API gateway realization

- **Spring Cloud Gateway** - Intent: a single reactive (non-blocking, Project Reactor / Spring 5) edge server that hides internal services, routes by URL path, terminates TLS, and integrates with Spring Security OAuth2/OIDC to protect APIs and propagate caller identity downstream. When to use: the default Spring edge server (replacing the older blocking Netflix Zuul v1, which handled fewer concurrent connections). Trade-offs: high concurrency at the edge and clean OAuth integration; another component to operate. *(Larsson ch. 8, 10–11)*
- **Ocelot** - Intent: a lightweight open-source .NET API gateway co-deployed with your services (Docker, Kubernetes). When to use: simpler .NET gateways needing routing, JWT auth, caching, rate limiting, request aggregation, transformations, and Polly-based retry/circuit-breaker policies, with upstream/downstream route config in JSON. Trade-offs: full control in-stack; if it grows custom C# it risks becoming a monolithic aggregator. de la Torre uses Ocelot in eShopOnContainers and recommends splitting it per client/business boundary. *(de la Torre ch. 4; Williams ch. 11)*
- **YARP (Yet Another Reverse Proxy)** - Intent: a .NET *middleware library* (not a standalone server) that turns an ASP.NET Core app into a configurable, extensible reverse proxy with routes→clusters→destinations defined in `appsettings.json`. When to use: when you want native, transport-level reverse proxying with C# extension points and you do not yet need business-aware gateway features (JWT validation, quota enforcement, aggregation). Trade-offs: minimal overhead and complete routing control; "good but not great" for gateway concerns, so teams often layer Ocelot or a managed gateway on top. *(Williams ch. 11)*
- **Managed gateway (Azure API Management) and other products** - Intent: offload gateway *and* management (insights, metering, security, rate limits, response caching) to a PaaS product. When to use: large production estates where a single "thin" gateway with no custom code is acceptable. Trade-offs: less monolith risk because there is no custom C# to bloat; vendor coupling and cost. Apigee, Kong, MuleSoft, WSO2 occupy the same space; Linkerd/Istio provide ingress at the mesh layer. *(de la Torre ch. 4)*
- **Backend for Frontend (BFF)** - Intent: one gateway per client form factor (mobile, web), each exposing an API tailored to that client and aggregating internal calls. When to use: multiple client types with divergent needs. Trade-offs: avoids one bloated gateway and reduces chattiness for remote (mobile/SPA) clients; more gateways to run. Both de la Torre and Williams treat the gateway and BFF as the same pattern viewed per-client. *(de la Torre ch. 4; Williams ch. 11)*

### Externalized configuration

- **Centralized configuration server** - Intent: store all services' configuration in one place, per-environment (dev/test/qa/prod), with hierarchical common + service-specific files and encryption of secrets. Realization (Spring): Spring Cloud Config backed by Git, filesystem, Vault, or JDBC; it detects changes and pushes refresh notifications over Spring Cloud Bus (RabbitMQ/Kafka) so affected services reload without redeploy. Realization (platform): Kubernetes ConfigMaps + Secrets. Trade-offs: single source of truth and live refresh; the config server and its backend become critical infrastructure. *(Larsson ch. 8, 12; Seroukhov chassis)*

### Resilience (the resilience library as a pattern bundle)

Both stacks ship a single resilience library implementing several patterns; the patterns themselves (circuit breaker, retry, timeout, bulkhead, rate limiter) are documented in the catalog, so here is how each library realizes them.

- **Resilience4j (JVM)** - Bundles **circuit breaker** (classic closed→open→half-open state machine, with configurable failure threshold/window and a half-open probe), **rate limiter** (cap requests per period), **bulkhead** (cap concurrent calls so one dependency cannot exhaust shared resources), **retry** (for random/transient faults only), and **time limiter** (bound waiting on slow dependencies). It integrates with Spring Boot Actuator so circuit state is observable at `/actuator/health`, and emits Micrometer metrics (e.g., `resilience4j_retry_calls`). Larsson stresses retry must target idempotent, transient failures and pairs with the circuit breaker to avoid retry storms. *(Larsson ch. 8, 13)*
- **Polly (.NET)** - Provides Retry, Circuit Breaker, Bulkhead Isolation, Timeout, and Fallback policies in a fluent, thread-safe API, wired into outgoing HTTP via `IHttpClientFactory` and `AddPolicyHandler` (the `Microsoft.Extensions.Http.Polly` package). `IHttpClientFactory` also solves socket exhaustion and stale-DNS problems of naively shared `HttpClient`. de la Torre's guidance: retries with **exponential backoff** plus **decorrelated jitter** (`Backoff.DecorrelatedJitterBackoffV2`) to avoid synchronized retry spikes, and a circuit breaker as the "defense barrier" so retries do not become a self-inflicted DoS on a failing service. The Typed Client (Service Agent) pattern pre-configures an `HttpClient` per downstream service. *(de la Torre ch. 7; Williams ch. 10)*
- **Caching as a resilience layer** - Intent: serve a cached response when a downstream is slow or down. When to use: read-mostly data tolerant of staleness, behind a gateway or in the caller. Trade-offs: improves availability and latency; risks stale reads and cache-invalidation complexity. *(Williams ch. 10)*

### Distributed tracing and observability realization

- **Correlation ID + trace tree / spans** - Intent: tag every request and message in a flow with a common correlation ID (`TraceId`) and identify each unit of work as a span (`SpanId`) so logs and latency can be reconstructed across services (Dapper model). Realization (Spring): Spring Cloud Sleuth generates and propagates IDs, decorates log records, and ships spans to Zipkin (preferably asynchronously over RabbitMQ/Kafka to avoid runtime coupling to the tracing backend). Realization (.NET): OpenTelemetry instrumentation (`AddAspNetCoreInstrumentation`, `AddHttpClientInstrumentation`) exporting OTLP to Jaeger/Zipkin; Dapr auto-propagates W3C trace context and generates spans for invoke/pub-sub/state. *(Larsson ch. 8, 14; Williams ch. 16)*
- **Centralized logging** - Intent: stream structured logs to stdout, tagged with the correlation ID, collected into a searchable store. Realization: EFK stack (Elasticsearch + Fluentd + Kibana) on the JVM side; Serilog + Seq on the .NET side. Requirement: a canonical log format so collectors can normalize across services. *(Larsson ch. 19; Williams ch. 15)*
- **Centralized monitoring and alarms** - Intent: collect per-instance resource and app metrics, including from autoscaled instances, and alert on thresholds. Realization: Micrometer/Prometheus + Grafana (JVM), OpenTelemetry metrics → Prometheus (.NET). *(Larsson ch. 1, 20; Williams ch. 16)*
- **Health checks** - Intent: expose an endpoint reporting whether the instance and its dependencies are healthy so orchestrators route traffic only to ready instances. Realization (.NET): `Microsoft.Extensions.Diagnostics.HealthChecks` with `AddHealthChecks()` and `MapHealthChecks("/hc")`, extended by `AspNetCore.Diagnostics.HealthChecks` for dependency probes and a UI. Realization (platform): Kubernetes **liveness** (restart if dead) and **readiness** (withhold traffic until ready) probes - note Larsson's tip to expose health on a separate management port so mesh metrics are not polluted by probe traffic. *(de la Torre ch. 7; Larsson ch. 17–18; Williams ch. 1)*

### Sidecar and service mesh realization

- **Sidecar** - Intent: run cross-cutting functionality (discovery, retries, logging, encryption, telemetry) in a companion process beside the service, interacting over a backward-compatible interface. When to use: to augment existing services without changing their code, especially across heterogeneous languages. Trade-offs: low risk of breaking the service, real-time updates, language independence; extra CPU/memory per sidecar and added local latency. Dapr is the canonical multi-language sidecar. *(Seroukhov ch. 3; Williams ch. 16)*
- **Service mesh** - Intent: delegate all service-to-service traffic concerns to a dedicated network layer of sidecar proxies (data plane, e.g., Envoy) configured by a control plane: mTLS/zero-trust, automatic retries with backoff, load balancing, traffic shaping (canary/A-B), service discovery, and uniform observability (Prometheus/Jaeger). When to use: regulated or large estates needing consistent, code-free security and observability and advanced deployment strategies. Trade-offs: consistency and zero-trust for the whole ecosystem versus roughly doubled container count, a control plane to operate and upgrade, added latency per hop, and harder triage (service vs proxy vs control-plane config). Implementations: Istio (Envoy-based, feature-rich on Kubernetes), Linkerd (lightweight), Consul Connect, Open Service Mesh. Istio injects proxies automatically into namespaces labeled `istio-injection: enabled`. *(Williams ch. 16; Larsson ch. 18; Seroukhov ch. 3)*
- **Development-time orchestration (.NET Aspire)** - Intent: a single app model (`AppHost`) plus shared `ServiceDefaults` library and a live dashboard that wires logging, OTel, health checks, discovery, and Polly resilience consistently and brings up the whole service graph (plus Redis/Postgres/RabbitMQ) for local dev. When to use: to give developers a "cockpit" with uniform telemetry without hand-wiring each service. Trade-offs: dramatically smoother local dev and a consistent chassis; it is a dev-time layer, not a production deployment target (you still ship to AKS/ACA/Kubernetes). *(Williams ch. 16)*

## Principles & best practices

- **Prefer the enabler you already operate.** If you run Kubernetes, its Services, ConfigMaps/Secrets, and probes already cover discovery, configuration, and health; do not bolt on Eureka or a config server unless you need their extra metadata or live-refresh (Larsson).
- **Pick current components, not famous ones.** Use Resilience4j over Hystrix, Spring Cloud Gateway over Zuul v1, Spring Cloud LoadBalancer over Ribbon (Larsson).
- **Always combine timeout + retry-with-jitter + circuit breaker.** Each alone is insufficient; together they fail fast, avoid retry storms, and prevent self-inflicted DoS (de la Torre; Larsson).
- **Retry only idempotent, transient faults**, with exponential backoff and jitter, and a bounded count (de la Torre; Larsson).
- **Trace context must be standardized.** Use W3C Trace Context / OpenTelemetry so spans cross language boundaries without business-code changes; export tracing asynchronously to avoid coupling services to the tracing backend (Larsson; Williams).
- **Codify a chassis.** Standardize structure, config, communication, error propagation, observability, tests, and packaging so new services start production-ready; "golden standard" services age better than template engines (Seroukhov). `ServiceDefaults` is the modern .NET embodiment (Williams).
- **Stream logs to stdout in a canonical format, tagged with the correlation ID** (Larsson).
- **Use a separate management/health port** so probe and metric traffic do not pollute mesh observability (Larsson).

## Anti-patterns & pitfalls

- **Distributed monolith via synchronous chains.** Long request/response chains of HTTP calls re-create a monolith over the network; one slow link drains thread pools and cascades. Minimize sync chains; prefer async messaging or async HTTP polling decoupled from the original request (de la Torre; Williams; Seroukhov).
- **Single bloated API gateway / aggregator.** A gateway that aggregates all internal services accretes custom code and couples everything, violating service autonomy. Segregate by client (BFF) and business boundary; keep managed gateways "thin" (de la Torre; Williams).
- **Careless retries → self-inflicted DoS.** Retrying a slow/failing service from many clients exponentially increases its load; always gate retries with a circuit breaker (de la Torre).
- **DNS round-robin for discovery.** Clients pin to one IP, no health checks, no metadata; unsuitable for volatile instances (Larsson; Seroukhov).
- **Overlapping resilience layers.** Running Dapr *and* a service mesh duplicates retries/mTLS/traffic-shaping; decide which layer owns which behavior (Williams).
- **Sidecar/mesh as default.** For small or simple systems the sidecar/mesh's CPU, memory, latency, and operational cost outweigh the benefit; resilient HTTP clients or minimal middleware suffice (Williams).
- **Distributed monolith via monorepo coupling.** Shared code referenced without versioned dependencies, monolithic build/deploy, and broad multi-component commits couple service lifecycles (Seroukhov).
- **Shared library breaking changes.** Modifying a shared library breaks dependents; mitigate with full backward compatibility (well tested) or namespace/version-suffixed releases (Seroukhov).

## Decision guidance

- **Where should a concern live?** Default to the platform if you already run Kubernetes (discovery, config, health, basic load balancing). Add a library (Resilience4j/Polly, Spring Cloud Config) when you need richer behavior or live refresh inside the app. Add a sidecar (Dapr) when you need uniform cross-cutting APIs across multiple languages without re-coding. Add a mesh (Istio/Linkerd) when you need fleet-wide mTLS, traffic shaping, and uniform observability and can afford the control plane. Do not stack mesh + Dapr for the same concern.
- **Client-side vs server-side discovery?** Client-side (Eureka + LoadBalancer) when one team owns callers and services and wants rich metadata; server-side (Kubernetes Service / mesh) for language neutrality and zero client coupling.
- **Gateway choice (.NET).** YARP for pure, extensible reverse proxying in C#; Ocelot for an in-stack gateway with auth, rate limiting, aggregation, and Polly resilience; managed (APIM) for large estates wanting management features and minimal custom code; split per client (BFF) and business boundary regardless of product.
- **Resilience defaults.** Wrap every synchronous call with timeout + exponential-backoff-with-jitter retry (idempotent/transient only) + circuit breaker; add bulkhead to isolate critical dependencies; add caching/fallback for read-mostly paths.
- **Observability baseline.** Correlation ID on every flow, structured stdout logs in a canonical format, OpenTelemetry traces (async export) to Jaeger/Zipkin, metrics to Prometheus/Grafana, and orchestrator liveness/readiness probes on a dedicated management port.

## Recent developments (2024–2026)

- **Sidecar-less "ambient" service mesh shifted the where-does-the-concern-live decision.** Istio's ambient mode (ztunnel for L4 + waypoint proxies for L7) reached production maturity, delivering mesh mTLS, telemetry, and routing without injecting a sidecar per pod, cutting per-pod resource overhead and the operational tax that made meshes hard to justify for smaller estates. KubeCon 2026 added ambient multicluster and a Gateway API Inference Extension (mesh features aimed at AI/agent traffic). This directly updates the file's four-layer "library vs sidecar vs platform vs mesh" model: the mesh layer is now cheaper to adopt. (Cloud Native Now 2026; ambientmesh.io; Solo.io)
- **OpenTelemetry + OTLP became the convergence point the file predicted.** Istio 1.20+ exports traces directly via OTLP (superseding Zipkin/Jaeger-specific formats), and the W3C Trace Context + OTel propagation story the file describes is now the default across Spring Cloud Sleuth's successor (Micrometer Tracing) and .NET. Telemetry from Envoy/ztunnel can be stitched with application spans for full request visibility. (istio.io; OpenTelemetry blog 2024; OneUptime 2026)
- **.NET Aspire's `ServiceDefaults` is now a concrete, mainstream chassis.** The file already cites Aspire; by 2025-2026 it is the standard .NET answer for wiring OTel, health checks, discovery, and Polly resilience uniformly, plus Podman support and a Docker-Desktop-free local dev loop. Dapr integration with Aspire is officially documented. (The New Stack; Microsoft Learn Aspire/Dapr docs)
- **Spring Cloud continued its "pick the current enabler" trajectory.** The Netflix-OSS replacement story (Hystrix to Resilience4j, Ribbon to Spring Cloud LoadBalancer, Zuul to Spring Cloud Gateway, with only Eureka remaining) is fully settled; modern Spring Boot 3.x on Spring Framework 6 leans on Micrometer Observation/Tracing and OTel rather than Sleuth, and increasingly defers discovery/config/mTLS to Kubernetes + mesh. (Larsson's mapping, validated by 2025 ecosystem state)
- **Platform engineering reframed the layer choice organizationally.** The 2025-2026 platform-engineering movement makes "push the concern to the platform/mesh, owned by a platform team" the default posture for large estates, reinforcing the file's lesson that choosing where a concern lives shifts burden between app and platform teams. (The New Stack 2025-2026)
