# Modern Data Architecture

**Domain:** 08 - Data Architecture and Engineering
**Primary sources:** Data Management at Scale, 2nd ed. (Strengholt, 2023); Modern Data Architecture in AI (Choudhury, Puchakayala & Badlani, 2025)

## Overview
Modern data architecture extends the classic foundations (system of record, modeling layers, warehouse) to a world of cloud elasticity, decentralized ownership, real-time integration, and AI/ML workloads. The two forces reshaping it are scale and analytics fragmentation: enterprises are saddled with outdated centralized architectures (a single monolithic enterprise data warehouse, or a centralized data lake that becomes a swamp) that cannot keep pace with the speed of software delivery, the cloud, privacy/security demands, the need to integrate operational and analytical systems, and collaboration across ecosystems. The dominant response is to move data closer to the business through domain ownership while still providing platforms, contracts, metadata, and governance that make distributed data trustworthy and reusable.

Strengholt supplies the enterprise-scale operating model: organizing data by domains (data mesh) backed by data fabric metadata, treating data as a product, separating read-optimized from write-optimized stores (CQRS), and binding it all with data contracts, federated governance, a metadata "metalake," and modern master data management. Choudhury et al. supply the AI/ML and infrastructure layer: lakehouse storage, data versioning and lineage, feature stores, distributed training and model serving, MLOps, privacy-preserving AI, and the data demands of LLMs and generative AI. Together they describe how to choose and run a data architecture at scale for both analytics and AI.

## Core concepts

**Read-optimized vs. write-optimized (CQRS).** Operational commands (writes) and analytical queries (reads) are fundamentally different operations and should be served by separate models. A durable write performs many steps (storage allocation, metadata retrieval, record finding, locking, verification, commit, index update); reads need far fewer. Command Query Responsibility Segregation (CQRS) splits them into two models kept in sync via events. Benefits: independent technology choice and scaling for each side, per-use-case read models, different consistency models, and protecting the busy transactional system from intensive reads. Every read from a replica, data warehouse, data lake, materialized view, or operational data store (ODS) is a form of CQRS. The future model: at least one read-optimized data store per application whenever others read its data intensively. (Strengholt)

**Data domains and domain ownership.** Setting boundaries for ownership is the most important act in architecture. Using domain-driven design, a **bounded context** sets the logical boundary of a domain's solution space; boundaries are explicit and enforced where cohesion is high. Domains take roles: **source-system-aligned (data providers)** and **consumer-aligned (data consumers)**, sometimes both. Each application has a data store, each application's data is unique (so a transformation is always required when moving data between applications - the "data integration dilemma"), and the authoritative origin of any datum is its **golden source** (system of record). Fix data quality at the golden source. (Strengholt)

**Data as a product, and the data product.** "Data as a product" is a mindset: data owners treat consumers as customers and ship well-shaped, documented, SLA-backed data, not a byproduct. A **data product** (Dehghani's "architectural quantum") is the smallest independently deployable node of the mesh. Strengholt argues against gluing code + data + metadata + infrastructure into one container (it complicates lineage, security, ownership, and duplication); instead define a data product as an **autonomous logical entity** that describes data meant for consumption, with references to physical, read-optimized assets - technology-agnostic, semantically consistent, possibly with multiple physical shapes. Below it sit data elements (atomic units linking to physical/technical metadata). (Strengholt)

**Integration architecture and cross-domain interoperability.** Moving data across domains uses two families of patterns: **data distribution** (publishing read-optimized data products for analytical reuse) and **application integration** (APIs and events for operational, low-latency exchange). API management evolves from classic SOA/ESB toward a federated model: API gateway, API-as-a-product, composite/experience APIs, API contracts, GraphQL and backend-for-frontend. Event-driven architecture distributes notifications vs. carried-state events through brokers and streaming platforms, with event stores doubling as data-product stores or application backends ("turning the database inside-out"). (Strengholt)

**Metadata-driven architecture and the metalake.** Metadata "binds everything together" - validating integrity, routing/replicating, transforming, and knowing the meaning of data all rely on it. A **metalake** is a unified repository of all metadata (business, technical, operational, lineage, quality), enabling discovery, lineage, observability, and democratization. Its components: a **data catalog** (inventory of metadata, often weak alone - lacking automated enforcement, integrations, and pushing a vendor's worldview), a **knowledge graph** (real-world concepts and relationships linking sources into a network), and a **data marketplace** (self-service portal driving consumption). The next-gen architecture is a hybrid of **data mesh** (decentralized ownership) and **data fabric** (intelligent, metadata-driven automation). (Strengholt)

**Data lakehouse and AI-era storage.** The lakehouse combines the flexibility/scale of data lakes (schema-on-read, raw and unstructured data, cheap object storage) with the reliability/performance of warehouses (schema-on-write, ACID, fast queries). Open table formats - **Delta Lake** and **Apache Iceberg** - add ACID transactions, schema enforcement, time travel (query historical versions), and optimized indexing on top of object storage. A common best practice is a hybrid: raw data in the lake, curated high-value data in the warehouse. (Choudhury et al.)

**Data versioning and lineage.** Versioning datasets (like code, via Git/DVC) ensures reproducibility, accountability, and rollback. **Lineage** traces a datum's origin and transformations end-to-end (sources, transformations, dependencies, usage, output destinations), captured via workflow tools (Airflow, Kubeflow), data catalogs (Collibra, Alation, Apache Atlas), and frameworks with built-in lineage (Spark, Flink). Both are essential for AI reproducibility, debugging, bias-source identification, and regulatory audit. (Choudhury et al.)

**Feature stores.** Centralized repositories that store and serve ML features for both **offline** (training) and **online** (low-latency inference) use, ensuring training/inference consistency and feature reuse across models. They commonly integrate versioning, lineage, and model-registry links (e.g., Feast). (Choudhury et al.)

**MLOps.** DevOps applied to the ML lifecycle: version control (code, data, models), CI/CD for model deployment, automated testing (code, data validation, model accuracy), monitoring for model/data drift with feedback loops, and governance/compliance. Tooling: MLflow (experiment tracking, model registry), Kubeflow (Kubernetes-native pipelines), TensorFlow Extended (TFX), Amazon SageMaker. (Choudhury et al.)

**Data for LLMs and generative AI.** LLMs need enormous, diverse, high-quality datasets (Common Crawl, Wikipedia, books) with heavy preprocessing (deduplication, normalization, tokenization, filtering). They impose distributed object storage (S3, GCS), versioning/metadata/lineage, distributed training (data and model parallelism, parameter-server vs. all-reduce, TPUs, mixed precision), scalable serving (SageMaker, Azure ML, edge/CDN for low latency), and MLOps-driven CI/CD. Generative AI (GANs, VAEs, diffusion) adds synthetic-data generation and novel storage/processing needs. (Choudhury et al.)

## Frameworks & models

**Domain topologies (managing problem spaces).** A spectrum from fully decentralized to centralized, chosen by an organization's maturity and constraints: fully federated, governed, partially federated, value-chain-aligned, coarse-grained, coarse-grained-and-partially-governed, and centralized. Pick the topology that matches how much autonomy vs. control the organization can sustain. (Strengholt)

**Landing-zone topologies (managing solution spaces).** How domains map to cloud technology footprints: single data landing zone, source/consumer-aligned landing zones, hub landing zone, multiple data landing zones, multiple data-management landing zones. (Strengholt)

**Federated data governance framework.** Governance is unique per organization but rests on defined roles: **chief data officer** (strategy/vision), **data owner / trustee** (accountable for data, quality, definitions, classifications), **application owner / data custodian** (maintains the application and interfaces, access control), **business user**, **data user**, **data creator**, **data steward** (enforces policies/standards, domain SME). Data owner and application owner are deliberately split (applications are shared; correcting data quality vs. building pipelines are different skills). The model is federated domain teams plus a centralized governance team, captured in a living framework of roles, responsibilities, policies, standards, and working instructions. (Strengholt)

**Data contracts.** A formal agreement between provider and consumer specifying what data may be consumed, for what purpose, with what guarantees (SLA/SLO, uptime, error rates, versioning, deprecation, interface compatibility, quality, scope, usage/privacy limits). Often implemented as a metadata record (using stable GUIDs, not file paths), embedded in metadata-driven ingestion/quality frameworks, validated with tools like Great Expectations or dbt test, and gated by provider/consumer handshakes (e.g., sign-off via pull request). Data contracts anchor **data observability** (freshness, integrity, volume, lineage, quality). (Strengholt)

**Master data management styles.** Reference data (codes, classifications, hierarchies) and master data (core enterprise entities) are managed differently. MDM implementation styles - **registry**, **consolidation**, **coexistence**, and **centralized/transactional** - are not mutually exclusive (start registry, move to coexistence; different styles per dataset). Choose by organizational/data need, not technology. Modern, domain-oriented MDM distributes via the same integration backbone: APIs/events/state stores (NoSQL, ML-augmented matching) for low-latency operational paths; the data-product architecture for higher-latency analytical paths (and feed MDM from the same data products consumers use, to avoid inconsistency). Ask domains to conform their data products to centrally managed reference data. (Strengholt)

**Privacy-preserving AI techniques.** Differential privacy (statistical noise), federated learning (train across devices/orgs without centralizing raw data), homomorphic encryption (compute on encrypted data), secure multi-party computation (split computation so no party sees the full dataset), and anonymization/pseudonymization. Choose by data sensitivity and regulatory need; embed across development, training, and deployment. (Choudhury et al.)

**AI data governance framework.** Spans the data lifecycle: governance policies (ownership/stewardship, classification, access/usage), data-quality management (profiling, cleansing, metrics), security/privacy (encryption, RBAC, masking/anonymization, zero-knowledge proofs), regulatory compliance (GDPR, CCPA, HIPAA; audits, DPIAs, record-keeping), metadata management, and ethical AI (bias detection/mitigation, transparency/explainability, accountability). Implemented via stakeholder engagement, governance committees, training, tooling, and continuous improvement. (Choudhury et al.)

## Patterns

**CQRS / read replica as data product** - Intent: serve intensive reads from a separate, read-optimized copy synced from the write store via events. When to use: any application whose data is read intensively by others; the basis of data-product architectures. Trade-offs: independent scaling/technology, protects transactional systems, supports multiple read models; adds a sync layer, latency, and complexity. (Strengholt)

**Data product as a logical entity** - Intent: describe consumable data as a technology-agnostic logical entity referencing read-optimized physical assets, keeping metadata separate from data. When to use: distributing data across domains at scale where the same semantic data has multiple physical shapes. Trade-offs: clean ownership, lineage, security, and flexibility; requires a metamodel and discipline vs. the simpler "everything in one container" view. (Strengholt)

**Domain-oriented decentralization (data mesh)** - Intent: assign data ownership to domain teams, treat data as a product, provide self-serve infrastructure and federated governance. When to use: large organizations where centralized platforms have become bottlenecks. Trade-offs: agility, scalability, and accountability close to the business; needs strong governance, contracts, and metadata or it fragments. (Strengholt; Choudhury et al.)

**Data fabric (metadata-driven automation)** - Intent: use a metalake (catalog + knowledge graph + ML) to automate discovery, lineage, quality, classification, and delivery across a distributed estate. When to use: complement to a mesh, to add the intelligence the mesh lacks. Trade-offs: enables self-service and observability at scale; significant metadata-management investment and cultural change. (Strengholt)

**Data contract** - Intent: a versioned, machine-checkable agreement guaranteeing interface compatibility, SLAs, and usage/privacy terms between provider and consumer. When to use: any popular, widely consumed data product in a distributed architecture. Trade-offs: detects breaking changes, decouples teams, adds transparency; requires schema-validation tooling and handshake workflows. (Strengholt)

**Lakehouse with open table format** - Intent: ACID transactions, schema enforcement, and time travel on cheap object storage (Delta Lake / Iceberg), unifying lake flexibility with warehouse reliability. When to use: AI/analytics estates needing both raw and curated data with reproducibility. Trade-offs: one platform for storage/processing/analytics, reproducible historical queries; table-format and engine lock-in considerations, optimization/maintenance overhead. (Choudhury et al.)

**Feature store** - Intent: centralize and serve ML features for offline training and online inference. When to use: multiple models reusing features, needing training/inference consistency. Trade-offs: reuse, consistency, integrated versioning/lineage; another platform to operate and keep in sync. (Choudhury et al.)

**Partitioning + indexing for AI workloads** - Intent: split datasets (horizontal/sharding, vertical, time-based) and index (B-tree, bitmap, inverted, spatial) to enable parallelism and fast retrieval. When to use: large-scale training, cross-validation, scalable inference, time-series AI. Trade-offs: faster queries and parallel processing; index maintenance overhead, data-skew/hotspot risk, requires adaptive strategies as workloads evolve. (Choudhury et al.)

**Federated learning / privacy-preserving compute** - Intent: train across distributed data sources without centralizing raw data (plus differential privacy, homomorphic encryption, SMPC). When to use: edge devices, cross-organization collaboration, regulated/sensitive data. Trade-offs: privacy and compliance with collaboration; added cryptographic/coordination complexity and potential accuracy/latency cost. (Choudhury et al.)

## Principles & best practices
- Capture only unique data, always directly from the golden source; fix data-quality issues there. (Strengholt)
- Treat data as a product with defined shapes, interfaces, refresh cycles, and SLOs; process, cleanse, shape, and (de)normalize before exposing it. No raw data; don't conform to a single consumer; keep semantic consistency. (Strengholt)
- Separate the concerns of managing data from managing technology; keep data products technology-agnostic. (Strengholt)
- Always start onboarding new data by defining an owner; don't share data without clear ownership. (Strengholt)
- Standardize the data-pipeline framework across domains while keeping control and responsibility with the domains; keep the framework and contract metadata under central governance. (Strengholt)
- Implement robust governance to prevent data swamps in lakes; adopt a hybrid (raw in lake, curated in warehouse); optimize with caching, indexing, partitioning. (Choudhury et al.)
- Automate versioning and lineage as part of CI/CD; link dataset versions to model versions in the registry for reproducibility. (Choudhury et al.)
- Apply MLOps: version everything, automate testing of data and models, monitor for drift, build governance and explainability in from the start. (Choudhury et al.)
- Bake privacy and compliance (GDPR/CCPA/HIPAA) across the lifecycle, not as an afterthought; classify data by sensitivity and apply encryption, RBAC, and masking accordingly. (Choudhury et al.)
- Combine mesh (ownership) and fabric (metadata intelligence) - the next-gen architecture is a hybrid. (Strengholt)

## Anti-patterns & pitfalls
- **Centralization pain** - a single monolithic EDW or a centralized data lake becomes a bottleneck and an integration tax; the "distributed big ball of mud" appears when many services/domains couple directly without boundaries. (Strengholt)
- **Gluing code + data + metadata + infrastructure into one data-product container** - overcomplicates lineage, security, ownership, and duplication; metadata and data should be managed from separate viewpoints. (Strengholt)
- **Point-to-point MDM connections** - connecting the MDM hub directly to providers/consumers risks inconsistency; feed MDM from the same data products consumers use. (Strengholt)
- **Treating a data catalog as the whole solution** - catalogs lack automated enforcement and integrations and push a vendor's worldview; position the catalog as one component in a broader metadata architecture. (Strengholt)
- **Data swamps** - lakes without schema, governance, or quality discipline become disorganized and unusable; raw-only querying is slow and resource-intensive. (Choudhury et al.)
- **Ignoring lineage, versioning, and bias** - undermines reproducibility, auditability, and fairness; biased or noisy training data produces poor, discriminatory models. (Choudhury et al.)
- **Model drift left unmonitored** - models degrade as data and behavior shift; without monitoring and feedback, accuracy silently decays. (Choudhury et al.)
- **Skew from poor partition keys** - creates hotspots and reduced performance in distributed AI systems. (Choudhury et al.)

## Decision guidance
- **Read vs. write optimization:** keep the transactional (command) store ACID and optimized for writes; create at least one read-optimized store (replica, materialized view, data product) per application whenever others read it intensively. Tune consistency per read model; scale read and write sides independently.
- **How decentralized to go:** match the domain topology to organizational maturity - start governed or partially federated and move toward fully federated as domains gain capability; fall back to centralized where regulation or low maturity demands it. Pair mesh ownership with fabric metadata automation so decentralization doesn't fragment the estate.
- **Storage choice:** use a lakehouse (Delta/Iceberg) when you need both raw and curated data with ACID and reproducibility; keep a hybrid where curated, high-value structured data lives in a warehouse for BI and raw/unstructured data lives in the lake for ML training. Choose object storage (S3/GCS) as the scalable backbone for large training datasets and model artifacts.
- **Integration style:** distribute analytical data via read-optimized data products; use APIs/events for operational, low-latency exchange. For MDM, use APIs/events/state stores on critical low-latency paths and the data-product architecture for higher-latency analytical paths.
- **Governance binding:** enforce data contracts on widely consumed products to detect breaking changes and decouple teams; split data-owner and application-owner roles; run federated domain governance under a central framework; anchor observability (freshness/integrity/volume/lineage/quality) to the contracts.
- **AI/ML data:** centralize features in a feature store for reuse and training/inference consistency; automate versioning and lineage in CI/CD and link them to the model registry; apply MLOps (MLflow/Kubeflow/TFX/SageMaker) for reliable, monitored, compliant pipelines; choose privacy-preserving techniques (federated learning, differential privacy, homomorphic encryption, SMPC) by data sensitivity and collaboration need; for LLMs, plan for enormous diverse high-quality preprocessed corpora, distributed training, and scalable low-latency serving.

## Recent developments (2024–2026)

- **Open table formats converged on interoperability, reshaping the lakehouse layer.** Databricks acquired Tabular (Iceberg's creators) in June 2024; Delta UniForm now exposes Iceberg-compatible metadata, and Iceberg has become the de facto multi-engine standard. The contest moved from format to catalog (Snowflake's open-source Polaris vs. Databricks Unity Catalog). This validates this file's "lakehouse with open table format" pattern while shifting the lock-in question to the metadata/catalog layer. (The New Stack, 2024, https://thenewstack.io/snowflake-databricks-and-the-fight-for-apache-iceberg-tables/; Snowflake Engineering Blog, 2025, https://www.snowflake.com/en/engineering-blog/apache-polaris-supports-iceberg-delta-lake/)
- **"Data mesh as the prerequisite for trustworthy AI" became the dominant business case.** Thoughtworks' 2026 state-of-data-mesh review frames clean, owned, contract-backed data products as the foundation for production-grade AI/ML, and shipped a Data Mesh Accelerator update (Nov 2025) with standardized data-product-contract templates for hybrid cloud. This extends the mesh+fabric+contracts model in this file directly toward AI. (Thoughtworks, "The state of data mesh in 2026," 2026, https://www.thoughtworks.com/insights/blog/data-strategy/the-state-of-data-mesh-in-2026-from-hype-to-hard-won-maturity)
- **Data contracts matured into machine-readable governance objects.** They increasingly bundle schema, quality expectations, SLAs, lineage, ownership, and policy enforcement into one framework, reinforcing the contract-anchored observability described here. (OvalEdge, "Data Contract in Data Mesh," 2025, https://www.ovaledge.com/blog/data-contract-in-data-mesh)
- **The semantic / metrics layer became the governed bridge between data and AI agents.** dbt's Semantic Layer (built on MetricFlow, open-sourced under Apache 2.0) went GA in 2025, and the dbt MCP server now exposes governed models, metrics, and lineage as Model Context Protocol tools that AI agents can call. Snowflake and others launched the Open Semantic Interchange (OSI) as a cross-vendor metric standard. (AtScale, "State of the Semantic Layer: 2025 in Review," 2025, https://www.atscale.com/blog/semantic-layer-2025-in-review/; dbt Developer Blog, "Introducing the dbt MCP Server," 2025, https://docs.getdbt.com/blog/introducing-dbt-mcp-server)
- **Vector storage consolidated back into mainstream databases.** Rather than standalone vector stores, 2025-2026 saw relational/operational engines add native vector indexing (pgvector on PostgreSQL, DiskANN vector search in Cosmos DB), letting embeddings sit beside transactional data with ACID guarantees, an evolution of the feature-store/AI-data thread in this file. (DataCamp, "Best Vector Databases 2026," 2026, https://www.datacamp.com/blog/the-top-5-vector-databases; Microsoft Fabric Blog, "GA of Cosmos DB in Microsoft Fabric," 2025, https://blog.fabric.microsoft.com/en-US/blog/announcing-ga-of-cosmos-db-in-microsoft-fabric-and-cosmos-db-mirroring/)
- **AI-augmented data management went mainstream.** Industry surveys report a strong majority of organizations adopting AI-assisted data management, with quality/observability tooling moving from rule-based checks toward systems that learn distributions, detect drift, and surface root causes automatically. (lakeFS, "The State of Data and AI Engineering 2025," 2025, https://lakefs.io/blog/the-state-of-data-ai-engineering-2025/)
