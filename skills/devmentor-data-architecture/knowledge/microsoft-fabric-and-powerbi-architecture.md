# Microsoft Fabric and Power BI Architecture

**Domain:** 08 - Data Architecture and Engineering
**Primary sources:** Architecting Power BI Solutions in Microsoft Fabric (Venkatesan, 2025); Pro Power BI Architecture (Rad, 2018); Implementing Analytics Solutions Using Microsoft Fabric - DP-600 Study Guide (Makhija and Odunukwe, 2025); Learn Microsoft Fabric (Ali and Schacht, 2024)

## Overview

Microsoft Fabric is a software-as-a-service (SaaS) analytics platform that unifies the full analytics lifecycle - ingestion, storage, transformation, serving, data science, real-time intelligence, and reporting - into a single tenant with one shared storage layer (OneLake) and one billing model (capacity units). Power BI is one workload inside Fabric, focused on semantic modeling and visualization. Before Fabric, an end-to-end analytics solution required provisioning, securing, monitoring, and paying for many separate Azure services (Data Factory, Data Lake, Synapse SQL pools, Databricks, Analysis Services). Fabric collapses those into integrated experiences over a common lake, eliminating most data copying between engines.

This topic matters because BI and analytics are where the software development lifecycle meets the business: design decisions about storage mode, intermediate data stores, semantic modeling, security, and governance directly determine report performance, data trustworthiness, cost, and the degree of self-service an organization can safely allow. The recurring architectural theme is decoupling - storage from compute, semantic models from reports, and development from production - and choosing, per scenario, how much control central IT retains versus how much it delegates to functional teams.

## Core concepts

**Power BI components.** Power BI Desktop is the free Windows authoring tool where you connect to data, transform it with Power Query, build a semantic model (tables, relationships, calculated columns, DAX measures), and design visuals. The Power BI Service (powerbi.com) is the cloud home where content is published, collaborated on, and distributed via workspaces. Supporting components include the on-premises data gateway (a bridge for private/on-prem data sources), paginated reports (pixel-perfect printable reports built in Report Builder), Power BI Report Server (limited on-prem service), dataflows (cloud-based Power Query that lands transformed data in Azure Data Lake), and scorecards/goals (KPI tracking). (Venkatesan, 2025)

**Semantic model (dataset).** The center of every Power BI solution: the in-memory tabular model of tables, relationships, and measures that reports query via DAX. Data is stored columnar and compressed by the VertiPaq engine. Getting the semantic model right (storage mode, modeling, security, refresh) drives the quality of every report built on it. (Venkatesan, 2025)

**Storage / connectivity modes.** How a semantic model relates to its source data:
- **Import** - data is copied into the model and stored in OneLake/Azure Storage; fastest performance; data is only as fresh as the last refresh.
- **DirectQuery** - no data stored in the model; queries are translated to the source query language at interaction time; always-fresh data, slowest performance, source-dependent.
- **Live connection** - the report connects to an already-published semantic model or Analysis Services model; performance equals whatever that model uses.
- **Composite model** - mixes Import and DirectQuery per table (e.g., small dimensions imported, large fact tables in DirectQuery).
- **Direct Lake** - Fabric-only mode where the Power BI engine reads Delta-Parquet files natively from a lakehouse/warehouse, giving near-Import performance with DirectQuery freshness and no refresh schedule. (Venkatesan, 2025)

**OneLake and OneCopy.** OneLake is Fabric's single, tenant-wide data lake built on ADLS Gen2, supporting the same APIs/SDKs as existing ADLS Gen2 applications. Every workspace is a container; every data item is a folder hierarchy. OneCopy means every Fabric compute engine (Spark, SQL, Power BI) reads and writes the same data, eliminating the data silos and duplication created when developers each provision isolated storage. (Ali and Schacht, 2024)

**Open Delta Lake format.** Every Fabric engine reads/writes the open-source Delta Lake format by default. Standardizing on one open format (Delta-Parquet) prevents the need to copy data from a lakehouse into a warehouse or vice versa, avoids vendor lock-in, and lets Spark, SQL, and Power BI all operate on a single physical copy. (Ali and Schacht, 2024)

**Shortcuts.** OneLake shortcuts are references to data in other locations (other lakehouses, other workspaces, external ADLS Gen2, or Amazon S3) without copying. They create a data virtualization layer, making OneLake a multi-cloud lake and enabling data mesh architectures across business domains. (Ali and Schacht, 2024)

**Lakehouse vs. warehouse.** Both store data as Delta-Parquet and suit analytics. A **lakehouse** is Spark-centric: data engineers load and transform with notebooks (PySpark, Scala, SparkSQL, R), pipelines, or dataflows; it exposes a read-only SQL analytics endpoint. A **warehouse** is T-SQL-centric: it supports full read/write SQL (SELECT/INSERT/UPDATE/DELETE, DDL) over an MPP engine with separated compute and storage. Choose by team skillset - T-SQL teams pick warehouse, Spark teams pick lakehouse - since capabilities are otherwise similar. (Venkatesan, 2025; Ali and Schacht, 2024)

**Capacity units (CUs).** Fabric capacity (F-SKUs, F2–F2048) provides the compute for all workloads in a workspace, measured in CUs per second. F64 = 64 CUs/sec. Capacities are assigned to workspaces (not users), can be paused to stop billing, and decouple compute from workload so each project/department can have its own capacity and avoid contention. (Venkatesan, 2025)

## Frameworks & models

**Storage-mode decision tree.** Venkatesan frames storage-mode selection as a nine-question decision tree. Key drivers, in order of typical importance: (1) high performance required → Import or Live-to-Import; (2) need the absolute latest data → DirectQuery; (3) data residency/security where no copy may leave the source → DirectQuery (queries run in the end user's security context, inheriting source RLS); (4) an existing Import-mode model exists → Live connection; (5) does the model fit in the license memory limit? (Pro = 1 GB, F64 = 25 GB, etc.) → Import if it fits; (6) if not, can selected hot tables be Import while cold tables stay DirectQuery? → composite model or aggregations. The performance preference order is: Import → Live-to-Import → Direct Lake → DirectQuery → Live-to-DirectQuery. (Venkatesan, 2025)

**Intermediate-data-store decision tree.** When a live connection alone is too restrictive (can't pick specific tables or blend other sources), introduce an intermediate store. Options, by team persona and data size: **dataflows** (citizen developers, no-code Power Query, JSON in ADLS, <5 GB), **datamarts** (citizen developers, no-code, columnstore SQL, RLS, <100 GB), **lakehouse** (data engineers, Spark, unlimited, Direct Lake), **warehouse** (SQL engineers, T-SQL, unlimited, Direct Lake). The decision tree uses team skill as the primary factor because capabilities largely overlap. (Venkatesan, 2025)

**Medallion architecture (Bronze/Silver/Gold).** The standard lakehouse layering: Bronze (raw, as-is ingestion), Silver (validated/cleansed Delta tables), Gold (enriched business aggregates). It builds a single source of truth by progressively improving data quality through zones. Implemented in Fabric as three lakehouses or three zones, often wired with a Data Factory pipeline (source → Bronze), notebooks (Bronze → Silver), and notebooks (Silver → Gold business aggregates). (Ali and Schacht, 2024)

**Data mesh via domains.** A Fabric **domain** logically groups all data and code artifacts for a business area (commonly a department). Combined with shortcuts (virtual data products without movement) and OneSecurity (define security once, honored by all engines), domains enable hub-and-spoke data mesh: independent domain teams contribute to the same lake, data is blended across domains without movement, governed centrally yet discoverable, and certified by domain experts. (Ali and Schacht, 2024)

**Usage-pattern model.** Three patterns drive nearly every governance and ownership decision: **Enterprise BI** (IT builds model and reports, distributes via apps to 100+ users, tight controls); **Managed self-service BI** (IT builds a certified semantic model/lakehouse, functional teams build their own reports, 10–100 users); **Self-service BI** (business users build everything for themselves or a small team, <10 users). As audience shrinks, IT control shrinks and user flexibility grows. (Venkatesan, 2025)

**VertiPaq compression model.** Import semantic models store each column separately (columnar) and compress each column with one of three algorithms: **hash encoding** (dictionary + index, for strings), **value encoding** (mathematical offset, for numbers), and **run-length encoding** (run counts, for sorted/repeating values). Compression of 10–15x is common and is why Import queries are fast - a DISTINCTCOUNT on one column reads only that column's dictionary. (Venkatesan, 2025)

## Patterns

**Composite model** - *Intent:* fit a too-large model in memory while keeping hot data fast. *When to use:* model exceeds the license memory limit; some tables are large but rarely accessed (put large fact tables in DirectQuery, small dimensions in Import). *Trade-offs:* DirectQuery tables/visuals are slower; you cannot switch a table from Import back to DirectQuery without recreating the connection. (Venkatesan, 2025)

**Aggregations** - *Intent:* combine the size savings of DirectQuery fact tables with Import-level speed for summarized queries. *When to use:* large fact table used in most visuals; users mostly view aggregates (sums/averages by product/store) but occasionally drill to detail. *How:* pre-aggregated tables (hidden) serve summary queries from Import ("hit"); detail queries fall through to the DirectQuery fact table ("miss"). Automatic aggregations require PPU or dedicated capacity; manual aggregations work on Pro. (Venkatesan, 2025)

**Direct Lake** - *Intent:* Import-class performance with always-fresh data and no refresh schedule. *When to use:* lakehouse/warehouse is the source and the model fits the SKU's row/memory limits. *Trade-offs:* single lakehouse/warehouse source only; no Import or DirectQuery tables in the same model; no calculated columns/tables or date-based relationships; views and capacity overruns trigger fallback to DirectQuery. (Venkatesan, 2025)

**Dataflows as centralized transformation** - *Intent:* avoid duplicating data-prep logic across reports. *When to use:* one team's transformed data (e.g., daily sales) is needed by many downstream reports across departments. *Trade-offs:* JSON storage is slower than columnar; no RLS; permissions only at workspace role level. (Venkatesan, 2025)

**Row-level security (RLS)** - *Intent:* control which rows each user can see within a table. *When to use:* one report serves many users who must each see only their own data (e.g., each salesperson sees only their sales). *How:* define a role with a DAX filter such as `SalesMan[email] = USERPRINCIPALNAME()`; the one-to-many relationship propagates the filter to the fact table. *Trade-offs:* applies only to viewers (not contributors/editors); filter dimension tables, not busy fact tables, and keep DAX simple to avoid per-interaction performance cost; combine with OLS using the same roles. (Venkatesan, 2025; Rad, 2018)

**Dynamic RLS with Analysis Services live connection** - *Intent:* enforce RLS defined once in an on-prem SSAS Tabular model across Power BI. *When to use:* the enterprise already maintains security in SSAS. *How:* Power BI passes the user's identity through the gateway via EffectiveUserName (with UPN mapping if needed); SSAS applies the user's role filters and returns only permitted data. Do not also configure RLS in Power BI. *Trade-offs:* requires gateway and domain-user mapping. (Rad, 2018)

**Object-level security (OLS)** - *Intent:* control which users can read which tables or columns. *When to use:* some columns/tables are sensitive (e.g., salary) and must be hidden from certain roles. *Trade-offs:* a hidden referenced object can break visuals/measures for restricted users; combine with RLS via shared roles. (Venkatesan, 2025)

**Deployment pipelines (Dev/Test/Prod)** - *Intent:* promote vetted content through environments to protect end users from in-progress work. *When to use:* enterprise solutions needing controlled release. *How:* three workspaces (Dev, UAT, Prod) on dedicated capacity; the pipeline copies artifacts stage to stage; **deployment rules** rebind data sources per environment. *Trade-offs:* requires Premium/F-SKU/PPU and workspace admin role. (Venkatesan, 2025)

**Endorsement (Promoted/Certified/Master)** - *Intent:* signal artifact trustworthiness to consumers. *When to use:* shared models/reports consumed by other teams. *Badges:* Promoted (author thinks it's usable), Certified (verified by authorized reviewers), Master (single source of truth for master/dimensional data). *Trade-offs:* certification must be enabled and whitelisted in tenant settings. (Venkatesan, 2025)

**Multi-geo capacities** - *Intent:* store semantic model data near regional users or satisfy data-residency rules. *When to use:* global organizations or regulatory boundaries. *How:* provision dedicated capacity in a region different from the home tenant; the model data and dedicated cluster live in that region (metadata stays in the home region). *Trade-offs:* dedicated capacity only - not available on Pro or PPU workspaces. (Venkatesan, 2025)

## Principles & best practices

- **Decouple storage, compute, and workload.** OneLake (storage) + Fabric capacities (compute) + workloads being independent lets multiple engines work on one copy of data, prevents duplication, and lets each department's capacity scale or pause without affecting others. (Venkatesan, 2025; Ali and Schacht, 2024)
- **Secure data where it is stored.** Connectivity mode dictates where to apply security: Import → secure in Power BI (encryption, RLS, OLS); DirectQuery → secure at the source; Live → secure in the target model or source. (Venkatesan, 2025)
- **Model as a star schema.** A central fact table with surrounding dimension tables yields simpler DAX and faster queries than snowflake/complex-relationship designs. Filter RLS on dimensions, not facts. (Venkatesan, 2025)
- **Right-size the semantic model.** Reduce cardinality, drop unneeded columns, prefer measures over calculated columns, and check size with VertiPaq Analyzer; the whole Import model loads into memory, so it must fit the SKU limit. (Venkatesan, 2025)
- **Optimize reports, not just models.** Limit visuals per page, apply default filters (Top N), avoid large table/matrix visuals (use paginated reports or Excel for row dumps), and use only Power BI-certified custom visuals. Diagnose with Performance Analyzer (visual timings) and DAX Studio (FE vs. SE timings - push work to the multithreaded Storage Engine). (Venkatesan, 2025)
- **Incremental refresh for large models.** Partition by date and refresh only recent partitions; use the enhanced refresh REST API (parallelism, cancellation, status) on dedicated capacity for large models. (Venkatesan, 2025)
- **Match governance control to usage pattern.** Tighten central control for enterprise BI; delegate capacity/domain/workspace administration to functional teams for self-service. Multiple usage patterns coexist in one tenant via domains, capacities, and delegation. (Venkatesan, 2025)
- **Define security once with OneSecurity.** Set table/file/folder permissions in the lakehouse and have Spark, SQL, and Power BI all honor them, avoiding inconsistent multi-place policies. (Ali and Schacht, 2024)
- **Establish a data governance framework.** Define objectives; form a cross-functional team (governance council, data stewards, data custodians, data users); write policies for quality, access, privacy/compliance, and security; implement lifecycle procedures; monitor and enforce; train; review and refine. Tie it to compliance regimes (GDPR, CCPA, HIPAA). (Makhija and Odunukwe, 2025)
- **Apply version control and CI/CD discipline.** Clear naming conventions, small frequent commits with messages, short-lived branches, peer review before merge, automation/CI-CD pipelines, documentation, and access control; Fabric Git integration and deployment pipelines operationalize Dev/Test/Stage/Prod promotion. (Makhija and Odunukwe, 2025; Venkatesan, 2025)

## Anti-patterns & pitfalls

- **Unmanaged self-service sprawl.** Letting every user bring any source and publish freely causes data-security gaps (untrained users misapplying policies), data-quality drift (uncontrolled sources/logic), and data duplication (multiple copies refreshing redundantly, wasting storage and compute). Managed self-service mitigates this. (Venkatesan, 2025)
- **RLS on fact tables or with complex DAX.** Filtering busy fact tables re-evaluates the RLS function on every interaction; complex DAX filters slow reports. Filter simple dimension columns instead. (Venkatesan, 2025)
- **Assuming RLS protects editors.** RLS applies only to viewers; anyone with contributor or higher can edit the model and bypass it. (Venkatesan, 2025)
- **Letting functional teams assign workspaces to a shared enterprise capacity.** In enterprise BI, a runaway report from one team can starve critical shared reports; keep capacity assignment with the platform team. (Venkatesan, 2025)
- **Data swamps.** Dumping raw data into a lake without metadata, cataloging, and curated zones makes valuable data undiscoverable and pushes inconsistent transformation onto consumers. (Pena, 2025; Ali and Schacht, 2024 - medallion zones counter this)
- **Direct Lake fallback surprises.** Exceeding SKU row/memory limits or querying views silently falls back to slower DirectQuery; design within the SKU's Direct Lake limits. (Venkatesan, 2025)
- **Switching Import to DirectQuery in place.** Not supported - you must recreate the source connection; plan storage mode up front. (Venkatesan, 2025)
- **Relying on preview features in production.** Preview features carry no SLA or guaranteed support; many organizations restrict production to generally available features (a reason datamarts lagged dataflows). (Venkatesan, 2025)

## Decision guidance

- **Choosing a storage mode:** Start with performance and freshness needs. If sub-5-second interactivity is required and the model fits memory → Import. If users must always see the latest source data, or no copy may leave the source → DirectQuery. If a good Import-mode model already exists → Live connection. If the model is too big → composite model (hot dimensions Import, cold facts DirectQuery) plus aggregations, or push the data into a Fabric lakehouse/warehouse and use Direct Lake. (Venkatesan, 2025)
- **Choosing an intermediate data store:** Decide primarily by team skill and data volume. Citizen developers wanting no-code → dataflow (small, JSON, no RLS) or datamart (columnar, RLS, ≤100 GB). Spark engineers with big data → lakehouse. T-SQL engineers with big data → warehouse. Prefer lakehouse/warehouse for Direct Lake, unlimited storage, and default semantic models. (Venkatesan, 2025)
- **Lakehouse vs. warehouse:** Capabilities largely overlap on Delta-Parquet. Pick warehouse if the team knows T-SQL and needs full read/write SQL; pick lakehouse for Spark-based engineering and code-first transformation. Cross-database queries and shortcuts let both coexist and combine at runtime. (Ali and Schacht, 2024)
- **Licensing/capacity:** Free for personal use in My workspace (≤1 GB, no sharing). Pro for collaboration (≤1 GB models). Fabric F-SKUs for dedicated compute, larger models, and Fabric workloads; F64+ unlocks unlimited free-user read sharing, making it cost-effective for hundreds of consumers. PPU for individual premium features. (Venkatesan, 2025)
- **Governance model:** Map each solution to a usage pattern and set control accordingly. Enterprise BI → central domain/capacity owned by IT, contributor-only access for developers, certification gating, app-only access for users. Managed self-service → functional team owns workspace/capacity/certification atop IT-certified models. Self-service → functional users own everything but cannot publish org-wide or move to shared capacity without approval. Use domains, capacities, and role delegation to let these coexist. (Venkatesan, 2025)
- **Capacity sizing and throttling:** Understand CU smoothing (background jobs spread over 24 hours, interactive metered immediately) and the throttling ladder - bursting (>100% for <10 min, smoothed over 10 min), interactive delay (>10 min), interactive rejection (>1 hr), background rejection (>24 hr). Monitor with the Fabric Capacity Metrics app; assign critical workloads their own capacity. (Venkatesan, 2025)

## Recent developments (2024–2026)

- **Operational databases moved into Fabric (GA, Nov 2025).** Fabric SQL database and Cosmos DB in Fabric reached general availability, each provisioning in seconds with data auto-synced into OneLake, bringing transactional (OLTP) and NoSQL workloads alongside the analytics engines in one SaaS tenant. Cosmos DB in Fabric adds native vector indexing/search via DiskANN plus reverse-ETL, extending OneCopy to semi/unstructured and AI workloads. (Microsoft Fabric Blog, "GA of Cosmos DB in Microsoft Fabric and Cosmos DB Mirroring," 2025, https://blog.fabric.microsoft.com/en-US/blog/announcing-ga-of-cosmos-db-in-microsoft-fabric-and-cosmos-db-mirroring/)
- **Mirroring expanded as the default zero-ETL ingestion path.** Mirroring for PostgreSQL, Cosmos DB, and SQL Server (2016-2022 and 2025) reached GA, letting external operational stores land continuously in OneLake without building pipelines, reinforcing this file's decoupling and OneCopy principles. (Microsoft Fabric Blog, "What's new in OneLake and the Fabric platform," 2025, https://blog.fabric.microsoft.com/en-us/blog/whats-new-in-onelake-and-the-fabric-platform-more-sources-security-and-capacity-tooling)
- **OneLake security and governance deepened.** OneLake security added ReadWrite access controls for fine-grained write permissions, and OneLake diagnostics now answer "who accessed what, when, and how" across workspaces, advancing the OneSecurity/federated-governance goals described here. (Microsoft Fabric Blog, "Fabric November 2025 Feature Summary," 2025, https://blog.fabric.microsoft.com/en-us/blog/fabric-november-2025-feature-summary)
- **Fabric positioned as a OneLake "data control plane."** At FabCon/SQLCon 2026, Microsoft framed Fabric as the unified control plane over OneLake, consolidating the multi-engine, single-copy vision and pushing Direct Lake and agent-facing access as defaults. (Windows News, "Microsoft Fabric Emerges as OneLake Data Control Plane," 2026, https://windowsnews.ai/article/microsoft-fabric-emerges-as-onelake-data-control-plane-at-fabcon-sqlcon-2026.405512)
- **Industry-wide, the catalog/open-format layer Fabric standardizes on (Delta-Parquet) is converging with Iceberg.** Delta UniForm and Iceberg interoperability mean Fabric's OneLake increasingly interoperates with Snowflake/Databricks estates, relevant to multi-vendor data-mesh designs built on shortcuts. (datalakehousehub.com, "2025 & 2026 Ultimate Guide to the Data Lakehouse," 2025, https://datalakehousehub.com/blog/2025-09-2026-guide-to-data-lakehouses/)
