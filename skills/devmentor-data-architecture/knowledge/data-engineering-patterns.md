# Data Engineering Design Patterns

**Domain:** 08 - Data Architecture and Engineering
**Primary sources:** Data Engineering Design Patterns: Recipes for Solving the Most Common Data Engineering Problems (Bartosz Konieczny, O'Reilly, 2025)

## Overview
Software design patterns (the Gang of Four) keep a codebase maintainable, but they are not enough for data engineering. Data engineering layers data-specific concerns on top of code quality: failure management, backfilling, idempotency, late-arriving data, schema drift, and data correctness. Konieczny's catalog fills that gap with roughly seventy named recipes, each presented in a consistent Problem / Solution / Consequences / Examples form and grounded in a single running case study (a blog analytics platform built on a Medallion-style Bronze/Silver/Gold layering with both online streaming and offline batch ingestion). The patterns are deliberately tool-agnostic in intent but illustrated with popular open-source engines (Apache Spark, Apache Flink, Apache Airflow, PostgreSQL, Delta Lake) and occasionally managed cloud services.

The catalog is organized as a journey along a typical data flow: ingest the data, manage errors, guarantee idempotency under retries and backfills, add business value, wire the pipeline into a larger data flow, secure it, store it efficiently, enforce its quality, and finally observe it. This file captures the catalog as a reference. The intent is that an agent facing a concrete data problem ("duplicates from at-least-once delivery," "late events beyond my window," "GDPR deletion in immutable storage," "small-files metadata overhead") can name the right pattern, understand its trade-offs, and reach for the appropriate engine feature.

## Core concepts

- **Medallion layering (case study)** - raw data lands in the **Bronze** layer, is cleaned and enriched into the **Silver** layer, and is aggregated/served from the **Gold** layer. Patterns are introduced in the context of moving data through these layers.
- **EL vs ETL vs ELT** - Extract-Load (passthrough) jobs move data without transformation and suit homogeneous stores; a thin transform layer between extract and load makes it ETL for heterogeneous stores; ELT defers transformation to the destination warehouse.
- **Batch vs streaming** - many patterns have a batch form and a streaming form (for example Incremental Sessionizer vs Stateful Sessionizer); the streaming form trades lower latency for stateful complexity and checkpointing.
- **Idempotency and backfilling** - retries (automatic or manual) and backfills re-run pipelines over data that may already be written. Idempotency is the property that multiple runs produce a single correct output rather than duplicates. The book treats reprocessing and backfilling as the same class of "processing past data."
- **At-least-once delivery and duplicates** - streaming brokers retry producers, so duplicates are normal; exactly-once processing is achieved through deduplication and idempotent writes, not by assuming the broker is perfect.
- **Late and out-of-order data** - networks drop and buffer; events arrive after their event-time window has closed and need explicit detection and integration strategies.
- **Schema evolution and data contracts** - upstream producers change fields without warning; the consumer must detect incompatibility, enforce compatibility, or migrate the schema gracefully.
- **Data quality vs data observability** - quality enforcement predefines checks and blocks bad data before publication (gatekeeping); observability monitors properties of the data and pipeline over time to detect issues the predefined checks did not anticipate.

## Frameworks & models

- **The Problem / Solution / Consequences / Examples template** - every pattern states a realistic problem, the solution and its implementation model, the trade-offs ("gotchas," each ideally paired with a mitigation), and concrete code. The Consequences section is where the real engineering judgment lives.
- **Ten-category catalog (the data-flow journey)** - Ingestion, Error Management, Idempotency, Data Value, Data Flow, Data Security, Data Storage, Data Quality, Data Observability. Each category groups two to eight patterns by sub-problem (for example, within Ingestion: Full Load, Incremental Load, Replication, Compaction, Readiness, Event-Driven).
- **Pattern pairing / evolution chains** - patterns are frequently introduced as upgrades of one another as requirements grow: Full Loader leads to Incremental Loader leads to Change Data Capture; Static Joiner leads to Dynamic Joiner; Static Late Data Integrator leads to Dynamic Late Data Integrator; Merger leads to Stateful Merger; Aligned Fan-In leads to Unaligned Fan-In; Single Runner leads to Concurrent Runner. This models the natural maturation of a pipeline.

## Patterns

### Ingestion (full / incremental / CDC / replication / compaction / readiness / event-driven)

- **Full Loader** - Intent: reload an entire small, slowly evolving source on each run when there is no change-tracking attribute. When to use: reference/dimension data with no "last updated" column, total rows small (for example under a million). Trade-offs: simplest possible two-step extract-load, but compute cost and runtime grow with data volume; mitigate with autoscaling; static clusters can fail when a dataset suddenly doubles.
- **Incremental Loader** - Intent: ingest only records added since the last run, tracked by a high-watermark (timestamp or monotonic id). When to use: continuously growing, immutable append-only sources. Trade-offs: efficient and bounded, but needs a reliable watermark and care at boundaries to avoid missing or double-counting edge records.
- **Change Data Capture (CDC)** - Intent: stream every insert/update/delete from a transactional table into a broker within seconds, rather than polling. When to use: low-latency replication of an OLTP table, downstream consumers waiting on slow batch ingestion. Trade-offs: near-real-time and complete, but requires CDC infrastructure (log reading, connectors) and downstream handling of update/delete semantics.
- **Passthrough Replicator** - Intent: copy a dataset across environments (dev/staging/prod) unchanged. When to use: promote reference datasets between identical environments. Trade-offs: trivial when stores are homogeneous; cannot adapt format or strip sensitive data.
- **Transformation Replicator** - Intent: replicate production data to a lower environment while transforming it (for example masking PII) so real-shaped data is testable safely. When to use: realistic testing where synthetic data cannot reproduce real quality issues but raw PII may not leave production. Trade-offs: enables faithful testing and compliance, at the cost of a maintained transformation step.
- **Compactor** - Intent: merge many small files produced by streaming sync into fewer large files. When to use: object-store datasets suffering small-files metadata overhead (batch jobs spending most time listing files). Trade-offs: restores read performance, but adds a periodic compaction job and must coordinate with readers to avoid reading half-compacted state.
- **Readiness Marker** - Intent: publish an explicit signal (a marker file or flag) that a dataset/partition is complete before consumers read it. When to use: downstream ML/BI consumers complain about incomplete datasets. Trade-offs: eliminates partial reads, at the cost of an extra publish step and a convention all consumers must honor.
- **External Trigger** - Intent: run ingestion only when an external event signals new data, instead of on a fixed schedule. When to use: upstream refreshes irregularly (for example backend feature releases a few days a week) and scheduled reloads waste compute. Trade-offs: removes wasted runs, but couples the pipeline to a reliable external trigger/event source.

### Error management (dead-letter / dedup / late data / filtering / fault tolerance)

- **Dead-Letter** - Intent: route unprocessable records to a side store instead of failing the whole job. When to use: streaming or batch jobs where bad producer records would otherwise crash and require manual offset surgery. Trade-offs: keeps the pipeline running and preserves bad records for later inspection/reprocessing, at the cost of a dead-letter store and a triage process so it does not silently fill up.
- **Windowed Deduplicator** - Intent: drop duplicate records within a bounded time window to approximate exactly-once. When to use: streaming sources with producer retries feeding business-facing data. Trade-offs: simple and stateful-bounded, but only deduplicates within the window; duplicates separated by more than the window slip through.
- **Late Data Detector** - Intent: identify events that arrive after their event-time window so a per-use-case strategy (ignore, integrate, alert) can be applied. When to use: any event-time pipeline where clients buffer offline. Trade-offs: makes lateness explicit and actionable; requires event-time tracking and a defined allowed-lateness policy.
- **Static Late Data Integrator** - Intent: re-integrate late data within a fixed allowed window (for example 15 days) by reprocessing affected partitions. When to use: approximate statistics with a bounded correction horizon. Trade-offs: bounded reprocessing cost, but records older than the window are silently skipped.
- **Dynamic Late Data Integrator** - Intent: integrate arbitrarily late data beyond a fixed window without blindly replaying a fixed range. When to use: when the business needs all late data corrected, not just the last N days. Trade-offs: full correctness, at the cost of tracking which partitions each late record affects and more complex reprocessing logic.
- **Filter Interceptor** - Intent: instrument and expose the volume/reason of filtered-out records so a sudden spike (data regression vs code regression) is visible. When to use: distributed jobs where silent over-filtering corrupts results. Trade-offs: adds observability into the filter step; small overhead to count and emit metrics.
- **Checkpointer** - Intent: persist streaming progress and intermediate results so a fatal failure resumes rather than reprocessing from the beginning. When to use: long-running stateful streaming (for example windowed unique counts). Trade-offs: fast recovery and fault tolerance, at the cost of checkpoint storage and careful checkpoint/version compatibility on restart.

### Idempotency (overwrite / update / database / immutable)

- **Fast Metadata Cleaner** - Intent: achieve idempotency by dropping and recreating table partitions via cheap metadata operations rather than slow row-level DELETE. When to use: large partitioned tables where DELETE-then-INSERT has become the bottleneck. Trade-offs: very fast re-runs, but requires a metadata-aware table format (for example partition-level operations) and partition-aligned writes.
- **Data Overwrite** - Intent: guarantee idempotency by overwriting an entire event-time partition location on each run. When to use: object-store, partition-by-event-time datasets without a metadata layer that would enable Fast Metadata Cleaner. Trade-offs: simple and storage-format-agnostic; rewrites whole partitions even for small changes.
- **Merger** - Intent: synchronize CDC changes into a target table with an upsert/merge so the table mirrors the source without duplicates. When to use: replicating a changing source into a Delta-Lake-style table that must reflect current state. Trade-offs: keeps target consistent with source; merge cost grows with table size and needs a reliable key.
- **Stateful Merger** - Intent: extend Merger with versioning so the dataset can be restored to a known-good version before a backfill. When to use: when a bad merge must be rolled back before reprocessing. Trade-offs: safe backfills with point-in-time restore, at the cost of retaining historical versions.
- **Keyed Idempotency** - Intent: deduplicate by writing to a key-value store keyed on a deterministic identity so retries overwrite rather than append. When to use: streaming aggregations (for example per-user sessions) where a task retry must not create duplicates. Trade-offs: clean idempotency for keyed writes; needs a store that supports keyed upsert.
- **Transactional Writer** - Intent: wrap writes in a transaction so partial/failed tasks (for example on spot-instance preemption) leave no partial data. When to use: cost-optimized runtimes (spot/preemptible) where node loss is routine. Trade-offs: atomic all-or-nothing writes protect quality, at the cost of transactional overhead and a store that supports transactions.
- **Proxy (immutable dataset)** - Intent: keep every produced version immutably but expose only the latest through a single stable pointer/view. When to use: legal/audit requirements to retain all past versions while consumers see only current data. Trade-offs: full history with a simple consumer contract; storage grows and a pointer-management step is required.

### Data value (enrichment / decoration / aggregation / sessionization / ordering)

- **Static Joiner** - Intent: enrich events by joining against a static reference dataset. When to use: add stable context (for example user registration date) to activity records. Trade-offs: simple batch enrichment; stale when the reference data changes frequently.
- **Dynamic Joiner** - Intent: enrich events against a continuously changing reference fed by CDC, so enrichment reflects the latest profile. When to use: high churn in the reference data makes static joins irrelevant. Trade-offs: fresh enrichment, at the cost of streaming join state and CDC plumbing.
- **Wrapper** - Intent: normalize heterogeneous input schemas into a single structure for downstream consumers. When to use: multiple providers emit different shapes. Trade-offs: one clean downstream contract; the wrapper must evolve with each new provider.
- **Metadata Decorator** - Intent: attach technical context (job version, processing time) to each record for traceability. When to use: frequently released jobs where you must reason about which version produced which data. Trade-offs: cheap lineage/debuggability; slightly larger records and a convention to maintain.
- **Distributed Aggregator** - Intent: compute large aggregates (OLAP-cube-style counts/averages) across a cluster with a shuffle. When to use: building dashboard/analytical rollups over big data. Trade-offs: scales horizontally; the shuffle is expensive.
- **Local Aggregator** - Intent: aggregate within partition boundaries to avoid the grouping shuffle when partitioning is stable. When to use: static partitioning where the partition set never changes. Trade-offs: removes shuffle cost; only valid when grouping aligns with partitioning.
- **Incremental Sessionizer** - Intent: build user sessions in batch from time-partitioned events. When to use: sessions of bounded duration spanning a few partitions, analyst-acceptable hourly latency. Trade-offs: simple batch sessions; latency bounded by partition granularity.
- **Stateful Sessionizer** - Intent: build sessions in streaming with managed state for low latency. When to use: consumers need sub-hour session availability. Trade-offs: seconds-level latency, at the cost of streaming state management and complexity.
- **Bin Pack Orderer** - Intent: batch and order records into size-optimized payloads before delivery to an external API. When to use: cost-optimized synchronization to a downstream API/storage. Trade-offs: efficient packing; adds buffering and ordering logic.
- **FIFO Orderer** - Intent: forward a filtered subset of events in strict processing order with no buffering. When to use: deliver matched events as soon as possible while preserving order. Trade-offs: lowest latency and strict order; cannot batch for network efficiency.

### Data flow (sequence / fan-in / fan-out / orchestration)

- **Local Sequencer** - Intent: split a giant monolithic job into a sequence of steps within one pipeline so failures resume at the failed step. When to use: long, fragile jobs that restart from scratch on failure. Trade-offs: easier debugging and partial restarts; you cannot remove business logic, only restructure it.
- **Isolated Sequencer** - Intent: separate concerns into independent pipelines owned by different teams, chained by a published dataset. When to use: clear ownership boundaries (for example data prep team vs visualization team). Trade-offs: clean ownership and decoupling; requires a stable inter-team dataset contract.
- **Aligned Fan-In** - Intent: aggregate many fine-grained partitions (hourly) into a coarser view (daily) leveraging the partitioning. When to use: consumers want the full coarse view but you want to avoid reprocessing all data. Trade-offs: efficient rollup; assumes all input partitions are present.
- **Unaligned Fan-In** - Intent: produce a coarse aggregate even when some input partitions failed, filling gaps later. When to use: partial-but-timely delivery is preferable to none. Trade-offs: availability over completeness, with a gap-backfill mechanism required.
- **Parallel Split** - Intent: run an old and a new implementation in parallel to validate a migration. When to use: rewriting a legacy (for example reverse-engineered) pipeline where the new logic may be imperfect. Trade-offs: safe migration via comparison; doubles compute during the overlap.
- **Exclusive Choice** - Intent: route execution to one of several job versions based on a condition (for example run-date) within a single pipeline. When to use: cut over to a new version from a date while old dates still backfill with the old version. Trade-offs: preserves full execution history in one pipeline; branching logic to maintain.
- **Single Runner** - Intent: execute a pipeline graph as a single sequential orchestrated run. When to use: ordered dependencies between steps. Trade-offs: simple and correct for dependent steps; serializes everything.
- **Concurrent Runner** - Intent: run independent pipeline instances concurrently so a slow run does not delay the next. When to use: independent loads where sequential execution (Single Runner) causes backlog. Trade-offs: higher throughput; only safe when runs are truly independent.

### Data security (removal / access control / protection / connectivity)

- **Vertical Partitioner (security)** - Intent: split immutable PII attributes into a separate store so each is held once and can be governed/removed independently. When to use: storage overhead from repeated immutable PII and removal requirements. Trade-offs: less duplication and cleaner deletion; joins needed to reassemble.
- **In-Place Overwriter** - Intent: comply with deletion requests on legacy time-partitioned storage by overwriting affected partitions with the record removed. When to use: legacy systems lacking a personal-data strategy but bound by privacy law. Trade-offs: achieves erasure without a metadata layer; rewrites whole partitions.
- **Fine-Grained Accessor for Tables** - Intent: enforce row/column-level access policies beyond table-level grants. When to use: users authorized for a table but not for specific sensitive rows/columns. Trade-offs: precise least-privilege access; policy maintenance overhead.
- **Fine-Grained Accessor for Resources** - Intent: apply least-privilege so a job can only touch the specific datasets/resources it needs. When to use: audits find overly broad permissions (a job could overwrite all datasets). Trade-offs: limits blast radius; finer IAM policies to manage.
- **Encryptor** - Intent: encrypt data at rest and in transit. When to use: protect against interception or physical theft. Trade-offs: confidentiality; key management and slight performance cost.
- **Anonymizer** - Intent: remove PII columns entirely before sharing with third parties. When to use: simplest privacy-compliant sharing. Trade-offs: strong privacy; removed columns prevent many analytical queries.
- **Pseudo-Anonymizer** - Intent: replace PII with stable surrogate values that hide real identities but remain usable for grouping/joining. When to use: third parties need to analyze by entity without seeing real PII. Trade-offs: preserves analytical utility; pseudonyms can still enable re-identification if not managed carefully.
- **Secrets Pointer** - Intent: reference credentials from a secret manager instead of embedding them in code/config. When to use: any external credential (for example a billed API login/password). Trade-offs: prevents leaks and reduces billing risk; depends on a secret-management service.
- **Secretless Connector** - Intent: authenticate to managed resources via identity/role rather than long-lived API keys. When to use: small teams wanting to avoid key management. Trade-offs: no credentials to leak; requires platform identity-federation support.

### Data storage (partitioning / records organization / read optimization / representation)

- **Horizontal Partitioner** - Intent: split data into partitions (commonly by time) so queries prune to the relevant partitions. When to use: filtering on a partition key (for example last four days) has become slow at scale. Trade-offs: large read speedups via partition pruning; risk of too many/too few partitions and skew.
- **Vertical Partitioner (storage)** - Intent: store immutable attributes once instead of repeating them per row. When to use: visit-style records with mutable and immutable attribute groups. Trade-offs: reduces storage/update cost; joins to reassemble.
- **Bucket** - Intent: hash a high-cardinality predicate column into a fixed number of buckets when it cannot be a partition column. When to use: an attribute is used in most queries but has cardinality too high to partition on. Trade-offs: enables pruning/co-location without partition explosion; bucket count is fixed up front.
- **Sorter** - Intent: physically sort data within files by common predicate columns to speed range queries. When to use: known query patterns and a fixed table layout (for example weekly tables). Trade-offs: lower read latency; sorting cost on write.
- **Metadata Enhancer** - Intent: add column statistics/zone maps so engines skip non-matching data within partitions. When to use: analysts target small row subsets within large partitions and complain about latency/cost. Trade-offs: faster, cheaper scans; metadata maintenance.
- **Dataset Materializer** - Intent: precompute a materialized table for a query that a logical view served too slowly. When to use: consumers query a multi-partition view repeatedly. Trade-offs: fast reads; staleness and a refresh job.
- **Manifest** - Intent: maintain a file manifest so query engines avoid expensive file listing on object stores. When to use: exposing a Parquet dataset to a warehouse/analyst layer where listing dominates runtime. Trade-offs: large query speedups; manifest must stay in sync with files.
- **Normalizer** - Intent: split repeated attributes into related tables to remove duplication and ease updates. When to use: immutable attributes repeated per event inflate storage and slow updates. Trade-offs: less duplication and cheaper updates; more joins on read.
- **Denormalizer** - Intent: flatten relational models into wide tables to remove expensive analytical joins. When to use: analytical query latency dominated by joins as data volume grows. Trade-offs: fast analytical reads; storage growth and update anomalies.

### Data quality (enforcement / schema consistency / observation)

- **Audit-Write-Audit-Publish (WAP)** - Intent: compute results to a staging location, audit them, and only publish if they pass. When to use: business-critical aggregates where publishing wrong numbers is costly. Trade-offs: prevents bad data from ever being seen; adds a staging step and publish gate.
- **Constraints Enforcer** - Intent: declare data constraints (not-null, ranges, referential rules) so the load fails fast on violation without bespoke validation code. When to use: jobs getting random nulls/invalid values in required fields. Trade-offs: declarative, centralized validation; failing the load is the intended behavior and must be operationalized.
- **Schema Compatibility Enforcer** - Intent: validate incoming schema against an expected/compatible schema and reject breaking changes. When to use: upstream teams remove or alter fields the job depends on. Trade-offs: protects against silent breakage; requires a schema registry/contract and a rejection policy.
- **Schema Migrator** - Intent: evolve a sprawling message schema into a cleaner domain-aligned structure without breaking consumers. When to use: messages have grown to dozens of dispersed fields that obscure the domain. Trade-offs: clearer long-term model; migration effort and dual-read/dual-write during transition.
- **Offline Observer** - Intent: periodically profile dataset properties (distributions, null counts) to catch drift the predefined rules miss. When to use: monitoring evolving upstreams without blocking the pipeline. Trade-offs: broad anomaly visibility; periodic cadence means issues can be detected after consumers see them.
- **Online Observer** - Intent: check data properties at runtime, in the pipeline, to catch regressions before publication. When to use: when a weekly Offline Observer detected an issue too late. Trade-offs: real-time detection and non-propagation; inline cost and the need to choose which metrics to compute live.

### Data observability (detectors / time detectors / lineage)

- **Flow Interruption Detector** - Intent: detect when a job runs successfully but writes nothing (silent flow break). When to use: streaming sync feeding many downstreams where "green but empty" is a real failure mode. Trade-offs: catches silent gaps; requires defining "expected output" baselines.
- **Skew Detector** - Intent: detect partial/half-empty datasets caused by upstream generation problems. When to use: a job processes an incomplete input without failing. Trade-offs: catches completeness regressions; needs volume baselines per partition.
- **Lag Detector** - Intent: monitor how fast a consumer processes input relative to arrival rate. When to use: data volume spikes risk slower delivery and a need to scale. Trade-offs: enables proactive scaling/alerts; needs throughput and backlog instrumentation.
- **SLA Misses Detector** - Intent: alert when a job will miss or has missed its completion SLA. When to use: critical downstreams depend on a job finishing by a deadline. Trade-offs: early warning to act; requires SLA definitions and timely signals.
- **Dataset Tracker** - Intent: track table-level lineage and dependencies so schema/type changes can be traced to producers. When to use: failures from inconsistent upstream schema across a multi-team chain. Trade-offs: dependency visibility; lineage capture/maintenance overhead.
- **Fine-Grained Tracker** - Intent: track column-level lineage to answer which inputs feed which output columns. When to use: wide denormalized tables where column provenance questions recur. Trade-offs: precise impact analysis; more detailed lineage to compute and store.

## Principles & best practices
- Treat data concerns as first-class alongside code quality: failure management, idempotency, late data, schema drift, and correctness need explicit patterns, not ad hoc fixes.
- Read the Consequences before adopting a pattern; the gotchas and their mitigations are where the engineering decision is made.
- Prefer evolving a pattern to its next form only when requirements demand it (Full leads to Incremental leads to CDC); do not pay streaming/state complexity until latency or churn requires it.
- Make idempotency a property of every pipeline so retries and backfills are safe by construction; choose the cheapest mechanism the storage layer supports (metadata cleaner over row DELETE; keyed upsert; transactional writes).
- Gate critical outputs behind quality enforcement (WAP, constraints, schema compatibility) and back it with observability detectors so the issues your predefined checks did not anticipate still get caught.
- Push transformations and validations as early in the flow as possible to prevent error cascades and wasted downstream compute.
- Use partitioning, bucketing, sorting, manifests, and materialization deliberately against known query patterns; storage layout is a performance lever, not an afterthought.

## Anti-patterns & pitfalls
- Static compute on a Full Loader whose source can double overnight; the job slows or fails. Use autoscaling or switch to Incremental.
- Row-level DELETE-then-INSERT for idempotency on large tables; it degrades over time. Prefer Fast Metadata Cleaner or Data Overwrite.
- Assuming exactly-once from the broker; at-least-once delivery means duplicates are normal and must be deduplicated.
- Ignoring late and out-of-order data, or hardcoding a fixed lateness window that silently drops older corrections.
- "Green but empty" runs and half-empty datasets that succeed without producing correct output; without Flow Interruption/Skew detectors these are invisible until a consumer complains.
- Embedding credentials in code/config instead of using Secrets Pointer or a Secretless Connector.
- Over-partitioning a high-cardinality column until the metadata layer breaks; use Bucket instead.
- Relying only on predefined quality checks; upstream evolution produces anomalies the checks never anticipated, which only observation catches.

## Decision guidance
- Ingesting? No change attribute and small data leads to Full Loader; a watermark exists leads to Incremental Loader; you need seconds-level latency leads to CDC. Irregular upstream leads to External Trigger; small-files overhead leads to Compactor; partial-read complaints lead to Readiness Marker.
- Errors and retries? Bad records crashing the job lead to Dead-Letter; producer-retry duplicates lead to Windowed Deduplicator (plus Keyed Idempotency or Transactional Writer for writes); late events lead to the Late Data Detector then Static or Dynamic Integrator; long streaming jobs lead to Checkpointer.
- Adding value? Stable context leads to Static Joiner, changing context leads to Dynamic Joiner; big rollups lead to Distributed Aggregator, stable partitioning leads to Local Aggregator; sessions, with hourly latency acceptable, lead to Incremental Sessionizer, else Stateful Sessionizer.
- Wiring flow? Fragile monolith leads to Local Sequencer; team boundaries lead to Isolated Sequencer; rollups lead to Aligned/Unaligned Fan-In; migrations lead to Parallel Split then Exclusive Choice; independent loads lead to Concurrent Runner.
- Securing? Deletion needs lead to In-Place Overwriter or Vertical Partitioner; access scoping leads to Fine-Grained Accessors; sharing externally leads to Anonymizer or Pseudo-Anonymizer; credentials lead to Secrets Pointer or Secretless Connector.
- Storing for reads? Time filters lead to Horizontal Partitioner; high-cardinality predicate leads to Bucket; range queries lead to Sorter; object-store listing cost leads to Manifest; join-heavy analytics lead to Denormalizer.
- Quality and observability? Block bad data leads to WAP plus Constraints Enforcer plus Schema Compatibility Enforcer; watch for the unexpected leads to Offline/Online Observer plus Flow Interruption, Skew, Lag, and SLA detectors plus Dataset and Fine-Grained Trackers.

## Recent developments (2024–2026)

- **Open table formats made many idempotency/storage patterns first-class engine features.** As Iceberg, Delta, Hudi, and Paimon converged in 2025 (Delta UniForm exposing Iceberg metadata; Iceberg v3 adding deletion vectors and row lineage), patterns like Merger, Stateful Merger, Fast Metadata Cleaner, and Compactor increasingly rely on built-in MERGE, snapshot/time-travel rollback, and auto-compaction rather than hand-rolled logic. (Databricks Blog, "Apache Iceberg v3," 2025, https://www.databricks.com/blog/next-era-open-lakehouse-apache-icebergtm-v3-public-preview-databricks; datalakehousehub.com, "Ultimate Guide to Open Table Formats," 2025, https://datalakehousehub.com/blog/2025-09-ultimate-guide-to-open-table-formats/)
- **Real-time streaming moved into the engine core, reshaping the batch/streaming pattern pairs.** Spark 4.1 (Dec 2025) added Structured Streaming Real-Time Mode (millisecond latency) and Flink 2.2 added native AI/ML inference in SQL, lowering the cost of choosing the streaming form (Stateful Sessionizer, Dynamic Joiner, Keyed Idempotency) over batch. (Modern Data 101, 2025, https://moderndata101.substack.com/p/understand-the-new-spark; Apache Flink, "Apache Flink 2.2.0," 2025, https://flink.apache.org/2025/12/04/apache-flink-2.2.0-advancing-real-time-data--ai-and-empowering-stream-processing-for-the-ai-era/)
- **Quality and observability patterns are being augmented by ML.** Industry practice shifted from purely predefined rules (Constraints Enforcer, Schema Compatibility Enforcer) toward systems that learn data distributions and auto-detect drift and anomalies, complementing the Offline/Online Observer and the detector patterns in this file. (lakeFS, "The State of Data and AI Engineering 2025," 2025, https://lakefs.io/blog/the-state-of-data-ai-engineering-2025/; Revefi, "Ways AI is Transforming Data Engineering," 2025, https://www.revefi.com/blog/ways-ai-is-transforming-data-engineering)
