# Azure Infrastructure and Platform

**Domain:** 09 - Cloud Infrastructure and Platform
**Primary sources:** Building Enterprise-Ready Azure Infrastructure: Learn Security, Scalability, and Reliability with IaC & DevOps (Gavandi, 2025); Azure Cloud Projects: Learn Microsoft Azure through Hands-On Projects (Saleh, 2025); Developing Microservices Architecture on Microsoft Azure with Open Source Technologies (Chandaka & Khan, 2021)

## Overview

This file covers how to design, govern, and operate enterprise-grade infrastructure on Microsoft Azure, and how to realize a microservices reference architecture on top of it. Azure offers a deep ecosystem, but lifting and shifting workloads into it does not by itself deliver scalability, security, or operational excellence. Enterprise readiness comes from rethinking how environments are designed, deployed, and managed so that infrastructure is defined in code, compliance is embedded in pipelines, identity is the new perimeter, and reliability is engineered through redundancy and automation (Gavandi).

The material spans three layers. First, the platform foundation: the core service trinity (compute, storage, networking), the resource hierarchy (management groups, subscriptions, resource groups), governance (Azure Policy, RBAC, cost management), identity (Microsoft Entra ID), networking topology (hub-and-spoke, private endpoints, zero trust), high availability and disaster recovery, and the Cloud Adoption Framework landing-zone model. Second, the platform-engineering disciplines: infrastructure as code with Bicep and Terraform, GitOps, safe deployment practices, and observability. Third, the application reference architecture: microservices on AKS fronted by Azure API Management, communicating through Service Bus / Event Hubs / Event Grid, secured with Entra ID, and delivered through Azure DevOps and GitHub Actions. The recurring theme is "secure foundations, automated provisioning, and resilient architecture" (Gavandi), because functional requirements rarely change in the cloud but the non-functional ones (scale, availability, governance) are satisfied in a fundamentally different way.

## Core concepts

- **Shared responsibility model.** Microsoft secures the underlying infrastructure; the customer secures workloads, identities, data, and access. Azure supplies rich primitives (managed identities, Key Vault, Defender, Policy) but the customer must compose them correctly. (Gavandi)
- **The core service trinity.** Compute, storage, and networking are the substrate on which every higher-order service is built. Compute is a spectrum of control-vs-simplicity: VMs / VM Scale Sets (full OS control, IaaS) → App Service (PaaS web/API hosting with deployment slots) → Container Apps (serverless, event-driven containers with KEDA autoscaling) → AKS (full Kubernetes). Storage spans Blob (unstructured, hot/cool/archive tiers, immutability for compliance), Disk (block storage for VMs/AKS), Files (SMB/NFS shares), and managed databases (Azure SQL, Cosmos DB, Table Storage). Networking is the invisible fabric: VNets, subnets, NSGs, load balancers, Front Door, Private Link. (Gavandi)
- **Resource hierarchy.** Azure governance scopes nest: management group → subscription → resource group → resource. Policy and RBAC assigned at a higher scope cascade downward, so a single security baseline can govern hundreds of subscriptions. (Gavandi)
- **Service Group (logical overlay).** Enterprises think in services, capabilities, and departments, not in technical scopes. A Service Group is a logical overlay (implemented through tags + Azure Policy) that binds related resources spanning multiple subscriptions, regions, and resource groups under one business or operational identity (for example `SG-ERP`, `SG-Identity`, `SG-Production`). It aligns infrastructure governance with service ownership and cost accountability. (Gavandi)
- **Identity is the new perimeter.** Microsoft Entra ID (formerly Azure AD) underpins access control. Conditional Access, MFA, Privileged Identity Management (PIM, with just-in-time activation), and Managed Identities (eliminating secrets in code) move security from network walls to verified identity. (Gavandi; Saleh)
- **Landing zone.** An opinionated, enterprise-ready environment template that incorporates policies, RBAC assignments, and network topology from day one. Landing zones succeeded the now-deprecated Azure Blueprints as the governance baseline and are the unit of repeatable, compliant cloud adoption. (Gavandi)
- **FinOps.** A practice uniting engineering, finance, and business so cost constraints are embedded in the same pipelines that deploy infrastructure (budgets, tags, policy-enforced tagging) rather than enforced after the fact. (Gavandi)
- **Composite SLA.** Stacking service components multiplies their SLAs (a 99.95% App Service plus a 99.99% database yields a lower combined number); multi-region active-active raises it back up. The arithmetic drives architecture decisions. (Gavandi; see also site-reliability-engineering.md)

## Frameworks & models

- **Cloud Adoption Framework (CAF) and landing zones.** Microsoft's prescriptive guidance for enterprise cloud adoption. The landing-zone realization bakes in management-group hierarchy, policy guardrails, RBAC, hub-and-spoke networking, identity, and CI/CD from the outset, so teams innovate inside guardrails rather than building governance retroactively. Case studies in Gavandi show "scalable landing zones" as the first design step in large migrations (financial services, national health systems). (Gavandi)
- **Azure Well-Architected Framework (WAF).** Five pillars - reliability, security, cost optimization, operational excellence, and performance efficiency - used to assess and improve workloads. Saleh applies the WAF lens to IAM and security architecture; it is the standard checklist for design reviews. (Saleh)
- **Hub-and-spoke network topology.** A central hub VNet hosts shared and connectivity services (DNS, Active Directory, Azure Firewall, VPN/ExpressRoute gateways, security appliances); spoke VNets host workloads and peer to the hub. Centralizes security enforcement, monitoring, and hybrid connectivity while letting spokes scale independently. The default topology for large, complex Azure estates. (Gavandi; Saleh)
- **Zero Trust model.** Three principles: verify explicitly (authenticate and authorize on every request from all signals), use least-privilege access (JIT/JEA, risk-based adaptive policies), and assume breach (segment, encrypt end to end, use analytics to detect threats). Realized through Conditional Access, Private Link, micro-segmentation, and Defender for Cloud. (Gavandi; Chandaka & Khan)
- **Microservices chassis pattern.** When choosing a microservice technology stack, verify it supports the cross-cutting concerns every service needs: externalized configuration, logging, health checks, exception handling, security, metrics, distributed tracing, and connectivity to third-party services/databases. The chassis keeps these concerns out of business logic. (Chandaka & Khan)
- **Twelve-factor app methodology.** The baseline methodology for cloud-native microservices (codebase, dependencies, config, backing services, build/release/run, stateless processes, port binding, concurrency, disposability, dev/prod parity, logs as streams, admin processes). Used as the design check for the Online Auction System reference app. (Chandaka & Khan)
- **Decomposition strategies (DDD).** Decompose by business capability or by subdomain, using ubiquitous language and bounded contexts to draw service boundaries. Avoid over-fine-graining into deep subdomains and avoid a shared database across services. (Chandaka & Khan)

## Patterns

- **Landing zone (governance baseline)** - Intent: provision a pre-governed Azure environment (management groups, policy, RBAC, hub-and-spoke network, identity, CI/CD) as the repeatable unit of cloud adoption. When to use: any enterprise onboarding workloads at scale, especially regulated industries. Trade-offs: strong day-one hygiene and consistency vs. up-front platform-engineering investment and opinionated structure. (Gavandi)
- **Hub-and-spoke topology** - Intent: centralize shared services, security, and hybrid connectivity in a hub VNet with workloads in peered spokes. When to use: multi-subscription/multi-region estates needing consistent security and central egress. Trade-offs: simplified governance and monitoring vs. a central hub that can become a chokepoint and adds peering/routing complexity. (Gavandi; Saleh)
- **Private endpoints / Private Link** - Intent: consume PaaS services (SQL, Storage, Key Vault) over private IPs inside the VNet, bypassing the public internet. When to use: regulated workloads requiring data isolation and no public exposure. Trade-offs: strong isolation and exfiltration control vs. DNS and networking complexity and per-endpoint cost. (Gavandi)
- **API gateway with Azure API Management (APIM)** - Intent: a single front-door proxy that routes to backend microservices and centralizes cross-cutting concerns (auth, TLS, rate limiting, IP filtering, token validation, request aggregation) instead of repeating them per service. When to use: any microservice estate exposed to clients. Trade-offs: central policy and simpler clients vs. a potential bottleneck and an operational component to run. APIM can also implement the aggregator pattern via policies. (Chandaka & Khan)
- **Aggregator service** - Intent: a dedicated service (or APIM policy) makes the downstream calls, aggregates the results, and issues a single call to the target service. When to use: a client needs data composed from several services. Trade-offs: simpler clients and one round trip vs. an extra hop and the aggregator needing retry/resilience logic. (Chandaka & Khan)
- **CQRS with a synced read model** - Intent: separate read and update models; keep a denormalized local read copy synchronized through a message broker so reads avoid cross-service HTTP calls. When to use: read-heavy paths where direct HTTP aggregation causes latency/timeouts. Trade-offs: fast, resilient reads vs. eventual consistency and sync machinery. (Chandaka & Khan)
- **Saga (event-driven distributed transaction)** - Intent: maintain consistency across services without distributed transactions; each service performs its local transaction and publishes an event that triggers the next, with compensating events to roll back on failure. When to use: a business transaction spans multiple service-owned databases. Trade-offs: consistency without tight coupling vs. significant implementation complexity and reasoning about compensation. (Chandaka & Khan)
- **Pub/sub asynchronous communication** - Intent: decouple producers from consumers via a broker so components scale independently and failures do not cascade. When to use: event notification, fan-out, buffering load spikes. Azure realizations: Event Hubs (high-throughput streaming, Kafka protocol, partitions and consumer groups), Service Bus (enterprise queues/topics with ordering and dead-lettering), Event Grid (reactive event routing). Trade-offs: elasticity and resilience vs. eventual consistency and async debugging. (Chandaka & Khan; Gavandi; Saleh)
- **Multi-region active-active failover** - Intent: deploy a workload across regions behind a global router (Azure Front Door / Traffic Manager) with replicated data (Cosmos DB multi-region) to survive a regional outage and raise composite availability. When to use: mission-critical, latency-sensitive, or residency-bound global workloads. Trade-offs: highest availability and locality vs. cost, data-consistency complexity, and diminishing SLA returns beyond three regions. (Gavandi)
- **Safe Deployment Practices (SDP) for infrastructure** - Intent: roll out infrastructure changes progressively (ring-based, canary, with health gates and automatic rollback) using a GitOps, commit-driven life cycle in Azure DevOps. When to use: multi-region IaC pipelines where a bad change could break global infrastructure. Trade-offs: controlled blast radius vs. slower, more orchestrated rollouts. (Gavandi)

## Principles & best practices

- **Define everything in code (IaC).** Use Terraform (plan/apply/evolve, remote state, modules) or Bicep/ARM (declarative, incremental vs. complete deployment modes, template specs). Prefer modular architecture, separate configuration from logic, embed security and governance from day zero, manage state securely and centrally, and use CI/CD pipelines for delivery and drift detection. (Gavandi)
- **Design for horizontal scale, not vertical.** Make services stateless (store state in Redis or Cosmos DB), decouple them through Service Bus/Event Grid, and plan multi-region readiness with Traffic Manager/Front Door. Scale out by adding instances triggered on CPU, request rate, or business metrics. (Gavandi)
- **Build security in, not bolt it on.** Identity first (Entra ID, MFA, Conditional Access, PIM, Managed Identities), network isolation (VNets, subnets, NSGs, Azure Virtual Network Manager for consistent rules, Private Link), encryption at rest (platform or customer-managed keys) and in transit (TLS 1.2+), and edge protection (WAF, DDoS Protection, Defender for Cloud Secure Score). (Gavandi; Chandaka & Khan)
- **Governance as guardrails, not roadblocks.** Use management groups for hierarchy, Azure Policy (deny/audit/DeployIfNotExists/Modify effects) for policy-as-code that auto-remediates, RBAC with least privilege and regular access reviews, and budgets/tags for FinOps. Policies map directly to compliance standards (ISO 27001, HIPAA, FedRAMP, SOC 2, PCI-DSS). (Gavandi)
- **Plan HA and DR explicitly.** Use Availability Zones/Sets and VM Scale Sets for redundancy, Zone-Redundant Storage, Azure Site Recovery (continuous replication, orchestrated failover with recovery plans, failback), Azure Backup with point-in-time restore, and immutable blob storage. Define RTO and RPO per workload during risk assessment. (Gavandi)
- **Choose hybrid connectivity by requirement.** VPN Gateway for encrypted connectivity over the public internet (lower cost, variable performance); ExpressRoute for private, SLA-backed, dedicated connectivity (higher performance and cost). Extend identity and governance to on-premises with Azure Arc. (Gavandi)
- **Centralize observability.** Azure Monitor is the control plane; Log Analytics workspaces hold queryable correlated telemetry; Application Insights gives distributed tracing for apps. Establish centralized monitoring for global estates. (Gavandi; Chandaka & Khan)
- **Right-size for AKS at enterprise scale.** Spread node pools across zones, use Cluster Autoscaler + Horizontal/Vertical Pod Autoscalers, govern base images through Azure Container Registry with immutable tagging, secure the control plane (private clusters), integrate secrets via Key Vault + workload identity, and deliver via GitOps (Flux/Argo CD) with canary/blue-green strategies. (Gavandi; Saleh)

## Anti-patterns & pitfalls

- **Lift-and-shift expecting cloud benefits.** Moving monoliths into Azure without re-architecting yields "inflexible, fragile, expensive" systems; cloud satisfies non-functional requirements differently. (Gavandi)
- **Treating governance as an afterthought.** Unchecked agility becomes architectural debt; without management-group hierarchy, policy, and tagging from the start, large estates drift into noncompliance and uncontrolled spend. (Gavandi)
- **Overly permissive RBAC.** Broad roles lead to data exposure and infrastructure drift; least privilege plus PIM and continuous auditing are required. (Gavandi)
- **Shared database across microservices** and **unnecessary fine-graining into deep subdomains**, both of which reintroduce tight coupling and defeat independent deployability. (Chandaka & Khan)
- **Skipping the API gateway.** Without it, clients call services directly, repeating auth, rate limiting, and routing logic everywhere and exposing internal topology. (Chandaka & Khan)
- **Assuming more regions always raise the SLA.** Composite availability gains flatten out; three regions is typically the sweet spot, beyond which cost and complexity outpace reliability gains. (Gavandi)
- **Secrets in code.** Use Managed Identities and Key Vault rather than embedding connection strings and keys. (Gavandi)

## Decision guidance

- **Choosing a compute model.** Move along the control-vs-simplicity spectrum: VMs when full OS control or legacy lift-and-shift is required; App Service for standard web apps/APIs wanting PaaS simplicity and slots; Container Apps for serverless, event-driven microservices without Kubernetes overhead; AKS when you need granular orchestration, custom networking, service mesh, stateful workloads, or AI inference at scale (accepting a steeper operational curve). Azure Monitor spans all of them. (Gavandi; Saleh)
- **Sync vs. async communication.** Use request/response (HTTP) for queries needing an immediate answer; use pub/sub (Service Bus, Event Hubs, Event Grid) to decouple, buffer spikes, and scale producers and consumers independently. Async is the default for resilience between services. (Chandaka & Khan)
- **Event Hubs vs. Service Bus vs. Event Grid.** Event Hubs for high-throughput telemetry/streaming (Kafka-compatible, partitions, consumer groups); Service Bus for enterprise messaging with ordering, sessions, and dead-lettering; Event Grid for lightweight reactive event routing across Azure services. (Chandaka & Khan; Saleh)
- **VPN Gateway vs. ExpressRoute.** VPN for cost-sensitive or lower-throughput hybrid links over the internet; ExpressRoute for predictable, private, SLA-backed connectivity for enterprise-grade or regulated workloads. (Gavandi)
- **Terraform vs. Bicep.** Terraform for multi-cloud portability and a mature module/state ecosystem; Bicep/ARM for the tightest Azure-native integration and deployment-mode control (incremental for safe evolution, complete for deterministic teardown). Both belong in CI/CD with drift detection. (Gavandi)
- **Governance reasoning.** Assign the broadest correct scope: bake baselines into the landing zone and management-group level so they cascade; reserve resource-level policy for exceptions. Prefer DeployIfNotExists/Modify policies so compliance self-heals rather than merely audits. (Gavandi)

(Azure, https://azure.github.io/AI-Landing-Zones/; GitHub, https://github.com/Azure/AI-Landing-Zones)
- Microsoft Entra ID-centric, zero-trust identity became the default control plane: Cloud Adoption Framework guidance now emphasizes Entra ID with tenant-aware claims and conditional access, alongside Azure Arc, Azure Monitor, and AKS for unified hybrid management. (Microsoft Learn, https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/)
- AKS is increasingly positioned as the central hosting platform for AI agents, inference services, and gateways in enterprise architectures, reflecting Kubernetes' broader role as the AI substrate. (Microsoft, https://techcommunity.microsoft.com/blog/azurearchitectureblog/architecting-an-azure-ai-hub-and-spoke-landing-zone-for-multi-tenant-enterprises/4491161)
- Platform engineering and FinOps/GreenOps practices tightened around Azure estates, with self-service IDPs over Bicep/Terraform and growing carbon reporting as AI workloads drive both cost and emissions scrutiny. (FinOps Foundation, 2025, https://data.finops.org/2025-report/)
