# MLOps

**Domain:** 09 - Cloud Infrastructure and Platform
**Primary sources:** Hands-On MLOps on Azure: Automate, secure, and scale ML (De, 2025)

## Overview

Machine Learning Operations (MLOps) is the discipline that brings together machine learning, DevOps, and data engineering to streamline and automate the end-to-end life cycle of ML models, from development and experimentation through deployment and monitoring. It exists because ML systems break in ways traditional software does not: models are non-deterministic (they can produce different outputs for the same input depending on the data they were trained on), and their performance degrades over time as real-world data drifts away from the training distribution. Without MLOps, organizations face "model disasters" - degraded performance going unnoticed for months, or the inability to reproduce a successful model when it is needed (De).

MLOps is a specialized extension of DevOps. It borrows the core DevOps principles - continuous integration, continuous delivery, and infrastructure as code - and extends them to handle the realities of ML: versioning data as well as code, automated retraining, model registries, drift detection, governance, and reproducibility. To CI and CD it adds continuous training (CT): models are retrained automatically on new data or code changes. This file captures the vendor-neutral MLOps life cycle and its principles, alongside their Azure Machine Learning (AML) realizations (AML workspaces, MLflow tracking, components and pipelines, model registry and packaging, online/batch endpoints, DataCollector-based monitoring, Azure Monitor/Log Analytics, Event Grid alerting, GitHub Actions CI/CD) and a brief look at LLMOps and responsible AI. The principles transfer across clouds; AML is the concrete toolchain (De).

## Core concepts

- **The MLOps life cycle.** A continuous loop: data preparation → training and experimentation → model registration and packaging → deployment (batch or online) → monitoring → retraining. Each stage feeds back into the next, and reproducibility and automation tie them together. (De)
- **Non-determinism and drift.** Because ML models are non-deterministic and data evolves, models suffer **data drift** (the statistical properties of input features change over time) and **concept drift** (the fundamental relationship between inputs and the target variable changes, e.g., fraudsters inventing new techniques). Both are managed by monitoring for drift indicators and retraining on updated data. (De)
- **Reproducibility.** Unlike traditional software where versioning code suffices, true ML reproducibility requires versioning code, training data, and model parameters/hyperparameters together, plus reproducible environments (containerization/Docker, dependency tracking). Without all three you cannot recreate a model. (De)
- **Experiment tracking.** Recording parameters, metrics, and artifacts for every training run (via MLflow / AML jobs and experiments) so runs can be compared, the best model selected on metrics, and successful approaches iterated quickly. (De)
- **Model registry.** A versioned store for trained models that links each model version to the datasets and experiments that produced it, with metadata and annotations. The registry is the handoff point between training and deployment and the backbone of lineage. (De)
- **Lineage.** The auditable record tracing the entire life cycle of datasets, experiments, and models - which data and code produced which model - transforming debugging from guesswork into systematic investigation and underpinning compliance. (De)
- **Feature engineering and data versioning.** Transforming raw data into meaningful features, plus versioning the data used in training so models can be reproduced and troubleshooted with the exact same data. (De)
- **Inference modes.** **Real-time / online inference** serves low-latency predictions through a deployed web-service endpoint (multiple deployments can sit behind one endpoint with traffic split for A/B or canary). **Batch inference / scoring** processes large volumes asynchronously on a schedule. The choice drives the deployment infrastructure. (De)

## Frameworks & models

- **From DevOps to MLOps (CI/CD/CT + IaC).** MLOps adapts the DevOps toolbox to ML. **CI** automates code linting, unit testing, and data validation, and integrates data scientists' changes into a central repo, also automating data preprocessing and feature engineering for consistency. **CD** automates model training/retraining, streamlines deployment to test/staging/production, and enables A/B testing to pick the best candidate. **CT (continuous training)** is the ML-specific addition: automated retraining triggered by new data or performance thresholds. **IaC** defines data pipelines, compute (CPU/GPU), and deployment environments in machine-readable code (YAML) for consistent, scalable, recoverable provisioning. (De)
- **AML workspace and pipelines.** The AML workspace is the top-level container for datasets/datastores, compute, environments, jobs/experiments, models, and endpoints. **Components** are reusable, parameterized steps (data prep, train, score); **pipelines** chain components into repeatable end-to-end workflows that track lineage at each stage. Environments capture software dependencies for reproducibility. (De)
- **Model packaging and formats.** Standardize on the **MLflow** model format for portability and a common interface across tooling, or use custom formats when required, weighing portability against control. Packaging bundles the model with its dependencies and scoring logic for deployment. (De)
- **ML governance focus areas.** Model integrity, compliance requirements, lineage, and ethical considerations (bias detection and mitigation, fairness across demographic groups). Governance is embedded across the whole life cycle - from data ingestion and preprocessing through evaluation/validation (testing protocols, bias detection, performance monitoring) to deployment - not bolted on at the end. (De)
- **Six AML monitoring signal categories.** Data quality monitoring (missing values, outliers), data drift detection (input feature distribution shifts), prediction drift analysis (output distribution shifts), feature attribution drift (changes in how much each feature contributes to predictions), custom metric monitoring (business KPIs), and model bias monitoring (fairness across segments). DataCollector captures inputs/outputs/predictions to feed these signals. (De)
- **LLMOps and responsible AI.** Applying MLOps to large language models adds prompt engineering and model customization, retrieval-augmented generation (RAG), and responsible-AI practices (Azure RAI) for safety, fairness, and monitoring - an emerging extension of the MLOps discipline. (De)

## Patterns

- **Reproducible ML pipeline (components + pipelines)** - Intent: express data prep, training, and scoring as versioned, parameterized components chained into a pipeline, with versioned data, code, and environments, so any model can be recreated exactly. When to use: any production ML workflow. Trade-offs: full reproducibility and reuse vs. up-front engineering of components and environment definitions. (De)
- **Experiment tracking with a registry** - Intent: log parameters, metrics, and artifacts per run (MLflow), compare runs, register the best model linked to its data and experiment. When to use: iterative model development and team collaboration. Trade-offs: fast, comparable iteration and traceability vs. discipline in logging everything consistently. (De)
- **Continuous training (CT)** - Intent: automatically retrain and redeploy models when new data arrives or performance crosses a threshold, often triggered by drift detection. When to use: models facing data/concept drift in production. Trade-offs: sustained accuracy without manual intervention vs. pipeline complexity and the need for guardrails against bad retrains. (De)
- **Online endpoint with traffic-split rollout** - Intent: serve real-time predictions through an endpoint hosting multiple deployments, shifting traffic gradually (canary/A/B) before full rollout. When to use: latency-sensitive serving where you want to validate a new model on live traffic safely. Trade-offs: safe progressive delivery and comparison vs. operating endpoint infrastructure and managing traffic rules. (De)
- **Batch scoring pipeline** - Intent: score large data volumes asynchronously on a schedule via a batch endpoint. When to use: high-volume, latency-tolerant predictions (e.g., nightly forecasting). Trade-offs: cost-efficient throughput vs. no real-time responsiveness. (De)
- **Drift-triggered monitoring loop** - Intent: use DataCollector to capture inputs/outputs and monitor data quality, data drift, prediction drift, feature-attribution drift, and bias, alerting and triggering retraining when signals deviate. When to use: any deployed model whose accuracy can decay. Trade-offs: early detection of degradation and automated correction vs. monitoring setup and threshold tuning to avoid alert fatigue. (De)
- **Lineage-first governance** - Intent: automate lineage capture (datasets/datastores, experiment tracking, model registry, pipelines, audit logs) with consistent naming, comprehensive metadata, version control, and strict access controls so every model is auditable and compliant. When to use: regulated or high-stakes ML. Trade-offs: auditability, compliance, and systematic debugging vs. logging and documentation overhead. (De)
- **Event-driven ML alerting** - Intent: detect anomalies (deployment failures, drift, resource exhaustion) and trigger automated responses via event-driven alerts (Event Grid, Azure Monitor, Log Analytics), with thresholds tuned to avoid alert fatigue and integration with incident management. When to use: production ML at scale. Trade-offs: fast automated response vs. careful threshold design. (De)

## Principles & best practices

- **Version code, data, and parameters together.** Reproducibility requires all three plus reproducible environments; automate lineage capture with MLflow rather than relying on manual records. (De)
- **Automate the whole life cycle.** Replace manual, error-prone steps with pipelines that validate data, test models, and monitor performance; when problems occur, automation lets you find root causes fast and roll back to a stable version. (De)
- **Manage data as a first-class asset.** Version data, enforce data quality (validation, cleaning, anomaly detection, bias checks), and treat feature engineering as a tracked pipeline step. (De)
- **Monitor models and infrastructure separately but together.** Model performance monitoring (accuracy, F1, precision, recall, drift, bias) validates business logic; infrastructure monitoring (CPU, memory, storage, endpoint RPS/latency, deployment metrics, cost) keeps the system scalable, available, secure, and cost-effective. Integrate with Azure Monitor and Log Analytics for unified observability. (De)
- **Embed governance across the life cycle.** Ensure model integrity, compliance, lineage, and ethics from data ingestion to deployment; implement bias detection and mitigation and strict access controls. (De)
- **Tune alert thresholds to avoid fatigue.** Set appropriate thresholds and refine alerts (e.g., for deployment failures) so teams act on real signals rather than noise; integrate alerts with incident management. (De)
- **Use IaC for ML infrastructure.** Define data pipelines, compute, and environments in YAML for consistent provisioning, easy scaling, and quick disaster recovery. (De)
- **Standardize model formats.** Prefer MLflow for portability and a universal interface across MLOps tooling unless a custom format is justified. (De)

## Anti-patterns & pitfalls

- **Treating ML like deterministic software.** Ignoring non-determinism and drift leads to silent performance decay; continuous monitoring and retraining are mandatory. (De)
- **Versioning code but not data.** Defeats reproducibility - you cannot recreate or troubleshoot a model without its exact training data and parameters. (De)
- **No drift detection.** Models degrade unnoticed for months as data shifts; without data/concept/prediction/attribution drift monitoring, failures surface only as business impact. (De)
- **Manual, undocumented lineage.** Makes debugging guesswork and blocks compliance/audit; automate lineage capture instead. (De)
- **Alert fatigue.** Poorly tuned thresholds bury real anomalies in noise; refine thresholds and avoid over-alerting. (De)
- **Skipping bias and fairness checks.** Unmonitored models can perform inequitably across groups and breach fairness/compliance requirements. (De)

## Decision guidance

- **Online vs. batch inference.** Choose online/real-time endpoints when low-latency, per-request predictions are needed (and use traffic-split deployments for safe rollout); choose batch scoring for high-volume, latency-tolerant workloads on a schedule. (De)
- **When to retrain.** Trigger continuous training on drift signals (data, concept, prediction, or feature-attribution drift) or when monitored KPIs cross thresholds, rather than on a fixed calendar alone, so retraining tracks actual degradation. (De)
- **Which monitoring signals to enable.** Always cover data quality and data/concept drift; add prediction-drift and feature-attribution drift for explainability-sensitive models; add bias monitoring wherever fairness or compliance matters; add custom metrics for business-specific KPIs. (De)
- **Model format choice.** Default to MLflow for portability and tool interoperability; use a custom format only when the model or runtime demands it, accepting reduced portability. (De)
- **CI/CD/CT scope.** Put data validation and preprocessing in CI; put automated training, environment promotion, and A/B testing in CD; automate retraining as CT keyed to data changes and performance thresholds; define all ML infrastructure as IaC. GitHub Actions plus AML CLI v2 pipelines realize this, including multi-cloud workflows. (De)
- **LLMOps considerations.** For LLM solutions, extend MLOps with prompt engineering, RAG, and responsible-AI guardrails (Azure RAI), and monitor for safety and quality alongside conventional metrics. (De)

## Recent developments (2024–2026)

- LLMOps split off from classic MLOps as a distinct discipline for generative AI, adding prompt management, retrieval-augmented generation (RAG), fine-tuning, vector stores/embeddings, and guardrails to the model lifecycle. Surveys and reviews in 2025 describe a progression from MLOps to LLMOps to "GenAIOps." (MDPI, 2025, https://www.mdpi.com/2078-2489/16/2/87; Cloudera, https://www.cloudera.com/blog/technical/the-evolution-of-llmops--adapting-mlops-for-genai.html)
- AgentOps emerged for operationalizing, monitoring, and optimizing agentic AI systems, and "Agentic RAG" moved retrieval decisions into the model's reasoning loop rather than static pipelines. (ResearchGate review, 2025, https://www.researchgate.net/publication/393122731_LLMOps_AgentOps_and_MLOps_for_Generative_AI_A_Comprehensive_Review)
- Evaluation and monitoring of LLM systems became a defining challenge: metrics now span truthfulness, toxicity, and hallucination rate, and pipelines increasingly rely on LLM-as-judge plus subject-matter-expert review rather than simple accuracy. (MDPI, 2025, https://www.mdpi.com/2078-2489/16/2/87)
- Kubernetes solidified as the platform for AI/ML in production: per the CNCF 2025 survey (Jan 2026), 66% of organizations hosting generative AI models use Kubernetes for some or all inference workloads, making cloud-native MLOps tooling (KServe, Kubeflow, model gateways) central. (CNCF, 2026, https://www.cncf.io/announcements/2026/01/20/kubernetes-established-as-the-de-facto-operating-system-for-ai-as-production-use-hits-82-in-2025-cncf-annual-cloud-native-survey/)
- Cloud vendors shipped responsible-AI and agentic guidance into their architecture frameworks: AWS added a Responsible AI Lens and updated its Generative AI Lens (with an agentic-AI preamble) at re:Invent 2025, and Azure released AI Landing Zones (Foundry + APIM-as-AI-gateway) as reference architectures. (InfoQ, 2025, https://www.infoq.com/news/2025/12/aws-expands-well-architected/; Azure, https://azure.github.io/AI-Landing-Zones/)
